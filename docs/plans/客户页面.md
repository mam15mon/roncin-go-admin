# 客户档案全景页面实施计划

## 1. 文档目的

本文用于指导 `roncin-go-admin` 客户档案页面的后续实现和验收。最终目标是形成适合货代业务的高密度客户档案页面，但实施时必须先打通现有基础链路，再逐步增加二级资料，避免一次性改造导致前后端长期不可用。

本文以当前仓库代码和已实现后端契约为基线，不把竞品截图中的所有功能默认视为本期范围。截图仅作为信息密度、页面结构和交互形态参考，不直接复制其中不符合当前领域模型的字段与行为。

## 2. 总体结论

采用以下总体方向：

- 客户、供应商、国外代理共用一个 `Partner` 企业主体。
- 企业可同时拥有多个业务角色，角色之间可以新增或停用。
- 企业通用资料、角色专属资料、结算规则和二级资料分别建模。
- 客户基础资料和首条结算规则必须在一次后端事务中保存。
- 账户、合同、常用单证预设等二级资料必须在企业主体创建成功后独立维护。
- 行政区划和币种使用后端全局字典接口，不在正式页面中保留静默备用数据。
- 不实现没有正式供应商契约和凭据的“天眼查自动校验”。在此之前，只允许提供显式的外部查询跳转，并明确标注它不是系统校验结果。

## 3. 本期成功标准

核心基础阶段（阶段 0 至阶段 2）完成后，用户应能稳定完成以下流程：

1. 从客户列表点击“新增客户”。
2. 页面正常打开，已修复的请求体参数解码问题不再回归。
3. 用户、组织、币种和省市区数据均能正常加载，失败时能明确指出失败模块。
4. 填写客户基础资料、人员指派和结算信息。
5. 点击一次保存，后端以一个事务写入完整客户档案。
6. 保存成功后进入详情页或返回列表。
7. 再次打开详情页，所有已保存字段与提交内容一致。
8. 客户可后续增加供应商或国外代理角色，不重复创建企业主体。

## 4. 当前实现基线

### 4.1 已有后端能力

当前后端已经具备：

- `Partner` 企业主体。
- 客户、供应商、国外代理和承运人角色。
- 企业中英文资料、国家、省市区编码、详细地址、性质、开发方式、客户类型、业务类型和备注。
- 企业别名和联系人。
- 人员与组织结构化指派。
- 账户查询、创建和更新。
- 合同查询、创建和更新。
- 结算规则查询、创建和更新。
- 信用额度、信用额度币种和结算币种字段。
- 全局币种接口：`GET /api/v1/reference/currencies`。
- 行政区划接口：`GET /api/v1/reference/administrative-regions`。
- 民政部省、市、区县三级行政区划数据。
- 通用审计日志基础设施。

### 4.2 已有前端能力

当前前端已经具备：

- 客户、供应商和国外代理独立列表入口。
- 新建和编辑档案路由。
- 基础资料、别名、联系人、人员指派和结算信息表单。
- 账户、合同、结算规则和附件的抽屉式维护页面。
- 后端生成的币种请求客户端。

### 4.3 当前已知问题

已解决的基线问题：

- 提交客户资料时曾返回“管理参数不合法”。根因是 OpenAPI 客户端发送 camelCase 请求字段，而 Kratos 原 JSON 解码路径未按 ProtoJSON 契约解码，导致必填字段成为空值。提交 `d634216` 已改用 ProtoJSON 解码，并补充 camelCase、snake_case 和未知字段测试。

以下问题仍需处理：

1. 页面同时请求用户、组织和币种，但使用 `Promise.allSettled` 吞掉了具体失败来源。
2. 币种接口失败时仍静默使用硬编码币种列表，与全局字典真相不一致。
3. 省市区仍使用前端静态 JSON，没有消费后端行政区划接口。
4. 客户主体和结算规则通过两个请求保存，可能出现主体成功、结算规则失败的半完成数据。
5. 信用额度字段已存在于后端，但当前主表单没有完整读取和提交。
6. 当前页面只实现一个内部关联人员，没有截图中的第二个关联人员。
7. 当前 `CREATOR` 角色没有由后端自动写入。
8. 页面直接写在一个较大的 `partner-detail.tsx` 中，后续继续堆叠模块会降低可维护性。

## 5. 业务与模型决策

以下决策应在编码前固定，避免实现过程中反复修改契约。

### 5.1 企业主体与业务角色

企业主体保持统一：

```text
Partner
├── 企业通用资料
├── customer 角色
├── supplier 角色
├── foreign_agent 角色
└── carrier 角色
```

规则：

- 相同组织内，同一企业不得因为角色不同重复创建。
- 角色通过新增或停用转换，不移动或复制企业主体。
- 客户或供应商角色启用时，统一社会信用代码必填。
- 只有国外代理角色启用时，统一社会信用代码可为空。
- 国外代理转为客户或供应商时，必须先补齐统一社会信用代码。
- 每个角色维护自己的结算规则，客户规则不能覆盖供应商或国外代理规则。

### 5.2 企业通用资料与角色专属资料

企业通用资料包括：

- 单位编码。
- 公司抬头。
- 统一社会信用代码。
- 国家或地区。
- 省、市、区县编码。
- 中文详细地址。
- 英文名称。
- 英文地址。
- 企业别名。
- 联系人。

角色专属资料包括：

- 客户类型：直客、同行。
- 开发方式。
- 业务类型：SE、SI、AE、AI、LAND、RAIL。
- 角色级结算规则。
- 角色级信用额度。

当前实现把部分客户专属字段放在 `PartnerProfile`。本期不立即拆表，避免扩大迁移范围；但新增代码不得继续把供应商或国外代理专属字段堆进统一 Profile。后续发生以下任一情况时，应单独设计角色 Profile：

- 供应商需要独立分类字段。
- 国外代理需要独立区域、航线或资质字段。
- 同一企业不同角色需要不同业务类型或开发方式。

### 5.3 创建人员与责任人员

责任人员设计为“用户 + 所属组织”的结构化指派：

```text
PartnerAssignment
├── role
├── user_id
└── organization_id
```

规则：

- `CREATOR` 不允许在前端自由选择，由后端使用当前登录用户和当前组织自动写入。
- `OPERATOR`、`SALES`、`CUSTOMER_SERVICE`、`DOCUMENT`、`COMMERCIAL` 可以由用户选择。
- 内部关联人员允许最多两人。
- 不新增 `INTERNAL_CONTACT_2` 枚举。内部关联人员使用同一个 `INTERNAL_CONTACT` 角色，并增加顺序字段或调整唯一约束以支持两条记录。
- 选择用户后，所属组织只能选择该用户当前启用的成员关系组织。
- 用户和组织不匹配时，前端应阻止提交，后端仍必须再次校验。
- 所选组织必须位于当前组织的数据权限范围内。

### 5.4 行政区划

正式页面使用后端行政区划接口：

```http
GET /api/v1/reference/administrative-regions?level=1
GET /api/v1/reference/administrative-regions?level=2&parentCode={provinceCode}
GET /api/v1/reference/administrative-regions?level=3&parentCode={cityCode}
```

规则：

- 选择省后清空已选市和区县。
- 选择市后清空已选区县。
- 编辑时按已保存编码逐级加载并回显。
- 后端校验省、市、区县的层级和父子关系。
- 非中国企业不能提交中国省市区编码。
- 前端不再静默使用 `china-division` 数据替代接口结果。
- 如果为了测试保留静态数据，只能用于测试夹具，不参与正式运行逻辑。

### 5.5 币种与金额

规则：

- 币种选项只来自全局币种接口。
- 只允许选择后端返回的启用币种。
- 信用额度前端使用十进制金额显示，例如 `500000.00`。
- 提交前将金额精确转换为最小货币单位 `credit_limit_minor`。
- 回显时根据币种 `minor_unit` 转换为显示金额。
- 不使用 JavaScript 浮点数直接乘除金额，使用字符串或十进制定点转换函数。
- 信用额度与信用额度币种必须同时为空或同时有值。
- 本期默认信用额度币种可以与结算币种相同，但不能通过静默逻辑强制覆盖用户已保存的不同币种。

### 5.6 结算规则

本期支持：

- 对账方式：单票对账、汇总对账。
- 结算方式：票结、月结、周结、半月结、双月结、季结、45 天、预付。
- 结算基准：账单日、开航日、到港日。
- 结算日。
- 账期天数。
- 结算币种。
- 信用额度。
- 信用额度币种。

字段联动规则：

- 票结和预付不填写结算基准、结算日和账期天数。
- 月结等周期结算必须填写结算基准。
- 月结结算日范围为 1 至 31。
- 周结如使用结算日，范围为 1 至 7，并在界面显示星期语义。
- 账期天数范围为 1 至 365。
- 前端根据结算方式隐藏无效字段，提交时不发送隐藏字段的旧值。
- 后端仍执行同样的业务校验。

### 5.7 利息规则

利息规则不进入第一版。

原因：当前仅有“逾期利率”和“宽限期”两个字段不足以表达完整业务，至少还需要确认：

- 利率按日还是按月。
- 计息基数是逾期金额还是全部应收金额。
- 宽限期从账单日还是到期日计算。
- 是否存在封顶金额或封顶天数。
- 不同角色是否使用不同规则。

在财务规则确认前，不向 Proto 或数据库增加猜测性字段。

### 5.8 天眼查或企业工商校验

本期不实现系统自动校验。

允许的临时交互：

- 用户填写公司抬头后，点击“外部查询”。
- 新窗口打开企业查询网站的搜索页面。
- 页面明确标注“仅跳转外部查询，系统未自动验证”。

禁止：

- 把外部搜索跳转显示为“校验成功”。
- 在没有正式 API、服务地址和密钥时模拟验证结果。
- 外部查询失败后静默接受为已验证。

### 5.9 删除、停用与引用约束

本期不直接增加账户和合同物理删除。

后续增加删除接口前必须确认：

- 账户是否被订单、账单或收付款记录引用。
- 默认账户是否允许删除。
- 生效合同是否只能终止，不能删除。
- 删除采用软删除、停用还是物理删除。
- 删除是否要求额外权限和原因。

## 6. 目标页面结构

最终详情页采用纵向全景页面，不再把核心资料分散到不同抽屉中。

```text
吸顶操作区
├── 返回列表
├── 面包屑
├── 档案标题和单位编码
├── 保存状态
├── 取消
└── 保存档案

基础信息
├── 公司抬头、信用代码、单位编码
├── 中国省市区、详细地址
├── 英文名称、英文地址
├── 客户类型、开发方式、业务类型
├── 人员与组织指派
├── 企业别名
└── 联系人

结算信息
├── 对账方式、结算方式
├── 结算基准、结算日、账期
├── 结算币种
└── 信用额度与币种

账户信息
联系方式
常用信息
合同管理
客户备注
操作记录
```

### 6.1 创建页与详情页差异

创建页：

- 展示基础信息和结算信息。
- 二级资料区域展示“保存客户后可维护”，不允许提前创建账户或合同。
- 单位编码可编辑。
- 创建人员由系统自动确定，不显示可编辑下拉框。

详情页：

- 展示全部模块。
- 单位编码只读。
- 支持独立新增或更新账户、联系人、合同和常用预设。
- 展示创建人员和后续操作记录。

### 6.2 保存状态与脏检查

页面状态分为：

- `未修改`：保存按钮禁用。
- `有未保存修改`：保存按钮高亮。
- `保存中`：按钮 loading，阻止重复提交。
- `保存失败`：保留表单值，展示后端错误。
- `已保存`：刷新初始快照，按钮重新禁用。

离开有未保存修改的页面时，弹出确认提示。保存成功后离开不提示。

### 7.3 阶段 2：基础资料与结算规则原子保存

### 目标

点击一次“保存客户档案”，客户主体与首条客户结算规则要么全部成功，要么全部失败。

### 契约任务

在创建与更新契约中加入角色级结算规则输入。具体命名可根据现有 Proto 风格确定，但必须明确绑定角色：

```protobuf
message PartnerRoleInput {
  PartnerRoleType type = 1;
  bool enabled = 2;
  optional PartnerSettlementRuleInput settlement_rule = 3;
}
```

或者使用显式聚合输入：

```protobuf
message PartnerRoleProfileInput {
  PartnerRoleType type = 1;
  bool enabled = 2;
  optional PartnerSettlementRuleInput settlement_rule = 3;
}
```

最终只选择一种，不同时保留两套含义重叠的结构。

### 后端任务

1. 在同一个数据库事务中保存：

   ```text
   Partner
   PartnerProfile
   PartnerRole
   PartnerAssignment
   PartnerAlias
   PartnerContact
   PartnerSettlementRule
   ```

2. 结算币种和信用额度币种必须引用启用币种。
3. 执行结算方式对应的字段联动校验。
4. 更新时只更新本次目标角色的结算规则，不覆盖其他角色规则。
5. 事务失败时不留下半完成企业主体。

### 前端任务

1. 删除“先保存 Partner、再单独保存结算规则”的两段式流程。
2. 完整提交信用额度和信用额度币种。
3. 根据币种最小单位安全转换金额。
4. 根据结算方式清空不适用字段。
5. 保存失败时停留当前页面并保留输入。

### 验收

- 模拟结算规则校验失败时，数据库中不新增 Partner。
- 成功保存后，基础资料和结算规则同时存在。
- 信用额度可以正确往返转换，不出现浮点误差。
- 编辑客户结算规则不会修改供应商或国外代理结算规则。

### 建议提交

```text
feat: 支持客户档案与结算规则原子保存
```

### 7.4 阶段 3：全景详情页与二级资料卡片

### 目标

将已有账户、联系人和合同能力从分散抽屉整合到客户详情页内嵌模块。

### 页面任务

1. 吸顶操作区。
2. 可折叠基础信息区。
3. 可折叠结算信息区。
4. 账户卡片列表与新增、编辑弹窗。
5. 联系人卡片列表与新增、编辑弹窗。
6. 合同卡片列表与新增、编辑弹窗。
7. 客户备注区。
8. 各模块独立 loading、empty 和 error 状态。

### 交互规则

- 基础档案使用页面主保存按钮。
- 账户、联系人和合同使用各自弹窗独立保存。
- 子模块保存成功后只刷新当前模块，不刷新整个页面。
- 创建页不允许新增二级资料。
- 详情页在 Partner ID 存在后才请求二级资料。
- 不在一个前端请求中同时并发提交多个互不相关的二级模块。

### 删除策略

本阶段先提供停用或状态变更，不新增物理删除。需要删除时，另行完成引用约束设计后再增加契约。

### 验收

- 账户、联系人和合同均在页面内直接查看。
- 新增或编辑某个模块不影响其他模块。
- 子模块请求失败不会导致基础档案内容消失。
- 默认账户、主联系人等唯一规则保持有效。

### 建议提交

```text
feat: 重构客户档案全景详情页
```

### 7.5 阶段 4：货代常用单证预设

### 目标

支持客户常用发货人、收货人、通知人、英文品名、HS 编码和唛头。

### 建模原则

不直接把六种类型全部压缩成没有语义的 `title + content + code`。

建议分为两类：

#### 企业型预设

适用于发货人、收货人和通知人：

```text
company_name
address
contact_name
phone
email
country_code
tax_identifier
```

#### 文本型预设

适用于英文品名、HS 编码和唛头：

```text
title
content
code
```

如果最终坚持使用统一表，Proto 必须使用明确的 `oneof` 表达不同类型载荷，避免未来从自由文本中反向解析结构化数据。

### 业务规则

- 每种类型可有多条记录。
- 每种类型最多一个默认项。
- 设置新默认项时，后端在事务中取消旧默认项。
- HS 编码必须通过明确的格式校验。
- 排序值只影响同一客户、同一预设类型。
- 预设只能被当前组织范围内的订单使用。

### 验收

- 六类预设可以新增、编辑、查询和停用。
- 每类默认项互斥。
- 订单后续可直接引用结构化预设，无需解析展示文本。

### 建议提交

```text
feat: 增加客户常用单证预设
```

### 7.6 阶段 5：客户操作记录

### 目标

在详情页底部展示当前客户相关的操作时间线。

### 实现原则

优先复用现有 `AuditLog`，通过以下条件查询：

```text
organization_id = 当前组织
resource_type = partner
resource_id = 当前 Partner ID
```

如果现有审计查询接口不支持资源过滤，应优先扩展通用审计查询契约，而不是立即创建一套重复的 `PartnerAuditLog` 表。

### 审计事件范围

- 创建客户档案。
- 更新基础资料。
- 增加或停用业务角色。
- 修改人员指派。
- 修改结算规则。
- 新增或更新账户。
- 新增或更新合同。
- 修改常用单证预设。

### 安全规则

- 不记录密码、Cookie、令牌和完整请求体。
- 不记录银行账户完整敏感信息；展示时按系统脱敏规则处理。
- 字段差异只记录允许审计的业务字段。

### 验收

- 时间线按时间倒序展示。
- 每条记录包含时间、操作人、动作和资源标识。
- 无权限用户不能查看客户审计记录。
- 审计失败不能静默吞掉。关键业务变更与审计记录必须保持一致；如果当前架构无法同事务写入，应先设计可靠的审计投递机制。

### 建议提交

```text
feat: 增加客户档案操作记录
```

## 8. 权限设计

沿用统一权限真相，不在前端复制另一套规则。

建议权限映射：

| 操作 | 权限 |
| --- | --- |
| 查看客户列表和详情 | `business.partner.read` |
| 新建、编辑客户 | `business.partner.manage` |
| 查看币种和行政区划 | `system.master_data.read` |
| 加载可指派用户和组织 | 使用专门的可选项查询权限，不能要求普通客户维护人员拥有完整系统用户管理权限 |
| 查看客户操作记录 | `system.audit.read` 或后续独立客户审计权限 |

当前客户页面直接调用 `/api/v1/admin/users` 和 `/api/v1/admin/organizations`。长期应增加面向业务表单的“可指派用户与组织选项”接口，避免客户维护人员必须拥有系统用户管理权限才能填写人员指派。

该接口应只返回表单需要的信息：

```text
user_id
display_name
organization_id
organization_name
membership_enabled
```

不得返回用户角色、密码信息或其他管理字段。

## 10. 错误处理要求

禁止：

- 空 `catch`。
- 请求失败后静默使用旧硬编码数据。
- 把多个接口错误统一显示成“参数不合法”。
- 保存部分成功后仍提示“档案保存成功”。
- 后端返回明确业务错误时统一替换成“保存失败，请重试”。

页面应根据后端错误原因展示明确提示，例如：

| 错误原因 | 用户提示 |
| --- | --- |
| `PARTNER_CODE_EXISTS` | 单位编码已存在 |
| `PARTNER_NAME_EXISTS` | 企业名称已存在 |
| `PARTNER_USCC_EXISTS` | 统一社会信用代码已存在 |
| `PARTNER_TAX_IDENTIFIER_REQUIRED` | 客户或供应商必须填写统一社会信用代码 |
| `PARTNER_PRIMARY_CONTACT_CONFLICT` | 只能设置一个主联系人 |
| `REFERENCE_DATA_INVALID_ARGUMENT` | 行政区划查询参数不正确 |
| `ADMIN_INVALID_ARGUMENT` | 指派数据查询参数不正确；开发环境同时显示失败接口 |

开发环境可额外展示 `trace_id`，方便从后端结构化日志定位请求。

## 11. 测试与验收矩阵

### 11.1 后端业务测试

- 客户和供应商缺少统一社会信用代码时拒绝。
- 只有国外代理角色时允许缺少统一社会信用代码。
- 非中国企业提交中国省市区时拒绝。
- 市不属于省、区县不属于市时拒绝。
- 责任角色重复时拒绝。
- 两个内部关联人员允许保存，第三个拒绝。
- 指派用户不属于所选组织时拒绝。
- 所选组织超出当前组织树时拒绝。
- 币种不存在或已禁用时拒绝。
- 信用额度与币种未成对出现时拒绝。
- 结算方式与结算字段组合不合法时拒绝。
- 原子创建过程中任一步失败时数据库不留下 Partner。
- 编辑客户角色时不覆盖企业已有其他角色。

### 11.2 前端组件测试

- 新建和编辑路由正确识别。
- 省市区逐级加载和清空下级行为正确。
- 编辑时行政区划正确回显。
- 用户选择后组织选项正确过滤。
- 结算方式改变时无效字段被清空。
- 金额与最小货币单位转换正确。
- 表单脏检查正确控制保存按钮。
- 初始化请求失败时展示对应错误模块。
- 保存失败时表单输入保留。

### 11.3 浏览器联调场景

#### 新建客户

1. 打开 `/partners/customers`。
2. 点击“新增客户”。
3. 确认初始化请求全部成功。
4. 填写完整资料并保存。
5. 确认只出现一次成功提示。
6. 重新进入详情页检查回显。

#### 多角色转换

至少验证：

- 客户转为客户加供应商。
- 客户转为客户加国外代理。
- 客户加供应商停用供应商角色。
- 国外代理增加客户角色，并补齐统一社会信用代码。

#### 异常场景

- 单位编码重复。
- 统一社会信用代码格式错误。
- 用户和组织不匹配。
- 币种被禁用。
- 结算规则不合法。
- 网络中断。
- 后端事务失败。

### 11.4 每阶段检查命令

优先运行相关最小检查，阶段提交前运行：

```powershell
pnpm run generate:web-client
pnpm run check:web
pnpm run check:server
git diff --check
```

涉及完整页面交互时，增加浏览器联调，不以 TypeScript 编译通过代替实际流程验证。

## 14. 明确不在第一版实现的内容

- 自动天眼查或其他工商平台校验。
- 利息计算规则。
- 账户物理删除。
- 生效合同物理删除。
- 客户、供应商和国外代理各自复制一套企业主体表。
- 行政区划或币种接口失败时的静默备用数据。
- 把人员姓名和组织名称保存为自由文本。
- 把所有新增业务字段塞进一个 JSON `meta`。
- 自动修复不合法输入或静默降级。
