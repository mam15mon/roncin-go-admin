# 企业资源备忘录建设计划

## 1. 文档目的

本文用于指导 `roncin-go-admin` 企业资源备忘录的设计、实施与验收。目标是在顶部
“企业资源”菜单下统一管理地址、备注、图片、标签、发货人、收货人和通知人，并允
许每条资源选择关联一个企业，也允许作为当前组织的独立资源存在。

本文以当前仓库代码、数据库迁移链和权限清单为基线。本文是实施计划，不代表相关
功能已经完成；后续编码必须按阶段完成验证和提交，不能先增加无功能的菜单入口，也
不能用运行时回退掩盖迁移或存储能力缺失。

## 2. 业务目标

企业资源备忘录用于保存组织内可重复使用的轻量资料：

```text
企业资源
├── 企业档案
│   ├── 客户
│   ├── 供应商
│   └── 国外代理
└── 资源备忘
    ├── 地址管理
    ├── 备注管理
    ├── 图片管理
    ├── 标签管理
    ├── 发货人管理
    ├── 收货人管理
    └── 通知人管理
```

每条资源遵循以下归属规则：

- 必须属于当前组织，使用 `organization_id` 隔离租户数据。
- `partner_id` 可空；有值时关联当前组织内的客户、供应商或国外代理，无值时作为
  独立资源存在。
- 资源与企业的关联可以在编辑时建立或解除，解除关联不删除资源本身。
- 同一企业可以关联多条同类型资源。
- 客户、供应商和国外代理继续共用 `Partner` 企业主体，不为资源备忘复制企业档案。

## 3. 成功标准

全部阶段完成后，用户应能完成以下流程：

1. 从顶部“企业资源”进入任一资源分类。
2. 查看当前组织该分类下的全部资源，并按关键字、关联企业、关联状态和启用状态筛
   选。
3. 新建资源时可以选择企业，也可以不选择企业直接保存。
4. 编辑资源时可以建立、更换或解除企业关联。
5. 客户档案中的发货人、收货人和通知人与企业资源页面消费同一份数据，不产生两套
   资料真相。
6. 资源写入与审计日志在同一个数据库事务中提交，任一写入失败时整体回滚。
7. 用户只能访问当前组织及其权限范围内的数据，不能通过请求参数读取或关联其他组
   织的企业。
8. 图片通过正式对象存储链路上传、预览和删除，数据库不保存图片二进制或 Base64。

## 4. 当前实现基线

### 4.1 顶部菜单与路由

当前 `web/src/components/layout/HeaderMenus.tsx` 已提供顶部“企业资源”菜单，包含：

- 客户。
- 供应商。
- 国外代理。

三个页面对应的路由位于 `web/config/routes.ts`，并通过 `hideInMenu` 避免在左侧菜单
重复展示。当前尚无地址、备注、图片、标签、发货人、收货人和通知人的独立管理路
由。

### 4.2 企业地址

`Partner` 主表保存企业注册地址，`PartnerProfile` 和前端企业档案表单保存部分中英
文地址字段。当前模型适合企业档案地址，不支持一个组织维护多条可复用地址，也不支
持与企业无关的临时地址。

本期不把现有企业注册地址自动转换为地址资源，避免在无法判断地址用途时制造重复
数据。用户如需将档案地址保存为资源，应通过显式操作完成；该操作不属于第一阶段。

### 4.3 常用单证预设

现有 `PartnerShippingPreset` 支持以下类型：

- `SHIPPER`：发货人。
- `CONSIGNEE`：收货人。
- `NOTIFY_PARTY`：通知人。
- `ENGLISH_CARGO_NAME`：英文品名。
- `HS_CODE`：HS 编码。
- `MARKS`：唛头。

它已经具备公司名称、地址、联系人、电话、邮箱、国家代码、税号、默认项、排序、备
注和启用状态，但 `partner_id` 当前必填，只能作为 Partner 子资源存在。

发货人、收货人和通知人不能在新功能中另建第二套表。现有数据应迁入统一企业资源
表，客户档案与企业资源页面改为查询同一份数据。

### 4.4 附件与图片

现有 Partner 和 Order 附件只登记外部对象引用及文件元数据，包括文件名、MIME 类
型、文件大小、`object_key`、校验和与上传人。仓库当前没有完整的对象存储上传、预
签名 URL、图片访问和对象删除链路。

现有 Partner 附件可能包含合同、证照和 PDF，不能自动全部迁为图片资源。图片管理
必须在确定对象存储方案后单独实现，不允许仅提供 `object_key` 文本输入框冒充上传
功能。

### 4.5 备注与标签

当前备注和标签只是订单、费用、合同、账户等业务对象的字段，不是组织级可复用资
源。订单标签也不直接等同于企业资源标签，本期不自动迁移或合并。

### 4.6 权限

当前相关权限位于 `business.partner.*`，适用于企业档案、附件和单证预设。独立企业
资源可以没有 `partner_id`，继续使用 Partner 子域权限会造成领域含义和菜单权限错
位，因此需要新增企业资源权限。

## 5. 领域与数据模型建议

### 5.1 统一领域对象

新增统一领域对象 `EnterpriseResource`，不为七个分类复制七套 CRUD：

```text
EnterpriseResource
├── 组织归属
├── 可选企业关联
├── 资源分类
├── 通用显示与状态字段
└── 分类专属载荷
    ├── 文本载荷
    ├── 单证主体载荷
    └── 图片载荷
```

资源分类至少包括：

```text
ADDRESS
REMARK
IMAGE
TAG
SHIPPER
CONSIGNEE
NOTIFY_PARTY
```

为承接现有单证预设，还应保留以下内部资源类型：

```text
ENGLISH_CARGO_NAME
HS_CODE
MARKS
```

后三类继续供企业档案使用，本期不放入顶部“资源备忘”菜单。

### 5.2 通用字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | UUID 主键 |
| `organization_id` | 是 | 当前组织，负责租户隔离 |
| `partner_id` | 否 | 可选企业关联，必须属于当前组织 |
| `resource_type` | 是 | 资源分类 |
| `title` | 是 | 用户可识别的标题 |
| `enabled` | 是 | 启用或停用 |
| `sort_order` | 是 | 同分类下的排序值 |
| `remark` | 否 | 对资源本身的补充说明 |
| `created_by` | 是 | 创建人 |
| `created_at` | 是 | 创建时间 |
| `updated_at` | 是 | 修改时间 |
| `search_keywords` | 是 | 中文、英文、别名、全拼和拼音首字母检索键 |

索引至少包括：

- `organization_id + resource_type + enabled + sort_order`。
- `organization_id + partner_id + resource_type`。
- `organization_id + updated_at`。
- `search_keywords` 使用与当前动态候选项一致的检索索引策略。

### 5.3 地址与备注载荷

第一版使用受长度限制的多行 `content` 保存完整地址或备注，不立即拆分国家、省、市、
区、街道和门牌号。只有出现按行政区域筛选、自动补全或路线计算的明确需求时，再单
独升级地址结构。

校验规则：

- `ADDRESS` 和 `REMARK` 必须提供非空 `content`。
- 文本去除首尾空白，但保留内部换行。
- 不允许同时提交单证主体或图片载荷。

### 5.4 标签载荷

标签使用 `title` 作为标签名称，可选保存 `tag_color` 和 `remark`。

规则：

- 同一组织下，规范化后的标签名称唯一。
- 名称比较忽略首尾空白和大小写。
- 颜色值必须来自前端与后端共同约定的有限集合，不接受任意 CSS。
- 第一版不自动将企业资源标签同步为订单标签。

### 5.5 发货人、收货人与通知人载荷

继续复用现有单证主体字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `company_name` | 是 | 公司或主体名称 |
| `address` | 否 | 单证地址 |
| `contact_name` | 否 | 联系人 |
| `phone` | 否 | 电话 |
| `email` | 否 | 邮箱 |
| `country_code` | 是 | ISO 3166-1 alpha-2 国家代码 |
| `tax_identifier` | 否 | 税号或企业识别号 |
| `is_default` | 是 | 是否为关联企业在当前分类下的默认资源 |

规则：

- `SHIPPER`、`CONSIGNEE` 和 `NOTIFY_PARTY` 只能提交单证主体载荷。
- `partner_id` 为空时，`is_default` 必须为 `false`。
- 同一企业、同一分类最多只有一个启用的默认资源。
- 修改默认项时，在同一事务内取消原默认项并设置新默认项。

### 5.6 图片载荷

数据库只保存对象存储引用和元数据：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `file_name` | 是 | 原始文件名 |
| `mime_type` | 是 | 允许的图片 MIME 类型 |
| `file_size` | 是 | 文件大小 |
| `object_key` | 是 | 服务端生成的对象存储键 |
| `checksum` | 是 | 内容校验和 |
| `uploaded_by` | 是 | 上传人 |

禁止把图片二进制或 Base64 存入 PostgreSQL，禁止前端自行构造对象键，禁止在正式环
境缺少对象存储时静默写入本地目录。

## 6. 数据库迁移方案

新增版本化 SQL 迁移，执行以下明确步骤：

1. 创建 `enterprise_resources` 表、可空 Partner 外键、组织外键和必要索引。
2. 从 `partners.organization_id` 回填现有 `partner_shipping_presets` 的组织归属。
3. 将现有单证预设完整迁入 `enterprise_resources`，保留原 ID、`partner_id`、类型、
   默认状态、排序和时间。
4. 校验源表与目标表的迁移数量一致。
5. 删除旧的 `partner_shipping_presets` 表。
6. 更新 Ent Schema 并重新生成 Ent 代码。

迁移要求：

- 不修改已经执行过的历史迁移文件。
- 不使用运行时“双表查询”或“新表查不到再查旧表”的回退。
- 冷启动数据库执行完整迁移链后，结构必须与 Ent Schema 一致。
- 已有数据升级后，原客户档案的单证预设数量和内容必须保持一致。
- 现有 Partner 附件、企业注册地址、订单备注和订单标签不自动迁移。

## 7. 后端契约与分层

### 7.1 Protobuf 契约

新增独立的 `EnterpriseResourceService`，不继续扩大 `PartnerService`：

```http
GET    /api/v1/enterprise-resources
GET    /api/v1/enterprise-resources/{id}
POST   /api/v1/enterprise-resources
PUT    /api/v1/enterprise-resources/{id}
DELETE /api/v1/enterprise-resources/{id}
```

列表参数至少包括：

- `resource_type`：必填。
- `partner_id`：可选，只查询指定企业。
- `linked`：可选，区分已关联和独立资源。
- `enabled`：可选。
- `keyword`：标题、内容、公司名称、地址、联系人和检索键。
- `page` 与 `page_size`：遵循公共分页校验，`page_size` 最大值为 `200`。

创建与更新请求使用明确的分类载荷，不暴露任意 JSON：

```text
EnterpriseResourceInput
├── resource_type
├── partner_id（可选）
├── title
├── text（可选）
├── party（可选）
├── image（可选）
├── tag_color（可选）
├── remark
├── enabled
└── sort_order
```

Biz 层根据 `resource_type` 校验只能出现对应载荷，禁止一个资源同时提交多个不相关
载荷。

### 7.2 Kratos 分层

- `server/api/`：定义 Proto 契约并生成 HTTP、gRPC 和 OpenAPI 文件，不手改生成物。
- `internal/service`：处理请求 DTO、UUID 解析和领域对象转换，不访问 Ent，不写业务
  规则。
- `internal/biz`：定义 `EnterpriseResource`、仓储接口、类型校验、默认项规则和审计
  事件。
- `internal/data`：实现组织隔离、Partner 所属校验、分页查询、事务写入和 Ent 转换。
- `internal/server`：注册生成的 HTTP 与 gRPC 服务。
- Wire ProviderSet：分别注册 Repo、Usecase 与 Service，并重新生成 Wire。

### 7.3 现有 Partner 单证预设

现有客户档案不能继续访问旧表。Partner 单证预设接口改为使用统一企业资源仓储，并
固定传入当前 `partner_id` 和允许的单证资源类型。

是否删除现有 Partner 单证预设 RPC，应在实施前核对仓库外是否存在调用方。基线方案
是保留现有 RPC 路径并直接调用统一 Usecase，以避免破坏已有页面；它不是旧表回退，
所有读写都只访问 `enterprise_resources`。确认没有外部调用方后，可另行移除旧 RPC
并同步更新前端生成客户端。

## 8. 权限设计

新增以下权限：

```text
business.enterprise_resource.read
business.enterprise_resource.create
business.enterprise_resource.update
business.enterprise_resource.delete
```

权限目录使用“业务资料 · 企业资源 · 资源备忘”，依赖关系为：

- `create` 依赖 `read`。
- `update` 依赖 `read`。
- `delete` 依赖 `read`。

前端增加：

```text
canReadEnterpriseResources
canCreateEnterpriseResources
canUpdateEnterpriseResources
canDeleteEnterpriseResources
```

顶部菜单显示规则：

- 有 `canReadPartners` 时展示客户、供应商和国外代理。
- 有 `canReadEnterpriseResources` 时展示七个资源备忘入口。
- 两者任一成立时展示顶部“企业资源”。
- 后端权限和组织数据范围是最终边界，前端隐藏按钮不能代替后端授权。

修改 `server/internal/access/manifest.go` 后，必须运行
`pnpm run generate:permission-keys` 更新生成的前端权限键。

## 9. 前端页面与菜单

### 9.1 路由

新增以下隐藏侧边栏路由：

```text
/enterprise-resources/addresses
/enterprise-resources/remarks
/enterprise-resources/images
/enterprise-resources/tags
/enterprise-resources/shippers
/enterprise-resources/consignees
/enterprise-resources/notify-parties
```

七个路由指向同一个配置式 `EnterpriseResourcePage`，配置决定页面标题、资源类型、列
定义、表单字段和图标，不复制七套页面逻辑。

### 9.2 顶部菜单

顶部菜单使用两个可识别分组：

```text
企业档案：客户、供应商、国外代理
资源备忘：地址、备注、图片、标签、发货人、收货人、通知人
```

资源路由需要纳入顶部菜单激活状态。左侧菜单保持隐藏，避免相同入口重复出现。

### 9.3 列表与筛选

列表至少提供：

- 关键字搜索。
- 关联企业搜索。
- 关联状态：全部、已关联、独立资源。
- 启用状态。
- 稳定的 `rowKey=id`。
- 服务端分页和排序。

企业选择器使用服务端关键字过滤，不循环翻页或一次性加载全部 Partner。搜索范围复用
Partner 已有的业务代码、中英文名称、别名、全拼和拼音首字母能力。

### 9.4 表单

公共字段包括标题、可选关联企业、启用状态、排序和备注。分类字段如下：

- 地址：多行地址内容。
- 备注：多行备注内容。
- 标签：名称和有限颜色选项。
- 发货人、收货人、通知人：公司、地址、联系人、电话、邮箱、国家、税号和默认项。
- 图片：正式上传、预览和删除控件。

页面使用项目现有纯白高密度模板和 Ant Design 公共组件；实现前使用本地 Ant Design
CLI 查询涉及组件 API，完成后对变更路径执行 CLI lint。不得依赖未公开的 `.ant-*`
内部结构新增样式。

## 10. 图片存储决策门

图片管理开始编码前，必须明确以下内容：

1. 使用的对象存储供应方和 S3 兼容性。
2. Bucket、区域、访问域名和私有访问策略。
3. 允许的图片 MIME 类型、单文件上限和组织容量限制。
4. 图片删除是立即删除对象，还是先删除数据库引用再由后台任务清理。
5. 是否需要缩略图、压缩、方向纠正和恶意文件扫描。

推荐上传流程：

```text
前端请求上传凭证
    ↓
后端生成受对象键、MIME、大小和有效期限制的预签名 URL
    ↓
前端直传对象存储
    ↓
前端提交对象键和元数据创建图片资源
    ↓
后端校验对象归属并在事务内写资源与审计日志
```

在上述决策未完成前，可以先实现其他六类资源，但不展示不可用的图片管理入口，不添
加本地文件存储回退。

## 11. 审计与事务一致性

资源写操作使用以下审计动作：

```text
enterprise_resource.create
enterprise_resource.update
enterprise_resource.delete
```

审计详情至少包含：

- `resource.id`。
- `resource.type`。
- `partner.id`，有企业关联时记录。
- `linked`。

Data 层必须在同一个事务中执行资源写入和 `writeAudit`：

```text
资源写入成功 + 审计写入成功 = 提交
资源写入失败或审计写入失败 = 回滚
```

删除对象存储中的图片不是数据库事务操作。实施图片删除前需要单独确定一致性方案，
不能把对象删除失败静默处理为成功。

## 12. 分阶段实施计划

### 阶段 0：固定契约与外部决策

目标：

- 确认七类资源字段和名称。
- 确认是否存在仓库外 Partner 单证预设 API 调用方。
- 确认对象存储供应方和图片删除策略。
- 确认资源删除采用物理删除，还是仅允许停用；本文暂按物理删除并保留审计设计。

验收：所有决策形成明确记录，不用代码中的条件分支代替业务决策。

### 阶段 1：建立统一存储模型

目标：

## 13. 非目标

以下内容不进入本期，除非后续明确提出：

- 自动把 Partner 注册地址复制为地址资源。
- 自动把现有 Partner 附件识别并迁为图片。
- 自动把订单备注、订单标签同步到企业资源。
- 一个资源同时关联多个 Partner；第一版为零个或一个 Partner。
- 地址地图、经纬度、路线规划和地理编码。
- 图片 OCR、智能分类和内容识别。
- 资源跨组织共享。
- 缺少对象存储时使用本地目录、Base64 或数据库大字段兜底。

## 14. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 单证预设迁移后数量或默认项丢失 | 迁移前后按类型和 Partner 对账，并增加迁移验收查询 |
| 可空 `partner_id` 导致跨组织关联 | Data 层在写入事务内校验 Partner 的 `organization_id` |
| 七个页面复制后难以维护 | 使用一个配置式页面和统一请求层，分类只定义差异字段 |
| 通用表字段较多且部分为空 | Biz 按分类严格校验载荷，数据库使用明确列和索引，不使用任意 JSON |
| 图片上传暴露存储凭据 | 使用服务端生成的短时预签名 URL，前端不持有长期密钥 |
| 菜单隐藏被误认为权限控制 | 后端 Proto 权限规则和组织范围继续作为最终授权边界 |
| 审计失败留下已生效资源 | 资源写入和审计写入使用同一事务 |
| 新旧数据双写造成两份真相 | 迁移后只访问 `enterprise_resources`，不保留双写或查询回退 |

## 15. 完成定义

只有同时满足以下条件，企业资源备忘录才视为完成：

- 七个资源分类均有可用的管理入口，不存在空白占位页面。
- 资源可以关联当前组织企业，也可以独立保存。
- 解除企业关联不会删除资源。
- 客户档案与资源页面共享同一份发货人、收货人和通知人数据。
- 图片具备真实上传、预览和删除能力。
- API、权限、生成客户端和页面路由保持一致。
- 迁移链、后端测试、前端测试、类型检查和构建通过。
- 所有写操作具备事务内业务审计。
- 没有旧表查询回退、静默数据兼容、本地图片存储兜底或手改生成物。
