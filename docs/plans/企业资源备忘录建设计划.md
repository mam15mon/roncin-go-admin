# 企业资源备忘录建设计划

## 1. 文档目的

本文用于指导 `roncin-go-admin` 企业资源备忘录的设计、实施与验收。目标是在顶部
“企业资源”菜单下提供统一的“配置管理”入口，在同一页面管理地址、备注、图片、
标签、发货人、收货人和通知人。每条资源可以关联零个或多个企业；没有企业关联时，
资源仍作为当前组织的独立备忘资料存在。

本文以当前仓库代码、数据库迁移链和权限清单为基线。计划已于 2026-08-29 完成实施，
本文同时保留设计决策与验收基线；后续变更仍须按阶段完成验证和提交，不能增加无功能
的菜单入口，也不能用运行时回退掩盖迁移或存储能力缺失。

## 2. 业务目标

企业资源备忘录用于保存组织内可重复使用的轻量资料：

```text
企业资源
├── 企业档案
│   ├── 客户
│   ├── 供应商
│   └── 国外代理
└── 配置管理
    └── 页面标签
        ├── 地址管理
        ├── 备注管理
        ├── 图片管理
        ├── 标签管理
        ├── 收货人管理
        ├── 发货人管理
        └── 通知人管理
```

每条资源遵循以下归属规则：

- 必须属于当前组织，使用 `organization_id` 隔离租户数据。
- 资源本体不依赖 `partner_id`；通过独立关联表连接当前组织内的 Partner。
- 一个资源可以不关联企业，也可以关联一个或多个企业。
- 资源与企业的关联可以批量建立或解除，解除关联不删除资源本身。
- 同一企业可以关联多条同类型资源，同一资源也可以供多个企业复用。
- 客户、供应商和国外代理继续共用 `Partner` 企业主体，不为资源备忘复制企业档案。

## 3. 成功标准

全部阶段完成后，用户应能完成以下流程：

1. 从顶部“企业资源”进入“配置管理”，并在同一页面切换资源分类标签。
2. 查看当前组织该分类下的全部资源，并按分类提供的字段、关联企业、关联状态和启
   用状态筛选。
3. 新建资源时可以选择企业，也可以不选择企业直接保存。
4. 地址、收货人、发货人和通知人支持勾选一条或多条后批量关联或解除客户、供应商
   和国外代理；其他分类通过新建或编辑表单维护关联。
5. 客户档案中的发货人、收货人和通知人与企业资源页面消费同一份数据，不产生两套
   资料真相。
6. 资源写入与审计日志在同一个数据库事务中提交，任一写入失败时整体回滚。
7. 用户只能访问当前组织及其权限范围内的数据，不能通过请求参数读取或关联其他组
   织的企业。
8. 图片通过正式对象存储链路上传、预览和删除，数据库不保存图片二进制或 Base64。

## 4. 当前实现基线

### 4.1 顶部菜单与路由

当前 `web/src/components/layout/HeaderMenus.tsx` 已提供顶部“企业资源”菜单，包含：

- 客户。
- 供应商。
- 国外代理。

三个页面对应的路由位于 `web/config/routes.ts`，并通过 `hideInMenu` 避免在左侧菜单
重复展示。当前尚无统一配置管理页面和上述七个标签。

### 4.2 企业地址

`Partner` 主表保存企业注册地址，`PartnerProfile` 和前端企业档案表单保存部分中英
文地址字段。当前模型适合企业档案地址，不支持一个组织维护多条可复用地址，也不支
持与企业无关的临时地址。

本期不把现有企业注册地址自动转换为地址资源，避免在无法判断地址用途时制造重复
数据。用户如需将档案地址保存为资源，应通过显式操作完成；该操作不属于第一阶段。

### 4.3 常用单证预设

现有 `PartnerShippingPreset` 支持以下类型：

- `SHIPPER`：发货人。
- `CONSIGNEE`：收货人。
- `NOTIFY_PARTY`：通知人。
- `ENGLISH_CARGO_NAME`：英文品名。
- `HS_CODE`：HS 编码。
- `MARKS`：唛头。

它已经具备公司名称、地址、联系人、电话、邮箱、国家代码、税号、默认项、排序、备
注和启用状态，但 `partner_id` 当前必填，只能作为 Partner 子资源存在。

发货人、收货人和通知人不能在新功能中另建第二套表。现有数据应迁入统一企业资源
表，客户档案与企业资源页面改为查询同一份数据。

### 4.4 附件与图片

现有 Partner 和 Order 附件只登记外部对象引用及文件元数据，包括文件名、MIME 类
型、文件大小、`object_key`、校验和与上传人。仓库当前没有完整的对象存储上传、预
签名 URL、图片访问和对象删除链路。

现有 Partner 附件可能包含合同、证照和 PDF，不能自动全部迁为图片资源。图片管理
必须在确定对象存储方案后单独实现，不允许仅提供 `object_key` 文本输入框冒充上传
功能。

### 4.5 备注与标签

当前备注和标签只是订单、费用、合同、账户等业务对象的字段，不是组织级可复用资
源。订单标签也不直接等同于企业资源标签，本期不自动迁移或合并。

### 4.6 权限

当前相关权限位于 `business.partner.*`，适用于企业档案、附件和单证预设。独立企业
资源可以独立存在或关联多个 Partner，继续使用 Partner 子域权限会造成领域含义和
菜单权限错位，因此需要新增企业资源权限。

### 4.7 竞品功能基线

[易云配置管理竞品调研](../eyun-config-management.md) 记录了配置管理页面的只读调研结
果。竞品使用一个 `/base/config` 页面承载八个标签，而不是在顶部菜单平铺多个页
面：

```text
配置管理
├── 地址管理
├── 备注管理
├── 图片管理
├── 标签管理
├── 收货人管理
├── 发货人管理
├── 通知人管理
└── 业务信息代码管理
```

竞品的通用交互包括行勾选、当前页全选、列显示设置、分页、行内编辑与删除。地址及
三类单证主体支持批量关联客户、供应商和国外代理，三类单证主体还支持批量导入。

各标签的关键差异如下：

| 标签 | 竞品关键能力 |
| --- | --- |
| 地址 | 简称、联系人、电话、省市区和详细地址、地址类型、所属公司、创建人、关联人员、批量关联企业和地址类型 |
| 备注 | 备注名称、14 种业务备注类型、备注内容 |
| 图片 | 图片名称、上传、格式和 20M 限制、存储空间使用量 |
| 标签 | 标签组、组颜色、组内标签、勾选删除 |
| 收货人/发货人/通知人 | 相同页面结构，包含简称、企业名称、企业代码、地址、国家代码、电话、AEO、页面展示、批量关联和批量导入 |
| 业务信息代码 | 简称、代码一、代码二、创建人与所属公司 |

### 4.8 竞品能力采纳边界

本计划采用以下竞品结构：

- 顶部只提供一个“配置管理”入口，页面内使用标签切换。
- 列表支持勾选、当前页全选、列设置、分页和行内操作。
- 地址和三类单证主体支持批量关联企业。
- 地址支持地址类型和关联人员。
- 备注支持明确的业务备注类型。
- 标签使用“标签组 + 组内标签”模型，颜色属于标签组。
- 收货人、发货人和通知人复用同一页面与表单配置。
- 三类单证主体规划批量导入及结果反馈。

以下竞品行为不直接照搬，需要结合本项目边界处理：

- 竞品“所属公司”改为当前登录组织，不允许用户把资源写入权限范围外的组织。
- 企业关联使用统一 Partner 主体，批量关联入口按客户、供应商和国外代理角色筛选候
  选企业，不复制三套企业数据。
- 竞品的企业代码必须包含 `+` 的规则先记录为待确认业务规则，不在未确认前写入校验。
- “页面展示”的自动拼接格式需要先固定示例和换行规则，再由 Biz 层确定性生成。
- 图片空间配额需要对象存储和组织配额能力支持，不能仅在前端显示模拟数值。
- 竞品第八项“业务信息代码管理”不是用户当前明确提出的七项之一，列为后续候选范
  围，不进入本期完成定义。

## 5. 领域与数据模型建议

### 5.1 模型拆分原则

竞品信息表明七类数据的结构差异明显。采用“一张宽表 + 大量可空列”会把标签组、图
片元数据、地址行政区划和单证主体字段混在一起；采用任意 JSON 又会削弱校验、索引
和迁移能力。因此建议使用统一资源基表、明确的分类详情表和独立标签模型：

```text
EnterpriseResource（资源基表）
├── EnterpriseResourceAddress（地址详情，1:1）
├── EnterpriseResourceRemark（备注详情，1:1）
├── EnterpriseResourceImage（图片详情，1:1）
├── EnterpriseResourceParty（收/发/通知人详情，1:1）
├── EnterpriseResourceShippingText（英文品名/HS 编码/唛头详情，1:1）
├── EnterpriseTag（标签详情，1:1）
├── EnterpriseResourcePartner（企业关联，N:M）
├── EnterpriseResourceAssignee（关联人员，N:M）
└── EnterpriseResourceAddressType（地址类型，N:M）

EnterpriseTagGroup（标签组）
└── EnterpriseTag（组内标签，1:N，同时关联资源基表）
```

列表、批量选择、审计和权限可以共享，但不同实体继续使用明确字段和领域校验，不为
复用前端页面而牺牲后端模型边界。

### 5.2 资源基表

`EnterpriseResource` 保存七类资源的公共字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | UUID 主键 |
| `organization_id` | 是 | 当前组织，负责租户隔离 |
| `resource_type` | 是 | 七个公开分类及三个内部单证文本分类 |
| `short_name` | 是 | 列表简称或资源名称 |
| `enabled` | 是 | 启用或停用 |
| `sort_order` | 是 | 同分类下排序 |
| `created_by` | 新建必填 | 创建人；无法可靠追溯的历史迁移记录允许为空 |
| `updated_by` | 新建必填 | 最后修改人，创建时等于创建人；历史迁移记录允许为空 |
| `created_at` | 是 | 创建时间 |
| `updated_at` | 是 | 修改时间 |
| `search_keywords` | 是 | 中文、英文、别名、全拼和拼音首字母检索键 |

公开分类为 `ADDRESS`、`REMARK`、`IMAGE`、`TAG`、`SHIPPER`、`CONSIGNEE` 和
`NOTIFY_PARTY`。为承接现有数据，内部分类还包括 `ENGLISH_CARGO_NAME`、`HS_CODE`
和 `MARKS`；内部分类不显示在配置管理七个标签中。

资源基表不保存 `partner_id`。企业关联由多对多表维护，资源没有关联行时就是独立资
源。

索引至少包括：

- `organization_id + resource_type + enabled + sort_order`。
- `organization_id + updated_at`。
- `search_keywords` 使用与当前动态候选项一致的检索索引策略。

### 5.3 企业关联与关联人员

`EnterpriseResourcePartner` 至少保存 `resource_id`、`partner_id`、冗余的
`resource_type` 和 `is_default`，并对 `resource_id + partner_id` 建立唯一约束。冗余
类型只能由 Data 层从资源基表写入，不能信任客户端请求。七类资源都通过该表关联企
业。批量关联客户、供应商或国外代理时，入口只影响候选 Partner 的角色过滤，最终关
联的仍是统一 Partner 主体。

规则：

- Resource 和 Partner 必须属于同一组织。
- 一次批量请求可以处理多条资源和一个或多个 Partner。
- 重复关联返回明确的幂等结果，不插入重复记录。
- 解除关联只删除关联行，不删除 Resource 或 Partner。
- 列表中的客户、供应商和国外代理列，根据已关联 Partner 的启用角色分组展示。
- 单证主体的“默认项”属于 Resource 与 Partner 的关系，保存在关联行上。
- 数据库建立 `partner_id + resource_type WHERE is_default = true` 的部分唯一索引，
  保证同一 Partner、同一单证类型最多一个默认资源。
- 设置新默认项时，在同一事务内锁定对应 Partner 和类型的关联集合，清除原默认项，
  再设置新默认项并写审计日志；不能只做无锁的“先清后设”。
- 停用默认资源或解除其企业关联时，必须在同一事务中清除 `is_default`；已停用资源
  不能被设置为默认项。

地址的关联人员使用 `EnterpriseResourceAssignee` 保存资源与当前组织成员关系，不在
地址表中存姓名快照。第一版只在地址管理开放关联人员，后续其他分类确有需要时再复
用。

### 5.4 地址详情

`EnterpriseResourceAddress` 建议保存：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `contact_name` | 否 | 联系人 |
| `contact_phone` | 否 | 联系电话 |
| `country_code` | 是 | 国家或地区代码，中国地址为 `CN` |
| `province_code` | 否 | 省级行政区编码 |
| `city_code` | 否 | 城市编码 |
| `district_code` | 否 | 区县编码 |
| `address_detail` | 是 | 详细地址 |
| `remark` | 否 | 备注 |

中国地址使用现有后端行政区划字典和省、市、区县三级联动；海外地址不提交中国行政
区划编码。后端校验行政区划层级和父子关系，前端不静默使用另一套静态数据。

地址类型通过 `EnterpriseResourceAddressType` 维护，第一版固定支持：

```text
CONTAINER_OPERATION  拆/装箱地址
PICKUP               提货地址
DELIVERY             送货地址
```

一条地址可以关联多个地址类型，并支持对勾选地址批量设置或解除类型。

### 5.5 备注详情

`EnterpriseResourceRemark` 保存 `remark_type` 和多行 `content`。第一版按竞品基线支持
以下 14 种类型：

```text
BOOKING       订舱备注
ALLOCATION    配舱备注
TRANSPORT     运输委托备注
ORDER         订单备注
BILL_OF_LADING 提单备注
CUSTOMER      客户备注
SUPPLIER      供应商备注
FOREIGN_AGENT 国外代理备注
QUOTATION     报价备注
MANIFEST      舱单备注
PACKING_LIST  装箱单备注
OPERATION     操作备注
COMMISSION    提成备注
WAREHOUSE     仓储备注
```

类型使用明确枚举，第一版不引入后台可配置字典。若后续需要由管理员增删类型，应先确
认历史引用、停用语义和权限，再改为主数据模型。

### 5.6 标签组与标签

标签基表使用 `EnterpriseResource`，标签组与标签专属字段使用两个明确实体：

- `EnterpriseTagGroup`：组织、组名、十六进制颜色、排序和时间字段。
- `EnterpriseTag`：资源 ID、组织、标签组和排序字段；标签名称复用资源基表
  `short_name`。

规则：

- 同一组织下标签组名称唯一。
- 同一标签组下，规范化后的标签名称唯一。
- 颜色使用标准 `#RRGGBB`，允许清空；后端校验格式，不接受任意 CSS 表达式。
- 标签可通过统一企业关联表连接零个或多个 Partner，也可以作为独立标签存在。
- 删除标签组前必须确保组内没有标签，或由用户明确勾选并确认级联范围；第一版不静
  默级联删除。
- 第一版不自动将企业资源标签同步为订单标签。

### 5.7 发货人、收货人与通知人详情

`EnterpriseResourceParty` 由三种 `resource_type` 共用，建议保存：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `company_name` | 是 | 企业或单证主体名称 |
| `business_code` | 否 | 企业代码，具体格式规则在阶段 0 确认 |
| `address` | 否 | 单证地址 |
| `country_code` | 是 | ISO 3166-1 alpha-2 国家代码，默认 `CN` |
| `contact_name` | 否 | 联系人 |
| `contact_phone` | 否 | 联系电话 |
| `email` | 否 | 邮箱 |
| `tax_identifier` | 否 | 税号或企业识别号 |
| `aeo_code` | 否 | AEO 代码 |
| `custom_display` | 是 | 是否使用自定义页面展示内容 |
| `display_content` | 否 | 页面展示内容；非自定义时由 Biz 层按固定规则生成 |
| `remark` | 否 | 内部备注 |

三类页面使用同一个领域对象、列表配置、表单配置和导入流程，仅固定不同的
`resource_type`。

### 5.8 内部单证文本详情

`EnterpriseResourceShippingText` 明确承接现有三类非单证主体预设：

| 资源类型 | 详情字段 | 说明 |
| --- | --- | --- |
| `ENGLISH_CARGO_NAME` | `content` | 英文品名 |
| `HS_CODE` | `code` | 6 至 10 位数字编码，沿用现有领域校验 |
| `MARKS` | `content` | 唛头文本 |

三类内部资源继续由现有 Partner 单证预设接口读取和维护，不进入配置管理七个标签。
迁移后所有读写只访问资源基表、内部单证文本详情表和企业关联表，不保留旧表查询或双
写。

### 5.9 图片详情与配额

`EnterpriseResourceImage` 只保存对象存储引用和元数据：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `file_name` | 是 | 原始文件名 |
| `mime_type` | 是 | 允许的图片 MIME 类型 |
| `file_size` | 是 | 文件大小 |
| `object_key` | 是 | 服务端生成的对象存储键 |
| `checksum` | 是 | 内容校验和 |
| `width` | 否 | 图片宽度 |
| `height` | 否 | 图片高度 |
| `uploaded_by` | 是 | 上传人 |

竞品限制为 jpg、jpeg、png、bmp、gif 且小于 20M，建议作为本项目初始默认值，但必须
在阶段 0 明确按 MiB 还是 MB 计算，并由后端依据真实 MIME 和大小校验。3:2 只作为界
面建议，不作为强制裁剪规则。

存储用量按当前组织聚合展示。本期确认不设置默认组织配额，能力接口以 `0` 表示不限
额，页面展示已用空间和“不限额”；不照抄竞品的 5GB 数值，也不显示虚假的使用比例。

禁止把图片二进制或 Base64 存入 PostgreSQL，禁止前端自行构造对象键，禁止在正式环
境缺少对象存储时静默写入本地目录。

## 6. 数据库迁移方案

以 Ent Schema 为结构真相源，按以下顺序实施：

1. 新增资源基表、分类详情、内部单证文本、企业关联、关联人员、地址类型、标签组和
   标签 Ent Schema，并更新 Partner、Organization 和 User 边。
2. 重新生成 Ent 代码并审阅生成差异。
3. 根据 Ent Schema 差异生成或编写版本化 SQL 迁移，创建对应表、外键、唯一约束和
   索引。
4. 从 `partners.organization_id` 回填现有 `partner_shipping_presets` 的组织归属。
5. 将 `SHIPPER`、`CONSIGNEE` 和 `NOTIFY_PARTY` 迁入资源基表与单证主体详情表。
6. 将 `ENGLISH_CARGO_NAME`、`HS_CODE` 和 `MARKS` 迁入资源基表与内部单证文本详情
   表。
7. 将原 `partner_id` 迁入企业关联表，并把原默认状态和资源类型迁到对应关联行。
8. 分别校验源表、资源基表、两类详情表和企业关联表的迁移数量与分类数量一致。
9. 删除旧的 `partner_shipping_presets` 表。
10. 从空数据库执行完整迁移链，并运行迁移清单测试确认最终结构与 Ent Schema 一致。

迁移要求：

- 不修改已经执行过的历史迁移文件。
- 不使用运行时“双表查询”或“新表查不到再查旧表”的回退。
- 冷启动数据库执行完整迁移链后，结构必须与 Ent Schema 一致。
- 已有数据升级后，六类原客户档案单证预设的数量、内容、默认项和关联必须保持一致。
- 现有 Partner 附件、企业注册地址、订单备注和订单标签不自动迁移。

## 7. 后端契约与分层

### 7.1 Protobuf 契约

新增独立的 `EnterpriseResourceService`，不继续扩大 `PartnerService`。资源 CRUD 基


批量关联、标签和导入使用独立请求消息，建议契约能力包括：

```http
POST   /api/v1/enterprise-resource-associations:batchCreate
POST   /api/v1/enterprise-resource-associations:batchDelete
POST   /api/v1/enterprise-resource-address-types:batchAssign
POST   /api/v1/enterprise-resource-address-types:batchRemove

DELETE /api/v1/enterprise-tags:batchDelete

```

最终 URL 以 Proto 和项目现有 HTTP 风格评审结果为准，但预览导入与确认导入必须是两
个明确阶段，不能在用户确认重复覆盖前直接写库。

第一版批量企业关联接口只接受 `ADDRESS`、`SHIPPER`、`CONSIGNEE` 和
`NOTIFY_PARTY`；其他类型如需批量能力，必须作为后续明确需求扩展。七类资源的新建
与更新接口均支持可选的企业关联消息，因此备注、图片和标签仍可关联多个企业或保持
独立。

列表参数至少包括：

- `resource_type`：必填。
- `partner_id`：可选，通过关联表查询指定企业。
- `linked`：可选，区分已关联和独立资源。
- `enabled`：可选。
- `keyword`：简称、内容、公司名称、企业代码、地址、联系人和检索键。
- `page` 与 `page_size`：遵循公共分页校验，`page_size` 最大值为 `200`。

三类单证主体列表还支持企业名称、企业代码、企业地址、国家代码以及按客户、供应商
或国外代理关联状态筛选。地址列表支持地址类型和关联人员筛选。

创建与更新请求使用明确的 `oneof` 分类载荷，不暴露任意 JSON：

```text
EnterpriseResourceInput
├── resource_type
├── short_name
├── partner_associations（可选消息；显式空列表表示解除全部关联）
├── address（可选）
├── remark（可选）
├── party（可选）
├── image（可选）
├── enabled
└── sort_order
```

企业关联使用带字段存在性的独立消息，区分“本次不修改关联”和“显式解除全部关
联”；地址类型和关联人员使用专属字段或批量接口。Biz 层根据 `resource_type` 校验只
能出现对应载荷，禁止一个资源同时提交多个不相关载荷。

### 7.2 Kratos 分层

- `server/api/`：定义 Proto 契约并生成 HTTP、gRPC 和 OpenAPI 文件，不手改生成物。
- `internal/service`：处理请求 DTO、UUID 解析和领域对象转换，不访问 Ent，不写业务
  规则。
- `internal/biz`：定义资源、分类详情、标签组、标签、仓储接口、批量关联、默认项规
  则、导入确认和审计事件。
- `internal/data`：实现组织隔离、关联 Partner 所属校验、多对多查询、分页、事务写
  入和 Ent 转换。
- `internal/server`：注册生成的 HTTP 与 gRPC 服务。
- Wire ProviderSet：分别注册 Repo、Usecase 与 Service，并重新生成 Wire。

### 7.3 现有 Partner 单证预设

现有客户档案不能继续访问旧表。Partner 单证预设接口改为使用统一企业资源仓储，并
固定通过当前 `partner_id` 的企业关联查询和允许的单证资源类型过滤。

是否删除现有 Partner 单证预设 RPC，应在实施前核对仓库外是否存在调用方。基线方案
是保留现有 RPC 路径并直接调用统一 Usecase，以避免破坏已有页面；它不是旧表回退，
所有读写都只访问新资源基表、对应详情表和企业关联表。确认没有外部调用方后，可另
行移除旧 RPC 并同步更新前端生成客户端。

## 10. 图片存储决策门

图片管理开始编码前，必须明确以下内容：

1. 使用的对象存储供应方和 S3 兼容性。
2. Bucket、区域、访问域名和私有访问策略。
3. 允许的图片 MIME 类型、单文件上限和组织容量限制。
4. 图片删除是立即删除对象，还是先删除数据库引用再由后台任务清理。
5. 是否需要缩略图、压缩、方向纠正和恶意文件扫描。

推荐上传流程：

```text
前端请求上传凭证
    ↓
后端生成受对象键、MIME、大小和有效期限制的预签名 URL
    ↓
前端直传对象存储
    ↓
前端提交对象键和元数据创建图片资源
    ↓
后端校验对象归属并在事务内写资源与审计日志
```

在上述决策未完成前，可以先实现其他六类资源，但不展示不可用的图片管理入口，不添
加本地文件存储回退。

### 10.1 本期已采用决策

- 使用可配置的 S3 兼容私有对象存储；Endpoint、Region、Bucket、访问密钥和路径风格
  均通过环境变量注入，仓库不保存真实凭据。
- 允许 `image/jpeg`、`image/png`、`image/bmp` 和 `image/gif`，单文件上限按
  `20 MiB` 计算。对象键由服务端按组织和 MIME 生成，前端不能指定。
- 使用 S3 标准 SHA-256 校验头验证对象内容；登记资源前再次核对对象大小、MIME、
  校验和、组织元数据和对象键前缀。
- 当前不设置组织总配额，页面展示组织已登记图片的总用量并明确标记“不限额”。
- 图片采用立即物理删除：先删除对象，失败时不删除数据库记录且接口返回失败；对象
  删除成功后再在事务内删除资源并写审计。未引入后台清理或静默成功分支。
- 本期不做缩略图、压缩、方向纠正、OCR 和恶意文件扫描。
- 对象存储未启用时，能力接口返回不可用，前端不展示图片管理标签；不回退到本地目
  录、Base64 或数据库大字段。

## 11. 审计与事务一致性

资源写操作使用以下审计动作：

```text
enterprise_resource.create
enterprise_resource.update
enterprise_resource.delete
enterprise_resource.partner.batch_link
enterprise_resource.partner.batch_unlink
enterprise_resource.address_type.batch_assign
enterprise_resource.address_type.batch_remove
enterprise_resource.assignee.batch_assign
enterprise_resource.assignee.batch_remove
enterprise_resource.import
enterprise_tag_group.create
enterprise_tag_group.update
enterprise_tag_group.delete
enterprise_tag.create
enterprise_tag.update
enterprise_tag.delete
```

标签的资源公共字段和标签详情修改统一记录为 `enterprise_tag.update`，避免同一次标签
编辑在 `enterprise_resource.update` 与 `enterprise_tag.update` 之间产生两套口径。

审计详情至少包含：

- `resource.id`。
- `resource.type`。
- `partner.ids`，批量关联或解除时记录目标企业集合。
- `resource.ids`，批量操作时记录资源集合。
- `linked_count` 或 `unlinked_count`。

Data 层必须在同一个事务中执行资源写入和 `writeAudit`：

```text
资源写入成功 + 审计写入成功 = 提交
资源写入失败或审计写入失败 = 回滚
```

删除对象存储中的图片不是数据库事务操作。实施图片删除前需要单独确定一致性方案，
不能把对象删除失败静默处理为成功。

## 14. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 单证预设迁移后数量或默认项丢失 | 迁移前后按类型和 Partner 对账，并增加迁移验收查询 |
| 英文品名、HS 编码或唛头没有迁移落点 | 使用内部单证文本详情表分别承接并按六种原类型核对数量 |
| 并发设置默认项产生多个默认资源 | 关联表冗余资源类型、建立部分唯一索引，并在事务内锁定后切换默认项 |
| 批量关联混入其他组织 Partner | Data 层在同一事务内校验全部 Partner 的 `organization_id`，任一越界则整体拒绝 |
| 七个标签复制后难以维护 | 共享页面框架、批量工具栏和三类单证主体配置，保留分类专属表单与列定义 |
| 多态资源形成宽表或任意 JSON | 使用资源基表与明确分类详情表，Biz 按分类校验一对一详情 |
| 当前页全选被误解为全量选择 | 明确显示选择范围和数量，批量接口只处理请求中显式提交的资源 ID |
| 导入覆盖意外清空现有字段 | 预览与确认分离，只覆盖导入契约明确提供的字段 |
| 图片上传暴露存储凭据 | 使用服务端生成的短时预签名 URL，前端不持有长期密钥 |
| 菜单隐藏被误认为权限控制 | 后端 Proto 权限规则和组织范围继续作为最终授权边界 |
| 审计失败留下已生效资源 | 资源写入和审计写入使用同一事务 |
| 新旧数据双写造成两份真相 | 迁移后只访问新资源基表、详情表和关联表，不保留双写或查询回退 |

## 15. 完成定义

只有同时满足以下条件，企业资源备忘录才视为完成：

- 顶部“企业资源”下有一个“配置管理”入口，页面内七个标签均可用，不存在空白占位
  页面。
- 七类资源均可以关联当前组织内零个、一个或多个企业，也可以独立保存。
- 地址及三类单证主体批量建立或解除企业关联时不会删除资源。
- 地址支持省市区联动、地址类型、关联人员和批量关联。
- 备注支持计划定义的 14 种业务类型。
- 标签支持标签组、组颜色和组内标签管理。
- 三类单证主体支持竞品基线字段、筛选、批量关联和可确认的批量导入。
- 客户档案与资源页面共享同一份发货人、收货人和通知人数据。
- 英文品名、HS 编码和唛头迁入明确的内部详情表，现有单证预设接口不丢数据。
- 同一企业、同一单证类型在并发写入后仍最多只有一个可用默认资源。
- 图片具备真实上传、预览、删除和组织空间用量展示能力。
- API、权限、生成客户端和页面路由保持一致。
- 迁移链、后端测试、前端测试、类型检查和构建通过。
- 所有写操作具备事务内业务审计。
- 没有旧表查询回退、静默数据兼容、本地图片存储兜底或手改生成物。
