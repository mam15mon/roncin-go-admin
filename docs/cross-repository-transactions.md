# 跨仓储事务与外部副作用边界设计

> 状态：设计已确认，尚未实施  
> 基线：2026-08-30 代码复核  
> 适用范围：`server/internal/biz` 与 `server/internal/data`

## 1. 目标与非目标

本设计解决两类容易被混为一谈的一致性问题：

1. 一个业务用例需要调用多个 PostgreSQL 仓储时，关键写入、业务审计和任务意图
   应共享同一个数据库事务。
2. 对象存储、钉钉等外部系统不能参加 PostgreSQL 事务，必须在数据库提交后执行，
   并通过类型化任务记录保证可重试、可审计。

本设计不要求立即改造所有仓储，不引入分布式事务，不追求单据号绝对连续，也不在
事务回调外层增加自动重试。只有出现经过验证的跨仓储原子性需求时，才按本文方案
逐个用例接入。

## 2. 当前基线与问题校正

当前 `internal/data/transaction.go` 已提供以下统一生命周期：

- `Data.WithTx` 管理 Ent 事务；
- `Data.withSQLTx` 管理原生 SQL 事务；
- `runTransaction` 统一处理提交、错误回滚和 panic 回滚。

现有仓储通常按业务聚合组织写入。例如 `orderRepo.Create` 已经在同一个 Ent 事务内
完成订单号分配、订单主记录、关联记录、生命周期事件、通知意图和审计日志。因此，
旧治理记录中的“订单号分配与订单落库非原子”已经不成立，不应以此为由实施事务
抽象。

当前尚未提供的是由 Biz 用例控制、可被多个仓储共同参与的事务边界。已确认的相关
路径如下：

| 路径 | 当前行为 | 一致性判断 | 后续策略 |
| --- | --- | --- | --- |
| 订单创建 | 发号、订单、关联数据、通知意图、审计同事务 | 已满足数据库原子性 | 保持现状 |
| 账单创建 | 汇率快照在 Biz 层解析，账单仓储随后独立开启写事务 | 不会产生部分数据库写入，但汇率读取和账单写入不共享事务快照 | 作为共享事务首个试点 |
| 核销创建 | 汇率与本币信息先读取，核销仓储随后独立开启写事务 | 与账单创建同类 | 账单试点稳定后再评估 |
| 企业图片删除 | 先删除对象，再删除数据库记录 | 数据库删除失败时可能留下失效的图片元数据 | 改为事务内登记类型化删除任务，提交后删对象 |
| 钉钉通知 | 领取任务、发送、完成任务分步执行 | 属于有租约的最终一致性流程，不能放入长事务 | 保持外部发送在事务外 |

## 3. 一致性语义

### 3.1 必须原子提交的数据

同一业务动作中的以下 PostgreSQL 写入必须一起提交或一起回滚：

- 核心业务状态及其关系数据；
- 与本次业务状态对应的单据号分配；
- 业务审计日志；
- 需要在提交后执行的外部副作用意图。

单据号允许出现断号。不得为了保证号码连续而扩大锁范围、延长事务时间或在事务
失败后复用已经对外展示过的号码。当前能够随业务写入一起回滚的发号路径保持原状。

### 3.2 必须留在事务外的操作

以下操作不得在数据库事务回调中执行：

- HTTP、gRPC 或第三方 SDK 网络请求；
- 对象上传、下载和删除；
- 钉钉、企业微信等消息发送；
- 不受当前数据库连接控制的文件系统写入；
- 启动 goroutine 或把事务句柄传给异步流程。

这类操作需要可靠执行时，应在数据库事务内写入类型化任务记录，提交后由 Worker
领取。任务必须具有唯一幂等键、明确状态、租约和最大尝试次数；不能以“失败后静默
成功”或请求内自动回退代替任务状态。

### 3.3 隔离级别、锁与重试

- 默认继续使用 PostgreSQL `READ COMMITTED`，不全局提升隔离级别。
- 并发不变量通过唯一索引、版本号和针对性 `FOR UPDATE`/`FOR SHARE` 保证。
- 事务管理器不自动重试回调。调用方可能已经生成 ID、修改内存对象或记录指标，
  自动重放容易产生重复副作用。
- 若某个用例确实需要处理序列化失败，必须单独证明回调可安全重放，并在该用例内
  显式设计；不能作为公共兜底能力。
- 第一阶段不支持保存点。已加入外层事务的仓储返回错误后，用例必须原样向外传播，
  不得吞掉错误后继续提交。

## 4. 共享事务接口

事务接口由 Biz 层定义，保持领域层不依赖 Ent、`database/sql` 或 Data 实现：

```go
type Transactor interface {
	WithinTransaction(context.Context, func(context.Context) error) error
}
```

用例只负责声明事务范围：

```go
return uc.transactor.WithinTransaction(ctx, func(txCtx context.Context) error {
	if err := uc.firstRepo.Change(txCtx, input); err != nil {
		return err
	}
	return uc.secondRepo.Record(txCtx, event)
})
```

Data 层实现时，将当前 `*ent.Tx` 绑定到仅在 `internal/data` 可识别的派生
`context.Context`。参与用例的仓储通过统一客户端解析函数取得事务客户端；仓储内部
再次调用 `WithTx` 时必须加入已有事务，不能开启第二个独立事务。

该实现必须遵守以下约束：

- Biz 和 Service 层永远看不到 `*ent.Tx`；
- 没有外层事务时，现有仓储方法仍自行开启并提交事务；
- 有外层事务时，参与仓储只加入该事务，提交和回滚由最外层负责；
- 只改造试点所需的仓储方法，不一次性替换全仓库的 `d.db` 访问；
- 事务上下文只能同步使用，事务结束后继续使用应在测试中失败；
- `WithTx` 的 panic 回滚和提交错误传播语义保持不变。

共享事务关系如下：

```text
Biz Usecase
    │
    ├── Transactor.WithinTransaction(txCtx)
    │       ├── Repo A ──┐
    │       ├── Repo B ──┼── 同一 PostgreSQL / Ent Tx
    │       ├── Audit ───┤
    │       └── Task ────┘
    │
    └── 数据库提交后 ──> Worker ──> 对象存储 / 钉钉等外部系统
```

## 5. 首个实施试点：单账单创建

首个试点选择 `FinanceBillUsecase.Create`，暂不同时迁移批量建单和核销。原因是该路径
已经同时依赖 `FinanceBillRepo` 与 `ExchangeRateRepo`，范围有限，并且写入端已有
幂等键、费用锁、发号和事务审计基础。

建议执行顺序：

1. 在事务外完成请求格式校验和纯内存归一化。
2. 进入共享事务后，重新确认幂等键；数据库唯一约束仍是最终防线。
3. 通过事务上下文读取待转账单费用并构造账单候选值；最终状态仍由写入仓储锁内
   复核，不能把这次前置读取当作并发保证。
4. 通过同一事务上下文解析汇率和本币，固化汇率值、来源、日期及配置 ID。若要求
   配置在提交前不得变化，只锁定实际命中的配置行，不扩大到整张配置表。
5. 账单仓储加入已有事务，沿用当前 `FOR UPDATE` 重新验证费用状态、方向、结算
   单位、币种和金额，然后完成发号、账单与明细写入、费用状态变更和审计。
6. 提交后再读取完整账单作为响应；响应读取失败不能反向宣称写事务失败，客户端
   可通过幂等键查询已提交结果。

试点不得顺便重构批量建单。批量路径最多包含 500 条费用和多个账单，只有在单账单
试点获得锁等待及事务耗时数据后，才决定是否采用同一接口或保持仓储内聚合事务。

## 6. 企业图片删除的最终一致性方案

图片删除不能通过共享数据库事务解决。推荐使用与现有通知投递相同的“任务主记录
和类型化明细”模式，不建立承载任意 JSON 的万能 Outbox：

1. 数据库事务内删除或停用企业图片资源、写审计日志，并创建对象删除任务及包含
   `organization_id`、`object_key` 的类型化明细；
2. 数据库提交后，Worker 调用对象存储删除；
3. 删除成功后完成任务；失败则按任务策略记录错误并重试，超过上限进入死信；
4. 任务幂等键由资源 ID 和对象键确定，同一对象的重复删除只产生一条有效任务；
5. 运维可查看和显式回放死信任务，不能静默丢弃失败。

这样即使对象存储暂时不可用，最多留下不可见的孤立对象，不会留下指向已删除对象的
有效业务记录。上传确认仍保持“先验证对象存在，再写数据库元数据”的当前语义。

## 7. 验证要求

共享事务基础设施至少需要覆盖：

- 两个仓储写入均成功时只提交一次；
- 第二个仓储失败时，第一个仓储写入、审计和任务意图全部回滚；
- 参与仓储内部调用 `WithTx` 时不会开启第二个事务；
- panic 会回滚并继续向上抛出；
- Commit 和 Rollback 错误不被吞掉；
- 已结束的事务上下文不能继续查询或写入；
- 单账单并发创建仍由幂等键和费用状态约束保证唯一结果；
- 汇率配置并发变更时，账单保存的是同一事务内解析出的完整快照；
- 外部发送或对象删除不会发生在数据库事务回调中。

优先使用 Data 层集成测试验证真实事务边界；Biz 单测只验证调用顺序、错误传播和
业务分支，不能用 mock 的“成功返回”替代数据库回滚证明。

## 8. 风险与控制

| 风险 | 后果 | 控制措施 |
| --- | --- | --- |
| 仓储未识别事务上下文 | 看似被用例包裹，实际仍分两次提交 | 为每个参与仓储增加“仅一次 Begin/Commit”集成测试 |
| 在事务内调用外部服务 | 锁等待扩大，第三方超时拖垮连接池 | 代码审查禁止，改写类型化任务意图 |
| 外层吞掉内层错误 | 部分状态被提交 | 第一阶段不支持保存点，错误必须直接返回 |
| 锁顺序不一致 | 并发死锁 | 为试点固定“汇率配置→费用→号码规则与序列”的加锁顺序 |
| 事务自动重试 | 回调被重复执行 | 公共事务管理器不提供重试 |
| 为迁移而全量改仓储 | 变更面过大且难以证明收益 | 只迁移已确认的跨仓储用例 |
| 通用 Outbox payload 漂移 | 无法做编译期和迁移期校验 | 每类副作用使用类型化明细和显式版本演进 |

## 9. 分阶段实施与完成标准

### 阶段一：基础设施

- 在 Biz 定义 `Transactor`；
- Data 实现事务上下文、加入已有事务和相关测试；
- Wire 注入事务管理器；
- 不改变任何业务用例行为。

### 阶段二：单账单试点

- 仅迁移 `FinanceBillUsecase.Create`；
- 补充真实回滚、并发幂等、汇率快照和审计一致性测试；
- 记录事务耗时、锁等待和死锁情况。

### 阶段三：按证据扩展

- 复核核销创建是否需要同一事务快照；
- 单独实施企业图片删除任务；
- 其他用例只有出现多个仓储关键写入时才接入，不以代码风格统一为理由迁移。

完成标准是：试点用例的数据库状态、审计和任务意图可以通过失败注入证明原子性，
外部副作用可以通过任务状态证明最终一致性，并且没有 Ent 类型泄漏到 Biz/Service。
