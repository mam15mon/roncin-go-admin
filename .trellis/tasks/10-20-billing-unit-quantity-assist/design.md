# 技术设计

状态：用户已批准实施，箱量提供计划与实际两个明确来源。

## 架构

- 复用 BillingUnit 及现有维护权限；新增正式迁移补齐单位，不能重写旧迁移作为交付。
- 开发种子和正式初始化保持一致；只补缺失单位，不覆盖管理员配置。
- 在订单费用域提供只读数量预览：service 转 DTO，biz 决定算法，data 校验组织范围并聚合数据。
- 使用 PostgreSQL numeric 聚合并扫描十进制字符串，biz 用 decimal 换算，避免现有 float64 货量投影的精度损失。
- 首期不新增写入实体、锁或事务；正常保存走现有费用用例。

## 数据流

1. 操作员主动请求建议；箱量显式选择订舱计划或实际登记。
2. 服务端校验订单访问权限、单位有效性与明确的箱型映射。
3. 返回来源名称、原始数据、公式、建议数量，或不可计算原因。
4. 前端确认后仅填入表单并更新金额预览；取消不变。
5. 保存仍遵循现有费用校验，不将预览当作自动保存承诺。

接口以 server/api/order/v1/order_fee.proto 为源：GET /api/v1/orders/{order_id}/fee-quantity-preview，billingUnitId 和 source 必填。响应 data 含 available、quantity、sourceLabel、formula、inputs、reason。沿用 fee.read 组织范围权限，正常生成 Go、OpenAPI 与客户端。

## 单位与数量来源

- 完整目录为 38 项：原七项基础单位，加 HOUR/KG/RT、十八种既有箱型、CHE 和 PCS/PKG/CTN/PLT/TRIP/KM/WEEK/MONTH/TEU。已有同义旧码不删除，不额外恢复 BILL/SHIP/SHIPMENT 等模糊候选。
- is_container_unit 仅为布尔值，不足以表达自然箱和具体箱型；禁止靠中文名模糊匹配箱型。
- 按单位代码与公共 container_spec 代码精确匹配，不引入持久化映射配置；无法对应则明确不可带入。
- KG 明确毛重；吨 = KG / 1000；RT = max(CBM, KG / 1000)，不附带最低收费或进位合同条款。
- 包装单位首期只人工录费，不把 package_count 自动当作托盘或纸箱数。
- 货量采用本订单 cargo_items；不再累加独占箱或共享箱。订单有关联共享箱时 ACTUAL 整箱数不可确定，明确提示手工录入，PLANNED 箱量不受影响。

## 前端

- 统一查询和确认展示，覆盖表格、普通弹窗、复制、补录入口；复用请求客户端与服务端状态工具。
- 查询隔离订单、单位和来源；切换/关闭后迟到响应不能填入。
- 使用既有权限与字段可编辑判断；来源与公式使用业务名称，不显示内部 ID。

## 迁移与恢复

- 有序正式迁移验证全新库和已有库，搜索键遵循 searchtext；不依赖生产执行 sync-dev。
- 不自动重置数据库、不新增历史兼容分支、不改已有费用。
- 回退代码不得删除已引用单位；问题单位可经既有管理入口显式停用。

## 已收敛边界

- 实际开发库原来只有七个单位；正式迁移独立于组织补缺，开发 sync-dev 复用完整目录。
- 更正表单复用补录表单，复制新增复用普通表单，统一接入确认组件。
- 超出费用数量四位小数、整数规则或上限时 available=false，展示公式与原因，操作员手工确定。
- 首期依据仅在确认时展示，不新建持久化计算审计模型；如需扩展，重新审阅范围。
