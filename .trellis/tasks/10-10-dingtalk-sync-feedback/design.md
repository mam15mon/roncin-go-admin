# 技术设计

## 边界与数据流

失败 UI 不应通过前端请求全量人员/部门再做 ID 映射；姓名与部门信息在读取钉钉响应时已可取得，应在 owning 层采集并跨层保留。

失败 DO/PO/DTO 分别扩展 user_name、department_name 对应字段：biz 使用 UserName/DepartmentName，JSON PO 用 userName/departmentName，Proto 追加新的字段编号，不变更已有 ID 字段语义。service 显式转换。Ent JSON 类型扩展不改变数据库列类型；生成 Ent/API/OpenAPI/客户端，无需为仅 JSON 对象新增字段制造 DDL 迁移。旧历史记录不改写。

网关创建失败记录时携带已知人员姓名和部门名称；全局失败没有员工时不猜测。biz 身份冲突和 ApplyPerson 失败从当前读取快照携带已知名称与部门信息；多部门处理沿用当前汇总规则，不能借名称变化重绑身份或扩大权限。

## 邮箱空值规则（待最终方案审批）

只从不完整字段校验中移除 email，保留手机/头像规则。缺 email / null / 空字符串均无邮箱，不阻断其他资料。网关/持久化使用一致的邮箱空值口径，缺失或为空时清空旧邮箱，非空则以钉钉值更新；保持当前通讯录权威和只读边界，不加旧邮箱保留兼容。不可将 HTTP/API 整体异常当作无邮箱成功。

## 展示

失败列改为「人员」「部门」「失败原因」，名称主展示，ID 次要展示或提示内查看。人员/部门错误类型可能只知道其中一项，明确「姓名未取得」「部门名称未取得」或无人员语义，避免显示姓名为原始 ID。成功摘要保持紧凑；正常无邮箱不建立新的 warning 面板或缺失计数。

## 待分配列表

拟在列配置调用时按待分配页签明确控制所属组织展示，保留 canReadUserMemberships 权限判定；其他页签行为不变。系统组织来自 Membership 与 Organization，钉钉部门来自来源快照，两者不得混合或自动映射。仅隐藏待分配无业务数据的列，不改变返回权限或数据库成员关系。

## 操作与风险

重新同步形成新结果，让最近任务摘要自然替换旧失败，不删除历史错误。只读抽查当前钉钉邮箱缺失情况，更新后运行真实开发同步核对姓名、部门、手机号继续更新以及失败计数。

主要风险为误吞真实接口异常、清空旧邮箱与手机/头像规则被顺便放宽，实施后针对验证。权限/组织/租约写入逻辑保持，不新增锁/version或事务抽象。
