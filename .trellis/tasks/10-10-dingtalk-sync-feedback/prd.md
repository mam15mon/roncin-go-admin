# 优化钉钉同步缺失邮箱处理与失败展示

## 目标

管理员能够直接识别同步失败的员工和部门；员工缺少邮箱作为正常资料空值，不产生醒目的失败提示，也不阻断其他资料同步。

## 背景与证据

用户同意为失败记录展示姓名和部门创建 Trellis 任务，并补充要求「这种邮箱缺失，只是缺失，不应该这样明显的显示出来」。

- `web/src/pages/admin/components/users/DingTalkDirectorySyncPanel.tsx:278` 的失败列表只展示人员 ID / 部门 ID。
- `server/internal/data/dingtalk_directory_gateway.go:146` / `:182` 已获得人员姓名，但在可选字段不完整错误中只记录 ID。
- `server/internal/data/dingtalk_directory_gateway.go:214` 的校验函数将已授权 email 的缺键/null 作为整条失败；`server/internal/biz/dingtalk_directory.go:121` 将这些记录加入失败摘要。
- `server/internal/biz/dingtalk_directory.go:29`、`server/internal/data/ent/schema/dingtalk_directory_sync.go:37` 和 `server/api/admin/v1/admin.proto:620` 的失败结构均没有名称。
- `server/internal/data/dingtalk_directory.go:111` / `:135` 已按同步来源维护邮箱，无授权及 nil 清空，非空字符串写入；钉钉基础资料由通讯录维护，本地界面只读。

## 需求

1. 失败列表以员工姓名和部门名称为主要信息，钉钉 ID 为次要信息保留。接口失败确实无法取得名称时明确标注未取得，不编造名称或自动合并身份。
2. 邮箱是可选资料。已授权邮箱的缺键、null、空字符串均按无邮箱处理，不产生人员失败/警告、不增加失败统计、不阻断姓名、部门、手机号和头像的正常同步。
3. 邮箱非空继续同步并完整展示；无邮箱页面按既有列表空值显示。缺失邮箱同步后清空该钉钉人员旧邮箱，保持来源权威，不保留可能过期的地址；此数据处理规则在最终方案中明确待用户批准。
4. 身份缺失/冲突、实际接口失败、手机和头像既有不完整规则保持；真实失败仍可定位、查看原因及重试。
5. 名称由失败发生时的接口资料和已知部门信息保留在本次结果中，覆盖部门读取、人员读取、字段错误、身份冲突及写入失败路径中已知信息；不额外全量读取用户或循环翻页拼接数据。
6. 待分配页签拟隐藏「所属组织」列，保留「钉钉部门」；已开通和离职/停用页签保留所属组织及原有权限判断。用户询问该列来源，本方案待最终审批，不自动把钉钉部门映射为系统组织。证据：`userColumns.tsx:105` 只按 canReadUserMemberships 建列，未区分页签；当前开发库 27 待分配人员，0 人有启用组织关系。
7. 重新同步验证新结果，旧任务记录不追溯修改，也不为旧记录追加数据库查名兼容分支。

## 验收标准

- AC1：已知姓名/部门的失败记录展示名称，ID 次要呈现；名称无法取得时标注未取得。
- AC2：部门人员列表和独立人员详情中的 email 缺键/null/空字符串均可正常处理，只有邮箱缺失时失败计数为零、无整块失败提示。
- AC3：邮箱缺失人员的其他资料同步更新；已有邮箱按批准的来源空值规则处理，不改变用户身份、组织权限和开通状态。
- AC4：身份冲突、接口错误以及手机/头像既有失败仍保留名称和明确原因，不被邮箱规则掩盖。
- AC5：待分配页签无所属组织列、钉钉部门仍显示；其他页签保留当前组织展示与权限限制。
- AC6：源文件及生成物同步，定向前后端测试、真实隔离 PostgreSQL、全栈门禁及实际页面/API同步验收通过，提交并记录结果。

## 范围外

不调整手机号脱敏、不改邮箱权限或申请流程、不扩展到手机号/头像缺失策略、不新增告警中心/历史兼容、不删除或重建用户数据、不合并或推送分支、不改变钉钉开通规则。
