# 设计：提成账单固定加锁顺序

## 变更边界

最小行为差距是账单多行锁没有确定顺序。行为所在位置是 data 层
`loadCommissionCalculationSource` 的 `FinanceBill` 查询；预计只修改该查询和
`finance_commission` 相关测试。不会修改 biz、service、API、Schema 或前端。

## 查询契约

锁定路径保持原有谓词与 `WithLines()`，仅增加 `Order(bill.ByID())`：

```go
bq := store.bills.Query().
    Where(...).
    WithLines().
    Order(bill.ByID())
if lock {
    bq.ForUpdate()
}
```

显式排序对锁定和非锁定路径都生效，使返回账单顺序稳定；业务后续按 ID 映射金额，
不依赖原有无序结果，因此不改变计算语义。`ORDER BY` 由 Ent 生成在
`FOR UPDATE` 前，PostgreSQL 按主键升序访问候选行。

## 验证设计

### SQL 形态测试

在 data 层调用现有生产计算加载路径，使用 sqlmock 对账单查询设置严格正则，要求
出现：

```text
ORDER BY "finance_bills"."id" FOR UPDATE
```

测试夹具只补足执行到该查询所需的前置结果；在账单查询返回后可主动返回错误终止，
避免为本断言模拟无关的后续订单与费用查询。

### PostgreSQL 并发测试

集成测试使用临时组织和两张账单，开启两个独立共享事务，并让两边以相反的账单 ID
顺序进入同一生产账单查询构造路径。同步栅栏让事务尽量同时开始；每个上下文设置
有限超时。验收关注：两事务都成功取得并释放锁、都能提交、没有 SQLSTATE `40P01`
或超时。

为保证测试与生产不漂移，若完整计算夹具过重，可以抽取仅负责构造现有账单查询的
私有函数，由生产路径和集成测试共同调用；该函数不得新增业务分支或改变仓储接口。
只有在无法直接驱动现有生产路径时才允许该局部抽取。

## 并发与回滚

- 不增加重试：固定锁顺序是根因修复。
- 集成测试创建的数据使用唯一 UUID，并在测试清理函数中删除或由现有临时数据库
  清理机制回收。
- 修改只有查询排序，回滚时删除 `Order(bill.ByID())` 及对应测试即可，不涉及数据
  迁移或兼容处理。
