# 重构海运出口运输与主分单领域模型

## Goal

把海运出口从“订单上平铺主单号、分单号、航次、箱货和费用”的模型，重构为可明确区分业务流、运输执行、单证流和财务流的领域模型，使系统能一致处理 DIRECT、一个操作票多 HBL、一张 MBL 汇聚多操作票、整体甩柜改配、部分拆票、Switch B/L、箱货分配、承运人成本分摊及锁定后的改单，同时不篡改已确认的单证、申报和财务历史。

## Background

### 已确认的仓库事实

- 当前 `Order` 同时承载客户、操作人员、船名航次、港口、ETD/ETA、截关时间、订单级件重尺、箱量计划、实际集装箱、货物、费用、账单行、核销来源与提成来源，是现有业务和财务的核心聚合。
- 当前 `OrderConsolidation` 仅保存组织、业务类型、规范化主单号、主单单证类型和主单签放方式；它通过“组织 + 业务类型 + 规范化主单号”自动归组，尚不是完整的运输执行或承运人单证模型。
- 当前 `OrderShippingDocument` 实际承载 HBL，但契约和数据库强制每条记录同时存在 MBL 与 HBL，无法表达 DIRECT。
- 当前一个 `Order` 可以保存多组不同 MBL，也可以在同一 MBL 下保存多张 HBL；这与“一个操作票同一时点最多一个当前有效承运人单证”的拟定规约冲突。
- 当前集装箱只有一个可选 `shipping_document_id`，无法表达一箱多 HBL；货物行直接归属订单，尚无货物到 HBL、集装箱的定量分配关系。
- 当前费用只绑定订单；系统无法原生表达 MBL、运输航段、集装箱或 HBL 级费用及其向多个操作票的分摊。
- 当前共享主单属性会被其他操作票普通保存直接覆盖，没有独立版本、改单流程、跨票锁定或并发版本控制。
- 当前不存在操作票拆分谱系、拆分单、整体改配记录、Switch B/L 替代链和承运人单证不可变版本。
- 项目尚无历史业务数据，因此无需兼容既有业务记录；仍需提供可审阅、可回滚的正式 Schema 迁移，禁止静默生成虚拟 HBL 或隐式修正业务数据。

### 领域事实

- FCL/LCL/BREAK_BULK 描述装载形态；DIRECT/HOUSE 描述单证结构；二者不是同一个维度。
- 同一客户委托可以因部分分批而拆成多个独立运输执行单元；整票甩柜是同一执行单元从旧运输安排整体改配到新运输安排，不等同于拆票。
- 一个操作票可以签发零到多张真实 HBL；DIRECT 为零张，HOUSE 为至少一张。一个操作票多 HBL 不应被强制拆票。
- 同一 MBL 可以汇聚多个操作票和多张 HBL；同一集装箱也可能分配给多张 HBL。
- MBL/承运人单证是单证事实，不等同于订舱、主航程或多航段运输执行。
- 已确认或已签发单证、已提交 SI/VGM/舱单以及已确认/已核销财务记录必须引用当时的不可变版本，不能随当前字段变化而被改写。

## Requirements

### R1. 业务聚合与术语边界

- “委托单位”仅指发起业务的客户/合作伙伴主体，即当前订单的客户关系；不得与业务单据概念混用。
- “客户业务指令”指委托单位发来的一次运输需求；“操作票/执行票”指公司内部据此建立并实际执行的工作票。是否需要把客户业务指令独立持久化，取决于一份业务指令能否在建单时或后续稳定地产生多张操作票。
- 明确定义“操作票/执行票”“运输执行”“承运人运输单证”“HBL”“集装箱”“货物行”“费用”的职责与基数。
- 一个操作票在同一时点最多关联一个当前有效承运人运输单证，但可以保留多个历史关联。
- 一个承运人运输单证可以关联一个或多个操作票。
- 不把承运人运输单证等同于运输执行；运输执行必须能够表达订舱、主航程及多航段。
- 在没有独立管理客户业务指令、原始总量或拆分前业务事实的需求时，禁止仅为理论完整性新增“客户业务指令”聚合；当前 `Order` 继续收敛为操作票，并通过明确的拆分事件及来源谱系处理分批。

### R2. 单证结构与 HBL 基数

- 单证结构至少区分 `DIRECT` 与 `HOUSE`：
  - `DIRECT`：操作票关联承运人运输单证，不存在 HBL；禁止生成虚拟、隐藏或占位 HBL。
  - `HOUSE`：操作票必须存在至少一张真实 HBL；一个操作票允许存在多张 HBL。
- `CONSOLIDATED` 不作为与 DIRECT/HOUSE 并列的互斥单证结构；如需区分自拼、FCL part-load、买方集拼等，使用独立拼载类型或从成员关系派生。
- 每张 HBL 只归属一个操作票；确认/签发前可以尚未确定承运人单证，确认/签发后必须且只能归属一个承运人单证。
- 同一操作票的所有当前有效 HBL 必须归属该操作票当前有效的同一承运人单证。
- DIRECT 与 HOUSE 只允许在未对外确认阶段直接转换；外部提交或签发后必须走撤回、作废、更正或改单流程。

### R3. 货物、箱号与单证分配

- 货物事实独立归属操作票，不依赖 HBL 是否存在。
- DIRECT 草稿从操作票货物生成承运人单证内容；HOUSE 通过显式分配把操作票货物映射到一到多张 HBL。
- 支持一张 HBL 对应多个集装箱、一个集装箱对应多张 HBL、一个货物行分配到多个 HBL/集装箱。
- 分配必须保存件数、重量、体积等定量数据，并验证订单货物、HBL 和集装箱维度的总量守恒。
- 已确认单证从分配结果生成不可变快照，不实时镜像后续订单编辑。

### R4. 运输执行与承运人单证

- 建立独立运输执行边界，承载承运人、订舱标识、主航程、航段、港口、船名航次、ETD/ETA 与集装箱。
- 承运人运输单证关联运输执行，但二者不强制一一对应；需支持一个运输执行多张 B/L，以及业务确需时多个运输安排合并为一张 B/L。
- 多个操作票加入同一承运人单证前，必须验证承运/签发主体与主航程一致性；号码只用于候选检索，禁止仅凭号码静默归并。
- 一致性冲突时阻断普通关联并进入明确的纠错、重复记录合并、甩柜改配或改单流程；禁止提供无审计的“强制合并”兜底。

### R5. 拆票与整体改配

- 部分货物去往不同承运人单证或不同运输执行时执行正式拆票；整票甩柜到新航次执行整体改配，不创建虚假操作票。
- 拆票必须具有独立拆分单/拆分事件和父子谱系；原始业务事实永久保留，拆分后的可执行票据、原票状态及是否继续参与执行必须在设计中明确。
- 拆票以显式白名单继承客户、人员、参考号和允许共享的附件；货物、箱量、箱号、单证、航次、申报和费用必须分配或重新确认，禁止无条件复制。
- 拆票必须验证件数、重量、体积、箱货与可分配费用守恒，禁止重复复制已账单化、已核销费用或已生成提成。
- 整体改配保留同一操作票，终止旧的当前运输/单证关联并建立新关联，保存旧航次、旧单证、原因、责任方及全部受影响记录。
- 部分留在旧 MBL、部分转入新 MBL 时，先拆票，再对相应子票改配。

### R6. 单证身份、版本、替代与 Switch B/L

- 单证身份与不可变内容版本分离；主记录保存当前有效版本指针，历史版本采用追加式快照。
- SI、VGM、舱单、打印/签发记录、账单依据必须引用实际使用的具体版本 ID。
- 普通草稿允许原地编辑；内部确认后修改必须创建变更申请，审批通过发布新版本；原版本永久保留。
- Switch B/L 不创建虚假操作票；第一套单证交回/作废/被替代后，在同一操作票下签发新单证，并记录新旧替代关系、交回信息、审批、费用和舱单影响。
- 同一替代链在同一时点只能存在一张当前有效单证。

### R7. 正交状态与字段级锁定

- 单证、SI、VGM、舱单、运输和财务采用正交状态，不实现为一条假定严格线性的总状态机。
- 后端维护“字段组 × 状态”的允许动作策略；前端消费后端返回的允许动作，不能只依赖按钮禁用。
- 外部提交、确认、签发、装船、账单确认、开票或核销后的关键字段禁止普通更新；更正通过撤回、改单、新版本、红冲或调整单完成。
- 已发生的外部事实不得通过管理员简单解锁或状态回退伪装为“从未发生”。
- 明确哪些节点自动产生、哪些人工确认、哪些可跳过以及撤回/作废对锁定策略的影响。

### R8. 主体与号码唯一性

- 承运主体和签发主体使用法律/对外签发层级的主数据 ID，不使用显示名称或内部部门名称作为身份。
- HBL 唯一范围采用“签发主体 + 号码规则作用域 + 规范化 HBL 号”；承运人单证采用相应的承运/签发主体和号码作用域。
- 通用号码规范化只允许去首尾空白、统一 Unicode 与英文字母大小写；保留内部空格、标点、年份和前导零。任何额外归一化必须来自对应签发主体的显式编号规则。
- 数据库唯一约束、领域校验和所有写入入口必须消费同一规范化结果。

### R9. 费用追溯与分摊

- 费用必须声明计费对象：订单、运输执行/航段、承运人单证、HBL 或集装箱。
- 共享承运人成本通过显式分摊记录落到操作票/HBL；支持按箱数、件数、重量、体积、计费吨、固定比例或人工金额分摊，并记录方法和版本。
- 分摊金额合计必须等于原费用金额；重分摊保留调整历史，不覆盖已确认、已开票或已核销记录。
- 拆票、改配、改单或箱货重分配必须显式计算对费用、账单、发票、核销和提成的影响。

### R10. 审计、并发与数据完整性

- 关联、移除、拆分、改配、锁定、撤回、改单、Switch、箱货分配、费用分摊和作废均写业务审计。
- 操作票、运输执行、承运人单证、HBL、拆分单和变更申请使用版本号及预期版本校验；关键写入在统一事务内采用固定锁顺序。
- 能用数据库表达的不变量必须有外键、唯一索引或检查约束兜底；不能仅靠 UI。
- 删除采用作废/终止关系并保留历史；是否释放当前唯一关系由显式状态与部分唯一约束决定。
- 所有跨聚合命令必须原子提交，错误原样外传并完整回滚。

### R11. 分阶段交付

- 本任务作为父任务维护完整目标、领域词汇、跨阶段验收和迁移顺序；实现拆成可独立验收的子任务。
- 首阶段必须先建立不会阻碍后续扩展的核心实体和约束，再迁移现有主分单 UI；不得先在旧模型上继续叠加临时分支。
- Switch B/L、外部舱单通道、复杂费用自动分摊等高级流程可分阶段上线，但核心模型不得依赖虚拟 HBL、隐式复制或号码静默归组。

## Acceptance Criteria

- [ ] AC1：规划文档给出可审阅的领域关系图，明确每条关系的基数、所有权、当前关系与历史关系。
- [ ] AC2：规划文档分别定义操作票、运输执行、承运人单证、HBL、货物、集装箱、费用、主体、拆分单和变更申请的职责。
- [ ] AC3：规划文档给出 DIRECT、一个操作票多 HBL、一张 MBL 多操作票、一箱多 HBL 的完整数据流，且不生成虚拟 HBL。
- [ ] AC4：规划文档给出部分拆票、整体甩柜改配和 Switch B/L 三条互不混用的流程，明确产物、状态、守恒、版本、审计和失败回滚。
- [ ] AC5：规划文档给出正交状态、字段锁定和改单发布规则；已确认历史引用具体不可变版本。
- [ ] AC6：规划文档给出主体作用域、号码规范化与候选关联规则；冲突不得静默合并。
- [ ] AC7：规划文档给出订单、MBL/运输、箱号和 HBL 级费用的计费对象与分摊守恒规则。
- [ ] AC8：形成按依赖顺序排列的子任务地图，每个子任务都有独立可验证结果、迁移/回滚边界与测试门禁。
- [ ] AC9：首个实现子任务完成后，系统阻止同一操作票同时关联多个当前有效承运人单证，并保持现有订单—财务链路可用。
- [ ] AC10：最终集成验收覆盖 DIRECT、HOUSE 多 HBL、多票共 MBL、拆票、整体改配、Switch、箱货分配、费用分摊、并发冲突和历史版本重现。

## Out of Scope

- 本轮规划不直接实现任何产品代码、Schema 或迁移。
- 不把承运人网站的所有国家/航线特例做成首期范围；特殊规则后续通过明确主体/航线配置扩展。
- 不在没有正式接口契约时伪造船公司、海关、港区或国外代理的外部回执。
- 不为了兼容旧模型生成虚拟 HBL、占位号码、隐藏复制单或静默数据回退。
- 不承诺首个子任务一次上线全部打印模板、全部舱单国家规则和全部自动成本分摊策略。

## Open Question

- 实际业务中，委托单位发来一份运输需求时，是否可能在首次建单时就明确拆成两张或更多独立操作票，并要求系统持续保留这份原始需求的总件重尺、附件和对子票的汇总关系？如果没有该业务需求，则不新增“客户业务指令”实体，当前 `Order` 直接作为操作票。
