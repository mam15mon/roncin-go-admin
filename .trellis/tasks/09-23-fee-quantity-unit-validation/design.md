# 技术设计

## 数据与契约

- Ent BillingUnit 增加 quantity_must_be_integer 布尔字段，非空、默认 false。biz 对象、仓储读写、审计配置变更同步传递。
- fee_catalog.proto 的 BillingUnit、CreateBillingUnitRequest、UpdateBillingUnitRequest 增加属性；订单费用候选单位契约同步提供。按照 proto → Go/OpenAPI → 前端客户端流程生成。
- 前端管理列表与表单显示“数量规则：整数 / 允许小数”，API 字段 quantityMustBeInteger。保留已有权限及公共主数据组织边界。

## 迁移与初始化

- 新增正式 SQL 迁移，不修改已应用迁移。字段默认 false，然后将系统已知离散单位置 true。
- 明确整数代码：PIAO、BL、CONT、SET、DOC、CHE，以及正式种子箱型 12GP、20GP、20HC、20OT、20FR、20RF、20TK、20HT、20RH、40GP、40HC、40HQ、40FR、40PF、40RF、40OT、40RH、45HC。
- CBM、KG、TON、RT、HOUR、DAY 保持 false。其他已有代码包括 BILL、SHIP、SHIPMENT、BOARDS、PLYWOOD_PALLETS 缺乏已确认的数量语义，本期按未知单位保持 false，由管理员配置；不按名称批量猜测。
- 不按所有 is_container_unit=true 无差别回填自定义单位，仅初始化上述已知种子。以后管理员新建箱型通过 UI 默认值获得整数设置。
- 另一项费用种子任务当前有未提交的 20260923100000_fee_catalog_seed.sql，新增本任务迁移必须排在最终费用种子迁移之后，保证新插入的 CONT/BL/SET/DOC 得到初始化。实施前重查排序，禁止改写其他任务文件。
- sync:dev 仅在新建已知单位时设置初值；已存在单位保留管理员设置。全新库、现有库均走正式有序迁移验证。

## 校验边界

- 领域层提供基于单位布尔属性和 decimal 数值的最小校验函数，保持已有通用数量格式/精度限制；错误文案为“该计费单位的数量必须为正整数”。
- 新增及补录创建：解析数据库单位设置后执行校验，校验失败不写入费用或补录申请。复制新增同样按新建执行。
- 已有费用更新：比较 authoritative current.Quantity 与 requested.Quantity 的 decimal 数值，以及 BillingUnitID。二者都未变时不追加整数限制；变化时读取当前单位规则并校验。普通和已建账更新一致，仍保留原状态及字段限制。
- 已建账编辑需要读取既有单位属性，不通过要求费用目录启用的完整目录重解析改变原行为。单位停用不应阻止已有费用的合法维护。
- 后端信任数据库配置，不接受请求自报规则；前端候选缓存仅提供即时提示，提交以服务端当前配置兜底。
- 复用既有事务边界和 Data.client(ctx)。最终数量变更判定须与现有版本检查对应同一费用版本；实现审阅时核对单位配置读取与写入的一致性，不新建配置版本体系。
- 补录申请创建校验后快照不可变，审批沿用原快照，不重新套用单位最新规则。

## 前端交互

- 管理新建表单普通单位默认 false；箱型标记首次开启且规则未被用户主动选择时带入 true。使用表单自身 touched 状态或局部最小交互标记，编辑模式及已主动选择的值不覆盖。
- 订单费用模块就近共享校验辅助，接入 FeeFormModal、OrderFeeTableTabs、FeeSupplementModal，以及实际排查发现的其他可写费用入口。
- 编辑时保留原始数量/单位基线；当前组合未变的旧小数不显示新增整数错误。变更数量或单位时重新判定，改回原组合恢复基线语义。
- 切换费用项目导致默认单位变化时也触发数量重新校验。批量保存、复制新增不能绕过同一规则。
- 设置保存后刷新单位管理列表并失效相关费用候选缓存；重新打开/聚焦页面时读取更新，已打开旧表单的提交由服务端校验反馈。

## 风险与回滚

- 一次性初始代码表只服务迁移与种子，业务运行期不查代码表。管理员之后可自由修改配置。
- 本次新增字段、生成物和前后端必须整体交付；迁移保持增量，回滚应用代码时保留新增列及配置数据，不自动删列或重置数据库。
- 规则改变不追溯重写费用，但新建与数量变更必须通过新规则；这是统一更新语义，不按创建时间或版本增加历史兼容路径。
