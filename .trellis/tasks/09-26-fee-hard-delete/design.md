# 技术设计：费用账单关联作为唯一事实源

## 1. 事实查询与分层

data 层提取有效账单行查询条件：`active = true AND bill.status <> CANCELLED`。费用谓词、台账财务进度、候选和批量查询复用同一口径。保留账单行现有活动费用唯一索引，不放宽唯一性。

biz 使用纯 Go 的只读关联事实 `HasActiveBill bool`，不接收 Ent 类型，不自行访问数据库。费用读取由 data 批量投影该事实，service 只转换响应；禁止 service 查询 Ent，禁止逐费用 N+1 查询，禁止把未加载关联默认为未建账。覆盖 List/Get/GetByIdempotencyKey、编辑返回、建账返回及其它返回费用的路径。

API 的 OrderFee 暴露计算字段 `has_active_bill` 供订单费用编辑/删除判断；这不是持久化列，不接受请求写入。台账与建账工作台优先消费既有 bill_id/账单信息和 financial_progress，不能用显示用 billNo 文本是否为空代替可靠关联事实。前端不再维护 OrderFeeStatus 或同义两态枚举。

写入守卫仍在事务中锁定后重新查询事实。biz 的提前校验只用于尽早报错，不替代 data 的最终复核。沿用各写路径已确定的锁序（含已建账编辑的账单→账单行→费用）与共享事务封装；新增锁序若无法沿用现有契约，先报告冲突，不临时拼装另一套锁序。

## 2. 费用与账单写入

- 创建和补录批准移除 SetStatus。
- 单张/批量建账、取消账单移除状态回写，保留费用版本递增、受影响行数校验和事务内关联复核。
- 不能机械地把原 UPDATE 的 `StatusEQ(UNBILLED)` 替换成 NOT EXISTS：现有建账在更新费用版本前已经插入账单行，该时点新账单本身会使 NOT EXISTS 为假。关联资格在插入前锁内复核，随后版本更新使用已锁定目标及版本条件；取消同理按停用账单行的实际顺序设计。
- 保留预览过期、旧版本 409、已建账编辑设置、允许字段范围、单行换币与汇率快照规则。
- 正常取消必须同时停用账单行；不为 active=true 且账单 CANCELLED 的异常数据添加兼容修复。

## 3. 删除边界

普通 Remove/BulkRemove 沿用现有硬删除实现。事务内新增/明确 supplement_request_id 准入：存在补录来源即拒绝普通删除，错误提示从补录申请撤销；批量先整体验证，再删除并逐条审计，任何失败回滚全部。

专用撤销继续走已有授权和锁序，完整复核批准时间+申请 ID 的倒序约束、费用版本以及调整曾确认/支付记录。允许时取消 DRAFT 调整，DELETE 费用，写完整快照审计，原子提交；不删除申请和历史调整。费用标签使用现有级联，历史账单行使用既有 SET NULL；不存在独立「补录-费用链接表」，由费用上的 supplement_request_id 表达关联。

自动锁定重评发生在成功提交后。普通删除无需再用旧状态判断是否触发；补录撤销保留其现有用例联动。

## 4. 契约清理与补录响应

修改源文件 `server/api/order/v1/order_fee.proto`、`server/api/finance/v1/settlement.proto`：

| 契约 | 处理 |
| --- | --- |
| OrderFeeStatus | 删除整个枚举 |
| OrderFee.status | 删除，新增只读 has_active_bill |
| ListFeeLedgerRequest.status / FeeLedgerItem.status | 删除，使用财务进度及账单关联 |
| CommissionFeeDetail.status | 删除，提成费用快照与指纹同步去掉费用状态来源 |
| OrderFeeSupplementRequestData.fee_status | 删除；保留 fee_id，APPROVED 且生成费用不存在时展示「生成费用已删除」，can_cancel=false 并给出原因 |
| CancelApprovedOrderFeeSupplementResponse.fee | 删除；返回刷新后的申请 data，不重新查询已删除费用 |

删除的 Proto 字段号与名称 reserved，不复用；新增字段使用新编号。保留撤销 RPC 名称与路由，因为操作仍是撤销补录生成结果，前端按钮文案为「撤销补录费用」。领域撤销结果保留已删除费用 ID 与被取消调整 ID 等内部联动所需信息，不再要求现存 Fee 对象。

申请 APPROVED 且 fee_id 缺失的结果口径依赖「审批与生成费用同一事务、普通删除禁止补录来源」的不变量。重复撤销沿用明确的撤销受阻错误并提示费用已删除，无幂等成功回放层。列表/详情及前端测试覆盖该结果。

提成快照是历史快照，不回写历史已冻结账单/提成金额；新快照去掉 status，消费者同步删除该字段依赖，不增加双读兼容。检查既有来源指纹判重，避免算法变更让已计提来源重复计提。

## 5. 迁移与数据保全

Ent 删除 status、cancelled_at、cancelled_by、cancellation_reason、cancelled_by_user 及 User 反向边、费用状态 CHECK；索引按实际查询改为不含 status 的形式。生成 Ent 后检查正式 SQL 与生成元数据一致。迁移方法遵循 `server/migrations/README.md`，不改已发布历史迁移，不使用运行期自动建表。

迁移必须在丢弃旧字段前处理 CANCELLED 行：

1. 锁定/校验目标集及历史引用；有有效账单、未取消关联调整或曾确认/支付的冲减事实等异常时抛错，中止整个迁移。不得通过级联删除金融历史解决约束冲突。
2. 保留已有撤销审计；对将丢失的费用关键内容及旧撤销元数据写迁移归档审计，使用明确迁移来源，不伪造操作人。实施前核对 AuditLog 必填字段和原审计 action，快照含费用 ID、申请 ID、金额、币种、科目、结算单位及旧撤销信息。
3. 删除已作废费用，标签按实际 FK 清理，历史账单来源 SET NULL；补录申请、调整和历史金额快照保留。
4. 删除字段/CHECK/相关索引，建立需要的替代索引；整个过程原子执行。

以上在专用测试库通过夹具验证；应用现有开发库前只读输出数量、ID 与关联影响供授权，不输出秘密连接串，不自动清库。若无删除授权，不执行该库迁移，不把已作废行静默转为有效行。该操作闸口不阻止代码、迁移文件及隔离测试交付。

数据删除无法通过代码 revert 恢复。应用前按环境保留可恢复备份；回退必须恢复数据与匹配代码/Schema，不能承诺写回 status 列即可还原。

## 6. 消费方与性能

逐项执行研究清单，尤其保持结案与拆票门禁相反的判断方向。订单费用主表、面板、建账工作台与台账全部删除费用状态展示；补录显示生成结果，提成明细不再展示费用状态。FinanceSummaryBoard 删除排除 CANCELLED 的过滤，不新增同义过滤。

工作台统计、自动锁定、候选与台账查询使用 EXISTS/NOT EXISTS；在代表性夹具上比较 EXPLAIN，优先复用账单行 `(order_fee_id, active)` 及活动唯一索引，有明确劣化证据才增加索引，不为移除字段预建通用查询框架。

## 7. 验证与交付边界

以 PRD A1—A8 为验收矩阵。费用删除/补录撤销/账单竞争使用真实 PostgreSQL；测试先由实现驱动，再按风险补充，禁止 TDD。完整事务、版本、门禁与迁移验证不能用枚举映射单测代替。

契约、业务调用方与必要生成物作为可编译、可验证的一组提交，不按后端/契约/前端拆成相互断裂提交。规划提交独立；业务实施等待本版方案确认。
