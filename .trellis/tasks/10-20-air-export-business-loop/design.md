# 空运出口技术设计草案

状态：planning。Q1—Q3 以 prd.md 为唯一决策清单。本文列出建议实现和条件分支，不代表范围已批准。

## 1. 变更边界与数据流

差距主要在 AE 准入、空运专属字段、流程分支和前端注册。公共订单、权限、财务继续是唯一入口；空运和海运单证各自表达领域含义。

建议数据流：空运表单 → 生成客户端 → service 转换 → biz 按类型校验 → 公共订单事务和空运扩展 → 同事务版本及审计 → 重读详情。费用沿用现有用例，计费重作为明确的数量来源。

## 2. 订单和运输数据

- 公共 Order 保留公司、客户、业务类型、人员、货量摘要、编号、状态及版本。
- 建议一对一空运扩展保存航司、航班等专属内容，命名在契约设计时确定；不用 shipping_line_id 保存航司，不用 vessel_voyage 保存航班。
- 机场复用已有 AE/AI 地点校验与主数据，先核对现有字段语义，避免重复存储。
- SE/AE 分别做领域校验，未知业务继续拒绝；草稿允许暂缺操作资料，节点完成时校验已确定的必需字段。
- 时间契约携带明确时区，持久化为明确时刻，展示复用 formatDate；不能把本地字符串直接视为 UTC。
- 公共订单和空运扩展同事务；一对一扩展建议由订单版本统一管理。

## 3. 航空运单：Q1 两种方案

| 方案 | 关系和行为 | 取舍 |
| --- | --- | --- |
| A 单票登记（建议起步） | 订单拥有本票运输及主/分运单信息；相同号码不隐式共享信息 | 实现较薄；不支持跨票统一维护主单；号码重复范围和更正规则须在契约中明确 |
| B 共享主运单 | 独立主单、订单关联、分单、共享运输信息，主单与订单有明确版本边界 | 覆盖集运；需定义多票权限、锁顺序、关联结束、共享航程、货量汇总，以及费用分摊是否纳入 |

选 B 后先补齐 PRD 和验收，再冻结 schema。费用分摊不因存在共享主单自动进入范围。通用 OrderShippingDocument 字段不足以天然表达完整航空运单，需结合最终范围决定复用薄登记或新增实体。

海运 MBL/HBL 表不保存航空运单；空运界面建议明确使用 MAWB/HAWB 文案。海运的版本、审计设计可参考，海运箱和航次关系不直接套用。

## 4. 计费数量与金额边界

- 毛重与确认计费重分开；计费重使用 decimal/numeric，登记确认人、时间、依据和修改审计。
- KG 保持重量单位语义；毛重/确认计费重由明确来源区分，不能改写原 KG 分支。
- 当前预览契约仅有 PLANNED/ACTUAL。实施时选择扩展来源或新增数量依据参数，一次性同步 Proto、后端、OpenAPI、前端和测试。
- 缺确认计费重时返回不可带入及原因；人工录费继续受原审核、锁、数值约束。
- 首期建议人工确认；如 Q2 要自动计算，规则必须明确单位、除数、汇总层级和舍入，展示输入与公式，人工覆盖留痕。
- 修改货量不自动更改旧费用；应收、应付可分别确认费用数量，不能强制使用同一个最终结算重量。

## 5. 流程、时效与生命周期

建议节点：草稿 → 已订舱 → 已配舱 → 拖车已安排（可跳过）→ 已截单 → 报关已安排 → 已签单。这是待确认方案，不是普遍行业流程声明。

biz 按业务类型给出允许动作，仓储锁内复验。现有状态语义足够时不新增枚举；若 Q3 改变语义，同步数据库 CHECK、Proto、前端文案及完成条件。

节点明确必需资料、适用条件、责任人与完成记录，复用里程碑，不恢复退役模板平台。订舱/配舱与费用审核分别管理，不假定配舱自动冻结运价。

签单、业务锁、终止及财务结案独立。AE 结案复用活动异常、未建账费用、待审补录等门禁；关联终止/恢复随 Q1 明确，恢复不得隐式复活历史关联。

超时建议先在列表/详情呈现，复用异常记录；定时外发通知或逾期硬阻断需明确范围后加入。

## 6. 前端与外围入口

| 入口 | 必要调整 |
| --- | --- |
| web/src/pages/orders/order-kinds/ | 新增 air-export definition/adapter，扩展 OrderKind，注册唯一入口 |
| web/src/pages/orders/templates/ | 新空运模板复用 OrderFormTemplate，增加航司选择能力 |
| 公共 list/new/detail/fees 页面 | 空运字段、列、搜索、返回路径；仅解除真正阻碍复用的海运类型依赖 |
| list-resources.ts 与人员 hooks | 正确搜索机场/航司，AE 加载人员，组织切换清理旧请求结果 |
| web/config/routes.ts 与 access | AE 菜单复用已有权限，按钮与服务端授权对应 |
| workbench/notification | 定向补齐 SE 限定与业务链接，不自动开放其他业务类型 |

表格走官方 request/actionRef；表单服务端状态遵循现有 React Query 规范；请求走生成客户端；真实共用才提取抽象。

## 7. 服务端与一致性

重点入口：order_usecase.go、order_transition.go、order_write*.go、order_sync.go、订单 Proto、空运 schema、费用预览和读取投影。

组织校验绑定目标 ID 和允许公司；人员使用现有成员校验。复用幂等键、订单 FOR UPDATE、expected_version 和事务封装。多实体固定锁序由最终 Q1 模型确定。只有新增独立服务才扩展 ProviderSet、HTTP/gRPC 注册与 Wire。

## 8. 迁移和回退

Ent Schema 为源，追加正式迁移，在隔离测试库验证；契约生成物与源文件同步提交。按上线前规范一次性更新内部调用方，不添加历史双读/双写，不清空业务数据。

按阶段提交可验证变更，菜单在闭环具备条件时开放。若已有 AE 数据，不能直接回退到无法识别它的旧代码；暂停 AE 入口并使用兼容当前数据的已验证版本或修复迁移，保留业务记录。

主要回归风险为公共订单/费用契约以及公共页面；SE 与 AE 分别验证。
