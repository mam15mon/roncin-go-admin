# 海运出口拆票与改配

## Goal

让业务员在货物确实分批去往不同 MBL/航次时执行正式部分拆票，在整票甩柜时执行
整体改配；两条流程均保留完整历史、数量守恒、明确门禁，并且不会重复复制财务或
提成事实。

## 当前事实与前置条件

- 依赖任务 `09-02-sea-export-cargo-allocation` 已完成、独立检查、提交并归档。
- `Order` 就是操作票，不新增“客户委托单”。订单号由现有组织级号码规则在事务内
  分配，并由 `(organization_id, order_no)` 唯一索引兜底。
- 每张活动海运出口操作票已有且只能有一个 `ACTIVE` MBL 关系；历史关系使用
  `ENDED`、`ended_at` 和 `ended_reason` 保留，不删除旧关系。
- 本文“改配前当前 MBL”是指业务运行时，操作票在执行拆票或改配之前通过 `ACTIVE`
  关系正在使用的 MBL，不表示开发数据库中预先存在历史数据。当前开发库为空不影响
  此规则；用户未来新建订单录入 MBL 后，才会形成第一条当前关系。
- HOUSE 操作票的货物、HBL、实际箱定量关系已经由 `SeaCargoAllocation` 表达。
  `CONFIRMED` 分配保证逐货物、逐实际箱守恒，并禁止普通修改；拆票应消费这份已
  确认事实，不能重新猜测货物归属。
- HBL 是属于唯一操作票和唯一 MBL 的真实实体；实际箱和货物行也属于唯一操作票。
  因此拆票必须连同选定的 HBL、货物数量和整只实际箱一起迁移或重建归属，不能只
  修改 MBL 外键留下跨票引用。
- 订单费用已有 `DRAFT / CONFIRMED / BILLED / CANCELLED` 状态，账单行、核销分配和
  提成行均保存不可变来源引用或快照，可用于阻断不安全拆票。
- 当前仓库还没有 SI、VGM、舱单“已对外提交”的独立事实表或提交命令。阶段 4 不以
  订单总流程状态冒充这些正交状态，也不接受前端自行声明“未提交”；阶段 5 建立
  正交外部状态时，必须在开放任何提交动作前把这些事实补入同一个拆票/改配预检。

## 业务规则

### 部分拆票

- 部分货物去往不同承运人单证或不同运输执行时，执行正式拆票。一次拆票允许形成
  “原票 + N 张新操作票”：页面默认一张新票，并允许继续添加结果票；所有结果在
  同一次提交中完成守恒校验。原操作票保留原号和非零剩余，只为拆出的结果生成新
  操作票和新订单号；不允许把原票拆成零剩余，整票移动必须走整体改配。
- 拆票必须从一份 `CONFIRMED` 箱货分配开始。用户选择要拆出的 HBL/货物/实际箱后，
  系统在提交前实时显示原票和每张结果票的件数、毛重、体积、箱量及剩余；错误必须
  指出具体 HBL、货物或箱以及基准、已分配和差额。
- 拆票页面允许为每张新结果票直接选择目标 MBL，也允许暂时沿用改配前当前 MBL。
  服务端先记录拆分事件，再为选择不同目标 MBL 的结果票分别记录改配事件；两类事件
  在同一个事务中完成，任何一步失败都全部回滚。页面的一次操作不得把两个事件类型
  合并成无法区分的历史记录。
- HBL 和真实集装箱均为不可跨结果票的完整业务单位：一张 HBL 不得同时留在原票和
  新票，同一实际箱也不得跨两个结果票。若一张 HBL 或一只实际箱的现有分配同时覆盖
  “保留”和“拆出”货物，页面必须立即指出具体 HBL 号或箱号并阻止提交；业务员需先
  撤回箱货确认，重新分配或按实际业务新增 HBL 后再拆票。拆票命令不得静默切割真实
  单证或实体箱，也不得只在前端提示而由服务端放行。
- 拆分事件是不可变事实，至少保存组织、来源操作票、操作人、原因、拆分前快照、
  各结果票、分配明细、守恒结果和发生时间。原票与所有新票都能由事件反查谱系，
  但新票仍是普通 `Order`，不创造会污染列表和权限的特殊“子操作票”类型。
- 原票和新票的货物行应按结果数量形成各自独立事实；原货物行不能被多个操作票共用。
  HBL、实际箱和当前 MBL 关系同样只归属于最终结果票。旧 ID 与新 ID 的对应关系保存
  在拆分事件明细中，不依赖审计文本还原。
- 拆票提交本身承担所有结果票的箱货守恒确认。成功后，原票和每张新票的箱货分配均
  保持 `CONFIRMED`，各自建立新的聚合版本并记录来源拆分事件，不要求业务员逐票重复
  点击确认。任一结果票不完整或不守恒时，整次拆票失败且不得留下草稿结果；成功后如
  需修改货物、HBL、实际箱或分配，仍必须在对应操作票上显式撤回确认。
- 拆票继承采用显式白名单：组织、业务类型、委托单位、贸易方向、贸易条款、付款条款、
  装载类型、箱主类型、运输模式、服务类型、货物类别、订舱/承运/海外/船务代理、
  销售/操作/客服/单证/商务/关联人员、允许继承的参考号和备注。新票必须分配新订单号，
  创建人记录本次拆票操作人；主单关系、HBL、货物、实际箱、箱型计划、里程碑、异常、
  放货签收、费用、账单、核销、提成和历史审计不得无条件复制。
- 附件不能复制对象存储记录：当前 `object_key` 全局唯一。首版拆票只在事件快照中记录
  来源附件摘要，不自动挂到新票；附件共享/复制由后续独立需求定义。
- 草稿费用可以显式留在原票、整行移动到新票，或按相同币种和金额精度拆成多行；每条
  来源费用的结果金额必须严格守恒，且保留汇率、汇率日期、税率和来源对应关系。禁止
  自动按件重尺比例分摊，禁止复制幂等键。

### 整体改配

- 海关查验、船司爆舱或航次变化导致整票甩柜时，使用整体改配；保留同一操作票、订单号、
  HBL、货物、实际箱、费用和人员，不创建新操作票，也不要求业务员重新录入。
- 改配必须选择或创建一个通过既有 MBL 候选校验的目标 MBL，填写原因和责任方。事务内
  终止改配前当前 `ACTIVE` 关系并建立新的 `ACTIVE` 关系，同时保存改配前/目标 MBL、
  运输执行、版本、箱货分配和受影响记录快照。
- HOUSE 的 HBL 和已确认箱货分配随整票改配到新关系，但旧关系下的分配历史必须可重现；
  DIRECT 保持无 HBL，不得生成虚拟分单。
- “部分留在改配前当前 MBL、部分去目标 MBL”不是整票改配：必须先形成正式拆票事实，
  再为对应结果票形成改配事实；页面可以一次提交，但服务端必须按这个顺序原子执行。

### 门禁、事务与并发

- 普通拆票/改配要求操作票为活动、未结案，当前 MBL 关系存在，HOUSE 箱货分配已确认，
  所有 HBL 仍为 `DRAFT`，所有非取消费用仍为 `DRAFT`，不存在活动账单行、核销分配、
  提成行或提成调整。DIRECT 整体改配不要求 HBL/箱货分配。
- 当前系统尚不存在 SI/VGM/舱单提交动作，因此阶段 4 不伪造其状态。阶段 5 新增正交状态
  和提交动作时，必须先把“均未提交”加入同一服务端预检；前端按钮只能消费服务端返回的
  `allowed_actions` 和具体阻断原因，不能另写一套门禁。
- 超过普通门禁后，不允许原地覆盖历史，也不实现自动撤回单证、账单、核销或提成的复合
  更正。用户必须先通过已有合法流程撤回/作废下游事实，或等待后续独立“后置拆票”任务。
- 拆票和改配均由一个 `biz.Transactor.WithinTransaction` 编排。固定锁序为来源操作票，
  然后按 UUID 排序锁定涉及的 MBL/运输执行/关系，再按 UUID 排序锁定货物、HBL、实际箱、
  分配、费用和下游门禁记录。任一校验或写入失败全部回滚。
- 命令携带来源操作票、当前关系、箱货聚合和所有被分配实体的预期版本；版本不符统一返回
  HTTP 409 和“已被更新，请刷新后重试”。唯一约束失败映射为稳定中文领域错误。
- 预检接口只用于页面即时反馈；提交命令必须在事务和锁内重新执行全部门禁、归属与守恒
  校验，不能相信旧预检结果。

## 页面与交互

- 订单详情的服务端动作摘要在满足前置条件时显示“拆票”或“整体改配”；被阻断时仍可查看
  具体原因，例如“费用 OCEAN 已确认，请先撤回费用确认”。
- 拆票使用独立全页或大抽屉，不塞进新建订单长表单。页面左侧展示来源 HBL/货物/实际箱/
  草稿费用，右侧展示原票保留结果和新票结果；每张新票可选择“沿用当前 MBL”或目标 MBL。
  每次勾选或输入后实时计算件重尺、箱量和各币种费用的基准/已分配/剩余，使用蓝/绿/红
  表示进行中/完成/超出。
- 整体改配使用较短的确认抽屉：目标 MBL 候选、目标航次摘要、改配原因、责任方、影响范围
  和版本。提交前明确提示“保留当前操作票号，不会复制订单”。
- 成功后跳转到拆分事件详情或当前操作票详情，并提供原票、新票、改配前当前 MBL 和目标
  MBL 的互链；失败时保留用户输入，并根据结构化 metadata 聚焦具体冲突项。

## Acceptance Criteria

- [ ] 一次部分拆票可以产生一张保留原号的非零原票和一张或多张新票；所有结果在一次
      提交中完成，件数、毛重、体积、实际箱、HBL 和每币种草稿费用严格守恒，来源与
      结果可追溯。
- [ ] HBL 与实际箱均不可跨结果票；页面即时指出发生交叉的 HBL 号或箱号，服务端提交
      再次阻断，不发生静默拆分或绕过前端的非法写入。
- [ ] 每张新结果票可以沿用改配前当前 MBL 或选择目标 MBL；选择不同 MBL 时，一个请求在
      同一事务内依次形成拆分事件和独立改配事件，失败时不留下中间操作票或关系。
- [ ] 拆票成功后原票和所有新票的箱货分配均为 `CONFIRMED`，具有独立聚合版本和来源
      拆分事件；任一结果不完整时整个命令失败，后续修改仍需显式撤回确认。
- [ ] 新票只继承白名单字段，获得新订单号；账单、核销、提成和附件对象不被复制。
- [ ] 整票改配不创建新操作票，旧关系终止、新关系建立；DIRECT 与 HOUSE 各自保持结构，
      HOUSE 箱货历史可以按旧、新关系分别重现。
- [ ] 页面实时显示每个结果的基准、已分配和剩余，并对具体 HBL/货物/箱/费用给出可定位错误。
- [ ] 门禁任一不满足时不产生半成品、重复费用或提成；前端与提交端共用服务端门禁结果。
- [ ] 并发拆票/改配冲突稳定返回 409；真实 PostgreSQL 覆盖成功、门禁失败、写入中途失败和
      两个并发命令，证明事务全部回滚且无双活动关系。

## Out of Scope

- 已提交 SI/VGM/舱单的真实外部接口、不可变单证版本、改单和 Switch B/L；由阶段 5 实现。
- 已确认/已账单化/已核销/已生成提成后的自动后置拆票与跨单复合冲正。
- MBL、航段、集装箱和 HBL 级共享费用模型及自动成本分摊；由阶段 6 实现。
- 附件对象复制或跨订单共享、自动按件重尺分摊费用、合并操作票。
