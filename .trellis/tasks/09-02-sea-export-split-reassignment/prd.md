# 海运出口拆票与改配

## Goal

让业务员在货物确实分批去往不同 MBL/航次时执行正式部分拆票，在整票甩柜时执行
整体改配；两条流程均保留完整历史、数量守恒、明确门禁，并且不会重复复制财务或
提成事实。

## 当前事实与前置条件

- 依赖任务 `09-02-sea-export-cargo-allocation` 已完成、独立检查、提交并归档。
- `Order` 就是操作票，不新增“客户委托单”。订单号由现有组织级号码规则在事务内
  分配，并由 `(organization_id, order_no)` 唯一索引兜底。
- 每张活动海运出口操作票已有且只能有一个 `ACTIVE` MBL 关系；历史关系使用
  `ENDED`、`ended_at` 和 `ended_reason` 保留，不删除旧关系。
- 本文“改配前当前 MBL”是指业务运行时，操作票在执行拆票或改配之前通过 `ACTIVE`
  关系正在使用的 MBL，不表示开发数据库中预先存在历史数据。当前开发库为空不影响
  此规则；用户未来新建订单录入 MBL 后，才会形成第一条当前关系。
- HOUSE 操作票的货物、HBL、实际箱定量关系已经由 `SeaCargoAllocation` 表达。
  `CONFIRMED` 分配保证逐货物、逐实际箱守恒，并禁止普通修改；拆票应消费这份已
  确认事实，不能重新猜测货物归属。
- HBL 是属于唯一操作票和唯一 MBL 的真实实体；实际箱和货物行也属于唯一操作票。
  因此拆票必须连同选定的 HBL、货物数量和整只实际箱一起迁移或重建归属，不能只
  修改 MBL 外键留下跨票引用。
- 订单费用已有 `DRAFT / CONFIRMED / BILLED / CANCELLED` 状态，账单行、核销分配和
  提成行均保存不可变来源引用或快照，可用于阻断不安全拆票。
- 当前仓库还没有 SI、VGM、舱单“已对外提交”的独立事实表或提交命令。阶段 4 不以
  订单总流程状态冒充这些正交状态，也不接受前端自行声明“未提交”；阶段 5 建立
  正交外部状态时，必须在开放任何提交动作前把这些事实补入同一个拆票/改配预检。

## 业务规则

### 部分拆票

- 第 4 阶段的部分拆票只支持 `HOUSE`。`DIRECT` 没有 HBL 及已确认的 HBL 箱货分配，
  本阶段不得猜测货物与箱的拆分关系、生成虚拟 HBL，或要求用户把真实 DIRECT 业务
  伪装成 HOUSE；DIRECT 部分拆运需要未来独立建立“DIRECT 货物—集装箱定量分配”后
  再开放。
- 部分货物去往不同承运人单证或不同运输执行时，执行正式拆票。一次拆票允许形成
  “原票 + N 张新操作票”：页面默认一张新票，并允许继续添加结果票；所有结果在
  同一次提交中完成守恒校验。原操作票保留原号和非零剩余，只为拆出的结果生成新
  操作票和新订单号；不允许把原票拆成零剩余，整票移动必须走整体改配。
- 拆票必须从一份 `CONFIRMED` 箱货分配开始。用户选择要拆出的 HBL/货物/实际箱后，
  系统在提交前实时显示原票和每张结果票的件数、毛重、体积、箱量及剩余；错误必须
  指出具体 HBL、货物或箱以及基准、已分配和差额。
- 拆票页面允许为每张新结果票直接选择目标 MBL，也允许暂时沿用改配前当前 MBL。
  服务端先记录拆分事件，再为选择不同目标 MBL 的结果票分别记录改配事件；两类事件
  在同一个事务中完成，任何一步失败都全部回滚。页面的一次操作不得把两个事件类型
  合并成无法区分的历史记录。
- HBL 和真实集装箱均为不可跨结果票的完整业务单位：一张 HBL 不得同时留在原票和
  新票，同一实际箱也不得跨两个结果票。若一张 HBL 或一只实际箱的现有分配同时覆盖
  “保留”和“拆出”货物，页面必须立即指出具体 HBL 号或箱号并阻止提交；业务员需先
  撤回箱货确认，重新分配或按实际业务新增 HBL 后再拆票。拆票命令不得静默切割真实
  单证或实体箱，也不得只在前端提示而由服务端放行。
- 拆分事件是不可变事实，至少保存组织、来源操作票、操作人、原因、拆分前快照、
  各结果票、分配明细、守恒结果和发生时间。原票与所有新票都能由事件反查谱系，
  但新票仍是普通 `Order`，不创造会污染列表和权限的特殊“子操作票”类型。
- 原票保持拆票时的业务流程状态，每张新票继承同一流程状态，不强制退回 `DRAFT`，
  也不伪造从草稿到当前节点的逐条历史流转。新票新增一条不可变的“由拆票创建”生命
  周期事件，记录来源操作票、来源流程状态、拆分事件、操作人和发生时间；新票的终止
  状态固定为正常活动、结案状态固定为未结案。页面顶部显示“拆票产生”和来源操作票号。
- 原票和新票的货物行应按结果数量形成各自独立事实；原货物行不能被多个操作票共用。
  HBL、实际箱和当前 MBL 关系同样只归属于最终结果票。旧 ID 与新 ID 的对应关系保存
  在拆分事件明细中，不依赖审计文本还原。
- 拆票提交本身承担所有结果票的箱货守恒确认。成功后，原票和每张新票的箱货分配均
  保持 `CONFIRMED`，各自建立新的聚合版本并记录来源拆分事件，不要求业务员逐票重复
  点击确认。任一结果票不完整或不守恒时，整次拆票失败且不得留下草稿结果；成功后如
  需修改货物、HBL、实际箱或分配，仍必须在对应操作票上显式撤回确认。
- 拆票继承采用显式白名单：组织、业务类型、委托单位、贸易方向、贸易条款、付款条款、
  装载类型、箱主类型、运输模式、服务类型、货物类别、订舱/承运/海外/船务代理、
  销售/操作/客服/单证/商务/关联人员、客户业务编号和允许继承的备注。新票必须分配
  新订单号，
  创建人记录本次拆票操作人；主单关系、HBL、货物、实际箱、箱型计划、里程碑、异常、
  放货签收、费用、附件引用、账单、核销、提成和历史审计不得无条件复制。
- 客户业务编号由原票和所有新票共同继承，因为它们属于同一次客户委托。重复校验遇到
  同一拆票谱系的相同客户业务编号时，不作为普通重复错误展示，而应提示“同一拆票谱系
  下共有 N 张操作票”并提供互链；谱系之外的重复仍沿用现有校验。
- 企业内部编号只保留在原票，新票不自动复制且在拆票预览中明确显示为空；新票创建后可
  由业务员分别填写自己的企业内部编号。系统不得以隐藏复制、自动加后缀或静默清空的
  方式处理内部编号。
- 附件调整为“文件资产 + 操作票引用”：文件资产保存唯一对象存储地址和文件元数据，
  操作票通过独立引用关系使用该资产。同一物理文件只保存一份，不复制对象存储内容。
- 拆票页面列出来源操作票的附件，每个附件默认只保留原票引用；业务员可以逐个选择要
  引用该文件的新票，禁止按附件类型自动传播或默认全选。拆分事件保存文件资产、来源
  引用和全部结果引用快照。
- 从某张操作票移除附件只解除该票引用；只要仍有任何操作票引用，物理文件不得删除。
  最后一条引用解除后的实际对象删除继续通过现有对象删除流程执行。新增引用、解除引用
  和最终删除均写审计。
- 当前开发库无历史业务数据。附件关系迁移开始时必须显式检查旧附件表为空；发现数据
  立即失败并重新设计迁移，不添加旧结构兼容、自动复制或静默回填。
- 第 4 阶段只支持草稿费用整行归属：每条非取消草稿费用必须且只能选择原票或某一张
  新票，不得遗漏、重复或拆成多个金额。整行移动时，收支方向、结算单位、计费单位、
  数量、单价、含税/未税/税额、税率、币种、汇率、汇率日期、汇率来源、本位币金额及
  其他快照值原样保留；目标票生成新的幂等键，并在拆分明细记录来源费用 ID 与结果费用
  ID。一个来源费用跨多张结果票的正式分摊留给阶段 6，阶段 4 禁止自动按件重尺比例、
  百分比或金额拆分，避免形成临时财务口径。

### 整体改配

- 海关查验、船司爆舱或航次变化导致整票甩柜时，使用整体改配；保留同一操作票、订单号、
  HBL、货物、实际箱、费用和人员，不创建新操作票，也不要求业务员重新录入。
- 整票改配不改变业务进度，操作票的流程状态保持不变，不因为航程切换退回草稿或重新
  执行已完成的流程节点。
- 改配必须选择或创建一个通过既有 MBL 候选校验的目标 MBL，填写原因和责任方。事务内
  终止改配前当前 `ACTIVE` 关系并建立新的 `ACTIVE` 关系，同时保存改配前/目标 MBL、
  运输执行、版本、箱货分配和受影响记录快照。
- 目标 MBL 航程与改配前当前航程不同时，页面先逐项预览承运人、起运港、卸货港、中转港、
  船名、航次、ETD 和 ETA 的前后值；用户明确确认改配后，操作票当前航程展示切换为目标
  MBL 的权威运输执行。这里的“自动覆盖”只更新操作票当前投影，不得用原票航程反向覆盖
  目标共享 MBL，也不得改写改配前历史快照。
- 目标 MBL 已关联其他操作票时，必须复用既有共享 MBL 规则校验组织、签发主体、规范化
  主单号、候选版本和目标共享航程；目标输入必须与目标 MBL 的权威航程一致。目标航程可以
  与改配前当前航程不同，该差异是改配预览内容而不是候选冲突；校验失败时禁止静默归组。
- 改配原因始终必填，去除首尾空白后长度为 1 至 500 个字符。责任类型必选，固定为
  `CARRIER`（船公司/承运人）、`CUSTOMER`（客户）、`CUSTOMS`（海关/监管）、
  `OWN_COMPANY`（我方）、`FORCE_MAJEURE`（不可抗力）或 `OTHER`（其他）；选择
  `OTHER` 时原因必须明确写出具体责任情况。
- `CARRIER` 或 `CUSTOMER` 可以选择一个当前组织可访问的现有往来单位，但首版不强制，
  以允许责任主体尚未最终确定的现场情况。选中往来单位时，改配事件同时保存单位 ID 和
  当时名称快照，后续单位改名不得改变历史展示。首版不要求选择内部责任员工；审计仍独立
  记录命令操作人，内部责任到人的管理另立需求。
- HOUSE 的 HBL 和箱货分配随整票改配到新关系，分配原为 `DRAFT` 时继续保持
  `DRAFT` 及现有合法分配行，原为 `CONFIRMED` 时继续保持 `CONFIRMED`；不得为了
  改配强迫业务员补齐、确认或撤回箱货分配。旧关系及改配前分配必须由事件快照重现。
  DIRECT 保持无 HBL，不得生成虚拟分单。DIRECT 可以执行整票改配，保留原操作票、
  货物、实际箱和费用，不要求重新录入。
- “部分留在改配前当前 MBL、部分去目标 MBL”不是整票改配：必须先形成正式拆票事实，
  再为对应结果票形成改配事实；页面可以一次提交，但服务端必须按这个顺序原子执行。

### 门禁、事务与并发

- 新增独立权限 `business.order.se.split`（执行海运出口拆票）和
  `business.order.se.reassign`（执行海运出口整体改配），两者均依赖海运出口订单查看、
  编辑权限。管理员通过现有权限目录同步自动获得，不要求手工 Seed；其他角色由管理员
  按职责授权。
- 只有拆票权限时可以拆票，但每张结果票只能沿用改配前当前 MBL；在拆票请求中为任一
  结果票选择不同目标 MBL 时，必须同时具有拆票和整体改配权限。独立整体改配命令只需
  整体改配权限。前端按权限控制入口和目标 MBL 选项，后端对每个命令及组合动作再次校验，
  禁止仅靠隐藏按钮实施授权。
- 普通拆票/改配要求操作票为活动、未结案，当前 MBL 关系存在，所有 HBL 仍为 `DRAFT`，
  所有非取消费用仍为 `DRAFT`，不存在活动账单行、核销分配、提成行或提成调整。HOUSE
  部分拆票额外要求箱货分配为 `CONFIRMED`；HOUSE 整体改配允许 `DRAFT` 或
  `CONFIRMED` 并保持原状态，DIRECT 整体改配不要求 HBL/箱货分配。
- 当前系统尚不存在 SI/VGM/舱单提交动作，因此阶段 4 不伪造其状态。阶段 5 新增正交状态
  和提交动作时，必须先把“均未提交”加入同一服务端预检；前端按钮只能消费服务端返回的
  `allowed_actions` 和具体阻断原因，不能另写一套门禁。
- 超过普通门禁后，不允许原地覆盖历史，也不实现自动撤回单证、账单、核销或提成的复合
  更正。用户必须先通过已有合法流程撤回/作废下游事实，或等待后续独立“后置拆票”任务。
- 拆票和改配均由一个 `biz.Transactor.WithinTransaction` 编排。固定锁序为来源操作票，
  然后按 UUID 排序锁定涉及的 MBL/运输执行/关系，再按 UUID 排序锁定货物、HBL、实际箱、
  分配、费用和下游门禁记录。任一校验或写入失败全部回滚。
- 命令携带来源操作票、当前关系、箱货聚合和所有被分配实体的预期版本；版本不符统一返回
  HTTP 409 和“已被更新，请刷新后重试”。唯一约束失败映射为稳定中文领域错误。
- 预检接口只用于页面即时反馈；提交命令必须在事务和锁内重新执行全部门禁、归属与守恒
  校验，不能相信旧预检结果。

## 页面与交互

- 订单详情的服务端动作摘要在满足前置条件时显示“拆票”或“整体改配”；被阻断时仍可查看
  具体原因，例如“费用 OCEAN 已确认，请先撤回费用确认”。
- DIRECT 不显示可执行的部分拆票入口；查看阻断原因时明确提示“DIRECT 当前没有 HBL
  箱货分配，暂不支持部分拆票，可执行整票改配”，不得提示用户新增虚拟 HBL。
- 拆票使用独立全页或大抽屉，不塞进新建订单长表单。页面左侧展示来源 HBL/货物/实际箱/
  草稿费用，右侧展示原票保留结果和新票结果；每张新票可选择“沿用当前 MBL”或目标 MBL。
  每次勾选或输入后实时计算件重尺、箱量和各币种费用的基准/已分配/剩余，使用蓝/绿/红
  表示进行中/完成/超出。
- 预览明确展示原票保留客户业务编号和企业内部编号，新票继承客户业务编号且企业内部编号
  为空；用户提交前能看见该结果。
- 附件区逐项显示文件名和要引用的结果票；默认只有原票被选中，新票必须由用户明确勾选。
- 整体改配使用较短的确认抽屉：目标 MBL 候选、目标航次摘要、改配原因、责任方、影响范围
  和版本。责任方先选择固定责任类型，客户/承运人类型再显示可选的往来单位选择器；提交前
  逐项展示改配前/目标航程差异，并明确提示“保留当前操作票号和流程状态，不会复制订单”。
- 成功后跳转到拆分事件详情或当前操作票详情，并提供原票、新票、改配前当前 MBL 和目标
  MBL 的互链；失败时保留用户输入，并根据结构化 metadata 聚焦具体冲突项。

## Acceptance Criteria

- [ ] 一次部分拆票可以产生一张保留原号的非零原票和一张或多张新票；所有结果在一次
      提交中完成，件数、毛重、体积、实际箱、HBL 和草稿费用行完整归属，来源与结果
      可追溯。
- [ ] 只有 HOUSE 可以执行部分拆票；DIRECT 部分拆票得到明确阻断，但可以整票改配且
      不生成 HBL、不创建新操作票、不要求重新录入。
- [ ] HBL 与实际箱均不可跨结果票；页面即时指出发生交叉的 HBL 号或箱号，服务端提交
      再次阻断，不发生静默拆分或绕过前端的非法写入。
- [ ] 每张新结果票可以沿用改配前当前 MBL 或选择目标 MBL；选择不同 MBL 时，一个请求在
      同一事务内依次形成拆分事件和独立改配事件，失败时不留下中间操作票或关系。
- [ ] 拆票成功后原票和所有新票的箱货分配均为 `CONFIRMED`，具有独立聚合版本和来源
      拆分事件；任一结果不完整时整个命令失败，后续修改仍需显式撤回确认。
- [ ] 每条非取消草稿费用完整归属且只归属一个结果票，全部财税与汇率快照不变；不得在
      阶段 4 拆分单条费用金额，已确认或已有下游事实时继续阻断普通拆票。
- [ ] 新票只继承白名单字段，获得新订单号；账单、核销、提成和附件对象不被复制。
- [ ] 客户业务编号沿同一拆票谱系继承并在重复校验中显示关联票提示；企业内部编号只保留
      于原票，新票预览明确为空且不自动生成后缀。
- [ ] 同一文件资产可以被原票和多张新票引用且物理文件只有一份；新票默认不继承附件，
      用户逐项选择引用目标，解除单票引用不会删除仍被其他操作票使用的文件。
- [ ] 拆票和整体改配使用两个独立权限；只有拆票权限时结果票只能沿用当前 MBL，组合拆票
      与目标 MBL 改配要求同时具备两个权限，前端入口和后端接口均无法绕过。
- [ ] 原票和新票保持来源操作票拆票时的流程状态；新票为正常活动、未结案，并仅以
      “由拆票创建”事件记录来源，不伪造之前的逐级流程历史。
- [ ] 整票改配不创建新操作票，旧关系终止、新关系建立；DIRECT 与 HOUSE 各自保持结构，
      HOUSE 箱货历史可以按旧、新关系分别重现。
- [ ] HOUSE 整体改配接受 `DRAFT` 和 `CONFIRMED` 箱货分配，新关系保持原状态及现有
      合法分配，不要求临时补齐、确认或撤回；部分拆票仍只接受 `CONFIRMED`。
- [ ] 整票改配要求合法目标 MBL、1 至 500 字原因和固定责任类型；可选责任往来单位必须
      属于当前组织，并以 ID 与名称快照保存，后续主数据改名不影响历史。
- [ ] 改配预览逐项显示改配前与目标航程差异；确认后操作票当前投影采用目标 MBL 权威
      航程且流程状态不变，不反向覆盖共享 MBL，不把源/目标航程差异误判为候选冲突。
- [ ] 目标 MBL 已有其他操作票时，仍通过既有主体、号码、版本和目标共享航程校验；不匹配
      时阻断且不得静默归组。
- [ ] 页面实时显示每个结果的基准、已分配和剩余，并对具体 HBL/货物/箱/费用给出可定位错误。
- [ ] 门禁任一不满足时不产生半成品、重复费用或提成；前端与提交端共用服务端门禁结果。
- [ ] 并发拆票/改配冲突稳定返回 409；真实 PostgreSQL 覆盖成功、门禁失败、写入中途失败和
      两个并发命令，证明事务全部回滚且无双活动关系。
