# 海运出口单证版本与换单

## Goal

在不增加普通录单负担的前提下，为海运出口 MBL/HBL 建立可重现的内容版本、改单发布和
Switch B/L 替代链，并以唯一的订单级锁封存已经完成业务资料和费用录入的订单。订单锁定
后，解锁必须发起申请并经钉钉审批同意；用户仍从订单详情中的简洁入口完成低频操作。

## Background

- 阶段 1～4 已完成并归档：当前模型已有共享 MBL、一个操作票多 HBL、DIRECT/HOUSE、
  箱货定量分配、部分拆票、整体改配和不可变拆票/改配事件。
- `Order` 就是操作票，不新增“客户委托单”或虚假操作票。
- 当前 `SeaMasterBill` 和 `SeaHouseBill` 直接保存内容和 `DRAFT/CONFIRMED/RELEASED`
  等有限状态，还没有独立的不可变版本实体、正式签发事实或替代链。
- 当前 `Order` 已有 `locked_at` 字段和少量下游保护判断，但没有正式锁定/解锁命令、锁定人、
  锁定历史、解锁申请和审批结果，尚不能形成可审计的订单锁定闭环。
- 当前仓库没有船公司、海关、港区或国外代理的正式外部回执接口；本阶段不得伪造“外部
  已接受”“海关已放行”等系统无法证明的状态。
- 开发数据库已按授权清空并由正式迁移重建，没有需要兼容或回填的历史业务数据。
- 用户人数少，页面应保持简洁；完整版本、节点和 Switch 历史放在按需进入的抽屉或独立
  页面，不在订单录入页平铺状态矩阵。

## Confirmed Requirements

### 单证身份与内容版本

- MBL/HBL 的业务身份与内容版本分离：身份记录保存当前有效版本指针，版本记录保存当时
  完整提单内容、版本号、创建原因、创建人和时间。
- 订单未锁定时，当前 MBL/HBL 工作内容允许按现有权限直接编辑；锁定订单时形成该锁定
  周期引用的不可变单证版本。审批解锁不会删除或改写旧版本，继续修改后再次锁定时形成
  带原因和逐字段差异的新版本；不再设置单张单证的第二套“确认即锁定”机制。
- 共享 MBL 仍只有一套共享内容；从任一成员操作票看到同一当前版本。MBL 新版本发布后，
  所有当前成员看到新版本，但历史事件、打印、申报和财务依据继续引用其实际使用的版本 ID。
- HBL 各自独立版本化；修改、锁定快照、作废或 Switch 不得连带改写同一操作票下其他 HBL。
- 下游事实必须引用具体版本 ID，不允许只保存 MBL/HBL 身份 ID 后在历史查询时读取最新内容。

### 唯一订单锁与钉钉审批解锁

- 系统只有一把订单级业务编辑锁，不为 SI、VGM、舱单或单张 MBL/HBL 分别建立编辑锁。
  本阶段也不新增 SI、VGM、舱单的人工提交、撤回或“不适用”状态。
- 订单锁定用于表达“该订单的业务资料和费用已经录入完成，目前不再需要修改”。它是整张
  订单的封存动作，不是单独的提单确认、费用审核或外部业务节点。
- 订单锁定和批准解锁属于同一个业务角色。只有具备该角色对应权限的用户能够锁定订单或
  批准解锁；具体执行锁定的账号只用于审计，不成为该锁定周期唯一的审批人。
- 锁定事实必须至少记录订单、实际锁定操作人、锁定时间和本次锁定代次，并写入业务审计；
  不能只依赖一个可被普通 update 覆盖的时间字段。
- 订单锁定后，所有会改变该订单业务结果的普通写操作都被统一阻断，包括订单资料、MBL/HBL、
  箱货分配、费用录入、拆票、改配、改单、作废和 Switch；如需修改，必须先完成解锁。
- 锁定后的订单不得通过普通编辑直接恢复为可编辑。用户必须创建本地解锁申请；申请、订单
  锁定事实和后续钉钉审批实例必须能够一一追溯。
- 所有拥有订单编辑权限的用户都可以提交解锁申请，无需再配置单独的申请权限。提交申请不
  会赋予审批权；钉钉审批人必须来自订单锁定/解锁角色，不能因为某个账号是原锁定操作人、
  申请人、任意管理员或普通订单编辑人就自动获得审批权。
- 锁定/解锁角色存在多名有效用户时采用或签：任意一名角色成员在钉钉同意即可批准解锁，
  不要求多人会签；实际作出决定的账号和时间必须写入审批记录与业务审计。
- 解锁申请先在数据库事务内持久化，事务提交后再经通知 outbox/后台任务创建钉钉原生审批
  实例；禁止在数据库事务内等待钉钉网络调用，也禁止用普通机器人文字消息冒充审批。
- 钉钉同意或拒绝通过正式审批事件回传。服务端必须验证事件来源，对重复事件幂等处理，并
  保存钉钉流程实例 ID、审批结果、审批人和审批时间。
- 只有审批同意且订单仍处于申请针对的同一锁定代次和预期版本时才能解锁；订单状态已变化
  时不得把过期审批套用到新的锁定周期。回传的审批人还必须属于订单锁定/解锁角色；审批
  拒绝时订单继续保持锁定。
- 审批解锁成功后，订单立即恢复普通可编辑状态；此后所有拥有订单编辑权限的用户都可以
  编辑，不只限于解锁申请人、审批人或原锁定人。
- 钉钉未配置、审批实例创建失败、回调校验失败或审批状态不明确时，均不得静默解锁；页面
  显示当前申请状态和具体失败原因。
- 后端统一返回订单当前是否锁定、允许动作和具体阻断原因；前端只消费该结果，不复制锁定
  规则。阶段 4 的拆票、改配以及本阶段的改单、作废和 Switch 均必须服从同一订单锁。

### 单改、作废与 Switch B/L

- 单改以当前有效版本为基线，展示修改前后差异并要求填写原因；成功后追加新版本、切换
  当前指针并写业务审计，旧版本永久保留。
- 单改和 Switch B/L 自身不设置申请、待审核、审核人、审核通过或驳回状态。订单处于可编辑
  状态时，有相应权限的操作员填写原因，查看新旧差异及影响范围并明确确认后，在一个事务
  内直接发布或执行；订单已锁定时必须先完成统一解锁审批，不能绕过订单锁。
- 作废是显式状态和事件，不物理删除单证身份或版本；作废原因、操作人、时间和受影响的
  外部/财务事实必须可查。
- Switch B/L 不创建新操作票。第一套 HBL 保留在原操作票下并进入交回/作废/被替代状态，
  同一操作票下创建新的真实 HBL 身份和首个版本，以替代关系连接新旧两套单证。
- 同一替代链同一时点只能有一张当前有效 HBL；Switch 必须记录原 HBL、新 HBL、原因、
  原件交回/作废信息、操作人、时间以及 SI/舱单/费用影响摘要。
- Switch 不自动创建费用、红冲账单、撤销核销或重算提成；发现既有财务下游事实时明确
  阻断或列入阶段 6 的显式调整范围，不做静默复制和自动兜底。

### 身份更正

- 相关订单未锁定、MBL 只有一个成员操作票且没有外部/财务下游事实时，允许有权限用户填写原因
  后直接更正 MBL 号或签发主体；重新执行号码规范化、候选查重、版本和审计校验。
- 单票更正后命中既有共享 MBL 时，必须进入已有候选摘要确认与关联/改配流程，不能原地
  制造重复身份。
- MBL 已被多票共享时，普通订单编辑不能改 MBL 号或签发主体。仅当前票关联错误走整体
  改配；整张共享 MBL 身份错误必须使用列出全部成员影响范围的共享更正动作。
- 相关订单已锁定、已登记外部提交或已有受影响财务事实后，身份字段不得原地更正，只能通过
  作废重建、改单或改配保留旧身份。

### 页面与权限

- 订单详情顶部显示业务人员可理解的锁定摘要，例如“未锁定”或“已锁定 · 张三 · 2026-09-04”，
  并提供与权限和状态匹配的“锁定订单”或“申请解锁”入口；完整版本和替代历史放在默认
  展开的提单区块内入口及独立抽屉。
- 普通订单新建页面仍只要求已确认的 MBL 号和签发方；不要求用户在录单时理解或填写
  SI/VGM/舱单/Switch 状态。
- 无读取权限不显示单证模块；只有读取权限显示只读摘要；相应维护权限才显示签发、单改、
  作废和 Switch 动作。锁定订单与申请解锁分别按其动作权限显示。
- 解锁申请提交后，页面立即显示“待创建钉钉审批”“审批中”“已拒绝”“已同意但未生效”或
  “已解锁”等真实状态；审批仍在处理中时不得向用户显示已经解锁。
- 所有写入使用预期版本、固定锁序、幂等键、同事务业务审计；失败完整回滚。

## Acceptance Criteria

- [ ] 订单未锁定时 MBL/HBL 工作内容可普通编辑；锁定时形成不可变版本，审批解锁后继续
      修改并再次锁定会形成新版本，旧版本仍可完整读取。
- [ ] 两个操作票共享一张 MBL 时读取同一当前版本；发布新版本不会改写历史下游引用。
- [ ] 有锁定权限的用户可以锁定订单；锁定人、时间、锁定代次和审计可查，订单进入统一的
      封存状态，订单资料、单证、箱货、费用及其他业务修改均被阻断。
- [ ] 锁定订单不能被直接解锁；创建本地解锁申请后才异步创建钉钉原生审批，数据库事务不
      等待外部网络调用。
- [ ] 任意拥有订单编辑权限的用户都能发起解锁申请，无需额外申请权限；发起申请不会使其
      获得批准解锁的权限。
- [ ] 锁定与批准解锁使用同一个业务角色；实际锁定操作人只用于审计，同角色的其他用户也
      可以在钉钉中批准解锁，非该角色用户不能批准。
- [ ] 锁定/解锁角色有多个用户时，任意一名有效角色成员同意即可通过，不等待其他成员会签；
      实际审批人和审批时间可查。
- [ ] 钉钉审批同意且锁定代次、预期版本仍匹配时订单解锁；拒绝、过期、重复、验签失败或
      状态不明的事件均不会误解锁。
- [ ] 解锁成功后不建立新的人员限制；所有拥有订单编辑权限的用户均可恢复编辑。
- [ ] 系统没有正式外部回执时，不出现“船公司已接受”“海关已放行”等无法证明的状态，也
      不新增 SI/VGM/舱单人工状态来模拟外部流程。
- [ ] Switch 在同一操作票下保留旧新 HBL、不可变版本和替代关系，同一替代链只有一个当前
      有效单证，不创建虚假操作票或隐藏 HBL。
- [ ] 单改和 Switch 自身不出现审核人或审批状态；订单可编辑时由有权限操作员确认后直接
      执行，订单已锁定时统一要求先完成解锁审批。
- [ ] MBL 身份更正按单票未锁定、多票共享、已锁定/下游事实三种情况执行不同门禁，冲突
      不静默合并或创建重复 MBL。
- [ ] 阶段 4 拆票/改配以及本阶段改单、作废和 Switch 均服从同一订单锁，不各自复制锁定规则。
- [ ] 并发发布、作废或 Switch 只有一个成功；幂等重放返回原事件，不产生双当前版本或双
      当前替代单证。
- [ ] 页面保持渐进展示；普通录单无需操作完整状态机，低频版本与 Switch 历史可按需查看。
- [ ] 真实 PostgreSQL 测试覆盖版本追加、历史重现、共享 MBL、Switch、锁定代次、解锁审批
      幂等、过期审批、门禁、审计失败回滚和并发冲突，且不得 SKIP。

## Out of Scope

- 不对接或伪造船公司、海关、港区、国外代理外部接口回执。
- 不新增 SI、VGM、舱单的人工状态机或独立字段锁。
- 不实现全部国家/航线舱单规范、打印模板或电子提单协议。
- 不实现阶段 6 的共享费用自动分摊、账单红冲、核销调整或提成重算。
- 不实现后置拆票的跨单证、申报和财务复合更正。
- 不增加虚拟 HBL、占位单证、隐藏复制、自动重试或旧模型兼容双写。

## Open Questions

- 共享 MBL 关联多张订单且锁定状态不同时如何限制共享字段修改，尚待确认。
- 钉钉审批模板、用户 DingTalk ID 映射、事件订阅和回调验签配置需要在设计阶段基于现有
  DingTalk 基础设施落地，不得以普通通知或轮询猜测审批结果。
