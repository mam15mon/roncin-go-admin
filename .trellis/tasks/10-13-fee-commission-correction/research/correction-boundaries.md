# 费用更正技术边界研究

## 已确认的业务结果

用户要求的四类异常仍保留：追加应收、调减应收/成本、金额或结算对象纠正、补录产生冲减后的纠错。结案后允许受控办理。更正审批认可经济变化并产生可追溯调整，实际补收/退款/补付/追回仍由财务执行。

## 现有代码的限制

- `server/internal/biz/order_fee.go:35` 的 totalAmountPattern 不接受负数；`:841`–`:848` 的数量、单价和总额必须为正，`:464`–`:465` 校验折本币金额。因此不能仅把补录 PAYABLE 限制放宽就得到合法调减。
- `server/internal/biz/finance_bill.go:367` 校验费用与账单方向、结算对象、币种及金额一致；`:448`–`:455` 从费用累加生成账单快照。简单修改已建账费用会破坏账单来源对照与当前有效费用含义。
- `server/internal/biz/finance_cashflow.go:131` 只支持正金额与 RECEIVABLE/PAYABLE 两方向；`:180` 创建 DRAFT 流水。审批若需展示追回900，必须有对应债权/抵扣事实，不能伪造现金流完成，也不能把减少成本直接当新增营业收入。
- `server/internal/biz/order_fee_supplement_usecase.go:419`–`:533` 是现有授权父锁 → Order → 申请 → 提成上下文 → 费用/冲减/批准快照同事务范本；`:545` 后计算仅支持新增成本边际冲减，并有订单行及父提成净额封顶。
- `server/internal/data/finance_commission_calculation.go:344` 从来源核销/对冲金额与账单总额求比例；`:527`–`:548` 根据费用方向汇总收入成本再分摊已实现利润。新增更正模型必须与后续首次计提及已确认提成调整保持一致，不能只修已存在的调整单。
- 系统冲减保留 SourceFeeSupplementRequestID；普通手工增减已存在但不能替代成本修正与幂等来源链。历史提成快照及已付事实需保留。

## 后续设计必须解决的技术问题

1. 明确有效经济内容如何表达：现有正数费用 + 显式调整，或独立的费用版本/调整记录；不以金额符号和收付方向的隐式约定混用。比较后选择覆盖本次用例成本最低的方案。
2. 更正前后费用、已建账原行、剩余应收应付、补收/退款或抵扣之间给出逐步数值表。至少覆盖已付1,000→成本100、部分支付、客户优惠、换结算对象和外币场景。
3. 明确审批生效时点、待财务执行状态及作废/再更正规则；原发票/核销历史不重写，不自动跨币种或跨结算单位抵扣。
4. 提成按原规则及来源快照计算边际差额，处理原补录已封顶、连续补录、已确认未付与已付差别；反向补提不能简单等于费用差额乘当前比例。
5. 费用汇总、批准快照、费用台账、建账、信用、提成候选、自动锁单及结案待办都列出明确调用方。正式迁移/生成物/开发数据与测试一次性同步，不用双读回退隐藏契约变化。
6. 新事务和版本设计必须复用现有分层；明确受影响实体及固定锁序后再评审，不在研究中擅自生成配置或代码。
