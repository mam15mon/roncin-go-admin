# 多组织快速上线薄底座 PRD

## 1. 文档结论

本任务采用“先建立薄底座，再覆盖首批核心业务”的上线策略，不建设全量多租户
安全框架。

项目尚未上线，当前目标是尽快形成可用、可验证的多组织能力。因此本任务默认：

- 只有一个公司集团，不引入 `tenant_id`、集团切换或跨集团隔离；
- 不兼容旧草稿键、旧接口字段、旧角色组织范围模型或旧开发数据；
- 不做双读、双写、灰度开关、自动回退和静默纠错；
- 契约和数据模型调整后，仓库内调用方一次性同步到新模型；
- 仍保留权限正确性、组织范围正确性、写入目标校验、事务与生成物要求；
- 涉及清空或重建本地数据库等破坏性操作时，实施阶段仍需用户明确授权。

## 2. 背景与问题

### 2.1 前端组织切换没有形成工作区边界

`OrganizationSwitcher` 当前只切换后端会话并刷新 `initialState.currentUser`。
`TagsView` 与路由页面没有作为一个整体随组织重建，因此旧组织页签、页面内存状态、
表单状态和迟到响应可能继续存在。各业务组件只能各自监听组织 ID 并手动清理，容易
遗漏。

### 2.2 草稿已经分组织存储，但归属信息仍暴露给业务调用方

现有 `formDraft.ts` 已使用 `userId:organizationId` 作为 scope，说明存储模型基本
正确；问题在于页面仍要计算并传递 `draftScope`。业务模板既负责业务，又承担工作区
命名空间拼装，边界不清晰。

### 2.3 跨组织授权只在订单域形成了专用模型

当前 `RoleOrderOrganizationAccess` 能配置角色可访问的订单组织及是否可写，但该
能力不能直接复用于往来单位和财务账单。与此同时，`Principal` 已保留角色级权限与
数据范围信息，具备按“角色 × 权限”解析组织集合的基础。

真正需要解决的是：某项权限来自哪个角色，该角色允许访问哪些组织。不能先把所有
角色权限和所有组织范围分别合并，再做全局判断，否则不同角色之间会发生权限串联。

### 2.4 原方案体量不适合当前上线目标

原方案计划给所有含 `organization_id` 的 Ent 实体增加全局查询拦截器、写入 Hook、
系统上下文豁免和管理面白名单。该方案长期可能有价值，但会同时影响认证、后台任务、
迁移工具、管理接口和大量既有仓储，首轮回归面过大，不适合当前快速上线目标。

## 3. 目标

### G1：建立前端组织工作区

当前用户和当前组织共同确定一个工作区。组织切换成功后，旧工作区的页签与页面组件树
整体卸载，跳转工作台并创建新工作区；切换失败或用户取消时，当前工作区保持不变。

### G2：把草稿命名空间收回基础设施

提供工作区上下文和 `useScopedDraft`，由基础设施内部获取用户、组织与页签信息。
业务模板不再接收外部拼装的 `draftScope`，但不同组织的草稿仍能分别恢复。

### G3：把订单专用组织授权泛化为角色组织范围

将 `RoleOrderOrganizationAccess` 一次性替换为通用
`RoleOrganizationAccess`，按具体权限解析可读和可写组织集合。首批只接入订单、
往来单位、财务账单三个核心聚合，继续在仓储查询中显式传入并应用组织过滤。

### G4：控制实施体量

不增加全局 Ent 拦截器，不建立 `SystemScope` 豁免框架，不追求一次覆盖全部业务实体。
在首批聚合验证模型后，再根据真实需求决定是否扩展。

## 4. 关键决策

### D1：单集团假设

本阶段的“全部组织”是当前部署中的全部启用组织，不区分集团或租户。组织树来自现有
组织模型。

### D2：切换组织后统一回到工作台

切换成功后使用 `history.replace('/welcome')`，清空旧组织的业务页签并重建工作区。
不尝试把旧组织的详情 URL 映射到新组织，也不为每个组织恢复一套页签。

### D3：切换前只保留一次明确确认

若当前工作区存在已登记的脏表单或草稿，切换器弹出确认，说明草稿仍保存在原组织。
用户取消则不调用切换接口；用户确认后才发起切换。切换失败时不清页签、不跳路由、
不修改前端用户状态。

### D4：草稿不做历史兼容

新 Hook 只识别新版本存储键。旧键不迁移、不双读，可自然过期或由开发者手工清理。
不同组织的新草稿仍必须相互隔离。

### D5：组织范围必须与权限所在角色绑定

解析时逐个处理“拥有目标权限的启用角色”，只合并这些角色各自允许的组织范围。
不得使用“全部角色权限并集 × 全部角色组织范围并集”的方式推导授权。

### D6：沿用现有四种 `data_scope`

- `organization`：当前组织；
- `organization_tree`：当前组织及其启用的下级组织；
- `all`：当前部署的全部启用组织；
- `self`：组织层面仍限定当前组织，实体的“本人数据”条件继续由对应业务域处理。

角色配置的 `RoleOrganizationAccess` 作为显式追加组织范围；其中 `writable` 决定
该角色对追加组织是否具备跨组织写入能力。当前组织能否写入仍由具体写权限决定。

### D7：写操作验证目标，不静默改写目标组织

创建、更新、状态流转等写操作必须验证请求中的目标组织是否位于当前权限的可写集合。
不允许把越界请求静默改写为当前组织，也不允许先写入再过滤响应。

### D8：仓储继续使用显式组织过滤

首批聚合的列表查询接收可读组织 ID 集合并使用 `OrganizationIDIn(...)`；详情与写入
同时使用主键和允许组织集合定位。显式指定了范围外组织的查询或写入返回权限错误。
本任务不注册全局 Ent Interceptor 或 mutation Hook。

### D9：保留有效的局部竞态防护

工作区重挂载负责隔离可见页面状态，但不会自动取消已经开始的 JavaScript 异步链。
请求序列号、组件存活判断、提交时组织快照等真正防止迟到回调的机制继续保留。只删除
经验证已被工作区边界完全替代的重复清理代码，不以“代码更少”为验收目标。

## 5. 需求范围

### 5.1 包含范围

#### Phase 1：前端组织工作区

- 在应用布局中新增 `OrganizationWorkspace`，同时包住 `TagsView` 和路由页面；
- 工作区 key 至少包含当前用户 ID 与当前组织 ID；
- 组织切换前统一检查当前工作区脏状态；
- 切换成功后更新 `initialState`、清理旧页签并跳转 `/welcome`；
- 切换失败或取消时完整保留旧工作区；
- 组织切换期间禁用重复提交；
- 复核模块级缓存，组织相关缓存必须按组织分键或在工作区销毁时释放；
- 保留仍有实际竞态价值的迟到响应防护。

#### Phase 2：工作区草稿

- 工作区上下文提供稳定的 `workspaceKey`、用户 ID 和组织 ID；
- 新增 `useScopedDraft`（或职责等价的 Hook），统一保存、读取、清理和判断草稿；
- `OrderFormTemplate`、`TagsView` 和订单页面改为消费工作区草稿能力；
- 删除 `OrderFormTemplate` 对外的 `draftScope` 参数，并一次性更新仓库内调用方；
- 新存储键按用户、组织、页签/路由和表单类型分区；
- 无有效用户或组织时不持久化草稿。

#### Phase 3：通用角色组织范围与首批业务接入

- 将 Ent 模型、Proto、服务转换、角色管理页面中的
  `RoleOrderOrganizationAccess` / `order_organization_accesses` 替换为通用命名；
- 不保留旧接口字段、旧类型适配器或双模型读取；
- `Principal` 保留角色级的权限、`data_scope` 与组织访问项，不提前打散为无来源并集；
- 在 Biz 层实现按权限解析可读/可写组织集合的统一能力；
- 首批接入以下聚合：
  - 订单：列表、详情和写操作；
  - 往来单位：列表、详情和写操作；
  - 财务账单：列表、详情和写操作；
- 角色管理界面使用通用“可访问组织 / 允许写入”语义；
- 更新受影响的 Ent、Proto、OpenAPI 和前端客户端生成物；
- 为权限与组织范围组合补充定向测试。

### 5.2 不包含范围

- 全局 Ent 查询拦截器、全局 mutation Hook 或自动组织回填；
- `SystemScope`、后台任务豁免清单、全实体隔离策略表和安全审计平台；
- 多集团、多租户、集团切换、物理分库分表；
- 历史接口、历史草稿键、历史角色组织范围数据的兼容读取；
- 灰度开关、双读双写、自动回退和旧行为保留分支；
- 为每个组织保存并恢复独立页签集合；
- 首批三个聚合之外的业务域接入；
- 重做现有 `self` 数据归属逻辑；
- 因追求统一而删除所有业务组件中的局部异步竞态保护；
- 集团内部对开单、跨组织结算和财务结转规则。

## 6. 功能要求

### R1：工作区生命周期

1. 初次登录或刷新时，根据 `userId:organizationId` 创建工作区；
2. 切换前检查当前工作区脏状态；
3. 用户取消时结束流程，不请求后端；
4. 后端切换失败时显示错误并保留当前工作区；
5. 后端切换成功后更新用户状态；
6. 工作区 key 变化触发旧 `TagsView` 和路由页整体卸载；
7. 路由替换为 `/welcome`，新组织只出现工作台初始页签。

### R2：草稿生命周期

1. 表单修改后写入当前工作区 scope；
2. 关闭页签和切换组织使用同一套脏状态登记与确认信息；
3. 切回原组织并重新打开同一表单时可恢复该组织草稿；
4. 提交成功后只清理当前工作区对应草稿；
5. 新建页和详情页使用不同业务键，不能相互覆盖；
6. 旧版本键不读取、不迁移。

### R3：权限组织范围解析

输入为当前 `Principal`、目标权限码和操作类型（读或写），输出为允许组织 ID 集合。

解析规则：

1. 只选择包含目标权限的启用角色；
2. 分别按每个角色的 `data_scope` 计算基础组织集合；
3. 合并该角色显式配置的通用组织访问项；
4. 读操作包含所有允许读取的组织；
5. 写操作只包含基础范围中可写组织及显式标记 `writable` 的追加组织；
6. 多个符合条件角色的结果取并集；
7. 没有任何符合角色或结果为空时返回权限拒绝；
8. 组织已停用时不进入结果集合。

### R4：首批业务应用

- 未传组织筛选时，列表在可读组织集合内查询；
- 显式筛选单个组织时，先校验该组织位于可读集合；
- 详情查询必须同时满足资源 ID 和可读组织范围；
- 创建、更新和状态流转必须校验目标组织位于可写集合；
- 数据层继续保留明确的 `OrganizationIDIn(...)` 或等价父实体谓词；
- 订单已有的业务类型权限过滤继续生效，不能仅凭组织范围放大订单类型权限。

### R5：契约与数据模型切换

- 新契约统一使用 `organization_accesses`；
- 仓库内所有调用方与生成物在同一阶段同步；
- 不保留 `order_organization_accesses` 别名；
- 数据库只保留通用角色组织访问关系；
- 迁移可以直接替换开发期旧模型，不承诺旧数据可继续使用；
- 任何清空或重建开发数据库的命令必须在执行前单独取得用户授权。

## 7. 验收标准

- [ ] **AC-1 工作区重建**：组织 A 打开的业务页签和页面内状态在成功切换到组织 B 后全部卸载；页面位于 `/welcome`，只展示新工作区初始页签。
- [ ] **AC-2 草稿隔离与恢复**：组织 A 的订单草稿不会显示在组织 B；切回 A 并重新打开对应表单后能恢复新版本草稿。
- [ ] **AC-3 切换守卫**：有脏表单时仅弹一次明确确认；取消不发请求，失败不改状态，成功才清页签并跳转。
- [ ] **AC-4 迟到响应**：切换后，旧组织已经发出的搜索或快捷创建响应不得回填到新组织工作区。
- [ ] **AC-5 模板解耦**：`OrderFormTemplate` 及其仓库内调用方不再声明、计算或传递 `draftScope`。
- [ ] **AC-6 无历史兼容分支**：新实现不存在旧草稿双读、旧 API 字段别名、旧角色组织模型双写或运行时回退。
- [ ] **AC-7 权限不串联**：角色甲拥有订单查看但仅当前组织，角色乙拥有财务查看且可看全部组织时，订单权限不得借用角色乙的组织范围。
- [ ] **AC-8 数据范围正确**：`organization`、`organization_tree`、`all`、`self` 四种范围按 D6 生效，停用组织不会进入结果。
- [ ] **AC-9 读写范围区分**：可读但不可写的追加组织能出现在列表和详情中，但创建、更新、状态流转返回权限错误。
- [ ] **AC-10 核心聚合覆盖**：订单、往来单位、财务账单的列表、详情和写入路径均使用统一解析结果及显式仓储过滤。
- [ ] **AC-11 订单业务类型权限保持**：跨组织范围不会让用户看到其角色未授权业务类型的订单。
- [ ] **AC-12 系统路径无额外框架依赖**：迁移、同步工具和既有 worker 不需要新增 `SystemScope` 才能运行，因为本任务未注册全局拦截器。
- [ ] **AC-13 生成链完整**：Proto、Ent Schema、迁移、OpenAPI 与前端客户端生成物一致，不存在手改生成文件。
- [ ] **AC-14 定向验证**：前端覆盖工作区切换、草稿隔离和角色表单；后端覆盖权限角色关联、四种范围、读写差异及三个核心聚合的越界场景。
- [ ] **AC-15 最终门禁**：任务全部阶段完成后只执行一次风险匹配的完整门禁；无法执行的检查及原因记录在任务交付说明中。

## 8. 风险与延期项

### 8.1 当前接受的风险

- 首批聚合之外的仓储仍沿用现有当前组织过滤，不在本任务中获得通用跨组织能力；
- 没有全局 ORM 兜底，新增查询仍需开发者显式应用组织过滤；
- 单集团假设不能直接支持未来集团 SaaS 化；
- 旧开发数据和旧浏览器草稿可能在模型切换后失效。

这些风险与项目未上线、优先快速交付的阶段相匹配。

### 8.2 后续满足条件再立项

仅在出现以下信号时重新评估全局安全框架：

- 组织范围接入的业务聚合明显增多，手写过滤开始频繁漏审；
- 后台任务和跨组织系统操作形成稳定、可枚举的调用协议；
- 项目进入外部用户或生产数据阶段，需要全局不可绕过的隔离保证；
- 多集团或 SaaS 租户需求已经确认。

后续任务再单独设计 Ent 拦截器、mutation Hook、系统上下文、全实体策略清单和审计，
不得在本任务中提前搭空框架。
