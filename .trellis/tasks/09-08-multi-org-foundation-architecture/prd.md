# 多组织快速上线薄底座 PRD

## 1. 结论

本任务采用“最小工作区边界 + 通用异步守卫 + 权限级组织范围”的薄底座方案，目标是
快速支持跨组织查看和安全切换，不建设全量多租户框架，也不重构已经可用的草稿体系。

项目尚未上线，因此默认不兼容历史接口、历史角色组织范围模型或旧开发数据，不做双读、
双写、灰度回退和静默纠错。仓库内调用方随新契约一次性更新。

## 2. 已确认事实

1. `OrganizationSwitcher` 当前只更新会话和 `initialState.currentUser`，`TagsView` 与
   页面没有作为整体随组织重建。
2. `formDraft.ts` 已使用 `userId:organizationId:tab:path` 隔离草稿，订单模板和
   `TagsView` 已消费这一能力；不存在必须重建草稿抽象的问题。
3. 天津员工查看北京订单是“当前天津工作区内的跨组织只读授权”，不是切换当前组织；
   查看只读详情不会产生北京组织编辑草稿。
4. `RoleOrderOrganizationAccess` 已具备角色追加组织和 `writable` 能力，但目前仅用于
   订单域。
5. React 工作区卸载能清理组件状态，但不能取消已经运行的 Promise；迟到回调、模块级
   缓存和服务端已执行写入仍需独立处理。

## 3. 目标

### G1：跨组织查看无需切换组织

天津员工可通过角色获得北京订单查看权限，在天津工作区直接查看天津和北京订单；不需要
切换成北京组织。额外组织访问默认是追加范围，不替代员工当前组织范围。

### G2：真正切换组织时重建工作区

组织切换成功后，旧组织的页签与页面组件树整体卸载，跳转工作台；取消或失败时保持当前
工作区不变。

### G3：减少业务页面竞态样板

提供小型通用异步守卫，统一解决“只接受最后一次查询”“组件卸载后不执行回填副作用”
和请求取消。业务页面不再重复拼装多个 sequence/mounted ref，但仍保留组织缓存分键、
重复提交锁和服务端组织校验。

### G4：泛化角色组织范围

将订单专用组织访问模型一次性替换为通用 `RoleOrganizationAccess`，按“权限所在角色”
解析允许组织。首批接入订单、往来单位和财务账单，仓储继续显式应用组织谓词。

## 4. 关键决策

### D1：单集团假设

“全部组织”表示当前部署的全部启用组织，不引入集团或租户维度。

### D2：额外组织是追加范围

角色基础范围为当前组织时，配置北京为额外只读组织后：

```text
可读组织 = 天津 + 北京
可写组织 = 天津
```

本阶段不支持“天津员工只能看北京、不能看天津”的替换型白名单。

### D3：权限与范围必须来自同一个角色

只合并“拥有目标权限的角色”各自允许的组织。订单查看权限不能借用另一个财务角色的
北京组织范围，避免角色之间发生权限串联。

### D4：沿用现有四种 `data_scope`

- `organization`：当前组织；
- `organization_tree`：当前组织及启用的下级组织；
- `all`：全部启用组织；
- `self`：组织层面为当前组织，本人数据条件继续由业务域处理。

显式 `RoleOrganizationAccess` 追加可读组织，`writable` 决定追加组织是否可写。

### D5：草稿保持现状

不新增 Workspace Context、`useScopedDraft`、v2 草稿键或旧键迁移。现有
`getFormDraftScope`、`getFormDraftKey` 和 `draftScope` 参数继续使用，仅补充工作区切换
回归测试。

### D6：切换成功后回到工作台

真实组织切换成功后使用 `history.replace('/welcome')`，重建页签和页面。不把旧组织
详情 URL 映射到新组织，也不为各组织保存页签集合。

### D7：通用异步守卫只控制前端副作用

- 查询使用 latest-wins，旧结果不得更新选项或 state；
- 写请求使用 loading 防重复，并在返回后验证 token 仍有效；
- 工作区卸载时所有 token 失效并尝试 abort；
- abort 不能撤销服务端已经完成的写入；
- 模块缓存仍必须按组织分键；
- 后端仍必须校验读写组织范围。

### D8：后端继续显式过滤

首批仓储接收允许组织 ID 集合并应用 `OrganizationIDIn(...)` 或等价父实体谓词。本任务
不增加全局 Ent Interceptor、mutation Hook 或 `SystemScope`。

### D9：写入验证目标，不静默改写

创建、更新和状态流转必须确认目标组织位于当前操作权限的可写集合。范围外请求返回权限
错误，不能改写为当前组织。

## 5. 范围

### 5.1 Phase 1：前端工作区与异步守卫

- keyed workspace 同时包住 `TagsView` 与路由页面；
- key 至少包含当前用户 ID 与当前组织 ID；
- 切换前检查当前已注册表单的 dirty 状态；
- 取消不请求后端，失败不改状态，成功后跳 `/welcome` 并重建工作区；
- 新增通用 latest-query / async-side-effect guard；
- 在首批高风险组件中替换重复的 sequence、mounted 和组织切换清理样板；
- 保留模块缓存组织分键、mutation 组织边界与重复提交锁；
- 草稿代码不重构，仅验证现有隔离行为。

### 5.2 Phase 2：通用角色组织范围

- `RoleOrderOrganizationAccess` 替换为 `RoleOrganizationAccess`；
- Proto 字段统一改为 `organization_accesses`；
- Principal 保留角色、权限、data scope 与组织访问项的对应关系；
- Biz 层按具体权限解析可读/可写组织集合；
- 首批接入订单、往来单位、财务账单的列表、详情和写操作；
- 角色管理页面改为通用“可访问组织 / 允许写入”；
- 更新 Ent、Proto、OpenAPI、Web 客户端与迁移生成物。

### 5.3 不包含范围

- 草稿 Context/Hook 重构、草稿键升级或迁移；
- 全局 Ent 拦截器、全局写 Hook、系统上下文豁免；
- 多集团、多租户、`tenant_id`、物理分库分表；
- 历史 API、历史角色范围或旧数据兼容；
- 所有业务页面的一次性竞态重写；
- 首批三个聚合之外的通用组织范围接入；
- 替换型组织白名单；
- 每个组织独立保存页签；
- 跨组织结算和内部对开单规则。

## 6. 功能要求

### R1：跨组织读取

1. 角色拥有目标订单查看权限且追加北京组织后，可在天津工作区查询北京订单；
2. 默认列表查询当前权限的全部可读组织；
3. 显式筛选北京时先校验北京位于可读集合；
4. 详情查询同时使用资源 ID 和可读组织范围；
5. 订单业务类型权限继续与组织范围求交集；
6. `writable=false` 时禁止对北京订单进行任何写操作。

### R2：组织切换生命周期

1. 选择当前组织时不请求；
2. dirty 表单只触发一次确认；
3. 取消时保持页面与页签；
4. 切换接口失败时保持旧工作区；
5. 成功后更新用户状态、replace 到工作台并重建 TagsView 与页面；
6. 切换期间禁止重复发起切换。

### R3：通用异步守卫

1. `useLatestAsync` 或等价 Hook 为每次执行生成 token；
2. 新请求开始时使旧 token 失效，并在可行时 abort 旧请求；
3. 组件卸载时使全部 token 失效；
4. Hook 只在 token 当前时调用页面提供的 apply 回调，统一执行 state、表单、缓存、
   跳转和消息等回填副作用；页面不自行重复判断 token；
5. mutation 仍必须使用 loading 或幂等约束阻止重复提交；
6. Hook 不吞掉当前请求的真实业务错误；过期请求只按统一 stale/abort 语义结束；
7. 不把写入成功与前端回填成功混为一谈。

### R4：草稿回归

1. 保持当前 `sessionStorage` 键格式；
2. 天津工作区只读查看北京订单不创建北京编辑草稿；
3. 真实切换到其他组织后，不显示原组织表单内容；
4. 切回原组织并重新打开表单时，现有草稿仍可恢复；
5. 不增加新草稿抽象或兼容分支。

### R5：权限组织范围解析

1. 只处理包含目标权限的启用角色；
2. 每个角色按其 `data_scope` 计算基础范围；
3. 合并该角色的显式组织访问项；
4. 读操作使用 readable 集合；
5. 写操作只接受基础可写范围及 `writable=true` 的追加组织；
6. 多个符合角色的结果取并集；
7. 停用组织不进入结果；
8. 无匹配角色时返回权限拒绝。

### R6：首批仓储接入

- 订单、往来单位、财务账单列表使用组织 ID 集合过滤；
- 详情和修改在数据库谓词中同时约束 ID 与组织集合；
- 账单继续遵守事务、锁与版本检查；
- Service 只做 DTO 转换，范围算法位于 Biz，Data 只构造谓词；
- 不注册全局 Ent 拦截器。

## 7. 验收标准

- [ ] **AC-1** 天津员工通过同一角色获得订单查看权限和北京只读范围后，可在天津工作区查看天津与北京订单，无需切换组织。
- [ ] **AC-2** 财务角色的北京范围不能被订单角色借用，权限与范围不会跨角色串联。
- [ ] **AC-3** 北京访问项 `writable=false` 时，列表和详情可读，创建、修改及状态流转返回 403。
- [ ] **AC-4** 组织切换取消不发请求，失败不清状态，成功才跳转工作台并重建页签与页面。
- [ ] **AC-5** 组织 A 的页面 state、选项和弹窗不会残留到组织 B。
- [ ] **AC-6** 同一组件连续搜索时只有最后一次结果可回填；组件或工作区卸载后，迟到查询和 mutation 不执行前端副作用。
- [ ] **AC-7** 首批改造组件不再重复实现等价的 sequence/mounted/reset 样板，但仍保留缓存组织分键和重复提交保护。
- [ ] **AC-8** 现有草稿键和调用方式保持不变；切换组织后草稿不串组织，切回后仍能恢复。
- [ ] **AC-9** 四种 `data_scope`、显式组织追加、停用组织和 read/write 差异都有测试。
- [ ] **AC-10** 订单、往来单位、财务账单的列表、详情和写入均显式应用解析后的组织范围。
- [ ] **AC-11** 不存在旧 API 别名、旧模型双写、全局 Ent 拦截器或草稿 v2 兼容代码。
- [ ] **AC-12** Proto、Ent、迁移、OpenAPI 和 Web 客户端生成物一致，不手改生成文件。
- [ ] **AC-13** 开发中运行定向检查，整个任务验收时执行一次风险匹配的完整门禁并记录结果。

## 8. 风险与延期项

- 通用异步守卫只在首批高风险组件落地，其他页面后续按触碰迁移；
- 没有全局 ORM 兜底，新增仓储仍需显式传入组织集合；
- abort 不能撤销服务端已执行的 mutation，写接口仍需服务端幂等和权限校验；
- 首批聚合外的业务域仍维持现有当前组织行为；
- 单集团与追加型组织范围不能覆盖未来 SaaS 或“只看外组织”需求。

当组织范围接入大量扩张、显式过滤开始频繁漏审或项目进入真实生产数据阶段时，再单独
评估全局 Ent 拦截器、系统上下文和审计框架。
