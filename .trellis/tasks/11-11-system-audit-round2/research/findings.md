## B1 / P1：主档聚合接口绕过结算规则独立读写权限

- 位置：`server/internal/service/partner_profile.go:142`；`server/internal/data/partner.go:758`；`server/internal/service/partner_convert.go:273`。
- 触发：用户只有主档 read/update 权限，没有 settlement_rule.update/create，仍可向主档聚合 API 提交 `roles[].settlementRule`，修改账期、规则启停或公司本币信用额度。例如将额度改为 0，`PartnerCreditExceeded` 不再判定超额。触发以直接 API 提交为准，前端独立规则读取可能先返回 403，不承诺仅通过正常页面即可完成。
- 同根读取：只有主档 read 也会通过 Get/List 的角色内嵌字段获得规则额度和账期；该角色总规则数恰好一条时完整投影，包含停用规则。Create/Import 同样透传内嵌规则写入。聚合写入只覆盖该角色现有规则数为零或一条的情形，多条规则时已有显式拒绝，不能表述为任意规则均可改写。
- 证据：Manifest 243–257 将上述权限分别定义；RPC/中间件仅校验外层主档权限，service 不检查嵌套动作，data 找到规则即更新或创建；没有权限裁剪响应。前端隐藏分节不能保护真实响应。
- 建议：按实际规则新建/更新动作校验独立权限，鉴权与写入保持原子；聚合响应按规则读权限裁剪。普通无内嵌规则的主档操作不增加额外要求。
- 独立复核：两个代理完整核对权限清单、中间件、Service→Biz→Data 及信用控制消费链，未发现授权例外。

## B2 / P2：切换默认开票抬头没有推进旧抬头版本

- 位置：`server/internal/data/partner_invoice_profile.go:51`、`:105`；版本比较 `:92`。
- 触发：甲打开默认 A(v1)；乙把 B 设为默认，A 被批量改成非默认但仍为 v1；甲只改 A 电话，原表单带 `isDefault:true, expectedVersion:1`，版本检查通过，又把默认切回 A。
- 后果：并发编辑没有冲突提示，后来明确选择的默认抬头被旧快照静默覆盖，影响后续新建发票的默认预选；不会据此改写已开票快照。
- 根因：批量 `SetIsDefault(false)` 未递增受影响行 Version；父档案行锁只能串行化，不能发现旧编辑基线。
- 建议：清除旧默认时同步递增其版本，覆盖“新建默认”和“编辑切默认”，旧表单保存返回版本冲突。
- 独立复核：两个代理核对创建、更新、版本检查与 UI 提交内容，一致确认。

## B3 / P2：取消已确认增提可能把提成净额变成负数

- 位置：`server/internal/data/finance_commission_adjustment.go:387`–`:395`；发放拒绝负额位于 `server/internal/biz/finance_commission_payment.go:59`。
- 触发：同一未发放、已确认父单及订单行原提成 100，确认手工增提 100，再确认手工冲减 150；确认冲减时余额 200 合法。随后使用正确版本及原因取消尚未执行的增提，剩余有效净额变为 100−150=−50。
- 后果：正常取消动作破坏确认时维持的非负净额，之后发放预览失败；原始提成金额不变，实际发放仍会锁内重算并拒绝负金额，不会直接付出负数。取消依赖的手工冲减可恢复余额。当前只校验冲减确认，未校验取消增提的反向影响。
- 建议：复用已有锁内订单行与父单有效余额计算，取消已确认增提前校验取消后均非负；不足则先撤销依赖冲减。
- 证据：前端正常提供取消动作，Service 无额外门禁；当前集成用例只覆盖冲减取消，不覆盖此操作序列。两个代理交叉核对确认，无上游兜底。

## B4 / P2：已结清历史账单耗尽对冲预览的 500 张上限

- 位置：`server/internal/data/finance_netting.go:189`–`:202`。
- 触发：同公司、同结算单位、同币种已有 500 张已完全结清但仍 CONFIRMED 的历史账单，再新增两张未结应收/应付；预览先查询所有 CONFIRMED 账单，达到 501 即报 TooManyBills，还没有计算未结余额。
- 后果：即使只有两张账单能参与对冲也无法预览；公开请求只有公司、单位和币种，用户不能继续按提示缩小范围。结论限于预览入口，不泛化为所有对冲创建途径均失效。
- 建议：在 LIMIT 及上限判定前复用 `billUnsettledPredicate()` 排除已结清账单，只限制真正可参与候选数。
- 证据：余额在 208 行后加载；现有上限用例直接构造 501 条，未覆盖已结清历史。两个代理交叉核对确认，既有上限约束针对参与账单，不能把已清历史算作候选。

## B5 / P2：空运 HAWB 首次签发后，同页改单缺少原因输入框

- 位置：`web/src/pages/orders/templates/air-template.tsx:163`；`web/src/pages/orders/detail.tsx:99`、`:808`；`web/src/pages/orders/order-kinds/air-export/form-adapter.ts:189`；`server/internal/data/air_order_sync.go:116`。
- 触发：打开尚为 DRAFT/CONFIRMED 的空运订单详情，将本票分单改为 RELEASED 并保存成功；留在同页再次修改分单内容或状态后保存。
- 根因：可编辑状态写入 `airHouseStatus`，原因框却读取表单元数据 `airExport.houseStatus`。首次初值被固定，保存后的后台 `loadData()` 没有通过 `resetTo` 推进表单内服务端状态基线，原因框仍隐藏。
- 后果：服务端已读到分单 RELEASED，拒绝空原因的内容/状态修改，提示「已签发分单修改请填写改单原因」，但页面没有输入入口；刷新或重进详情后才恢复。后端门禁有效，不能表述为无原因改单已落库。
- 相邻边界：首次签发允许无原因；单证内容/状态不变而只改普通订单字段，不要求原因。HAWB 号码本身另有禁止修改约束，不纳入本项可改单范围。
- 建议：成功保存后同步当前表单的服务端 HAWB 基线，并保护正在编辑的输入；不要只根据用户待提交的 `airHouseStatus` 显示原因框，否则已签发改回 DRAFT 会再次隐藏。保存失败不能推进基线。
- 独立复核：代理完整追踪表单注册、初值、保存刷新、提交映射及锁内改单校验，主代理复查核心链路一致。现有页面用例覆盖初始已签发，未覆盖首次签发后的同页连续操作；本轮未运行前端测试或浏览器复现。

## B6 / P2：并发切换拼箱与新增普通实际箱可破坏运输类型约束

- 位置：`server/internal/biz/order_usecase.go:284`；`server/internal/data/order_container.go:86`、`:99`；`server/internal/data/order_write_draft.go:182`；`server/api/order/v1/order_container.proto:66`。
- 范围：普通独占实际箱 `OrderContainer`；拼箱合法使用的跨订单共享箱不属于本问题。
- 前提：未审核锁定、ACTIVE、无普通实际箱的 FCL 订单；只切换 FCL→LCL，保持 MBL 身份及航程不变，其他参数有效。
- 交错一：切拼箱请求 A 在事务前 `HasContainers` 得到无箱后暂停；新增请求 B 检查 FCL，取得订单锁并新增箱、提交；A 再取得订单锁，因新增箱不推进父订单 Version，旧版本检查仍通过，保存 LCL，且没有锁内重查箱事实。
- 交错二：B 在事务前读到 FCL 并通过校验后暂停；A 确认无箱，取得订单锁并保存 LCL、提交；B 随后取得锁，只复查可编辑性而不重验 FCL，新增箱仍成功。
- 后果：两个合法请求都可能成功，最终 LCL 订单带有普通独占实际箱。写事务可以完全串行执行，错误仍成立，关键是事务前的旧判断没有在锁后重验。
- 已有防护及局限：双方确实共用订单行锁；统一可编辑门禁不检查运输类型；MBL 下游箱事实校验只在主单身份/航程变化的特定分支触发。正式迁移的外键、箱号唯一及货量检查不包含跨表 FCL 约束；新增接口也没有父订单版本参数。
- 建议：复用现有订单行锁，切为非 FCL 的仓储事务在锁后重查普通实际箱，新增箱在锁后用权威订单状态重验 FCL，并检查相邻更新入口。只修一侧或单独增加父版本都不足以覆盖两个交错。
- 独立复核：代理核对上游、锁内写入、MBL 分支、前端入口及正式迁移，主代理复查两种交错与版本行为一致。后续需正式迁移 PostgreSQL 双会话并发验证；本轮仅静态确认，未执行真实库复现。
