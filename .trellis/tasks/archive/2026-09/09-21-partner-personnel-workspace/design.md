# 技术设计

## 往来单位范围
在 biz.Principal 的统一权限组织范围解析中将 business.partner.* 的读写范围与真实会话工作台取交集，仍先校验动作授权。服务列表/导出与鉴权详情共用该结果，取消伙伴详情跨公司重定位。其他业务范围保持原规则。

## 人员边界
沿用 User + Membership + RoleGrant。候选返回人员标识、姓名及当前公司内的部门/团队展示信息，不返回登录账号；无部门时使用公司作为归属展示。同名不同 userId 保留为不同候选，同一 userId 多部门挂靠在服务端聚合。业务归属由服务端按伙伴/订单公司确定。现有组件已为单人选择，先核实用户所见入口后决定必要 UI 修改。数据库 organization_id 继续用于经营归属与提成快照，不能因界面简化删除。

## 契约与风险
人员候选须扩展 Proto 的部门/团队展示字段，并同步生成 Go 绑定、OpenAPI 和前端客户端；不涉及数据库 Schema 迁移。最大风险是共享权限范围误伤其他领域，须验证伙伴收窄、其他领域保留。

## 已有工作
任务建立前形成 server/internal/biz/auth.go 和 server/internal/server/auth.go 两文件未提交原型，进入 planning 后暂停实现；不能视为完成。

## 本期已知限制
同名且同部门的不同用户仍有相同展示文字，按不同 userId 保留候选；本期按批准方案不增加账号或手机号标识。人员旁公司下拉在当前源代码未检出，验收记录需明确源码与用户运行界面差异，不能声称删除了不存在的控件。
