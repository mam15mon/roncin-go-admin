# 海运出口共享主单基础

## Goal

建立海运出口共享 MBL、必填签发方与主单号、人工关联和航程一致性基础

## Requirements

- 本任务只实施父任务阶段 1；依赖父任务已确认的术语、MBL 格式、签发主体、共享规则和航程匹配，不得夹带完整主分单内容、箱货分配、拆票、版本/Switch 或共享费用。
- 当前 `Order` 继续表示操作票；仅对海运出口 `SE` 强制首次保存时存在一个当前有效 MBL 关联。
- 建立独立运输执行、共享 MBL 和操作票—MBL 当前/历史成员关系；MBL 不再通过 HBL 记录间接归组，也不把运输执行等同于单证。
- 新建 SE 订单必须提交真实主单签发主体 ID 与 MBL；MBL 输入实时转大写，最终必须满足 `^[A-Z0-9]+$`，任何其他字符明确报错。
- 主单签发主体必须是实际签发 MBL 的船公司或上游 NVOCC，不复用订舱代理文本，不根据号码前缀猜测。
- MBL 唯一范围为组织、签发主体和规范化 MBL；数据库唯一约束兜底。
- 命中已有 MBL 只返回候选摘要；用户明确确认关联后，服务端在同一事务中重验候选版本和航程，再创建当前成员关系。
- 起运港、卸货港、船名、航次为硬匹配；中转港双方有值时匹配；ETD/ETA 双方有值时匹配。最终目的地保留在操作票，允许不同。
- 一个活动 SE 操作票只能有一个当前 MBL；解除的旧关系保留历史，不允许普通接口删除历史。
- MBL 单票、未确认且无下游事实时允许带原因更正身份；共享后普通编辑禁止改号，阶段 1 只负责明确阻断并返回受影响成员，实际改配由阶段 4 实施。
- 新建/关联操作票、运输执行、MBL 和成员关系必须原子提交；使用预期版本、固定锁顺序和数据库约束处理并发。
- 当前没有历史业务数据；迁移执行前必须核对相关表为空，若非空则停止实施并返回父任务规划。
- 页面保持现有订单表单风格，在配舱信息直接展示必填“主单号”和“主单签发方/船公司”；命中候选时展示摘要与“关联此主单 / 返回修改”。

## Acceptance Criteria

- [ ] 空 MBL、空签发方、包含小写转换后仍有非法字符的 MBL 均被前后端拒绝；小写字母实时转大写。
- [ ] 新建不存在的 MBL 时，Order、运输执行、MBL 和当前成员关系在一个事务内全部成功或全部回滚。
- [ ] 同组织、同签发方、同规范化号码无法并发创建两张 MBL；不同签发方的同号码可以并存。
- [ ] 同一活动 SE 操作票无法拥有两个当前 MBL，数据库约束和领域错误同时覆盖该不变量。
- [ ] 命中已有 MBL 不自动关联；未经候选 ID/版本确认的创建请求失败且不产生订单或半成品关系。
- [ ] 用户确认且航程一致时关联成功；任一硬匹配字段或双方已有的中转港、ETD/ETA 冲突时完整回滚并返回具体字段值。
- [ ] 两张操作票共享 MBL/卸货港时可以保存不同最终目的地，关联不会覆盖本票最终目的地。
- [ ] 关联动作不会修改已有共享 MBL 或运输执行内容。
- [ ] 单票未确认 MBL 更正有版本检查、原因和审计；共享 MBL 普通改号被阻止并返回受影响成员。
- [ ] 订单列表、详情、费用等现有消费者改为读取当前共享 MBL 摘要，订单到费用/账单/核销/提成的既有链路测试不回退。
- [ ] Proto、Ent、OpenAPI、Web 客户端生成物来自源文件且重跑幂等；Go 测试/vet、前端测试/tsc/biome 和真实 PostgreSQL 约束/并发测试明确 PASS。
