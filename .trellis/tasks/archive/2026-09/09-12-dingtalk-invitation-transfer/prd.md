# 钉钉入职专属码、向上追溯与一键转派 PRD

## 1. 背景与核心痛点 (Background & Problems)

系统已完成钉钉基础扫码注册与多租户隔离，但面对实际复杂的企业扩招与分公司架构，存在三个根本性业务与架构痛点：

1. **分公司专属通用码缺失与窜公司风险**：
   - 现有邀请为单人一次性模型（强制填手机号且消费即停），无法生成面向团队扩招的「分公司专属入职二维码/链接」；
   - 员工使用无邀请码的公开扫码时需在前端自选分公司，一旦成都员工误选北京且北京管理员误批，将引发严重的跨分公司越权看数风险。
2. **分公司无管理员时通知死锁**：
   - 新成立分公司（如青岛分公司冷启动）、初创办事处或分公司管理员空缺期间，该组织内持审批权限的管理员数为 0；
   - 当前系统通知查询返回空集合，导致新员工申请进入死锁无人能批。
3. **误选误扫缺乏一键纠错（转派）**：
   - 若员工在大群误扫兄弟公司码或误选公司，当前管理员发现后只能点击“驳回”，新员工必须重新扫码并重新选；
   - 缺乏由管理员将申请平滑「一键转派」至正确分公司的高效纠错闭环。

---

## 2. 核心架构原则 (Architecture Principles)

1. **服务端凭证驱动，客户端零信任**：
   - 专属入职码通过 128-bit 随机不可枚举 Token 传递（`/login?invite=<token>`）；
   - 目标组织由服务端根据有效邀请凭证在底层解析并强行锁定，彻底屏蔽前端自选公司下拉框，客户端不可篡改或伪造目标组织；
2. **两类邀请模型严格解耦（kind 显式区分）**：
   - **定向邀请（TARGETED）**：单人一次性，手机号必填，扫码匹配后秒级自动激活，状态迁至 `CONSUMED`；
   - **通用邀请（GENERIC）**：多人多次扫码，手机号为空，状态永不 `CONSUMED`（仅 PENDING、EXPIRED、REVOKED），新员工扫码落库为 PENDING 待审批，不参与手机号自动匹配链；
3. **向上追溯精度兜底（通知兜底，非权限变更）**：
   - 目标分公司持权管理员为 0 时，沿 `parent_id` 逐级向上查找**第一个有候选人的祖先节点**；若中途均无候选人则落根组织（总部）；
   - 属于**通知路由兜底**，并非组织或权限层级变更：总部具备全局数据范围（`DATA_SCOPE_ALL`）的管理员依既有 RBAC 模型天然拥有对任何分公司的审批权限；
4. **一键转派（Transfer）原子切换**：
   - 转派仅作用于通道 B 的 `PENDING` 申请；转派后新组织的通知同样复用向上追溯兜底机制；
5. **企业白名单天然防护（回归确认）**：
   - 钉钉 OAuth 阶段已强制校验 `CorpID`（`ErrDingTalkOrganizationMismatch`），非本企业员工无法进入系统。

## 3. 详细功能需求 (Detailed Requirements)

### 3.1 分公司专属邀请管理（管理员端）

分公司管理员（或具备跨组织管理权限的总部管理员）在后台「成员管理」中发起邀请，权限统一受 `system.user.dingtalk_invitation.manage` 管辖：

1. **模式 A：分公司专属通用入职码 (`kind = GENERIC`)（主模式）**：
   - **适用场景**：日常团队扩招、部门群分发、线下展架扫码；
   - **配置字段**：
     - **目标分公司**：当前分公司管理员锁定本组织；总部超管可下拉选择任意分公司（支持为新分公司代发）；
     - **预设角色**（可选）：可预分配初始角色（如海运操作员），亦可留空至审批时指定；
     - **有效期限**：1~30 天（默认 7 天）；
   - **生成产物**：专属二维码图片（可复制/下载）与专属网页链接（`/login?invite=<token>`）；
   - **生命周期**：支持多人多次扫码；不填手机号；状态永不变为 `CONSUMED`，仅在到期后自然 `EXPIRED` 或被管理员手动 `REVOKED`。
2. **模式 B：定向手机号邀请 (`kind = TARGETED`)（保持并演进）**：
   - **适用场景**：关键岗位招聘、直接发在大群、快速免审入职；
   - **额外字段**：新员工 11 位规范化手机号；
   - **生命周期**：单人一次性；扫码匹配成功后自动激活入职，状态变更为 `CONSUMED`。

### 3.2 员工端扫码与防呆落地页

1. 员工扫描专属二维码或点击链接进入登录落地页；
2. **Token 安全与有效性验证**：
   - 服务端校验 Token：若不存在、已撤销或已过期，返回明确的提示（如*“邀请链接已失效或已过期，请联系主管重新获取”*）；
3. **专属欢迎落地页**：
   - 醒目大字展示：`【XX 分公司】入职申请，邀请人：XXX`；
   - 醒目警示：`若您属于其他分公司（如成都、深圳），请勿加入，请向所属分公司主管索取专属码`；
   - **彻底移除分公司自选下拉框**，强行绑定该邀请码对应的组织；
4. **OAuth 穿透**：
   - `invite` Token 随钉钉 OAuth 的 `state` 或会话 Cookie 穿透鉴权回调，在注册确认时由服务端直接兑现。

### 3.3 向上追溯通知路由（无管理员分公司代管）

1. 新员工提交通用邀请申请后，系统解析目标分公司；
2. 系统检索该组织内持 `system.user.dingtalk_invitation.manage` 权限的启用中管理员；
3. **首位祖先追溯算法 (First Ancestor Escalation)**：
   - 若候选人数 > 0：精确推送钉钉工作通知给该分公司的管理员（独立后台任务 + 明细三元组防坍缩）；
   - 若候选人数 == 0（新设分公司冷启动、微型办事处或人员空缺）：
     - 沿 `parent_id` 链向上查找**第一个有候选人的祖先节点**；若中途均无候选人，则兜底推送给根组织（总部）持权管理员；
     - 钉钉卡片醒目标注：`【XX 分公司新员工待审批（该组织暂无管理员，由总部代管审批）】`。

### 3.4 审批中心与一键转派（Transfer）

管理员（本分公司管理员或总部代管管理员）点击钉钉通知直接进入审批弹窗：

1. **同意 (Approve)**：指定分配系统角色，点击提交；单事务完成：启用 User + 建立目标分公司 Membership + 绑定角色 + 钉钉通知新员工；
2. **拒绝 (Reject)**：填写驳回理由（必填，<=200 字），钉钉通知新员工；
3. **一键转派 (Transfer)**：
   - 仅适用于通道 B 的 `PENDING` 注册申请；
   - 若北京管理员发现该申请人实际为成都招聘，点击「转派」，下拉选择「成都分公司」，填写转派原因（必填，<=200 字）；
   - 系统在事务中原子更新该申请记录的 `dingtalk_requested_organization_id = 成都分公司`；
   - 该申请即刻从北京管理员的待审批队列移出，进入成都分公司的待审批队列；
   - 系统向成都分公司管理员重新派发钉钉审批通知（若成都暂无管理员，同样自动执行向上追溯兜底）。

## 4. 权限与数据边界 (Access & Boundaries)

1. **唯一权限码真相源**：
   - 全链路（邀请创建/列表/撤销、审批列表、同意、拒绝、一键转派）统一由既有权限码 **`system.user.dingtalk_invitation.manage`** 判定；禁止新增未经授权的平行权限码；
2. **数据范围隔离**：
   - 分公司管理员仅能查看本分公司的邀请记录与待审批人员；
   - 总部具备 `DATA_SCOPE_ALL` 的管理员依既有权限模型天然具备跨分公司查看、代发邀请与代管审批/转派权限。

---

## 5. 验收标准 (Acceptance Criteria)

- [ ] **通用邀请 (GENERIC)**：成功生成无手机号的通用邀请码与链接，Token 为 128-bit 随机串；支持多名员工先后扫码申请，邀请状态不变为 CONSUMED；
- [ ] **定向邀请 (TARGETED)**：定向手机号邀请单人消费即变为 CONSUMED；GENERIC 行不参与手机号自动匹配链；
- [ ] **Token 安全与防伪造断言**：扫码落地页由服务端解析 Token 绑定组织，客户端请求中修改或篡改 `organization_id` 被服务端拒绝或忽略；过期/撤销 Token 呈现明确拒绝文案；
- [ ] **企业白名单（回归确认）**：非本企业钉钉扫码被 `ErrDingTalkOrganizationMismatch` 拦截；
- [ ] **向上追溯兜底精度**：目标分公司无管理员时，通知准确命中首个持权祖先组织（或总部），卡片标注代管提示；
- [ ] **一键转派原子性**：北京管理员将 PENDING 申请转派给成都，事务内原子更新目标组织，记录在原队列消失并在新队列呈现，新组织（含其追溯祖先）收到通知；
- [ ] **全量回归**：`go -C server test ./...`（含数据集成测试）全绿，前端 `tsc` 与 Biome 零报错。

---

## 6. 不在范围 (Out of Scope)

- 钉钉全量部门树双向镜像同步；
- 外部招聘管理系统（ATS）对接。
