# 技术设计：审批毛利预览

## 契约与分层

- 在 `server/api/order/v1/order_fee.proto` 增加只读的 `PreviewOrderFeeSupplementApproval` RPC，路径放在目标申请下，入参含订单 ID、申请 ID、`expected_version`，访问注解沿用审批接口的认证模式；实时审批资格在 biz 层按现有 grant 规则判定。
- 响应以十进制字符串给出本币、当前应收/应付/毛利/毛利率、补录成本、预计应付/毛利/毛利率及毛利变化。零应收时毛利率字段为空，由页面显示“不可计算”。服务层只做 DTO 转换，不查询 Ent。
- biz 用例先检查订单与申请归属、版本和 `PENDING` 状态、实时审批资格、固化锁依据；再复用现有审批的费用事实解析、汇率和金额计算。通过现有 `OrderFeeUsecase.List` 读取有效费用，使用 decimal 对 `baseCurrencyAmount` 求和，排除 `CANCELLED`；核对本币一致后计算预计值。
- data 层新增无写入的锁依据读取能力，复用现有证据计算函数，不改审批事务的 `ForUpdate` 流程。预览请求不新建写事务、不加新的版本字段或锁；预览与审批之间的竞态由审批事务原有二次校验兜底。

## 页面交互

- 列表的“通过”“驳回”收敛为“审核”。审核视图先呈现申请事实与毛利影响，再提供“确认通过”和“驳回”两个决定；驳回继续沿用现有必填原因的确认流程。预览加载中或失败时禁用“确认通过”，不让旧数值留在界面；若只是预览服务暂时失败且申请仍有效，驳回可按现有规则继续。该子任务在重提子任务完成后修改共享组件，保留新加入的重提动作。
- 审核视图按紧凑的金额对比展示“当前 → 预计”，突出本次成本与毛利率变化，并说明这是时点估算，审批提交时会重算。确认调用原审批接口，保留原 `expectedVersion`、错误处理和费用/申请表刷新。
- 不复用页面上可能滞后的汇总状态来计算预览；不复制提成冲减算法，不添加负毛利阻断。

## 生成与部署

- 依序运行 `make -C server api` 与 `pnpm run generate:web-client`，源 `.proto` 和所有必要生成物同组审阅、提交。
- 不变更 Ent Schema 或 SQL 迁移；旧客户端不需要保留兼容层。预览失败不影响既有审批 RPC，回滚时源契约与生成物同步回退。
