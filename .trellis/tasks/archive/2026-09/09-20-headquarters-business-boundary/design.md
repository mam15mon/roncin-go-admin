# 技术设计

## 统一边界
沿用组织模型及现有工作台会话。权限 Manifest 继续作为唯一真相源，增加显式的经营办理动作分类（覆盖动态订单权限）；不依据 `.create`、`system` 等前后缀猜测权限用途。混合查看、配置、办理的权限按端点动作进一步区分，必要时拆分并生成权限键，不能为禁业务误禁总部管理。

在 biz 统一表达工作台业务能力；`HasPermission`、`HasPermissionInScope`、`PermissionKeys` 及组织范围解析保持一致。总部有效权限不暴露纯经营写权限，保留角色原始授权用于切换后的重算。涉及混合权限时以统一动作策略和最小必要能力投影配合端点校验，避免前端复制另一套权限清单。

经营写范围 = 当前启用公司 ∩ 该动作原始授权范围；总部、部门、团队均不得作为经营写工作台。规则先于管理员特例。管理写范围继续按现有规则；读取保留原范围。

## 已确认的混合权限拆分

- `system.finance.commission.configure`：方案维护、员工分配与复制；`commission.manage` 专用于经营办理。
- `system.finance.bill.configure`：总部已计费费用编辑管控配置；`bill.update` 专用于经营账单修改。
- 原始角色权限保留；不把旧业务权限隐式映射到新配置权限。权限目录与管理员授权通过现有 migrate 同步流程更新。

## 接口与持久化
Service 只传递主体、操作和已解析范围；规则留在 biz。检查 `server/internal/server/auth.go` 的端点映射、所有 service 直接使用组织 ID 或 Principal.RoleGrants 的路径，防止只修组织范围 helper 而漏掉路径。仓储查询继续以目标 ID 与允许公司范围共同过滤，保留现有归属守卫和事务，不在本任务引入新锁或版本模型。

预览、候选、上传初始化和任务重试按真实副作用检查：业务办理专用入口与写入口同样限制；公共文件能力不得粗暴全禁，必须防止总部通过附件登记或可重试业务任务间接办理。后台自动化以既有公司归属运行，不把无交互主体一律视为总部。

已有业务链的公司一致性继续校验；不得信任客户端 organizationId，不以角色可读范围代替写范围。跨公司批量动作在写前拒绝，事务错误原样外传。

## 前端
`auth/me`、登录与切换响应使用一致有效能力。优先复用现有 permissions 字段；确需混合动作能力时先修改 Proto 再生成，不手改客户端。
`web/src/access.ts` 为页面唯一消费口，列表/详情/编辑路由/快捷动作/首页待办同步覆盖。总部保持现有只读统计与详情；不新建统计服务。
复用 `OrganizationSwitcher`、workspace key 和脏表单守卫；检查 React Query 及模块缓存生命周期，只补实际缺口。旧工作台请求不能在新工作台落入页面状态。

## 证据与风险
- `server/internal/service/organization_scope.go:12` 为通用范围 helper，但业务规则不能只置于传输层。
- `server/internal/biz/auth.go:268`、`:278`、`:297`、`:326` 是权限判定与输出的一致性检查点。
- `server/internal/service/settlement_bill.go:232` 当前按写范围解析费用归属，必须限制至当前公司。
- `web/src/components/OrganizationSwitcher.tsx` 已有轮转后状态更新与缓存清理；`web/src/app.tsx:148` 已按组织 key 重挂载。
- 经营归属规范明确保留的跨组织办理例外与新要求冲突，实施时同步修正文档及测试，不增加兼容分支。

## 数据、生成与回滚
预计不需要 Schema 变化；仅在检查发现必要结构调整时先完善设计，走正式 Ent/SQL 迁移。现有主数据 A/B/C 型及总部基线保持。
如权限/Proto 变化，执行对应生成并与源文件同组提交。数据库只做必要只读核验，不自动迁移总部旧数据。
按后端边界、前端消费分组提交；回滚以回退本任务提交为单位，不回滚其他任务或开发数据。
