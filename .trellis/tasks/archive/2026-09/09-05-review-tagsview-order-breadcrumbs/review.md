# TagsView 与订单面包屑联合审查报告

## 结论

联合审查最初发现的 P1、P2 和直接相关 P3 均已按用户要求修复，并通过独立检查与主会话复核；当前可以验收。

TagsView 的稳定页签、重定向归组、最新地址、动态标题、右键操作和键盘操作均符合要求；订单面包屑的层级、链接、加载态、空结果态和无效业务类型处理也符合要求。

问题不在面包屑显示本身，而在同一个订单页面实例从订单 A 切换到订单 B 时，部分页面级异步状态原先没有绑定订单 ID。以下记录保留初审证据；修复结果见文末“修复与复核结果”。

## 未修复发现

### P1：费用页可能以订单 B 的页面身份提交订单 A 的费用

涉及文件：

- `web/src/pages/orders/fees.tsx`
- `web/src/pages/orders/components/fees/OrderFeeTableTabs.tsx`
- `web/src/pages/finance/bills/components/BillCreationWorkbench.tsx`

`useOrderFeeOptions` 已经隔离订单主体、候选项和财务锁状态，但费用页下列状态仍由复用的父组件持有，没有绑定 `orderId`：

- 已选应收、应付费用 ID；
- 账单工作台开关及其费用 ID；
- 正在编辑的费用和各快捷新增弹窗；
- 应收、应付全部费用和汇总。

复现时序：

1. 在订单 A 的费用页选择费用并打开“生成账单”；
2. 不关闭工作台，直接在同一页面实例导航到订单 B；
3. 订单 B 加载完成后，工作台仍可能用订单 A 的费用 ID 重新出现；
4. 页面来源文字已经显示订单 B，但 `BillCreationWorkbench` 最终向预览和建账接口提交的仍是订单 A 的费用 ID。

账单工作台支持多订单费用，不能假定服务端会按照当前页面的订单 B 拒绝订单 A 的费用 ID。这会让业务人员误以为自己正在为 B 建账，实际处理的是 A，因此定为 P1。

此外，`OrderFeeTableTabs` 的应收、应付列表请求在响应后无请求序号或当前 `orderId` 校验。订单 A 的迟到响应仍可覆盖订单 B 的费用数组和汇总。

建议修复：订单 ID 改变时清空并关闭所有订单相关费用状态；账单工作台的费用 ID 显式绑定来源订单；列表响应仅在请求订单、当前订单和请求序号均匹配时写入；补充同一组件实例 A→B 切换和逆序响应测试。

### P2：详情页拆票、改配动作资格可能被订单 A 的迟到响应覆盖

涉及文件：`web/src/pages/orders/detail.tsx`。

`changeActions` 没有保存所属订单 ID，也没有请求序号保护。A→B 快速切换时，如果 B 先返回、A 后返回，A 的 `canSplit`、`canReassign` 和阻断原因会覆盖 B，导致 B 页面错误开放或禁用按钮。

服务端仍应执行最终业务校验，暂未发现直接绕过服务端规则的数据破坏路径，因此定为 P2。

建议修复：将动作数据保存为 `{ orderId, data }`，订单变化时立即清空；只有订单 ID 和请求序号都匹配时才接收响应；补充 A/B 逆序响应和 B 请求失败测试。

### P3：页面级跨订单场景测试覆盖不足

现有测试证明了订单主体 Hook、费用选项 Hook 和锁状态不会把 A 的主体数据暴露给 B，但没有覆盖仍然泄漏的父组件状态、费用列表迟到响应、已打开的账单工作台和 `changeActions` 竞态。

需要补充页面级路由参数切换测试，并保证在同一个 React 组件实例内从 A 改到 B；仅重新挂载页面无法复现本问题。

### P3：提交范围空白检查未通过

`web/src/pages/orders/components/OrderPageHeader.test.tsx` 第 161 行存在文件末尾多余空行。`git diff 9f2d6bd7^..HEAD --check` 会报告 `new blank line at EOF`，与原归档任务中“空白检查通过”的记录不一致。

### P3：历史任务记录中的定向测试命令实际会运行全量测试
