# 全业务类型订单锁定与解锁

## Goal

把现有仅限海运出口（SE）的订单业务锁扩展为统一能力，使系统支持的每种订单都能被明确
锁定和解锁。锁定后封存该订单的业务资料与订单费用，避免继续编辑；读取和后续合法财务
处理保持可用。

## Background

- `Order` 统一表已经为所有业务类型保存 `locked_at`、`locked_by`、`lock_generation` 和
  `version`，无需为各类型重复建立锁状态字段。
- 后端 `BusinessType` 当前定义 `SE`、`SI`、`AE`、`AI`、`LAND`、`RAIL` 六种订单类型。
- 现有锁定仓储、业务角色资格、审批候选和错误文案硬编码为 SE；订单权限目录和 HTTP
  鉴权映射只覆盖 SE、SI、AE、AI，其中只有 SE 登记了 `*.lock` 权限，LAND/RAIL 尚未纳入
  订单权限类型字典。
- 现有统一写门禁 `ensureOrderBusinessEditable` 已接入订单资料、状态、标签、里程碑、附件、
  人员、货物、箱、放货 POD、异常、订单费用和 SE 专属写入口，但函数会主动跳过非 SE 订单；
  非 SE 通用装运单证的独立增改、状态流转和删除入口尚未接入事务内门禁。
- 现有前端路由与详情模板只正式开放 SE；锁状态加载、失败关闭和锁定操作也按 SE 判断。
- SE 锁定时会原子形成 MBL/HBL 不可变版本；其他订单类型尚无等价的类型化单证版本模型。
- 已确认的解锁机制为：合格业务角色成员直接解锁、bootstrap 管理员紧急直接解锁、普通
  编辑人发起钉钉或签审批；订单解锁不绕过账单、发票、核销和提成等财务门禁。

## Requirements

### R1. 业务类型范围

- 锁定、锁状态、解锁和解锁历史必须支持 `SE`、`SI`、`AE`、`AI`、`LAND`、`RAIL`。
- 订单默认保持未锁定，不因迁移或业务类型而自动锁定。
- 未指定或非法业务类型不得进入锁定流程。

### R2. 统一锁状态与并发

- 继续复用 Order 上的唯一业务锁和代次，不按业务类型创建第二套锁表或状态机。
- 锁定和成功解锁都递增 Order version；只有新一轮锁定递增 `lock_generation`。
- 锁定、直接解锁、审批结果生效和并发请求必须保持现有幂等、悲观锁、乐观版本与审计语义。
- 所有阻断返回稳定 `ORDER_BUSINESS_LOCKED`，并包含订单编号、锁代次、锁定时间和锁定人。
- SE 锁定继续在同一事务中创建或复用 MBL/HBL 不可变版本，并把版本引用写入锁记录。
- SI、AE、AI、LAND、RAIL 锁定只封存 Order 及已存在的业务写入口，不为尚不存在的专属单证
  模型创建猜测性快照；这些类型的锁记录不携带 MBL/HBL 版本引用。
- 数据库必须用业务类型与可空单证引用的约束表达上述差异：SE 锁记录要求完整 MBL 版本引用，
  非 SE 锁记录要求这些 SE 专属引用为空，不能依赖应用层约定形成歧义记录。

### R3. 锁定后的统一写门禁

- 任一已锁订单都禁止修改会改变订单业务结果的数据，包括订单资料、状态流转、标签、里程碑、
  附件、人员、货物、箱、运输/放货资料、异常、订单费用以及对应类型的专属业务数据。
- 订单费用在锁定后只读；新增、修改、删除、取消和确认均不得绕过后端门禁。
- 门禁必须在 data 层事务锁内执行，前端禁用只作为交互提示。
- 查询和历史读取不受业务锁影响；后续财务结算是否可执行继续由财务权限与状态机决定。
- 解锁只恢复普通业务编辑能力，不能绕过已经进入账单、发票、核销或提成的财务事实。

### R4. 解锁流程

- 复用现有三路解锁、候选快照、钉钉 Outbox/Inbox、回调验签、本地幂等生效和过期请求处理。
- 六种业务类型共用现有一个钉钉 OA 审批模板和流程编码；模板使用通用“订单解锁审批”标题，
  审批表单字段与通知动态展示业务类型、订单号、申请人、原因和锁代次，不为各类型复制配置。
- 审批候选必须持有目标订单业务类型对应的独立锁定权限，不能让只负责一种业务类型的人员
  自动审批其他类型订单。
- 解锁申请、审批标题、通知、页面文案和审计不得继续硬编码“海运出口”。

### R5. 权限与前端

- 各业务类型使用独立锁定权限：`business.order.se.lock`、`business.order.si.lock`、
  `business.order.ae.lock`、`business.order.ai.lock`、`business.order.land.lock`、
  `business.order.rail.lock`。
- 锁定、角色直接解锁和钉钉审批候选资格均按目标订单的业务类型解析对应权限；任何一种
  `*.lock` 权限都不得自动授予其他业务类型的锁定或审批资格。
- 现有 `business.order.se.lock` 保持原权限含义和角色分配，不迁移成全局权限。
- LAND、RAIL 必须纳入现有订单权限业务类型字典，使路由层能够解析其 read、update 和 lock
  权限；这只登记现有通用权限，不开放尚不存在的订单页面或业务命令。
- 锁定和解锁按钮按后端返回的允许动作与统一权限真相展示，不在页面复制资格算法。
- 把锁状态、锁定/解锁动作和解锁历史改为不依赖 SE 的可复用前端能力；当前已开放的 SE
  列表/详情继续接入，未来其他类型页面可直接复用。
- 所有已经开放的订单详情和费用页在锁状态加载失败时写入口失败关闭；锁定后费用保持可读，
  仍可按财务规则选择已确认费用生成账单，但费用新增、编辑、确认、撤回、作废和标签维护禁用。
- 权限清单变更必须从后端 Manifest 生成前端权限键。

### R6. 兼容与数据安全

- 现有 SE 锁记录、不可变 MBL/HBL 版本、解锁请求和钉钉审批历史必须保持可读和可继续处理。
- 不自动锁定历史订单，不伪造锁定人、审批候选或历史快照，不静默修改旧代次。
- 不添加旧客户端静默兼容或自动回退分支；契约变化必须通过生成链更新服务端和前端客户端。

## Acceptance Criteria

- [ ] `SE`、`SI`、`AE`、`AI`、`LAND`、`RAIL` 的合法订单均能查询锁状态并完成一次锁定和
      解锁，订单版本/锁代次符合统一规则。
- [ ] 非 SE 锁定不再因业务类型硬编码返回参数错误；非法/未指定业务类型仍被明确拒绝。
- [ ] 每种订单在锁定后，至少用真实 PostgreSQL 回归证明订单资料与订单费用写入被
      `ORDER_BUSINESS_LOCKED` 原子阻断，查询仍可用且数据库无部分更新。
- [ ] 角色直接解锁、管理员紧急解锁和普通编辑人钉钉审批在所有类型下使用正确的权限、候选与
      通用文案；并发结果只形成一次有效解锁事实。
- [ ] 六种业务类型共用一个钉钉 OA 审批流程编码，审批实例携带并展示正确的业务类型与订单
      上下文；无需部署六套审批模板配置。
- [ ] 仅持有一种业务类型 `*.lock` 权限的角色不能锁定、直接解锁或审批其他业务类型订单；
      bootstrap 管理员紧急解锁仍按既有安全分支处理。
- [ ] 现有 SE 锁定仍原子创建/复用 MBL/HBL 不可变版本，历史行为无回归。
- [ ] SI、AE、AI、LAND、RAIL 锁定成功时不创建 MBL/HBL 或其他猜测性单证快照；锁记录保留
      Order version、代次、锁定人和时间，且 SE 专属引用为空。
- [ ] 现有 SE 活动审批在升级后仍能查询、回调、批准或拒绝，不因权限改造成为无法处理的孤儿。
- [ ] 已开放的订单详情在锁状态未加载成功或订单已锁定时失败关闭，锁定/解锁成功后刷新订单
      version 和允许动作。
- [ ] 已开放的订单费用页在锁状态加载失败或订单已锁定时保持只读；费用列表和合法的账单生成
      仍可使用，所有费用业务写按钮禁用且后端不可绕过。
- [ ] 前端公共锁组件不硬编码 `SE`、海运出口权限或海运文案；当前 SE 页面行为无回归，未新增
      SI、AE、AI、LAND、RAIL 的完整订单页面。
- [ ] Proto/OpenAPI、访问规则、权限键、Ent/Wire 和 Web Client 生成幂等；Go、前端、真实
      PostgreSQL、迁移和并发检查全部通过。

## Out of Scope

- 不在本任务中补齐尚未开放的 SI、AE、AI、LAND、RAIL 订单创建、列表、详情页面或完整
  领域模型；只提供它们未来可复用的锁能力。
- 不为不存在的海运进口、空运、陆运、铁路专属单证模型猜测并创建不可变版本表。
- 不改变账单、发票、核销、现金流或提成自身的状态机与权限。
- 不批量自动锁定现有订单，也不修改历史锁代次和审计事实。
