# 防止订单提成责任人因组织错配丢失

## Goal

落实「经营数据只能归属公司、责任人员业务归属一律等于客户档案所属公司」的 SaaS 化口径：总部只承担集团治理，部门/团队只承担组织架构展示与人员挂靠（Membership），二者都不作为客户、订单及提成等经营数据的归属主体，从结构上消除责任人员组织错配导致的提成丢失。

## Background

- 系统工作台只可能是总部或公司节点，部门/团队任何情况下不是工作台（`server/internal/biz/auth.go:67-69`）；但产品规则进一步收敛为：总部只做治理，经营数据只能归属 `kind=company` 的公司节点。
- 既有问题：客户责任人员保存时允许在客户组织子树内任选节点挂靠并要求该节点 Membership，导致提成快照按 `assignment.organization_id == order.organization_id` 严格匹配时可能零命中且静默成功（`server/internal/data/order_write.go:159-172`）。
- 本任务采用「收敛口径」而非「扩大匹配」解决：归属组织不再是一个可选维度，一律写入客户档案所属组织；部门只在组织树上承担人员管理职责。

## Confirmed Facts

- 订单创建时在同一事务内调用提成归属快照；查询严格要求 `assignment.organization_id == order.organization_id`，零条匹配直接成功返回，无告警（`server/internal/data/order_write.go:159-172`）。
- 草稿订单只有更换客户时才删除并重建提成归属；普通订单更新、客户档案责任人员后续变更都不会刷新已有订单快照（`server/internal/data/order_write.go:466-485`）。
- 提成候选员工与可计算订单均以 `order_commission_attributions` 为准；没有快照的员工不会进入候选（`server/internal/data/finance_commission.go:104-142,769-787`）。
- 后端保存客户责任人员时，当前校验「归属组织位于客户组织子树内 + 人员在该节点拥有启用 Membership」（`server/internal/data/partner.go:585-624`），需改为「归属组织 == 客户档案所属组织 + 人员在该公司子树内拥有启用 Membership」。
- `partners.organization_id` 是客户档案的数据归属边界，订单客户校验要求客户档案 `organization_id` 严格等于订单组织（`server/internal/data/order_sync.go:133-145`）；因此「归属组织 == 客户档案组织」即「归属组织 == 订单组织」，快照严格等值匹配无需改动。
- 人员 Membership 通常挂在部门/团队节点（工作台候选由成员关系向上取整为公司，`server/internal/biz/auth.go:1052-1066`）；归属组织收敛到公司后，成员关系校验必须按公司子树判定，不能要求人员持有公司直属 Membership。
- 前端责任人员表单为 9 个「人员 + 组织」成对槽位，组织下拉提供全量组织列表，允许任选（`web/src/pages/partners/partner-detail.tsx:196-205,384-402`；`web/src/pages/partners/components/BasicInfoSection.tsx`），是误选入口，需移除或改为只读展示。
- 领域模型对除「内部联系人」外的每个岗位最多一条责任分配，数据库唯一索引 `(partner_id, role, sort_order)`（`server/internal/biz/partner.go:538-567`；`server/internal/data/ent/schema/partner_assignment.go:34-38`）；归属组织收敛后，同一客户同岗位在多部门分别配人的旧诉求不再存在，该约束保持不变。
- `partner_assignment.organization_id` 的消费方仅三处：保存校验（`server/internal/data/partner.go:585-624`）、客户详情回显、提成快照匹配（`server/internal/data/order_write.go:159-172`），收敛口径影响面可控。
- 当前代码尚未执行“总部不经营”：总部工作台可以创建客户与订单；本地开发库曾有 3 份总部测试客户及其责任分配。用户已明确这些均为测试数据并授权删除，现已在单事务内删除，总部当前 `partners=0`、`orders=0`、`partner_assignments=0`。
- 总部仍需持有治理类数据；本地库现有总部归属包括 Membership、角色、会话、编号规则、审计日志和财务自定义配置，这些不属于本次已授权删除范围，也不能被“禁止经营数据”门禁误伤。

## Requirements

- 后端保存客户责任人员时，责任分配的归属组织一律写入客户档案所属公司（`kind=company`），不再接受总部、部门或团队节点；校验口径改为「人员在该公司子树内拥有启用 Membership + 启用用户」。
- 客户、订单及其派生经营数据不得归属总部；新建经营根数据时，目标归属组织必须为 `kind=company`。
- 前端客户档案责任人员表单移除逐槽位的组织选择（改为只读展示公司名或不再展示），杜绝误选入口；提交数据不再携带逐槽位组织。
- 提成快照匹配逻辑保持严格等值（`assignment.organization_id == order.organization_id`），不引入回退、猜测或跨组织兜底。
- 存量数据一次性收敛：以迁移方式把 `partner_assignment.organization_id` 重映射为其客户档案所属组织（幂等，可重复执行）。
- 订单创建与草稿更换客户重建快照时，客户档案缺少任一提成相关岗位（销售/操作/客服）责任人员的，阻止操作并返回可理解的中文错误，引导先到客户档案补全责任人（用户已确认：订单必须写上这些人员）。
- 责任人员候选接口改为按人员去重返回（同一人员多个部门成员关系只出现一条），不再让调用方感知候选的组织维度。
- 不自动改写既有订单的历史提成快照；快照仍只按现有重建时机（草稿更换客户等）刷新。
- 遵守现有 Membership、组织权限、事务与并发控制边界。

## Acceptance Criteria

- [x] 客户责任人员保存后，所有责任分配的 `organization_id` 一律由后端写入该客户档案的 `organization_id`；写契约不再携带逐条组织字段，客户端无法再指定归属组织。
- [x] 责任人员候选接口按人员去重：同一人员无论挂靠几个部门成员关系，候选中只出现一条。
- [x] 人员仅挂靠部门（公司子树内 Membership）时，可正常保存为该客户的责任人员；子树外或停用成员关系被拒绝。
- [x] 客户档案责任人员表单不再提供组织选择入口；已保存数据回显不再依赖逐槽位组织。
- [x] 客户档案按提成相关岗位配置责任人员后，创建订单能生成对应提成归属快照；缺少任一岗位时订单创建/草稿更换客户被阻止，返回中文错误并列出缺失岗位。
- [x] 迁移执行后，存量 `partner_assignment.organization_id` 全部等于其客户档案所属组织；重复执行无副作用。
- [x] 订单创建与受影响的更新路径具有针对性验证，覆盖正常匹配、未配置责任人员以及迁移幂等场景。
- [x] 不自动改写既有订单的历史提成快照。

## Out of Scope

- 通用佣金平台、复杂规则引擎或跨版本兼容层。
- 未经明确授权的数据库清空、重建或批量改写历史订单提成数据。
- 客户档案跨组织共享、总部经营、部门级提成归属等能力。
- 客户档案保存时强制要求提成岗位配齐（本期仅在开单环节拦截，档案保存口径不变）。

## 已确认的边界

- 本期总部不持有客户或订单。无显式目标公司的客户/订单创建入口在总部工作台拒绝；已有显式目标公司且具有相应跨组织权限的治理/财务路径继续生效，数据仍属于目标公司。本期不新增总部代公司创建客户/订单的接口。
