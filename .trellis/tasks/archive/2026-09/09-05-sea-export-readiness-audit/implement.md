# 海运出口业务完整度审计执行计划

## 1. 任务约束

- 全程只读审计产品代码；只允许在当前任务目录下新增或更新研究报告。
- 不把外部订舱、报关、SI、VGM、舱单等一键提交能力列为产品缺口。
- 不根据归档任务的完成状态直接判断能力已实现，必须核对当前代码、入口和测试。
- 不触碰或提交用户已有的 `clash-for-linux/`。

## 2. 执行步骤

### 2.1 建立现状证据清单

- 阅读海运出口领域规格、六阶段父任务和五个已归档阶段；确认第六阶段共享费用分摊的实际状态。
- 按 API → service → biz → data/Ent → web → tests 追踪海运出口的真实调用链。
- 把文件、测试和关键规则记录到 `research/current-capability-inventory.md`。

### 2.2 审计端到端业务场景

- 按 `design.md` 的八个能力维度建立矩阵。
- 对 FCL/DIRECT、FCL/HOUSE、多 HBL、LCL/HOUSE、共享 MBL、拆票/改配、锁后单证变更和费用到核销等代表性场景逐步核对。
- 对每一步记录输入事实、执行角色、状态门禁、下游结果、历史留痕和失败行为。
- 输出 `research/capability-matrix.md`，每项标记已具备、部分具备、缺失或不适用。

### 2.3 核验关键风险路径

- 核验组织隔离、按钮与后端权限、版本冲突、事务回滚、固定加锁顺序和数据库唯一约束。
- 核验订单锁是否实际阻断订单、MBL/HBL、箱货、费用、拆票、改配、改单、作废和 Switch 写入，同时不误伤合法查询和财务后续流程。
- 核验共享 MBL、多 HBL、箱货守恒及单证不可变版本是否有直接测试。
- 核验费用能否安全进入账单、发票、核销和提成，并确认共享费用分摊未实现时影响哪些真实场景。

### 2.4 运行非破坏性验证

- 先运行与海运出口领域直接相关的 Go 和前端测试；记录命令、结果和未覆盖风险。
- 根据风险运行 `go -C server test ./...`、`go -C server vet ./...`、`pnpm --dir web test`、`pnpm --dir web tsc`。
- PostgreSQL 集成测试仅在仓库既有隔离环境和明确测试连接存在时运行，不创建或接触生产数据。
- 本任务没有生成物源文件修改，因此不运行生成器；如检查发现生成漂移，只记录为缺口，不在审计任务中修复。

### 2.5 形成就绪度结论

- 根据证据将缺口分为 P0/P1/P2；每个 P0/P1 写明触发场景、影响角色、业务后果、当前人工替代方式和建议验收。
- 单独说明两个未归档规划任务与上线结论的关系，避免把整个父任务状态误判为未完成。
- 输出 `research/readiness-report.md`，给出正式上线、受限上线或内部试用结论，以及适用范围和前置条件。

### 2.6 独立检查

- 由检查角色复核矩阵中的“已具备”是否都有真实入口和后端证据，P0/P1 是否存在误判或遗漏。
- 复核外部提交能力均按“不适用”处理，没有被偷偷重新纳入范围。
- 复核报告没有把规划、注释或测试名称当作实现本身。

## 3. 验收映射

- PRD 能力矩阵要求：步骤 2.1、2.2。
- 单证、箱货、操作、财务、风控、权限与技术质量结论：步骤 2.2、2.3。
- 两个既有规划任务的影响：步骤 2.1、2.3、2.5。
- P0/P1 业务影响和建议验收：步骤 2.5。
- 明确回答是否可用及限制条件：步骤 2.5。
- 不修改业务代码并保护用户工作区：步骤 1、2.4、2.6。

## 4. 回滚与停止条件

- 若发现需要通过修改代码才能证明某项能力，停止该项验证并记录为证据不足，不在审计中修复。
- 若测试需要未知生产连接、真实外部账号或敏感凭据，跳过并记录限制。
- 任务输出仅位于当前任务目录，可通过删除相应研究文件回滚；不对数据库和产品代码执行回滚操作。
