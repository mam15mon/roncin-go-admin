# 海运出口业务完整度审计

## Goal

以中国国际货运代理企业的海运出口操作场景为基准，审计现有系统是否已经形成可供业务、操作、单证和财务协同使用的完整闭环，并给出可核验的上线就绪度、缺口与处理优先级。

## Background

- 用户希望从真实货代业务知识出发判断“海运出口是不是已经可以了”，不能只检查页面或接口是否存在。
- 仓库当前已经完成通用订单锁能力，但仍保留“海运出口运输与主分单领域模型”和“海运出口共享费用分摊”两个规划任务，需要判断它们是否构成上线阻断。
- 本任务首先执行只读审计并形成报告，不修改业务代码、不补功能、不调整数据库。

### 已确认的仓库事实

- 海运出口领域重构按六阶段规划；共享 MBL、DIRECT/HOUSE 主分单内容、箱货定量分配、拆票与整体改配、不可变单证版本及改单/作废/Switch/订单锁五个阶段已有归档任务，第六阶段共享费用分摊仍处于规划状态。
- 当前订单契约明确支持 FCL、LCL、BREAK_BULK 三种装载形态，并已经把 DIRECT/HOUSE 作为独立单证结构处理；因此审计默认覆盖这两个正交维度，而不是只看整箱直单。
- 当前代码已经存在 MBL/HBL 内容、箱货分配、改单/作废/Switch、拆票/改配、订单锁、异常、附件、节点、费用、账单、发票、核销与提成等领域入口，但仍需验证它们能否通过前端和权限形成端到端闭环。
- 既有海运出口规划明确没有实现真实 SI、VGM、舱单外部提交接口，也不伪造人工提交事实；用户已确认这些外部提交能力不属于本系统产品边界。

## Requirements

- 审计范围覆盖海运出口从接单至归档的业务链路：委托、订舱、配载、拖车或送仓、报关与查验、补料、提单确认、签单、开船、到付或预付信息、异常与完成归档。
- 审计核心数据模型及关联关系：订单、业务参与方、港口与航线、船名航次、柜型柜量、集装箱与封条、货物明细、MBL/HBL、主分单关系和操作节点。
- 审计财务闭环：应收应付费用、币种与汇率、费用确认、共享费用分摊、账单与结算、利润口径、锁定后限制及财务后续动作。
- 审计协作和风控：状态机、订单锁、费用编辑限制、并发版本、权限、审批、审计日志、历史快照、改单和作废边界。
- 同时核对后端契约、领域规则、持久化约束、前端可达入口和自动化测试，不能仅以代码文件或按钮存在作为“已具备”的证据。
- 每项能力按“已具备、部分具备、缺失、不适用”分类，并提供代码、测试、规格或任务文档证据；无法从仓库证明的能力不得评为已具备。
- 缺口按“P0 上线阻断、P1 重要业务缺口、P2 可后续增强”分级，并说明业务影响、当前替代方式和建议处理顺序。
- 最终给出明确结论：当前适合内部试用、受限上线或正式上线中的哪一级，以及成立所需前提。

## Constraints

- 审计只针对当前仓库已经实现和已经规划的能力，不凭空假设外部 ERP、订舱平台、报关系统或线下流程能够补足缺口。
- 外部系统集成不进入完成度评分，也不直接判定为系统内部实现缺陷。
- “业务可用”与“技术可运行”分开评分：构建和测试通过不能替代业务闭环完整性。
- 本阶段不产生产品代码变更；如需整改，审计结束后另行拆分实施任务并重新取得用户授权。

## Key Decisions

- 系统定位为货代内部业务、操作、单证和财务管理平台；员工可继续在船公司、海关、港区和舱单平台等外部渠道完成正式提交。
- 不要求系统通过 API、EDI 或平台连接一键提交订舱、报关、SI、VGM、AMS/ISF/ENS/ACI 等数据，也不要求自动接收外部受理回执。
- 缺少外部提交接口本身不记为缺口；但内部订单是否能记录相关责任人、截止时间、办理结果、凭证附件、操作节点和异常，仍属于本次审计范围。

## Out of Scope

- 船公司、海关、港区、堆场、单一窗口和目的国舱单系统的 API/EDI 对接能力。
- 对外部平台自身功能、稳定性、数据格式和合规认证进行评估。
- 在本任务中补齐发现的产品功能、重构领域模型或修改现有测试。

## Acceptance Criteria

- [x] 输出端到端海运出口能力矩阵，每项都有分类、证据和业务说明。
- [x] 输出单证、箱货、操作、财务、风控、权限与技术质量各维度结论。
- [x] 明确核验两个既有规划任务与当前上线就绪度的关系，避免重复提出已经实现的功能。
- [x] 所有 P0/P1 缺口都包含触发场景、影响角色、缺失环节和建议验收方式。
- [x] 最终结论能够直接回答“现在是否已经可以使用”，并写明适用业务范围与限制条件。
- [x] 审计过程不修改业务代码，工作区中用户已有的 `clash-for-linux/` 保持不变且不纳入任务。
