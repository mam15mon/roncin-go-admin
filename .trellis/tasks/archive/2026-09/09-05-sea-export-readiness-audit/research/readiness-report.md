# 海运出口上线就绪度报告

- 审计日期：2026-09-05
- 审计对象：当前仓库与当前分支实现
- 系统定位：货代内部业务、操作、单证和财务管理平台
- 最终等级：**受限上线 / 受控试运行**
- 不建议的表述：**“海运出口已经全场景正式可用”**

## 一、直接回答

你的海运出口**主体已经可以用了**，但现在适合的是限定范围、带操作规程的内部试运行或受限上线，还不适合无条件全量正式上线。

已经真正做成的部分不是简单页面，而是一套有后端强制规则和数据库事实的业务骨架：海运出口订单、FCL/LCL/BREAK_BULK、DIRECT/HOUSE、真实共享 MBL、多 HBL、完整提单内容、箱货守恒、拆票/改配、改单/作废/Switch、订单锁、订单费用、账单、发票、核销和提成。订单锁也确实会禁止海运出口订单资料、单证、箱货以及订单费用继续编辑。

当前不能称为“全量正式可用”，主要不是因为没有对接船公司或海关——这些外部提交已经明确不需要——而是内部还有以下断点：

1. 订单走到“已放单”后就可能结案，系统没有“实际开船/装船/操作完成”门禁。
2. 真实 Sea MBL/HBL 虽然有状态字段，却没有正常的确认、签发或放单命令，单证可能长期停在 DRAFT。
3. 多票共 MBL、共航程或共箱时，共享承运人成本还不能按规则、版本和币种守恒分摊。
4. 附件目前只是登记 object key，系统本身不能上传、预览或下载关键回执和文件。
5. 拆票/改配真实 PostgreSQL 完整测试存在一个并发错误分类失败；数据没有重复拆分，但失败用户得到的提示和恢复方式不正确。

## 二、上线等级判定

| 等级 | 当前是否满足 | 判断 |
| --- | --- | --- |
| 内部试用 | 满足 | 所有核心模块均有真实入口，可以开展业务演练和真实数据校验 |
| 受限上线 | **满足，但必须执行本文限制条件** | 把费用限定为单票直接归属，外部文件使用受控文件库，不以“已放单”自动代表运输完成，并限制结案权限后可以使用 |
| 正式全量上线 | 不满足 | 仍有无条件 P0、条件 P0 和一个失败的海运 PG 集成质量门 |

当前不是“系统不能用”，而是“系统可用范围必须写清”。若直接开放全部海运出口场景，页面上可表达共享 MBL 和复杂单证，但内部状态、凭证与共享成本不能全部形成一致、可审计的事实闭环。

## 三、建议立即允许的业务范围

在以下前提下，可以开始受控试运行：

- 订单类型：海运出口 SE。
- 装载形态：优先 FCL；LCL 可试运行；BREAK_BULK 建议先由熟悉业务的主管逐票复核。
- 单证结构：DIRECT 与 HOUSE 均可；HOUSE 支持一票多 HBL，FCL HOUSE 的箱货分配证据最强。
- 共享 MBL：可用于共享航程和主单内容；暂时不要宣称共享成本已经自动分摊。
- 单证变更：拆票、改配、改单、作废和 Switch 仅在系统返回允许、订单未锁且没有受保护下游财务事实时使用。
- 费用：仅录入已经明确归属某张操作票的应收应付；确认后可以进入账单、发票、核销和提成。
- 锁定：资料和费用确认完成后使用订单锁；解锁按业务角色、管理员紧急入口或钉钉审批执行。
- 外部办理：员工继续在船公司、海关、港区或其他平台完成正式提交；系统不承担外部提交。

## 四、受限上线的强制操作规程

如当前版本直接进入真实业务，至少落实以下临时控制：

1. **限制结案权限。** 只有主管可结案，并使用外部检查表确认实际开航/操作完成；在产品门禁修复前，不允许把 `DOCUMENT_RELEASED` 自动理解为运输完成。
2. **单证状态双重记录。** MBL/HBL 的真实确认、签发、放单结果暂时在受控文件库和操作记录中登记；不得因为工作实体仍是 DRAFT 就覆盖或丢弃已签发文件。
3. **关键文件使用受控文件库。** SI、VGM、报关放行、提单确认件、签单件和异常证据存放在已有的企业文件系统；订单仅登记经核对的 object key。没有受控文件库时，不应将当前附件模块用于正式证据管理。
4. **共享成本不得随意拆数。** 首期只允许单票直接归属费用；若确需多票共 MBL/共箱结算，必须由财务保存审批后的线下分摊表，并把结果逐票录入。系统内毛利只能解释为“人工分摊后结果”。
5. **从订单详情维护真实海运单证。** SE 用户不要使用列表页的旧“分单管理”抽屉；放单回单不要尝试关联旧 shipping document，直到入口迁移到真实 SeaHouseBill。
6. **删除箱/货物暂时绕开故障入口。** 当前前端删除漏传版本；若业务需要删除，应先修复，不能让用户反复点击或直接操作数据库。
7. **拆票并发只允许单人操作。** 同一票拆票期间避免多人同时执行；收到“分单数量不足”等与现场不符的错误时必须刷新重查，不可盲目重试。

## 五、P0：正式全量上线阻断

本报告的 P0 是“要宣布全量正式可用时必须解决，或必须通过书面方式排除相应业务范围”，不是生产事故等级。

### P0-1：结案缺少实际运输/操作完成门禁

| 项目 | 内容 |
| --- | --- |
| 触发场景 | 订单已流转到 `DOCUMENT_RELEASED`，没有活动异常，所有费用已 BILLED/CANCELLED，但货物尚未装船、实际开航或完成操作；用户点击结案 |
| 影响角色 | 操作、客服、单证、主管、财务 |
| 缺失环节 | 主状态止于“已放单”；结案事务不检查实际开航、装船、交付或操作完成节点，也不检查真实 MBL/HBL 状态 |
| 业务后果 | 系统产生“已结案”错误事实，后续异常、成本、收入、责任与绩效可能被过早冻结或遗漏 |
| 当前人工替代 | 结案权限仅给主管；使用外部完成清单，确认实际开航/业务完成后才结案 |
| 建议验收 | 新增“已开航/操作完成”或等价权威事实；结案在同一事务内重验该事实、活动异常和财务状态；并发状态变化必须回滚且返回稳定冲突；前端只展示服务端允许动作 |

### P0-2：真实 Sea MBL/HBL 没有正常确认、签发、放单流转

| 项目 | 内容 |
| --- | --- |
| 触发场景 | 单证人员完成补料和校对，需要把 HBL/MBL 标记为已确认、已签发或已放单 |
| 影响角色 | 单证、操作、客服、主管 |
| 缺失环节 | Schema 有 DRAFT/CONFIRMED/RELEASED，但 SeaDocument API、service、biz、data 没有正常 confirm/release 命令；新增固定写 DRAFT |
| 业务后果 | 订单主状态和真实单证实体语义分叉；不能可靠判断普通编辑是否应停止，也不能由历史证明何时确认或签发 |
| 当前人工替代 | 在受控文件库保存最终单证，在里程碑/备注记录日期；不得把 DRAFT 当作“未完成”的唯一依据 |
| 建议验收 | 提供有独立权限、expected version、订单锁和共享成员锁保护的确认/签发/放单命令；状态转换写不可变版本和审计；共享 MBL 对全部成员一致；订单主状态与单证状态规则明确并有真 PG 并发测试 |

### P0-3：共享海运费用分摊未实现（纳入共享结算时为 P0）

| 项目 | 内容 |
| --- | --- |
| 触发场景 | 一张 MBL、一个航次或一只箱包含多张操作票/HBL，承运人只给一笔总应付，需要计算各票成本和毛利 |
| 影响角色 | 操作、商务、财务、管理层 |
| 缺失环节 | OrderFee 只绑定 order_id；没有计费对象、共享原费用、分摊方法、分摊版本、调整历史和币种守恒 |
| 业务后果 | 成本可能重复或漏分，单票毛利缺乏可审计依据；拆票/改配后更容易出现历史被覆盖或重复进入财务 |
| 当前人工替代 | 财务在外部审批表中分摊后，逐票录入订单费用；限制系统内共享成本自动化声明 |
| 建议验收 | 完成现有 `09-02-sea-export-finance-allocation`：至少两种批准方法；按币种精确守恒；确认后调整只追加版本；拆票/改配/改单不重复账单、核销或提成；CNY 与外币真 PG 全链路通过 |

如果首发严格排除共享成本，只做单票费用直接归属，该项可暂降为 P1；但一旦开放多票共享 MBL 的真实财务结算，它立即恢复为 P0。

### P0-4：订单附件不是完整文件闭环（本系统承担唯一证据库时为 P0）

| 项目 | 内容 |
| --- | --- |
| 触发场景 | 用户要保存和查看 SI、VGM、报关放行、提单确认件、签发件或异常证明 |
| 影响角色 | 操作、单证、报关协作、客服、主管、审计 |
| 缺失环节 | 页面只手填 object key；没有上传准备/完成确认、对象存在性校验、授权下载/预览，也不能直接关联节点、异常或真实单证 |
| 业务后果 | 元数据可能指向不存在或无权读取的对象，系统不能独立证明关键文件真实存在 |
| 当前人工替代 | 使用已经经过权限和备份验收的企业文件库，由人员登记并复核 object key |
| 建议验收 | 上传准备与完成确认；校验大小/checksum/对象存在；受组织权限控制的预览/下载；审计；能关联操作节点、异常和 Sea MBL/HBL；失效对象有明确错误与修复路径 |

若企业已有受控文件库且明确它才是文件真相源，本项在当前系统可降为 P1；如果没有任何受控文件库，则是正式启用阻断。

## 六、P1：重要业务缺口

### P1-1：操作节点没有责任、计划与结果闭环

| 项目 | 内容 |
| --- | --- |
| 触发场景 | 订舱、拿 SO、截补料、VGM、截关、放行、进港、开航等节点需要指定责任人和截止时间 |
| 影响角色 | 操作、单证、客服、主管 |
| 缺失环节 | 里程碑只有自由类型、实际时间和备注；订单截止时间、人员角色与里程碑彼此不关联 |
| 业务后果 | 无法稳定识别逾期、责任人、办理结果和缺失证据，主要靠人记忆和群消息协作 |
| 当前人工替代 | 外部任务表/群提醒；在备注中写责任和结果 |
| 建议验收 | 受控节点定义；节点实例包含计划截止、负责人、状态、实际完成、结果、附件/异常引用；逾期查询与提醒；关键节点可被结案门禁消费 |

### P1-2：异常管理仍是标签，不是异常工单

| 项目 | 内容 |
| --- | --- |
| 触发场景 | 甩柜、退关、查验、破损、改单或客户原因异常需要跟踪原因、责任与解决方案 |
| 影响角色 | 操作、客服、商务、主管、财务 |
| 缺失环节 | 只有异常类型和 ACTIVE/RESOLVED，以及标记/解决人时间 |
| 业务后果 | 不能记录描述、级别、责任、处置、期限、损失、解决结论与证据，复盘价值有限 |
| 当前人工替代 | 在订单操作备注和外部文档中补充详情 |
| 建议验收 | 增加描述、严重级别、责任人/责任方、发现/要求解决时间、原因、措施、解决说明、损失与附件；活动异常继续阻止结案 |

### P1-3：SE 旧分单入口和放单回单仍指向废弃模型

| 项目 | 内容 |
| --- | --- |
| 触发场景 | 用户在 SE 列表点击“分单管理”，或打开放单回单并选择关联分单 |
| 影响角色 | 单证、操作、客服 |
| 缺失环节 | 前端调用 OrderShippingDocument；后端明确拒绝 SE；ReleasePod 外键也只验证旧分单，不能指向 SeaHouseBill |
| 业务后果 | 列表入口直接失败；多 HBL 放单/回单无法精确归属真实分单 |
| 当前人工替代 | 只从订单详情使用 SeaDocumentSection；ReleasePod 暂不关联旧 document_id，并在备注写明 HBL |
| 建议验收 | SE 列表入口跳转真实单证区或隐藏旧入口；ReleasePod 明确支持 MBL/HBL/DIRECT 归属；旧接口对非 SE 保持不变；前端与真 PG 关联测试通过 |

### P1-4：箱和货物删除前端漏传 expectedVersion

| 项目 | 内容 |
| --- | --- |
| 触发场景 | 用户从 ContainerDrawer 或 CargoItemDrawer 删除一条记录 |
| 影响角色 | 操作、单证 |
| 缺失环节 | API/service/biz/data 强制版本，但前端删除请求只传 orderId/id |
| 业务后果 | 正常删除请求会因版本为 0 被拒绝；用户看到操作失败，无法从界面完成合法删除 |
| 当前人工替代 | 不删除，改建正确记录并保留旧记录；不允许直接改数据库 |
| 建议验收 | 前端传 `record.version`；无版本时失败关闭；409 展示刷新提示；补两个组件请求断言和后端版本冲突测试 |

### P1-5：并发拆票失败方错误分类不稳定，完整 PG 质量门失败

| 项目 | 内容 |
| --- | --- |
| 触发场景 | 两个用户基于同一版本几乎同时执行拆票 |
| 影响角色 | 操作、主管 |
| 缺失环节 | 一个请求成功后，另一个可能在事务前 Preview 看到 HBL 已迁移，返回 400 `SEA_ORDER_SPLIT_INVALID_ARGUMENT`“分单数量不足”，没有进入锁内 expected version 检查返回 409 |
| 业务后果 | 数据安全目前仍是“仅一成功、无重复写”，但失败用户得到错误原因和恢复方式不正确；自动化完整质量门为 FAIL |
| 当前人工替代 | 同一票拆票只允许单人操作；任何异常错误先刷新整票上下文再判断 |
| 建议验收 | 权威版本检查优先于依赖可变状态的 Preview，或将并发状态漂移稳定映射为 VERSION_CONFLICT；完整 `TestSeaOrderSplitAndReassignment_PostgresIntegration -count=3` 通过，单独子测试也通过，并断言只有一个成功事实 |

### P1-6：运输执行只有单一主船名航次（业务包含中转/驳船时）

| 项目 | 内容 |
| --- | --- |
| 触发场景 | 一票有驳船、主船、中转或多段转运，需要分别记录计划/实际时间与异常 |
| 影响角色 | 操作、客服、主管 |
| 缺失环节 | SeaTransportExecution 只有单组 vessel_name、voyage_no、ETD、ETA；无 booking/SO 和多航段事实 |
| 业务后果 | 多段运输只能挤入自由文本，无法逐段追踪、改配或判定实际开航 |
| 当前人工替代 | 首期只做单航段航线；多段信息写在受控操作表和备注 |
| 建议验收 | 先由业务确认首发航线；若包含多航段，建立 booking/segment 与计划/实际状态、责任、历史；若只支持单航段，页面和上线说明明确限制 |

## 七、P2：后续增强与技术债

- 列表页部分子资源抽屉没有统一消费订单锁态；后端会安全拒绝，但用户提交后才看到错误。
- 部分存量订单子资源使用 `r.data.db` 做查询或事务前预检，没有统一走 `Data.client(ctx)`；核心写锁多仍在事务内，尚未证明数据错误，但偏离共享事务规范。
- 缺一套六种组合的全链路浏览器验收矩阵；现有证据以领域、Data 真 PG 和组件测试为主。
- bill form、release type、terms、milestone type 等部分值为自由文本，后续需要结合公司主数据口径治理。
- 测试数据库必须包含正式迁移所需的 `pg_trgm` 扩展/operator class；本次在未完整迁移的集成库首次跑 OrderLock 失败，换已迁移隔离 Schema 后通过。应把环境前置写进测试启动流程。

## 八、两个既有规划任务如何影响结论

### 1. 运输与主分单领域模型任务

`09-02-sea-export-transport-document-model` 仍处于 planning，不能简单理解为“海运运输和主分单都没做”。其五个已交付阶段已经真实形成共享 MBL、DIRECT/HOUSE、多 HBL、箱货分配、拆票/改配、单证版本/换单和订单锁。

它仍能提醒我们父目标没有全部完成：正常单证状态、多航段运输、共享费用以及最终组合验收仍有缺口。因此该父任务的状态本身不是 P0，当前代码中未落地的具体能力才参与本报告评级。

### 2. 共享费用分摊任务

`09-02-sea-export-finance-allocation` 是真实未实施任务，当前验收项全未完成，Schema 也没有相应计费对象和分摊记录。它与普通订单费用到财务链不同：后者已经可用，前者专门解决多票共享成本。

结论是：单票直接费用可以上线；多票共享成本自动、守恒、可审计分摊不可以上线。
