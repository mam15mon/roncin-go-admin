# 海运出口上线就绪度报告

- 审计日期：2026-09-05
- 审计对象：当前仓库与当前分支实现
- 系统定位：货代内部业务、操作、单证和财务管理平台
- 流程口径：所有步骤由人员判断完成后，在 UI 点击对应流程按钮确认
- 最终等级：**在批准的简单人工流程和明确边界内，可以正式使用**
- 不代表：外部事实自动验证、共享费用自动分摊、系统内完整文件管理或全部组合质量门全绿

## 一、直接回答

按照用户最终确认的业务方式，海运出口已经可以正式使用。

当前系统不是自动化船务平台。员工在外部渠道完成实际工作后，由有权限人员判断步骤是否完成，并在 UI 点击“已订舱”“已配舱”“已安排拖车”“已截单”“已安排报关”“已放单”等流程按钮。订单级状态是系统内正式业务事实；“已放单”是批准的流程终点，之后只要没有活动异常、没有未处理费用，就可以人工结案。

因此，实际开航、到港、交付或操作完成状态，每张 Sea MBL/HBL 独立确认/签发/放单，复杂节点任务、SLA、自动提醒、完整异常工单，共享费用自动分摊，系统内完整文件上传/预览/下载，以及外部提交与自动回执，都不是本次正式使用的前置条件。

这次重新评级不是把缺失能力描述成已经实现，而是明确它们不属于当前产品范围。系统只对人工确认、人工录入及其后的内部数据规则负责。

## 二、批准的正式使用边界

- 所有流程步骤由人员在 UI 人工确认；系统不从外部平台自动验证结果。
- “已放单”是主流程终点；已放单或已终止、没有活动异常、费用均已进入 BILLED/CANCELLED 后，可以人工结案。
- DIRECT 与 HOUSE 均可使用；HOUSE 支持一票多 HBL，多张订单可以共享一张 MBL。
- 当前不按每张 MBL/HBL 跟踪确认、签发、放单状态；Schema 中未启用的 DRAFT/CONFIRMED/RELEASED 不应在 UI 上被解释成与订单流程冲突的业务结论。
- 单票直接费用及人员线下分摊后逐票录入的费用，可以进入账单、发票、现金流、核销和提成链路。
- 系统不保存共享成本的分摊依据、分摊版本，也不自动校验跨票守恒。
- 关键业务文件保存在现有受控外部文件库；订单附件只登记 object key 和元数据，不能声称系统已完成文件上传、预览或下载。
- 订舱、报关、SI、VGM、舱单等继续在外部渠道办理；系统不承担外部提交或自动回执。

## 三、已经具备的核心能力

现有代码、数据库约束、前端入口与测试证据能够支持：

- 海运出口 SE 订单新建、编辑、人工状态流转、终止、结案和反结案；
- FCL、LCL、BREAK_BULK；
- DIRECT、HOUSE、共享 MBL 和一票多 HBL；
- 主分单内容、签发主体和号码唯一性；
- 实际箱、封条、货物明细及 HOUSE 箱货分配；
- FCL 件数、重量、体积三轴守恒，以及非 FCL 无虚假箱分配；
- 拆票、整体改配、不可变单证版本、改单、作废和 Switch B/L；
- 应收/应付费用、币种、汇率、账单、发票、现金流、核销和提成；
- 海运出口订单锁定/解锁，以及锁定后禁止修改订单资料、单证、箱货和订单费用；
- 组织隔离、操作权限、乐观版本、悲观锁、固定锁序、业务审计和不可变历史。

FCL + HOUSE 的自动化证据最强；LCL 与 BREAK_BULK 尚无覆盖六种“装载形态 × 单证结构”的统一浏览器全链路 E2E。该证据差异不改变批准边界内的正式使用结论，但首次开展低频组合时仍建议由熟悉业务的人员复核。

## 四、仍然存在的真实软件问题

业务简化不能消除以下四项 P1。它们不推翻主体正式使用结论，但启用对应入口前必须修复或执行明确规避。

### P1-1：SE 列表仍打开废弃的旧分单入口

- 触发场景：单证、操作或客服人员从 SE 订单列表点击“分单管理”。
- 影响角色：单证、操作、客服。
- 原因：前端打开旧 `OrderShippingDocument` 抽屉，后端明确拒绝 SE 使用旧模型。
- 影响：入口会失败，无法维护真实 SeaHouseBill。
- 当前规避：SE 只从订单详情的 `SeaDocumentSection` 维护 MBL/HBL。
- 验收：SE 隐藏旧入口或跳转真实海运单证区；非 SE 原入口不受影响；补前端入口测试。

### P1-2：ReleasePod 仍引用旧 HBL

- 触发场景：单证、操作或客服人员在 SE 放单/回单记录中选择关联 HBL。
- 影响角色：单证、操作、客服。
- 原因：面板仍查询旧 `OrderShippingDocument`，`shipping_document_id` 不能指向真实 `SeaHouseBill`。
- 影响：多 HBL 场景不能把放单/回单精确关联到真实分单。
- 当前规避：SE 不关联旧 `document_id`；需要时在备注中人工标明 HBL 号。
- 验收：ReleasePod 支持真实 MBL/HBL，或在 SE 隐藏该入口；补前端和真实 PostgreSQL 关联测试。

### P1-3：箱和货物删除漏传 `expectedVersion`

- 触发场景：操作或单证人员从箱、货物抽屉删除一条合法记录。
- 影响角色：操作、单证。
- 原因：后端要求非零版本，前端删除请求只传 orderId/id。
- 影响：合法删除也会被拒绝。
- 当前规避：不使用这两个删除入口，不直接修改数据库。
- 验收：前端传 `record.version`；无版本时失败关闭；409 明确提示刷新；补两个组件请求断言。

### P1-4：并发拆票失败方错误语义不稳定

- 触发场景：两名操作人员基于同一订单版本几乎同时执行拆票。
- 影响角色：操作、主管。
- 结果：两个用户基于同一版本同时拆票时仍只有一个成功，没有双成功或重复写入；失败方有时返回 400“分单数量不足”，而不是约定的 409 版本冲突。
- 影响：数据安全没有失守，但错误原因和恢复方式不准确；完整真实 PostgreSQL 父测试失败。
- 当前规避：同一张订单只允许一人拆票；异常错误出现后先刷新整票上下文，不盲目重试。
- 验收：版本检查优先于可变状态预检，或稳定映射为 VERSION_CONFLICT；完整父测试 `-count=3` 和单独子测试均通过。

## 五、P0 与后续增强结论

在用户批准的当前边界内，**没有因缺少复杂货代 ERP 能力而成立的 P0**。

“已放单后可以人工结案”、缺少逐张 MBL/HBL 状态、没有复杂节点/异常工单、没有自动分摊、附件不承担唯一文件库职责，均是已经确认的产品选择，不再列为 P0 或 P1。

实际开航、逐张单证状态、复杂节点、完整异常工单、共享费用自动分摊、系统内完整文件库、多航段和统一六组合浏览器 E2E 都可按未来需要增强。这些能力当前并未实现或证据不完整，报告不会将其美化为现有能力。

## 六、正式使用时的操作规则

1. 只有实际完成步骤后，人员才点击对应 UI 流程按钮；系统不替人员核验外部事实。
2. “已放单”后，由人员确认活动异常已解决、订单费用已处理，再执行结案。
3. 共享成本在线下计算并保留公司要求的依据，结果逐票录入；系统内毛利解释为“人工分摊后录入结果”。
4. 关键文件继续保存在受控外部文件库；订单只登记经核对的引用。
5. SE 只从订单详情维护 MBL/HBL，不使用列表旧“分单管理”。
6. ReleasePod 未迁移前不关联 SE 的旧 HBL；需要时在备注写明真实 HBL。
7. 箱和货物删除修复前不使用相应按钮，也不直接改数据库。
8. 同一票同一时间只允许一人拆票；异常提示出现后先刷新重查。
9. 资料和费用确认完成后使用订单锁；解锁按现有角色、管理员紧急入口或钉钉审批执行。

## 八、两个既有规划任务的影响

`09-02-sea-export-transport-document-model` 虽仍处于 planning，但共享 MBL、DIRECT/HOUSE、多 HBL、箱货分配、拆票/改配、单证版本/换单和订单锁已经真实落入代码。父规划中尚未落地的多航段与逐张单证状态不属于当前批准范围，不阻断正式使用。

`09-02-sea-export-finance-allocation` 确实尚未实施，当前 Schema 和 API 没有共享计费对象、分摊方法、版本或跨票守恒记录。用户已批准线下人工计算后逐票录入，所以它是自动化增强，不是当前上线阻断；系统只能证明录入后的订单费用能够进入财务链。

## 九、建议处理顺序

1. 修复箱/货物删除漏传版本，以及并发拆票错误语义，恢复对应操作和完整 PostgreSQL 质量门。
2. 迁移或隐藏 SE 列表旧分单入口，并把 ReleasePod 迁移到真实 MBL/HBL 或在 SE 禁用。
3. 保持人工流程、线下分摊和外部文件库的操作说明与权限配置一致。
4. 等业务明确提出需要后，再规划复杂节点、逐张单证状态、自动费用分摊、系统内文件库或多航段。

## 十、最终结论

> **在“人员判断完成后点击 UI 流程按钮、已放单为流程终点、共享费用线下计算后逐票录入、关键文件由外部受控文件库保存”的批准边界内，海运出口可以正式使用。**

这个结论不覆盖四个已证实的故障入口，也不等于系统具备外部自动提交、外部事实校验、自动共享费用分摊或完整文件管理。未来扩大业务边界时应重新审计。
