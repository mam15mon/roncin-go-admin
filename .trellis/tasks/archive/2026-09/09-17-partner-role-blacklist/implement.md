# 执行计划

## 实施顺序

1. 读取开发规范和相关原文，核对全部旧接口调用及角色变更/导入路径，不先写测试。
2. 修改 Proto、Biz 和 Service 角色级黑名单契约；Data 复用档案事务锁修改指定角色，推广角色防绕过规则。
3. 为订单创建/草稿换入增加角色黑名单校验，按主键固定锁序，保持原关联允许与财务不变。
4. 生成 make -C server api 与 pnpm run generate:web-client，更新前端列表弹窗、状态展示和审计展示。
5. 实现后更新/补充回归测试，运行最小相关检查；确认源文件与生成物一致。
6. 最终跨层审查、风险匹配完整门禁、更新规范、提交、归档。

## 验证场景

- 三角色独立加入/解除、散客、缺角色、空原因/超长原因、权限与公司范围拒绝。
- 已拉黑角色移除/重新添加不能解除状态，导入不得清除既有黑名单。
- 创建拒绝各字段的黑名单角色；草稿换入拒绝、原关联保留允许、可选字段清空允许；失败事务回滚。
- 并发拉黑与开单由档案锁确定先后；多档案固定排序不反转锁序。
- 历史费用、账单、收付款、核销路径无新拦截。
- 前端角色切换状态正确，不连带其他角色；审计正确显示目标角色与原因。

## 命令

先 go -C server test ./internal/biz ./internal/service ./internal/data 与修改文件 Biome/定向 Vitest，后按风险运行 go test/vet 全仓、前端 tsc 和一次完整 check:web。PostgreSQL 并发验证使用专用集成数据库，不借用开发库清空。

## 开始前门禁

PRD、design、implement 及 implement/check 上下文清单已完成。最终规划摘要交付后，等待用户基于该摘要明确批准实施；批准前不执行 `task.py start`、不派发实施代理、不修改业务代码。

批准后由主代理启动任务并协调实施，主代理负责方案取舍、真实差异审查、最终验证及提交。实施代理必须从当前任务路径与 `implement.jsonl` 的规范上下文开始，只实现本期范围。
