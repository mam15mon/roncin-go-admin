# 简化海运出口主分单模型

## Goal

在保留“一次订舱可有多个 HBL、多张订单偶尔共用一张 MBL”的真实能力前提下，把 HOUSE
订单模型收敛为“一张订单对应一张当前 HBL”，DIRECT 订单不创建 HBL。将 MBL 单证身份与
实际运输航次解耦，支持部分甩柜/漏装的单票分叉；箱货分配只服务于少量一箱跨多个 HBL 的
拼货例外；费用始终按订单独立结算。
同时保留公司自行制作、打印、签发 HBL 所需的正式版本、改单、作废与追溯能力，删除业务
实际不使用的 Switch B/L 专用模型。

## Background

### 已确认的业务事实

- 一张 HOUSE 系统订单代表一张当前 HBL；DIRECT 订单没有 HBL。一次订舱可能包含多个 HBL，
  因此也可能对应多张 HOUSE 订单。
- 业务人员可以通过相同的客户业务号、MBL 号或 Booking No. 聚合同一批次的多张订单；三者
  都是有效的查找入口。客户业务号与 Booking No. 只承担查询/展示，不产生跨订单联动；相同
  MBL 则来自真实 MBL 关系。当前不为此新增 Booking 聚合实体。
- 多张订单偶尔会形成“一主几分”，共用同一张 MBL；正常情况下共用船公司和船名航次，
  但甩柜、漏装时，可能
  只有其中一张订单改船公司、船名航次或港口。系统必须允许业务人员把异常订单独立调整，
  且修改不得传播到其他正常订单。
- 一张订单不允许有多张 HBL。需要把一票分成两张 HBL 时，业务会拆成两张订单，并在原
  分单号后追加小写 `a`、`b` 作为区分。
- HBL 通常由公司制作、打印并签发；同行货物也可能由同行自行签发并提供提单号与文件。
  因此 HBL 不是仅供查询的号码，必须同时支持本公司签发与外部同行签发两种来源。
- 存在 DIRECT 直单业务：公司不签发 HBL，直接把船公司或船代提供的主单交给客户。
- 创建订单时通常已经确定 HOUSE 或 DIRECT，因此新建 SE 订单必须显式选择单证模式；目标
  模型不保留 `UNDETERMINED`。
- HOUSE 订单创建时已经取得并确认 HBL 号；单证模式与 HBL 号必须随建单请求一次提交，
  不存在先创建 HOUSE 订单、以后再补建 HBL 的正常路径。
- 大多数集装箱只装一张订单/HBL 的货；少量客户自行拼货业务会把不同收货人的多个 HBL
  装入同一物理箱，因此跨 HBL 箱货分配是真实例外，但不应成为所有订单的必经流程。
- 换配和 MBL/HBL 更改经常发生；拆票、提单作废及一般意义上的更换提单偶尔发生。系统必须
  保留可靠的改配、版本和追溯能力，不能按低频功能一概删除。
- 业务不做真正的 Switch B/L（货物与航次基本不变、为贸易关系签发第二套不同贸易主体的
  提单）；换船公司、换航次或换提单号均属于普通改单/换配。
- 每张订单独立出账单；HOUSE 订单的一张当前 HBL 对应该订单账单，DIRECT 订单仍按订单出账，
  财务不做共享 MBL 费用分摊。
- 甩柜/漏装后既可能沿用原 MBL 号只更换航次，也可能改配其他船公司并取得新 MBL 号：
  更换 MBL 号一定伴随 ShippingLine 变化；ShippingLine 不变、只换航次时可能沿用原 MBL 号。
- 所有改单、换配、HOUSE/DIRECT 切换的真实授权来自客户提出后，船代反馈船司/承运方同意；
  ETD、实际离港和内部流程状态都不能代替外部确认。承运方不同意时，只修改内部系统没有业务
  意义；承运方同意时，系统不应再用时间或状态硬性阻断。
- 外部确认采用轻量留痕：正式变更必须记录确认方、确认时间和简短说明，邮件、聊天截图或
  船代回函作为可选附件；不为此建设内部审批流。

### 仓库现状证据

- `SeaMasterBill` 与 `SeaMasterBillOrderLink` 已支持一张共享 MBL 关联多张订单。
- `SeaMasterBill.transport_execution_id` 当前强制一张 MBL 只对应一个实际航次；这无法表达
  “同一 MBL 号下仅一张订单甩柜并改到后续航次、其他订单仍走原航次”的真实情况。
- `SeaHouseBill` 当前允许同一订单关联多行；`order_id` 只有普通索引，没有唯一约束。
- `SeaMasterBillOrderLink.document_structure` 当前维护 `UNDETERMINED | DIRECT | HOUSE` 三态，
  并通过 HBL 数量驱动转换。
- `SeaCargoAllocation` 当前带 `order_id`，而 `OrderContainer` 也强制归属单个订单；虽然能在
  一订单多 HBL 内分配，却不能正确表达真实的“一只物理箱跨多张订单/HBL”。
- 当前 API 和前端提供添加/删除多张 HBL、最后一张 HBL 删除确认、独立箱货分配抽屉以及
  多 HBL 摘要。
- HBL 已具备不可变版本、改单、作废、Switch、锁定快照和放货记录关联；版本、改单、作废、
  快照与放货关联需要按“订单唯一 HBL”重构，Switch 专用能力应完整删除。
- 当前本地开发库有 0 张 SE Order、0 张 MBL、0 条 Link、0 张 HBL、0 条箱货分配、0 条
  主分单版本及拆票/改配事件，因此可以直接迁移目标模型，不需要兼容或猜测既有 SE 数据。

## Requirements

### FR-1：MBL 单证身份与实际运输航次解耦

- 一张 MBL 可以关联多张订单；一张活动订单最多关联一张当前 MBL。
- 订单应保存可搜索的 Booking No.；订单列表和详情关联区支持按客户业务号、Booking No. 或
  当前 MBL 号找到同批订单。相同 MBL 号通过真实 MBL 关系聚合；客户业务号和 Booking No.
  只是文本查询键，即使相同也不得自动联动修改任何业务字段。
- 客户业务号允许同一客户的多张订单重复使用，不应以重复警告暗示录入错误；详情关联按
  “组织 + 客户 + 客户业务号”匹配，Booking No. 按“组织 + Booking No.”匹配，避免不同客户
  恰好使用相同客户内部编号时被错误归组。
- 一张实际运输执行可以承载多张订单；正常关联订单从同一 TransportExecution 读取
  ShippingLine、船名航次及共同港口日期，修改一次后仍属于该执行的订单读取同一结果。
- MBL 表达单证身份，TransportExecution 表达实际船司、航次和港口日期。一个 MBL 允许关联
  多个实际运输执行，每张订单与 MBL 的活动关系必须同时指明该票实际所属的运输执行。
- 甩柜、漏装等只影响单张订单的异常不得通过修改共享字段处理。业务人员必须显式执行“独立
  调整/改配”，将受影响订单移动到新的或已有的 TransportExecution；原执行中的其他订单
  保持不变。禁止在订单上保存隐式船名航次覆盖字段。
- ShippingLine 不变而仅换航次时，订单可以沿用原 MBL 并切换 TransportExecution；更换
  ShippingLine 时必须同时选择/创建新的 MBL，禁止只改船公司而沿用原 MBL 单证身份。
- MBL 与 TransportExecution 分别使用版本校验、组织隔离和操作日志；修改共享航次不得错误
  增加未受影响订单或 MBL 的版本。

### FR-2：HOUSE 与 DIRECT 单证模式

- 订单单证模式只保留 `HOUSE | DIRECT`：HOUSE 表示存在唯一当前 HBL（可由本公司或同行
  签发）；DIRECT 表示公司不签发 HBL，直接向客户交付 MBL。
- 创建 SE 订单时单证模式必填，不得依靠是否已填写 HBL 号推断模式，也不提供
  `UNDETERMINED` 默认值。
- HOUSE 模式下一张订单必须且只能拥有一张当前 HBL；DIRECT 模式不得拥有当前 HBL。数据库以
  `order_id` 的条件唯一约束兜底，服务端不得提供添加第二张当前 HBL 的入口。因历史改单、作废
  或 HOUSE/DIRECT 切换而失效的 HBL 身份和版本必须保留，不计入当前 HBL 数量。
- HBL 继续保存完整单证内容、签发主体、状态、当前正式版本和历史版本。本公司签发时保存
  本公司主体；同行签发时保存真实同行 Partner、外部提单号和文件，不伪装成本公司签发。
- HOUSE 订单创建时必须提交非空 HBL 号，并在同一事务中建立唯一 HBL；订单或 HBL 任一创建
  失败时整体回滚。除号码外的完整单证内容可在后续制作阶段按现有单证流程补齐；不提供建单
  后再“添加 HBL”或添加任意数量 HBL 的集合语义。本任务不另行定义签发必填字段集合。
- 订单详情只显示一个“分单信息”表单，不显示 HBL 列表、“添加分单”或“删除最后一张分单”。
- 分单号原值无损保存；规范化键继续用于唯一性。拆票产生的 `a`、`b` 后缀显示和打印时
  保留原始大小写。
- HOUSE 与 DIRECT 在创建后仍允许按外部确认结果切换；不得根据 ETD、距开船时间、实际离港
  或订单流程状态自动禁止切换。
- HOUSE 切换 DIRECT 时，原当前 HBL 形成作废版本并退出当前集合；DIRECT 切换 HOUSE 时必须
  提交已取得的 HBL 号及签发主体，并建立新的当前 HBL。切换必须形成不可变模式事件，不得
  覆盖已经对外使用的历史版本；系统继续执行权限、乐观版本和结构一致性校验。

### FR-3：常态直接归属与拼货例外分配

- 常态订单的货物与箱号直接归属于该订单唯一 HBL，不要求用户进入独立分配流程。
- 对少量“一只物理箱装多个订单/HBL”的客户拼货业务，系统必须提供显式共享箱及跨订单
  HBL 分配，记录每票在该箱内的件数、重量和体积，并保留守恒校验。
- 共享物理箱必须独立于单个 Order 建模；禁止复制相同箱号到多张订单后各自当成不同箱，
  也禁止继续使用只能在单订单内部工作的分配结构冒充跨订单分配。
- 普通订单入口隐藏分配复杂度；只有明确选择共享箱/拼货模式时，才展示跨 HBL 分配工作台。
- HBL 内容可从订单货物生成或显式同步，但正式签发后保存不可变内容快照；后续订单货物修改
  不得静默改写已签发版本。
- 拆票时普通独占箱完整归属一张结果订单；原本已标记为共享箱的物理箱才允许在多个结果
  HBL 间重新分配，并继续满足件重尺守恒。

### FR-4：订单独立费用

- 所有应收应付、账单和利润继续归订单，不新增或保留共享 MBL 费用分摊。
- 每张订单形成一张独立账单。拆票不得静默复制、按比例分摊或跨订单搬移已确认财务事实；
  存在无法保留原归属的受保护财务事实时明确阻断，具体处理由业务人员手工决定。改单和换配
  保持事实归原订单，不因已有财务事实而一概阻断，也不得自动改写财务记录。
- 共享 MBL 页面如展示金额，只能是关联订单的只读汇总，不形成独立结算主体。

### FR-5：低频变更能力收敛

- 拆票的结果实体是新订单，每张结果订单对应一张 HBL；不在原订单下新增多个 HBL。
- 换配/异常分离必须分别处理 MBL 与 TransportExecution：同船公司换航次时可保留 MBL、
  只移动实际运输执行；换船公司时必须同时更换 MBL 与运输执行。两类操作都要记录甩柜、
  漏装等原因和前后关系，且不得修改原执行中的其他订单。
- HBL 单改和作废继续保留正式版本及事件追溯，但所有命令只作用于订单唯一 HBL。
- 删除 Switch B/L 的 Preview/Execute API、Biz/Data 命令、事件表及关联边、权限、前端入口、
  生成客户端和专用测试；旧 Proto 字段/枚举编号按生成规范 `reserved`，不得复用于普通换配。
- 换船公司、换航次、换 MBL/HBL 号统一走改单/换配，禁止以保留 Switch 外壳的方式兼容。
- MBL/HBL 更改属于高频操作，必须保留 Preview、版本冲突、不可变正式版本/日志和锁单快照；
  实施审计只删除建立在一订单多 HBL 假设上的分支，不削弱真实改单追溯。
- 偶发操作保持显式确认、版本冲突、下游影响展示和历史归属校验，不自动红冲、自动分摊或
  静默纠错。
- ETD、离港、已放单、已开船等节点只用于风险提示和审计上下文，不作为改单或改配的绝对
  禁止条件。船代反馈船司/承运方同意后，授权用户可以按确认结果更新系统。
- 所有共享运输修改、正式改单、换配及 HOUSE/DIRECT 切换请求必须携带外部确认记录：确认方
  为非空文本、确认时间为有效时间、说明去空白后非空；附件可空。该记录随业务版本或关系
  事件不可变保存，不要求额外审批状态、审批人或系统内批准步骤。
- 已被业务锁定的订单仍允许通过上述携带外部确认的专用命令改单、换配或切换模式；命令不得
  自动解锁，也不得改写既有锁定快照。普通订单编辑继续遵守原业务锁。
- 已有账单、发票、核销、放货记录等下游事实不得被改单命令静默改写、删除或搬移；系统应
  展示影响并保留原事实关联。只有会直接破坏数据库一致性或无法保留历史归属的操作才阻断，
  不能仅因下游事实存在就一概禁止单证修改。

### FR-6：迁移原则

- 修改 Ent Schema、Proto、生成代码、OpenAPI、Web Client、服务端和前端必须一次闭环。
- 新增不可变增量迁移；不得修改已经提交的历史迁移。
- 因当前无 SE 业务数据，迁移发现任意 Order/MBL/HBL/Link/Allocation/相关版本或事件时应在
  DDL 前原子停止，不设计旧数据自动折叠、删除或映射。
- 重构多 HBL 与箱货分配结构时，所有外键、索引、权限、服务注册、路由、测试和生成物必须
  同步收敛；保留的跨订单共享箱能力必须使用与真实归属一致的新契约，不保留旧结构兼容 API。
- 用户尚未提交的 ShippingLine 同步文件不属于本任务，必须继续隔离。

## Acceptance Criteria

- [ ] AC-1：多张正常订单可关联同一 MBL 和同一 TransportExecution；修改共享航次一次后，
  该执行中的订单显示同一最新值，且 MBL/运输执行各自的版本冲突返回 409。
- [ ] AC-1b：甩柜/漏装订单可显式从原 TransportExecution 分离并手动改航次或港口；同船公司
  时可沿用原 MBL，换船公司时必须同时更换 MBL。原执行中的其他订单及版本均不变化，系统
  保留原因、原 MBL/执行和目标 MBL/执行历史。
- [ ] AC-1c：列表和订单详情关联区可分别按客户业务号、Booking No.、当前 MBL 号找到同批
  订单；客户业务号同值不作为重复错误，详情关联仅匹配同一客户。修改任一订单的客户业务号
  或 Booking No. 不修改同值订单，也不触发运输信息联动。
- [ ] AC-2：HOUSE 模式下一张订单恰有一张当前 HBL，DIRECT 模式没有当前 HBL；服务端拒绝
  第二张当前 HBL 和模式不一致数据，数据库条件唯一/检查约束兜底，前端不存在多 HBL 添加
  和列表入口；历史失效 HBL 仍可从版本/事件历史读取。
- [ ] AC-2a：创建 SE 订单必须明确选择 HOUSE 或 DIRECT；HOUSE 未提交非空 HBL 号、DIRECT
  携带 HBL 数据或模式与单证不一致时返回 400 且订单/HBL 均无写入。API、领域和数据库均
  不存在 `UNDETERMINED`，服务端不根据 HBL 输入有无猜测模式。
- [ ] AC-2b：授权用户可依据船代反馈的船司/承运方确认切换 HOUSE/DIRECT；ETD 前 24 小时、
  实际离港或流程状态本身均不导致 409。HOUSE→DIRECT 作废原当前 HBL，DIRECT→HOUSE 要求
  非空 HBL 号并创建新当前 HBL；两条路径均保留前后版本、原因、确认信息和操作日志。
- [ ] AC-3：HBL 完整内容、本公司/同行签发主体、正式版本、改单、作废、打印/附件所需数据
  与操作日志保留，并能按订单当前唯一 HBL 及历史失效 HBL 查询版本；Switch 专用 API、事件、
  权限和 UI 不再存在。
- [ ] AC-4：普通订单的货物和独占箱无需分配即可形成唯一 HBL 内容；明确启用共享箱模式时，
  一只物理箱可跨多张订单/HBL 分配件重尺并通过守恒校验，普通页面不暴露该工作台。
- [ ] AC-5：拆票产生多张订单而非一订单多 HBL；每张结果订单恰有一张 HBL，原始小写后缀
  可无损保存和打印，规范化唯一键仍防止等价重复。
- [ ] AC-6：换配按“同船公司换执行”和“换船公司并换 MBL”两条明确路径处理，保留唯一 HBL
  和变更历史；不得因 ETD、离港或存在下游事实一概禁止，也不得静默改写既有财务/放货事实。
- [ ] AC-6a：共享运输修改、正式改单、换配及 HOUSE/DIRECT 切换缺少确认方、确认时间或说明
  时返回 400；信息完整时随不可变版本/事件保存，可选附件保持关联，不产生内部审批流程。
- [ ] AC-6b：订单即使已业务锁定，上述外部确认专用命令仍可成功；订单保持锁定，旧锁定快照

## Out of Scope

- 不取消多订单共享 MBL，也不为正常关联订单建立可静默漂移的船名航次覆盖字段。
- 不新增 Booking 聚合实体；客户业务号和 Booking No. 不承担跨订单联动或共享字段真相。
- 不建设共享 MBL 费用分摊。
- 不把共享箱分配变成所有订单的必填流程，也不支持未显式标记共享的普通箱跨订单拆分。
- 不自动生成拆票后的 `a`、`b` 分单号；业务人员仍显式确认最终号码。
- 不新建 HBL 签发审批、打印模板或签发必填字段体系；本任务保留并适配现有版本和单证内容能力。
- 不对接船公司、船代、SI、VGM、AMS/ENS/ACI 或打印模板外部平台。
- 不为尚不存在的生产 SE 历史数据提供兼容、回填或猜测映射。
