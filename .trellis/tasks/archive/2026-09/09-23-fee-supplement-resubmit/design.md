# 技术设计：撤回并预填重提

## 边界与数据流

- 仅修改 `FeeSupplementSection`、`FeeSupplementModal` 及其测试；不新增服务端接口，也不修改补录申请实体或审批规则。
- 列表行继续消费服务端 `canWithdraw`，再与现有 `canCreate`、`lockActive` 组合控制重提入口。单独“撤回申请”保留。
- 点击“撤回并重提”时先由确认弹窗说明旧申请进入终态；调用现有 Withdraw API 并携带该行 `expectedVersion`。成功后从原行快照构造表单初值、刷新列表、打开补录表单；失败时保持关闭并刷新列表。
- 现有创建 API 负责新申请，重提使用新幂等键；原申请 ID 不写入新申请，不新增兼容字段。

## 表单初值与失效选项

- `FeeSupplementModal` 接收可选 `initialValues` 与可见的预填提示；新建入口沿用默认值，重提入口在表单打开时一次性设置初值，不能被默认 CNY/数量覆盖。
- 源记录的费用项目、结算单位、计费单位、币种、数量、单价、发生日期、原因和备注逐字段映射。`expenseDate` 使用现有日期组件支持的格式；不复制金额、税额等派生快照。
- 原 `exchangeRateSource=MANUAL` 时仅在当前具备覆盖权限时设置 `exchangeRateOverride` 并打开手动汇率态；失去权限时显示明确警告，要求用户确认按当前系统汇率重新发起，不静默沿用或改写。
- 对候选项已失效的字段，不造假选项或回退旧 ID。表单需显式标记不可用并要求用户重新选择；关闭弹窗只清除新建表单状态，原申请保持 `WITHDRAWN`。

## 并发与身份

- 继续使用当前组件的订单身份和请求序号守卫：迟到的撤回成功不能在已切换订单上打开表单。
- 撤回与审批并发由既有版本检查裁决；前端仅在成功响应后进入重提态。提交新申请仍由后端重新判定锁依据、选项和权限。
- 不增加事务、锁或版本字段，也不修改原申请历史。
