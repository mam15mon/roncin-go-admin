# 退役角色数据访问范围配置

## 目标

移除角色管理中的「数据访问范围」功能。管理员只配置功能权限与角色状态，访问边界由当前工作台决定：公司只处理本公司，系统管理按明确权限治理组织和公共资料。用户已明确要求创建任务、完成全部工作后合并 main 并安全删除分支，授权覆盖实现、验证、本地提交、合并和安全分支清理。

## 事实与范围

- 公司运行时已将 all / organization_tree / organization 收敛到当前公司（server/internal/biz/auth.go 的 workspacePermissionScope）。角色仍持有可配置 data_scope，表单描述与实际行为不一致。
- 角色存储、CRUD Proto、服务转换、权限画像、登录授权、种子和初始化均引用该字段；不是只删表单的任务。
- 系统管理与公司角色库独立，部门共享公司角色库；工作台归属与功能权限仍是授权底线。

## 需求

- R1：新增/编辑角色删除数据范围控件、默认值与提交字段；角色列表删除范围列及筛选；工作台等展示不再显示可配置角色范围。
- R2：角色创建/更新/响应 Proto 移除 data_scope，删未用枚举并重新生成后端、OpenAPI、前端客户端与常量。删除字段保留 Proto 编号/名称以免误复用，不保留旧契约兼容分支。
- R3：Ent Role 删除 data_scope，正式 SQL 迁移移除列；迁移保留角色、成员、权限关联与业务数据，不重建数据库。
- R4：必要的内部有效范围由工作台类型推导，公司 organization、系统 all，不能再从角色配置读取。内部 PermissionCapability 若供现有门禁消费可保留为推导结果，不作为可选功能。
- R5：保留权限与工作台边界、防提权、公司隔离、角色停用、管理员保护和成员分配规则。移除已停用 self 时，旧 self 角色必须先停用，避免自动变成有效授权；系统角色原 organization/tree 范围随退役按系统工作台统一 all，此变化仅作用治理权限，不授予新的功能权限或跨公司经营能力。
- R6：全部验收通过后提交，归档任务，合并 main，再用 git branch -d 安全删除已合入的本任务分支；本聊天前一权限查找分支若包含在合并历史中也安全清理。不得重置用户工作或强制删分支。

## 验收标准

- AC1：角色新增、编辑、列表与工作台不再显示或提交可配置范围；角色功能权限、搜索、选择保留仍正常。
- AC2：CreateRoleRequest、UpdateRoleRequest、AdminRole 及生成物中没有 data_scope；角色表与生成 Ent 无该字段，正式迁移冷启动和增量升级均可运行。
- AC3：公司 A 无论角色权限组合均不能读写公司 B；系统角色只能按工作台允许的明确功能权限执行治理；切换公司后重新计算授权。
- AC4：不能分配操作者不拥有的权限，停用/受保护角色规则有效；旧 self 不会因退役被激活；权限依赖联动正常。
- AC5：运行定向前后端测试、迁移集成与必要生成一致性验证，再运行 check:fast；不得以 SKIP 当集成已运行，不把秘密写入日志或 Git。
- AC6：main 包含本任务及前一权限查找功能的提交；本任务分支及本聊天已合入的前一分支不存在；工作区无本任务残留未提交修改，归档与日志已记录。

## 范围外

不移除公司隔离，不扩建细粒度数据策略，不新增事务框架，不改已有历史迁移文件，不清空或重建开发数据库；不推送或创建远端 PR（本次请求为本地合并）。

## 授权与状态

用户已明确授权端到端完成，无待确认的产品决策；采用最薄的工作台边界方案。规划据此收敛，实施与检查按下述 design.md / implement.md 执行。
