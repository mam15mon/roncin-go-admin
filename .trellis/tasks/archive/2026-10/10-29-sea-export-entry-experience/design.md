# 技术设计（规划稿）

## 边界

海运新建页负责创建提交状态与结果确认；SeaCustomerField 负责客户默认人员及就地反馈；OrderFormTemplate 仅负责通用表单草稿与布局，不依赖海运页面类型。共享组件变化需验证空运入口。

## 人员默认值与草稿

客户查询按组织和客户隔离，依照 React Query 规范提供 loading/error/refetch。区分查询结果与表单编辑状态，只有本次客户选择之后未被用户修改的字段才接受默认值；缓存回放/后台更新不能再次覆盖输入。
草稿机制必须观察完整表单变化或提供最薄的统一快照更新入口，涵盖程序回填、清空与隐藏字段。避免 monkey patch Form API 和把所有服务端状态复制入草稿。沿用原有用户、组织、路径隔离及日期恢复。

## 新建提交

状态至少区分可编辑、提交中、结果待确认、已成功；参考 use-sea-order-save.ts 的冻结载荷模式，先验证复用边界，避免为了共用而改写详情保存。
第一次发送前保存规范化请求快照与幂等键；请求在途与结果不确定均冻结业务输入。只有明确未写入的失败才解除冻结；错误分类按真实接口契约判断，不简单把所有 HTTP 错误当成未落库。
待确认意图与现有草稿身份一起保存到会话级存储，刷新恢复后只能确认原请求。成功取得服务端 ID 后清理待确认记录及草稿并导航；成功导航前正确解除脏状态，避免把成功跳转误作放弃录入。
不得在超时后自动换键创建，也不能用字段变化自动换键掩盖不确定结果。会话级恢复不承诺浏览器会话结束后的跨设备恢复，不扩展通用幂等平台。

## 交互

复用 StickyFooterBar；上下按钮消费同一提交状态。客户区显示明确人员加载反馈与恢复入口；档案维护受现有 access 约束。ETA 保留并通过依赖校验报告错误；错误定位继续复用已有隐藏区域展开及定位机制。

## 风险与回退

共享草稿与新建页同时服务多个订单品类，需要针对性相邻回归；本期无数据库迁移。按人员/草稿与新建提交两组审阅并提交，发现回归时按对应提交回退，不重置业务数据。正式实施前核对 R5 的真实 ProForm 行为以及 sessionStorage 持久化失败的处理，不能在无法保存待确认意图时虚假承诺刷新恢复。
