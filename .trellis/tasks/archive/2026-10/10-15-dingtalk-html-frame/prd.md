# 登录页 HTML 直接加载钉钉二维码

## 目标
浏览器收到登录页 HTML 后即开始请求本次钉钉二维码，减少等待前端主程序下载、执行和登录页渲染的时间。

## 已确认背景
现有配置已随 HTML 返回，首屏配置接口为零次，但 iframe 仍由 React 创建。用户已认可 HTML 直接输出 iframe、前端复用同一实例、验证扫码刷新回调的方案，并同意创建任务及推进。

## 需求
- R1：Go 同域入口与 Vite 开发入口仅在登录 HTML GET、合法启用配置时输出对应 iframe。
- R2：前端接管同一浏览上下文，不移动或重建导致重复导航；原始 iframe 不属于 React 根节点。
- R3：保留原有精确 origin/source/state/回调校验、一次成功处理、到期刷新、密码切换和回调流程。
- R4：Cookie、state 与 iframe 来自同次响应；无效、禁用或失败配置不提前加载；其他路径、HEAD 不覆盖 state。
- R5：页面布局与现有扫码区对齐，窄屏、窗口变化与切换模式不残留遮挡层。

## 验收标准
- AC1（R1/R2）：阻塞前端主程序时已观察到 iframe 授权请求；放行后仍为原实例且仅一次导航，配置 GET 为零。
- AC2（R2/R3/R5）：刷新先销毁旧实例再请求配置；密码切换移除预载实例，返回用新配置；卸载无残留。
- AC3（R3/R4）：非法消息不认证，合法成功仅一次；过期和旧消息无效，回调返回正确更新配置。
- AC4（R4）：开发与生产 HTML 输出安全转义、Cookie 一致、禁用/失败不输出可用 iframe。
- AC5：针对性测试、全栈门禁与生产构建通过，浏览器覆盖开发和 Go 同域入口。

## 范围外
不更换 SDK、不改授权协议与数据库、不做整个应用 SSR、不扩展后台依赖拆包、不承诺钉钉网络延迟下降。

## 风险与验证限制
DOM 重挂载会让 iframe 重新导航；必须实测导航次数。真实企业扫码需企业账号验证，本地协议模拟不替代该项。
