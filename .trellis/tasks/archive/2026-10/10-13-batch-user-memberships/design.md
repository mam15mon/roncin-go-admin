# 多组织加入技术设计

## 请求与分层

替换现有新增单成员 RPC 为 CreateUserMemberships，使用 POST /api/v1/admin/users/{user_id}/memberships:batchCreate，权限沿用原新增成员接口的 system.user.update。请求为 user_id + repeated items，每项 organization_id、repeated role_ids；成功响应为本次成员列表。单条编辑仍使用 UpdateUserMembership。

批量允许一项；全仓单项新增调用迁入新接口，不保留旧接口兼容转发。service 校验 UUID、非空 items、重复组织等结构问题，biz 校验待分配/身份状态及每项授权，data 负责锁、唯一性和写入。错误沿用业务错误并标明可见的目标组织，不泄露越权对象信息。

## 表单

所属组织多选，每个组织一行独立的角色多选，均可空。按 organizationId 作为稳定 key，删除某个组织只移除该行及角色，其他行保持；重新选回不悄悄复用已丢弃角色。每行复用组织角色生成客户端，用 React Query 按组织 key 隔离候选，请求结束不能把另一行或已取消组织的角色写进来。

ModalForm.onFinish 返回保存 Promise，失败不关闭表单，展示原因；成功刷新成员查询并通过父页面 actionRef 刷新列表。权限复用 useAccess。数据检查使用当前管理范围；已有成员关系（包括停用记录）不在新增候选中，恢复通过既有明确的成员编辑入口。

## 原子写入（D7）

当前 AdminUsecase 构造器只有 AdminRepo，需显式注入 biz.Transactor，同步 Wire 和全部测试构造调用；不得用 nil 时跳过事务的兼容分支。

biz.Transactor.WithinTransaction 包住该用户本批校验与写入。参与仓储都经 Data.client(txCtx)；现有 WithTx 自动合并外层。只在事务提交后重读响应，不在回调内调用原生 SQL 事务仓储。

1. 规范化请求并拒绝同一 organization_id 重复出现，不合并/覆盖重复项。
2. 对参与授权校验的操作者及目标用户按 ID 排序加锁；保持目标用户变更串行。
3. 对涉及组织及解析其工作台所需节点按 ID 固定顺序读取并按需共享锁，复核有效性与管理范围。
4. 涉及的现有成员按 ID 固定顺序锁定；新增目标若已有启用或停用关系均返回明确冲突，不当作成功也不自动恢复。
5. 对授权校验涉及的角色按 ID 排序共享锁，并锁定/复核操作者授权依据；在同一事务中再次验证目标角色所属工作台、启用态和不得提权。空角色仍要检查组织管理范围。
6. 创建成员与角色绑定；所有成功审计跟随事务提交，任何失败原样传出并整批回滚。

用户 → 组织 → 成员 → 角色为本子任务目标顺序；实施前审查触及的既有方法是否重复或反序加锁，必要时在 data 提取本次真实复用的锁内写入方法，不能仅在外层加事务后继续使用事务外权限查询。沿用成员及角色绑定唯一索引，ent.IsConstraintError 映射冲突；不新增版本字段、持久化幂等键或自动重试框架。

## 相邻行为

无角色只建立成员资格，不新增业务权限。已开通用户与待分配用户保持不同入口，员工待分配多人开通仍使用原逐人原子规则。成员停用/移除时的会话撤销与提成等业务阻断沿用现有规则。

## 验证重点

跨公司角色隔离、同公司多个部门、空角色、输入重复组织、已有停用成员、并发两个批量请求、角色撤权/组织停用竞争、事务中途写入和审计失败；均证明失败后无本批新增成员/绑定且已有授权不变。
