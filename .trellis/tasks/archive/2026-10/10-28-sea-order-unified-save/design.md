# 技术设计：海运订单统一保存

## 最小改动边界
扩展现有 UpdateOrder 聚合更新，不增加并排的聚合写接口。前端详情统一负责单证加载与保存基线；SeaDocumentSection 负责字段、页签和专用业务动作。领域校验在 biz，事务/锁/写入在 data，service 仅转换。

## 接口与领域契约
- 复用 `UpdateOrderRequest.sea_document`、`SeaOrderDocumentInput.expected_mbl_version/expected_link_version` 和 `SeaHouseBillInput.id/expected_version`；已有字段足以表达当前 HBL 普通编辑，不预建新协议或版本字段。
- 创建语义不变；更新时允许修改当前活动主单下本票已有 HBL，要求 ID、HBL 版本与 Link 版本齐全。
- 整单更新不携带模式切换，不允许借缺失 ID 创建 HBL，也不允许把另一票/另一组织 HBL 指定为目标。
- 修改 proto 注释/契约说明并通过生成器更新绑定、OpenAPI 与客户端，禁止手改生成物。若研究发现确需新增字段，在实施前记录差异并复审，不能暗增接口范围。

## 服务端事务
1. 复用 `orderRepo.UpdateDraft` / `Data.WithTx`、幂等检查和现有共享主单成员预锁逻辑。
2. 修改共享主单时先按主键顺序锁定成员订单，再依既有 Order → MBL → Link → HBL 顺序取锁与重验；仅改本票 HBL 不扩大到其他票写入。
3. 同一请求可能同时调整 MBL 身份/航程与正文：所有 expectedVersion 对事务开始时的目标快照校验，不能拿前一阶段自行递增后的版本与原请求比较。复用既有身份更正/共享航程规则，不因聚合编辑放宽门禁。
4. 将独立 HBL 更新的身份校验、终态校验、签发方、正文、重号映射、HBL/Link 版本推进和审计事实提取为 data 层内部复用逻辑；两个入口共享同一规则。只在发现真实复用后提取，不创建通用变更平台。
5. 主单、分单、订单写入及日志共用外层事务；任一步失败原样返回并整体回滚。成功后用普通上下文重读响应，禁止泄漏已结束 txCtx。
6. 不可变历史继续沿现有审核锁/正式单证动作生成，普通保存不得修改历史记录；保留原始审计口径与旧新版本事实。
7. 客户变更与客户签发 HBL 的既有限制保留；不能用同包改签发主体来绕过先验门禁。

## 前端数据流
- 详情在初始化表单前通过 React Query 获取订单和海运聚合单证，构造完整初始值及单证基线，再由模板恢复草稿。取消单证组件挂载后无条件覆盖已恢复字段的所有权冲突。
- 基线包含当前主单/HBL/Link 身份、版本与用于编辑的规范化字段。对比规范化提交值，只为有修改的 MBL/HBL 组装 sea_document；显式清空字段不得被当作未提交。
- FormAdapter 负责从完整表单生成一个 UpdateOrder 载荷。DIRECT 和终态单证不产生无效 HBL 更新。
- 复用整页 onFinish、错误揭示和 StickyFooterBar。移除局部保存处理器及旧文案，主分单历史/模式切换入口继续使用已有命令。
- 保存时冻结当前编辑区及提交动作。写入成功后重新获取完整订单与单证快照，再同时回填表单、基线和版本并清理草稿/脏状态；不能只刷新版本而保留另一来源的正文。
- 已确认成功但刷新失败：保留当前显示输入，进入明确的“已保存、等待重读”状态，按钮重试读取，不重发写命令；读取恢复前不允许用旧版本发起新编辑提交。
- 写响应丢失/结果未知：保留原提交快照及幂等键；重试同一次提交。不得把用户新编辑后的不同载荷继续复用未知结果的旧幂等键。
- 所有异步回填检查订单与组织身份；后台刷新和专用动作不得无条件重置当前未保存字段。

## 取舍与回滚
- 使用现有整单事务可消除前端串行保存的半成功状态；代价是跨层同步调整与事务回归。
- 不新增 Schema，无数据库重建或兼容双轨；仅保留仍有真实调用的独立服务端命令，共用规则防止漂移。
- 前后端、生成物与测试必须作为可共同回滚的功能批次提交，不能只上线前端按钮移除。
