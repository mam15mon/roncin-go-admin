# 登录页默认展示钉钉二维码

## 目标

员工打开即扫码，管理员通过次级入口使用密码。承接父任务 R1/R2/R7。

## 事实

login/index.tsx:93 当前点击后获取 authorizeUrl 并跳转；dingtalk-callback.tsx:63 已有多工作台选择。auth.proto:76 配置仅有 enabled、authorize_url；服务端每次获取配置会生成 300 秒 state Cookie。

## 需求

- 默认真实嵌入式二维码，不用静态示意图或普通授权 URL 二维码冒充 SDK 登录。
- 次级“管理员账号登录”切换密码表单，可返回扫码；保留品牌布局与小屏可用性。
- 加载、失效、失败、刷新与重试可识别；切换方式和离开页面正确清理实例/监听，避免重复认证。
- 保留 state、企业身份校验与服务端换码，秘密不返回前端。
- 复用现有单工作台直进、多工作台选择及会话轮转；保留未同步/待分配/停用提示。
- 钉钉未启用或加载失败明确展示状态，管理员密码入口可达，不静默改换认证流程。

## 验收

- [ ] 打开即出现可扫二维码；切换密码与返回扫码均正确。
- [ ] 两种登录覆盖单/多工作台、回跳地址和失败提示。
- [ ] 刷新二维码后 state 与扫码实例一致，不被重复配置请求覆盖。
- [ ] SDK失败、二维码过期、重复回调、切换再返回有针对性验证。
- [ ] 开发代理及生产同域分别核验；真实扫码未测时明确记录，不以 mock 宣称联调通过。

## 技术核验与边界

官方动态文档未返回 SDK 参数正文；已直接读取钉钉托管的 0.21.0 登录脚本，核实内嵌 OAuth2 iframe 与 message 成功回传协议（见父任务研究文件）。设计采用可清理监听的最小嵌入组件。真实企业扫码、当前应用参数与回调地址仍需联调，不能将源码协议核验视为已验证真实登录。不改人员同步、不禁用普通账号密码接口、不做通用登录平台。用户已于 2026-10-13 回复“开始”，批准整体实施。
