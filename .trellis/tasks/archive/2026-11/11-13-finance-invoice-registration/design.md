# 发票登记与免票设计

本轮用户要求接续现有实现并做完财务任务，已授权实施已确认范围。本文基于父任务和账单任务设计第 15 节，不重新引入历史兼容。

## 当前缺口

已有发票记录、开具、作废、红冲及有效关联锁定；创建时总是取整张账单的全部可开票行，且存在任何有效关联即排除该账单，因此尚不能分次按费用指定金额。账单的无需发票事实目前只有投影扩展位。

## 数据与接口

- 发票与账单仍复用 FinanceInvoice / FinanceInvoiceBill；新增 FinanceInvoiceFeeAllocation，逐项记录账单行、来源费用、含税额、未税额、税额与税率不可变快照。唯一约束为同一发票账单关联内来源费用唯一，有效性沿父关联 active 与发票状态推导。
- 登记输入明确每张号码、日期、登记总额及逐账单分配（账单版本、金额、逐费用金额），逐层求和相等；同公司、方向、结算对象、币种与本币。创建成功即形成已登记发票；既有作废/红冲保留，按原分配解除进度，不重分摊历史。
- 当前账单与行查询补充已登记、可登记金额；候选按真实剩余额过滤，不能因已有部分发票排除整张账单。同步费用台账的关联账单投影和筛选，不能因存在一张部分发票就认整账票齐，也不能把免票伪装为已开票。
- 新增 FinanceInvoiceExemption，字段含公司、账单、原因、操作者、时间、版本及撤销人/时间/原因；同账单有效标记唯一，撤销保留原记录。复用账单 expectedVersion；新增独立 system.finance.invoice.exempt 权限，由管理员显式分配，不默认授予普通财务。
- 标记/撤销接口属于发票任务；返回账单当前投影，详情展示历史。免票记录不是零税率或发票号码，不产生核销事实。

### 直接登记契约

剩余实施将用 `RegisterInvoices` 一次接收本次多条登记记录：每条 `invoice_profile_id / invoice_type / tax_invoice_no / invoice_date / total_amount / allocations[]`，分配为 `bill_id / expected_version / amount / fees[{order_fee_id, amount, tax_amount}]`。顶层只有一个幂等键，调用方公司固定当前工作区。一次最多100条、合计来源费用按当前可批量处理规模设显式上限，避免无界载荷；外部页面的100行只作为本次薄UI容量选择随方案审阅，不冒充服务端观察事实。RPC各自独立请求/响应命名以满足仓库buf规则。

独立发票列表、账单详情及建账组内共用登记表单。现有“创建开票草稿→开具”的双步骤入口与 `CreateInvoice/IssueInvoice` 契约在仓库调用方同步替换为直接登记；取消/红冲按有效已登记记录操作。本轮已对开发库只读盘点：2张ISSUED、0张DRAFT，号码/日期均有值。新正式迁移对缺号码/日期的DRAFT显式拒绝并提示先处理，绝不伪造号码/日期、删除记录或长期运行两套交互；本次开发数据无此阻断。旧的完整登记事实通过正式迁移补齐逐费分配；当前操作与测试/种子一次性同步新契约。

已确认修改契约为 `ReviseInvoiceRegistrations`：只有所涉账单**既无有效核销、也无已确认对冲**才可接收同弹窗记录集的更改、增加、移除。原因必填。锁内比较来源账单和发票版本、重新读取有效结算事实、校验金额/手填税额/逐层分配与余额，保存完整修改前后快照及操作人/时间/原因，再停用被替换分配、追加新有效分配，整次原子。建议新增 `FinanceInvoiceRevision` 不可变JSON快照及修订序号；父发票更新当前投影，旧来源金额事实永久保留，不以原地改历史行实现修订。

两项任一存在时转受控更正：只读预览返回有效核销/对冲及相关单号、影响账单/金额、可执行的既有反向操作；用户按原授权流程取消、冲回或调整，操作成功后重读才允许发票更正。发票作废/红冲写入口同样锁内复核关联依赖，不能以按钮隐藏或预览成功为授权；不自动撤销资金/对冲，也不让已停用分配再恢复余额。跨账单票据显示全量关联影响与原分配，未授权/陈旧/部分解除一律拒绝本次更正。


## 一致性

- 写入遵循现有订单闭包 → 账单按 ID 排序 ForUpdate；账单版本不匹配返回 409，增加分配或免票/撤销成功推进账单版本。
- 锁内重读有效发票分配与免票；逐费分配不超过该费实时余额，重复项、其他账单费用、未活动行整次拒绝。分配之和必须等于账单分配、账单分配之和必须等于发票总额。
- 任一有效发票存在即拒绝免票；有效免票时拒绝登记。共用订单和账单锁，避免并发形成互斥事实。
- 免票加入 protectedFinanceFactPredicate、费用锁定事实、完成状态与 SQL 筛选；全部事实撤销后才恢复费用增删及后续日期更新的系统汇率资格。
- 创建与组合入口使用共享事务，回调错误原样返回，响应提交后重读；幂等指纹覆盖号码/日期/所有分配，不自动分摊或修正输入。

- 多条登记一次锁定全部受影响订单及账单（稳定主键序），本次中同账单可出现在多张票；每次在本事务已登记额之上累计复核，但它们基于同一用户提交基线，不要求用户手工给第二张票填写自己递增后的版本。对外整个命令失败则全部回滚。
- 提供明确的“只写编排”内部入口给账单F，在传入共享txCtx时不组装完整响应；独立RPC在外层提交后重读。核销 `CreateWithCashflow` 同理不能直接当作已经提交的命令调用。

## 已确认：财务手填税额（2026-11-14）

用户选择“税额由财务逐项填写”。每个选中的费用明确填写本次含税金额与本次税额；服务端要求0≤税额≤本次含税额、分配各层合计相等、含税分配不超实时余额。未税额为含税额减填写税额；不按来源税率自动重算，不在最后一笔静默补尾差。来源税率仍为只读来源快照，登记税额不反写费用及提成税基。金额精度复用项目当前decimal契约，不照搬海管家仅已观察到的两位控件限制。

## 登记入口与操作边界

围绕账单提供多行登记弹窗，在详情继续登记或在建账组内一并提交，独立发票台账用于查询和追溯。录入的是已有发票，不是调用在线开票；不因登记入口要求开发税务平台。

一张弹窗可含多张发票，每张分别记录号码、日期、类型、含税总额与逐账单/费用分配；整次多记录登记原子，任一行失败不留下部分登记。批量同一发票跨多账单仍保留一个发票实体和明确分配，不把相同号码复制成多个实体。

直接修改与增删已确认按“既无有效核销、也无已确认对冲”执行，修改原因必填并保留前后快照。已有任一结算事实先检查关联、按原业务规则完成必要反向处理，再更正发票；不假定作废/红冲总能直接执行，不重复回退余额。这是本项目产品决定，外部相同服务端规则仍未验证。

## 正式迁移

逐费用分配为新增不可变事实表；既有整额登记数据通过正式迁移按当时来源费用快照补齐分配并核对账单关联总额，不能用运行期旧数据分支或凭当前费用重新分摊历史掩盖缺失。无法确定来源的开发记录需显式报告，不清库、不自动删除。新开发数据与生成物同步新契约。

## 前端

登记界面提供号码、日期、总额、逐账单/费用金额；可继续选择部分登记的账单。保持当前公司、官方表单提交 loading、成功报文守卫和失败保留输入。账单详情可查看逐费用进度、发票记录与免票历史；免票/撤销原因必填，仅相应权限显示。

## 验证

实施后补三层金额/不同税率/尾差/幂等/并发超开验证；真实 PostgreSQL 验证免票互斥、版本冲突、公司隔离、部分撤销仍锁定、最后事实解除、费用汇率保护与 SQL/展示同源。前端覆盖默认值省略、失败输入保护、部分登记继续入口、权限和公司守卫。生成物通过生成器同步，阶段完成后提交。
