# 发票登记与修订易用性优化

## 目标

让常见的简单发票登记场景（一张账单、一条费用）达到海管家的操作量：只填开票时间、发票号、类型和金额。多账单、多费用场景继续保留逐账单、逐费用的明确分配，并提供分配辅助和差额提示。现有服务端的校验、事务、幂等、修订历史和结算依赖阻断都保持不变。

海管家只作为交互参照：它的登记弹窗只填日期、号码、类型和金额，没有逐条分配。它的服务端分配算法尚未查明，本任务的设计不得写成“海管家算法”。

## 现状（仓库证据）

- 共享编辑器在 `web/src/features/finance/invoice-registration/InvoiceRegistrationEditor.tsx`，由 `InvoiceRegistrationModal.tsx`（入口为发票台账和账单详情）和 `features/finance/bill-creation/BillGroupCard.tsx`（建账附带登记）共用。
- 现在打开弹窗后，用户要依次完成：添加发票 → 添加账单分配 → 选择账单 → 填写账单金额 → 添加费用分配 → 选择费用 → 填写费用金额和税额。没有任何自动带入。
- 提交载荷由 `types.ts` 的 `invoiceRegistrationPayload` 组装，检查三层守恒和余额，金额统一为 `toFixed(8)`。
- 费用 `total_amount` 一律是含税额。`server/internal/biz/order_fee.go:451` 的 `calculateAmounts` 按 `tax_inclusive` 换算未税额和税额，但存储的总额总是含税。因此按含税分配金额 G 和税率 r 计算建议税额，公式为 G×r/(100+r)。例如 1,060 元、6% 时为 60。
- 来源税率 `FinanceBillLine.tax_rate` 是 proto `optional`：字段未设置表示税率未设置，显式 `"0"` 表示零税率。
- 服务端契约 `.trellis/spec/server/backend/finance-invoice-registration.md` 已覆盖三层守恒、`0<=tax<=gross`、实时余额、版本 409、幂等、整次回滚和结算依赖 409。R1–R7 不改服务端分配行为；R8 另按正式契约流程扩展票种。
- 修订弹窗用原值预填表单，但没有原值与修改后值的对照；结算依赖阻断提示已经存在。

## 需求

### R1 一账单一费用自动带入
- R1.1 登记会话只有一张账单、且该账单只有一条可登记费用时，打开后自动生成一张发票记录，选好该账单和费用。
- R1.2 用户输入发票含税总额后，自动把同一金额带入账单分配和费用分配。
- R1.3 金额超过该费用的当前可登记余额时，在行内提示并阻止提交。
- R1.4 来源税率明确时，按 R5 把建议税额直接预填到税额输入框（可编辑），并标注“建议值，请以实际发票税额为准”；财务核对无误可直接保存。
- R1.5 来源税率未设置时不给建议，也不按零处理，税额留空，必须由财务填写；明确的零税率建议 0。

### R2 用户修改保护
- R2.1 每个自动带入的金额和税额都记录“系统带入”状态。用户手动改过的字段变为“手动”状态，之后发票金额、账单或费用变化时不再改写它。
- R2.2 三层不一致时，在发票和账单层显示待分配差额，阻止提交，不静默修正。
- R2.3 重新自动分配只能由用户点击触发，触发后覆盖范围明确（见 R3.3）。

### R3 多账单、多费用
- R3.1 发票层显示：总额、已分配、待分配差额。
- R3.2 账单层显示：可登记余额、本次分配、费用合计与账单分配的差额。费用层显示：可登记余额、来源税率（未设置显示 `-`，零显示 `0%`）、本次含税金额和税额。
- R3.3 提供用户主动点击的“按可登记余额分配”：按账单、费用的列表顺序，把发票总额逐项填到可登记余额为止，扣除本会话其他发票已占用的部分。余额不足时保留未分配差额，不补齐；结果直接显示在表单中供核对。
- R3.4 混合税率时，每条费用按各自来源税率单独计算建议税额，不用平均税率，也不在发票层补尾差。

### R4 修订已有发票
- R4.1 没有有效核销、也没有已确认对冲时，继续允许修改日期、号码、类型、金额、税额和分配，以及增删登记行，修订原因必填。
- R4.2 修订界面展示原值与修改后值的对照，修改过的字段要明显标出。
- R4.3 有结算依赖时，继续展示关联单号、账单和金额，并禁止保存，不自动反向处理。修订弹窗中保留的分配不做自动带入，只在用户主动操作时生效。

### R5 建议税额口径
- 建议税额 = 含税分配金额 × 税率 ÷ (100 + 税率)，四舍五入到 2 位小数。按费用逐条计算。
- 建议税额只是前端辅助，提交值以表单中的实际值为准，不反写原费用。
- 金额展示统一用 `formatAmount`，提交载荷保持 8 位精度，不截断用户输入。

### R6 底线（不改变）
- 服务端继续在事务内重新校验权限、公司、版本、实时余额、分配、税额边界、结算依赖和幂等。失败时整次回滚，前端保留输入。
- 跨币种、跨结算单位、不同收付方向能否组合，继续按现有服务端和候选表规则执行。

### R7 默认总额（后续增强，用户 2026-11-15 追加）
- R7.1 新建发票时，总额默认带出所选账单的可登记余额合计（扣除本会话其他发票已占用的部分），并按可登记余额自动生成分配和建议税额；总额下方提示“默认为所选账单未登记余额，请按实际发票金额修改”。
- R7.2 继续添加发票时，默认总额为尚未分配的剩余余额；余额为 0 时总额留空。
- R7.3 登记弹窗中增减勾选账单时，只重建“完全未手改”的发票（总额与分配均为系统带入），保留已填写的抬头、号码、日期、类型和备注；有手改值的发票保持不变。
- R7.4 用户手改总额后，单账单单费用继续按 R1.2 跟随；多费用时不自动重分配，显示差额，需用户主动点击“按可登记余额分配”（R2.3 不变）。

### R8 发票类型细分（用户 2026-11-15 追加，已完成）

- 目的：登记时记录实际票种，便于查询与记录；不对接税务。
- 追加需求时的原状：`finance_invoices.invoice_type`、`partner_invoice_profiles.default_invoice_type` 均为 Ent 枚举 `NORMAL/SPECIAL`；服务端 `finance_invoice_registration.go:310` 只接受两类，`:407` 专票要求抬头地址电话开户行齐全；前端发票台账、导出、抬头维护、登记编辑器、修订对照/历史按两类展示。
- 改动需走契约流程：Ent Schema + 正式 SQL 迁移、biz 校验、proto 注释/生成、前端选项与展示；不做旧值兼容，开发数据一次性迁移。
- 票种（用户已定）：数电普票 `DIGITAL_NORMAL`、数电专票 `DIGITAL_SPECIAL`、纸质普票 `PAPER_NORMAL`、纸质专票 `PAPER_SPECIAL`、电子普票 `ELECTRONIC_NORMAL`、电子专票 `ELECTRONIC_SPECIAL`；不含形式发票（非税票，登记会扣减可开票余额）。
- 三类专票均要求抬头登记地址、电话、开户行、账号齐全（沿用现有专票规则）。
- 开票抬头默认票种同步扩展为同一枚举；登记新发票时票种默认取所选抬头的默认票种。
- 开发数据迁移：`NORMAL→DIGITAL_NORMAL`，`SPECIAL→DIGITAL_SPECIAL`；不保留旧值。
- 验收：登记/修订可选6类并保存；专票类缺抬头资料被服务端拒绝；发票台账、导出、抬头维护、修订对照与历史显示中文票种；迁移后开发库无旧值。

## 验收标准

1. [x] 一账单一费用：打开后只填日期、号码、类型和总额就能提交；账单和费用金额自动带入；建议税额能改，改后的值写入登记。（前端测试 + 浏览器）
2. [x] 税率未设置时，税额为空且必须手填；零税率建议 0；6% 下 1,060 元建议 60。（单元测试）
3. [x] 手改税额或费用金额后，再改发票总额，手改的值不变，差额可见并阻止提交；点击重新分配后才更新。（前端测试）
4. [x] 混合税率、多费用时，“按可登记余额分配”不超余额，余额不足时显示未分配差额，每条费用的税额按各自税率计算。（单元测试）
5. [x] 超额、分配不平、版本过期时，服务端拒绝且不部分保存，回归现有服务端测试；前端提示错误并保留输入。
6. [x] 无核销、无对冲的已登记发票可以修订，界面显示原值与修改后值对照，保留修订历史。（前端测试 + 浏览器）
7. [x] 有核销或对冲时显示影响并禁止保存。（现有测试回归 + 浏览器）
8. [x] 真实浏览器验证简单登记表单、阻断提示和修订流程。用户已授权使用和修改开发库中的测试财务数据来制造样本。
9. [x] 批量勾选两张账单：默认总额等于两张账单余额合计并已分配平；改总额后显示差额；继续添加发票默认总额为剩余余额。（单元/组件测试 + 浏览器）

10. [x] 六类票种登记和修订实际落库、三类专票缺抬头资料拒绝；正式迁移对票据、抬头默认及修订前后快照一次性映射且经济事实不变。（真实隔离 PostgreSQL + 前端选项/展示测试）

## 关键决策

- 建议税额直接预填（用户 2026-11-15 选定），而非“采用”按钮；同步修改发票规范中“不自动算税”的表述为“前端预填可编辑建议、服务端不算税”。
- 默认总额带出所选账单未登记余额合计（R7，用户追加）。

## 不在范围内

- 服务端分配算法与自动分摊接口；R8 所需的票种枚举、正式迁移和契约注释/生成物属于本期范围。
- 自动反核销、反对冲。
- 免票、作废、红冲流程的改动。
