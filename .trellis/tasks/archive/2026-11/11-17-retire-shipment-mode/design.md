# 技术设计

## 最小行为差异与落点

移除没有当前业务用途的运输模式录入与存储，退役误称独立自拼业务的只读汇总，普通费用改用中性名称。真实落点是Proto→service→biz→data及页面领域适配器；仅隐藏控件会留下默认写入、拆票复制和数据库列，因此按完整链一次性删除。

## 文件与生成边界

1. 以research/scope-audit.md为入口删除order.proto的ShipmentMode枚举和3处字段；在各消息reserved字段号13/11/12及shipment_mode名称。删除ListOrderConsolidations及其专用请求、响应、成员、汇总、件重尺消息。
2. 同步删除service枚举/读写转换、汇总方法，biz枚举/字段/校验/创建意图哈希/汇总仓储接口和对象，data创建更新投影、拆票复制和汇总查询。清除由删除造成的未使用导入，不重构相邻逻辑。
3. 从Ent Order Schema移除shipment_mode，通过现有Ent生成入口更新生成物，新增正式SQL迁移删列。历史迁移仍按原顺序执行；不修改既有Migration校验和。
4. 前端删除两类公共表单模式片段及模板插槽、form-values和所有适配器读写。sea-order-policy仅保留仍实际使用的托运类型策略项。删除ConsolidationDrawer、列表接入及模板回调；普通列表菜单维持现有动作。
5. routes.ts作为标题真相源改为“费用明细”，同步工作台提示及标题测试，保留现有路径和页签身份算法。
6. 通过make -C server api生成Go绑定、OpenAPI与访问规则，再pnpm run generate:web-client；删除领域错误后运行node scripts/generate-error-catalog.mjs。所有生成物只由生成器更新。

## 数据与幂等

迁移仅删除失效模式列，不删除订单、单证、主单链接或货物费用，不回填成另一模式。先在隔离库覆盖NULL、传统货代、跨境三种模式前态，验证新增迁移前后其他业务字段与关系不变；再验证空Schema的完整正式迁移链。

orderCreateIntentHash在请求和已有订单比对时使用同一当前函数，删除失效字段后不增加旧哈希分支。实施时补查其持久化与重放路径，验证同键同意图重放和真实经营字段变化冲突。历史审计及不可变快照不改写；如发现额外持久指纹依赖，先回到本设计说明影响。

## 保留能力及局部精简证明

普通LCL不等于独立集运／跨境业务；保留全部ShipmentType、共享主单和箱货实体。汇总查询是仅供已退役RPC使用的投影，删除它不改变主单链接写路径。策略对象只删除无调用项，通过箱量计划和散杂计费吨定向测试证明保留行为。

## 验证与风险

跨层契约及Schema变更属于高风险退役，定向验证后运行check:fast；不以构建替代迁移或业务验证。真实数据库测试必须使用独立数据库并实际运行，禁止把SKIP记为通过。页面四类新建/编辑保存、LCL共享主单、拆票复制、费用导航和相邻菜单分别回归。

本次无新权限、事务或版本设计，不改变锁顺序。后续若需要重新经营小单业务，单独按真实闭环设计，不恢复无效模式字段作为占位。
