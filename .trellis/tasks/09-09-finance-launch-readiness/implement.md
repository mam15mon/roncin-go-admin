# 财务模块上线收口实施计划

## 1. 实施前提

- 当前阶段只完成计划；用户复核并在后续消息明确批准后才运行 `task.py start`；
- 开始前重新检查 `git status`，来源不明或与财务重叠的未提交改动必须先报告；
- 不兼容历史数据，但清库、删数据或重建开发数据库仍属于破坏性动作，必须另行取得授权；
- 每个阶段先做定向验证并独立提交，提交信息使用中文 Conventional Commits；
- 契约和 Ent Schema 先改真相源，再统一生成，禁止手改生成代码；
- 第一轮实施与定向测试使用 Trellis 实施代理；Codex 主会话复核真实差异、跨层数据流和提交。

## 2. 阶段依赖

```text
Phase 1 权限组织范围与公共 DTO
  ├── Phase 2 往来结算账户
  │     └── Phase 3 批量建账与多币种折算
  │             └── Phase 4 同币种对冲
  ├── Phase 5 发票部分分摊
  └── Phase 6 汇总、逾期与提成约束

Phase 3 + Phase 4 + Phase 5 + Phase 6
  └── Phase 7 跨链路验收与最终门禁
```

Phase 5 依赖账单 DTO 的组织、账户和最终账单币种语义，但可在 Phase 3 稳定后独立实施。
Phase 4 必须等待最终账单币种与余额模型稳定。Phase 6 的跨组织汇总依赖 Phase 1。

## 3. Phase 1：统一财务权限组织范围

目标：账单、发票、资金流水、核销、对冲和提成均按各自权限码的数据范围读取和写入，不固定
任何角色或公司。

重点文件：

- `server/api/finance/v1/settlement.proto`
- `server/internal/service/settlement_*.go`
- `server/internal/biz/finance_*.go`
- `server/internal/data/finance_*.go`
- `web/src/pages/finance/**`

步骤：

1. 盘点每个 RPC 的权限码及 read/create/update/status 动作；
2. 为财务 DTO、列表项和详情补 `organization_id`、`organization_name`；
3. 各用例用具体权限码解析 readable/writable 组织集合；
4. 仓储查询显式应用 `OrganizationIDIn`，详情与写入同时约束 ID 和组织集合；
5. 来源驱动的创建从来源实体确定唯一组织；无来源创建显式选择一个 writable 组织；
6. 拒绝发票、核销、对冲或提成混用多个组织来源；
7. 前端列表、详情、导出和确认框增加所属组织，筛选候选只来自权限范围；
8. 增加全部组织、指定组织、组织树、当前组织、只读拒写和无权限拒绝测试。

建议提交：

```text
feat(finance): 统一财务权限组织范围
```

## 4. Phase 2：往来单位结算账户

目标：账户直接归属往来单位，支持多账户、应收/应付用途、币种默认值和账单快照。

重点文件：

- `server/internal/data/ent/schema/partner_account.go`
- `server/api/partner/v1/partner.proto`
- `server/internal/biz/partner_account.go`
- `server/internal/data/partner*.go`
- `server/internal/service/partner_account.go`
- 往来单位账户管理页面与账单工作台

步骤：

1. 将账户外键从角色调整为 `partner_id`，删除角色专属账户类型假设；
2. 增加账户用途、应收/应付默认值、币种、SWIFT 和启停约束；
3. 同单位、币种、用途默认账户切换在事务内锁定并由唯一约束兜底；
4. 列表按往来单位、用途、币种、启用状态查询；
5. 账单增加账户 ID 及名称、户名、银行、账号、币种、SWIFT 快照字段；
6. 草稿账单允许改选并更新快照，确认后拒绝修改；
7. 前端支持同一主体维护应收、应付或两者通用账户，不按角色复制；
8. 验证错单位、错币种、错用途、停用账户、并发切默认账户均被拒绝。

生成与定向验证后建议提交：

```text
feat(finance): 建立往来结算账户与账单快照
```

## 5. Phase 3：批量建账与账单币种

### 5.1 契约和领域计算

1. 扩展 `BillGroupingPolicy`，加入账单模式与 `split_by_currency`；
2. 普通模式服务端预览和创建均拒绝应收、应付混合费用；
3. 保留组织、结算单位、本位币强制边界，按可选币种/税率/订单形成确定性叶子；
4. 关闭分币种时按结算单位继承默认结算币种，缺失时要求显式配置；
5. 账单日期驱动汇率解析，相同原币到目标币种统一使用一条组合汇率；
6. 支持确认前人工覆盖组合汇率，强制原因并记录建议值与操作者；
7. 缺少有效汇率时 fail-closed，不做任何静默回退；
8. 每条账单明细固化原币和目标账单币种金额及完整汇率快照；
9. 账单头、明细与舍入尾差进行不变量检查；
10. 预览令牌绑定费用版本、策略、币种、日期、汇率、账户和分组配置；
11. 创建事务内重读、稳定加锁和重新计算，整批原子提交。

### 5.2 工作台交互

重点文件：

- `web/src/pages/finance/bills/components/BillCreationWorkbench.tsx`
- `BillSplitStrategyCards.tsx`
- `BillGroupCard.tsx` 及就近拆出的导航/汇总组件

步骤：

1. 费用管理允许混合选中方向，但混合时禁用普通账单并显示准确原因；
2. 默认开启分币种、分订单，关闭分税率；结算单位显示为不可关闭的固定边界；
3. 将扁平服务端叶子投影为结算单位 → 可选维度的层级标签；
4. 表单值按 `group_key` 保存，禁止用数组下标绑定叶子；
5. 展示叶子总数、完成数、缺失数、当前叶子金额和按原币分组的批次总计；
6. 每个叶子独立配置币种、日期、账户、组合汇率、预计开票值和备注；
7. 币种、日期、汇率或拆分策略变化后重新预览，latest-wins 丢弃迟到响应；
8. 保存前校验全部叶子并定位首个错误；
9. 一次保存全部叶子，成功页展示实际生成的全部账单编号；
10. 回归批量确认逐账单 `expected_version`。

重点测试：

- 单一方向、多结算单位、多币种、多税率、多订单的组合矩阵；
- 取消分订单后的正确合并；
- 混合方向普通账单前后端拒绝；
- 关闭分币种后的默认币种、人工改选、缺汇率和人工汇率审计；
- 14 家单位、40 条费用的导航、状态保持和整批校验；
- 两次快速改币种/日期时旧预览不覆盖新预览；
- 并发抢占同一费用只有一个批次成功。

建议拆成两个可验证提交：

```text
feat(finance): 支持可配置拆单与多币种折算
feat(web): 完善批量建账层级工作台
```

## 6. Phase 4：同币种对冲

目标：财务主动选择对冲时，保留应收/应付原始账单并用独立结算单抵销相同最终账单币种余额。

步骤：

1. 新增对冲单、对冲分摊 Ent Schema 与 Proto；
2. 增加预览、创建、确认、反转、列表和详情 RPC 及权限码；
3. 对冲预览按组织、结算单位、最终账单币种分支计算双方余额和较小值；
4. 事务内稳定锁定全部来源账单，校验版本、状态、方向和可用余额；
5. 创建应收、应付分摊并更新双方未结余额；
6. 反转恢复双方余额并保留审计，不触碰发票和账单折算快照；
7. 前后端拒绝跨组织、跨结算单位和不同最终账单币种；
8. 对冲工作台明确展示毛额、抵销额和净应收/净应付；
9. 验证相等、净应收、净应付、部分余额、并发和反转场景。

建议提交：

```text
feat(finance): 支持同币种应收应付对冲
```

## 7. Phase 5：发票多对多部分分摊

目标：一张发票可分摊多张账单明细，一条账单明细可分多次开票或收票。

步骤：

1. 调整 `FinanceInvoiceBill` / `FinanceInvoiceLine` 或新增最小分摊实体，删除整账单唯一占用约束；
2. API 改为提交账单明细 ID 与本次价税合计金额；
3. 服务端按明细税率计算未税和税额，末次分摊吸收尾差；
4. 创建时稳定锁定来源账单和有效分摊，重新计算可开余额；
5. 同一发票校验同组织、结算单位、方向、账单币种、本位币和开票抬头；
6. 允许同结算单位不同银行账户的账单合并，账户只做来源追溯；
7. 取消、作废、红冲使对应分摊失效并准确恢复余额；
8. 发票确认按实际开票日获取汇率，确认前允许财务调整，确认后固化；
9. 销项使用开具语义，进项使用收票语义；
10. 页面按账单展开明细，显示总额、有效已开、本次和剩余金额；
11. 详情展示账单预计开票值、发票实际值和差异。

重点测试：部分开票、多发票累计、跨账单合票、不同账户合票、超额与并发争抢、尾差、取消/
作废/红冲恢复、进项文案和实际开票日汇率。

建议提交：

```text
feat(finance): 支持发票明细部分分摊
```

## 8. Phase 6：汇总、逾期和提成约束

### 8.1 汇总与逾期

1. 账单、发票、资金、核销的列表与汇总提取共享有效谓词；
2. 汇总 DTO 改为按本位币返回数组；
3. 账单查询增加未结清、逾期和到期日范围；
4. 服务端按统一业务日期派生 `overdue_days`；
5. 前端显示按本位币分组的逾期应收，不混币；
6. 验证草稿、取消、红冲、反核销均不进入有效指标。

建议提交：

```text
fix(finance): 统一财务汇总与逾期口径
```

### 8.2 提成防重与发放闭环

1. 将基础提成唯一性收紧到核销、员工、人员角色，不以规则 ID 放开重复；
2. 增加数据库唯一约束和 Biz 冲突错误；
3. 保留确认前来源指纹复核；
4. 补齐 `CONFIRMED → PAID` 的操作者和时间；
5. 验证反核销对草稿、已确认未发、已发提成的处理和扣回调整。

建议提交：

```text
fix(finance): 防止基础提成重复计提
```

## 9. Phase 7：生成、验收与最终门禁

### 9.1 每个契约阶段

按实际变更运行并审阅：

```bash
go -C server generate
make -C server api
pnpm run generate:web-client
git diff --check
```

不得把无关生成漂移带入提交。

### 9.2 定向验证

服务端按实际包运行：

```bash
go -C server test ./internal/biz/... ./internal/data/... ./internal/service/...
```

前端按实际受影响文件运行：

```bash
pnpm --dir web exec vitest run <受影响测试文件>
pnpm --dir web exec biome lint <受影响文件>
pnpm --dir web tsc
git diff --check
```

### 9.3 PostgreSQL 连续链

复用并扩展现有财务验收编排，覆盖：

1. CNY 应收主链不回归；
2. 应收外币链不回归；
3. 应付外币费用 → 账单 → 进项发票 → 付款 → 核销与汇兑损益；
4. 多结算单位批量建账、关闭分币种折算和人工汇率；
5. 发票部分分摊、并发超额拒绝、作废/红冲释放；
6. 同币种对冲、净额、反转和并发；
7. 提成确认、发放与反核销扣回；
8. 多种角色数据范围、只读拒写和无权限组织拒绝；
9. 多本位币汇总不混算。

### 9.4 最终检查

Codex 主会话复核：

- Proto → Service → Biz → Data → Ent → Web 字段完整往返；
- 所有事务均经统一封装，事务内仓储均使用 `Data.client(ctx)`；
- 所有多行锁稳定排序，版本与幂等摘要完整；
- 财务权限没有角色名、公司名或当前工作区硬编码；
- 不同动作没有借用 read 或其他动作的数据范围；
- 不存在不同币种直接相加、缺汇率静默回退或前端金额充当真相；
- 未加入历史兼容、无关抽象和超出 PRD 的功能。

整个任务完成后，由于属于跨层财务高风险变更，执行一次：

```bash
pnpm run check
```

若生产入口、依赖或构建配置发生变化，再增加 `pnpm run build`；否则不把构建作为固定门禁。
