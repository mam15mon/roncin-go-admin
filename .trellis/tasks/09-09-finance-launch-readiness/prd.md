# 财务模块上线收口

## 目标与用户价值

在不重建现有财务架构的前提下，收口订单费用、账单、发票、资金流水、核销和提成的上线业务规则，使业务与财务人员能够完成应收、应付、外币和异常冲回闭环，并让跨组织授权在各财务页面保持一致。

本任务以快速上线为优先：项目尚未上线，不兼容历史数据，不建设完整 ERP、总账或银行系统；只处理会造成错误金额、重复计提、权限链路断裂或日常财务无法操作的问题。

## 已确认事实

1. 现有主链为“订单费用确认 → 批量生成并确认账单 → 发票与资金流水并行 → 多对多部分核销 → 汇兑损益与已实现收入 → 提成确认/发放”。领域拆分合理，本任务不更换架构。
2. 批量建账单已经具备服务端预览令牌、幂等、事务、稳定加锁顺序和创建时重新校验。
3. 已出账费用仅能在所属账单仍为草稿、组织策略允许且字段在白名单内时修改；费用、账单行和账单汇总在同一事务内更新。已确认账单不可反改。
4. 核销已经支持多对多、部分核销、应收/应付、外币快照、汇兑损益和反核销；反核销会处理关联提成。
5. 提成以有效应收核销为来源，按已实现收入或已实现毛利计算；确认时重新校验来源指纹，确认后锁定相关订单费用，后续差异使用提成调整单。
6. 当前发票关联以整张账单金额为单位，同一账单只能进入一个有效发票记录，一张发票可以合并多张账单；目标业务口径已改为账单与发票多对多，并允许部分开票。
7. 当前销项和进项共用 `ISSUED` 状态及“确认开具”等前端文案。
8. 当前同一核销、员工、规则只允许一个未取消提成，但不同规则可以针对同一核销和员工分别生成，存在基础规则重复计提的可能。
9. 账单已保存到期日和未核销余额，但查询尚不支持到期日、仅未结清、仅逾期筛选，也没有逾期金额汇总。
10. 资金流水的我方账户和对方账户是文本快照；提成“已发放”是人工确认外部支付已完成的状态，不直接执行付款。
11. 现有一次性 PostgreSQL 验收覆盖 CNY 主链和 USD 本位币/EUR 业务币的应收外币连续链，但报告明确未覆盖提成 `CONFIRMED → PAID`、应付外币连续链、低权限拒绝及双组织隔离。
12. 当前仅账单读取和既有单据写操作使用权限解析出的多组织范围；发票、资金、核销和提成只认当前工作区组织。账单 DTO 又缺少所属组织，跨组织列表无法辨认数据归属。
13. 不同组织可以具有不同本位币。当前财务汇总 DTO 只返回一个 `base_currency`，数据层却可能把多个本位币分组金额累加后仅保留最后一个币种，不能直接用于跨组织聚合。
14. 当前账单金额汇总没有默认排除草稿和已取消账单；发票金额汇总可能包含已经取消或红冲但仍保留本币快照的记录，统计卡口径不等于“已确认账单”或“有效已开票金额”。
15. 往来单位账户当前已支持同一客户角色维护多个账户，但只查询 `customer` 角色，账户类型固定为 `customer_settlement`；供应商角色尚不能维护结算账户，账单也没有保存对方账户引用或快照。目标模型应改为账户归属往来单位，并由账户自身的应收/应付用途决定可用方向，避免同一账户在双重角色下重复维护。
16. `Partner` 是公司主体，客户、供应商和国外代理是可同时存在的业务角色；“同行”是客户分类而非互斥角色。同一同行既可能委托我方形成应收，也可能接受我方委托形成应付，甚至在同一结算周期同时存在双向往来。
17. 当前批量建账工作台已经支持“按订单”“按税率”两个可选拆分维度，并通过服务端预览令牌、分组标签和逐组表单批量创建账单；但服务端把收付方向、结算单位、原币和本位币全部写死为强制分组键，尚不支持财务自主选择是否按币种拆分。
18. 旧系统的成熟交互是“选费用 → 勾选拆分维度 → 以层级标签预览多张账单 → 逐张编辑 → 批量保存”。顶部维度包括结算单位、分币种、分税率和分订单；结算单位及收付方向属于不能跨越的账单边界，币种、税率和订单由财务决定是否进一步拆分。
19. 一次普通建账批次可以选择同一收付方向下的多个结算单位；系统先按结算单位绝对隔离，再按启用的币种、税率和订单维度逐层细分。不同结算单位绝不进入同一张账单，但不要求财务按结算单位重复打开工作台和逐次保存。
20. 旧系统通过“结算单位 → 账单币种 → 订单”等层级标签定位一个叶子分组；下方只展示并编辑当前叶子对应的一张拟生成账单，点击任一层其他标签会联动切换后续层级及表单内容。
21. 旧系统在同一次建账中展示全部选中费用按币种分别计算的批次总计，同时展示当前叶子账单金额；一次保存会为所有叶子组合批量生成各自的账单编号。取消“分订单”后，同一结算单位、币种及其他有效分组维度一致的多票订单合并为一张账单。
22. 旧系统在账单编辑阶段展示按“开票汇率”折算的预计开票金额，例如 `1878 USD × 6.7828 = 12738.1 CNY`，并允许逐张调整汇率和发票类型。目标系统已明确：账单上的该汇率和折算金额只作为预估对账值，不约束后续真实发票。
23. 关闭“分币种”时，每个结算单位的叶子账单默认继承该往来单位主数据中的默认结算币种；未配置时必须由财务显式选择，禁止静默采用组织本位币、CNY、USD 或费用中第一个币种。
24. 同一批次的不同结算单位分别继承和改选自己的账单币种，互不联动；改选只重算该结算单位受影响的叶子，但会使整个批次的旧预览令牌失效。
25. 自动账单折算汇率以账单日期为基准；账单日期尚未填写时可用当前业务日期提供临时预览，但填写或修改账单日期后必须重新解析汇率、重算金额并签发新预览令牌。
26. 人员能查看哪些财务数据、能执行哪些财务操作以及权限覆盖哪些组织，全部由角色配置的权限码与数据范围决定；产品代码不得根据人员所属公司、岗位名称或“财务”字样固定授予任何能力。

## 上线原则

1. 不为上线收口引入新的财务微服务、工作流引擎、事件总线或通用规则 DSL。
2. 不兼容历史数据；若契约或约束需要调整，直接迁移当前开发库和测试数据，不增加旧字段 fallback、双写或静默修复。
3. 服务端继续作为金额、状态、权限范围和分组结果的唯一真相源；前端只负责选择、展示和明确反馈。
4. 保留现有 Decimal、本位币快照、幂等键、版本号、事务和锁机制，不以快速上线为由削弱金额正确性或并发约束。
5. 读取和写入必须使用权限自身解析出的组织范围；页面当前组织不能代替目标资源组织的权限判断。
6. 会计凭证、税务申报、银行真实支付与工资发放属于外部事实；首版只记录可审计的业务状态，不宣称已自动完成外部动作。

## 需求

### R0 往来结算账户与账单账户快照

- 同一往来单位可以维护多个结算银行账户；账户直接归属于往来单位，不因该单位同时具有客户和供应商角色而重复创建。
- 账户至少包含账户名称/户名、银行名称、银行账号、币种、SWIFT（适用时）、启停状态、允许用途和默认标识。
- 账户允许用途为应收、应付或两者；用途只控制账户可被哪种方向的账单选择，不要求为同一银行账户按客户、供应商或国外代理角色重复建档。
- 同一往来单位、用途和币种最多一个默认账户；默认账户只用于页面预选，不替代创建账单时的显式选择。
- 应收账单只能选择结算单位名下允许应收用途的启用账户；应付账单只能选择结算单位名下允许应付用途的启用账户。账单方向由具体费用事实决定，而不是由公司只能拥有某一个角色决定。
- 账单账户币种必须与最终账单币种一致；选择分币种时通常等于费用原币，关闭分币种并折算成统一账单币种时则以统一账单币种为准。不允许选择其他往来单位、已停用、用途不符或币种不匹配的账户。
- 每个账单创建分组必须显式提交一个 `settlement_account_id`。默认账户只用于界面预选，服务端不得在缺失时静默猜测。
- 账单创建时固化账户 ID、账户名称/户名、银行名称、银行账号、币种和 SWIFT 快照；账户后续修改或停用不得改变既有账单快照。
- 批量建单预览需要为每个拆单分组返回结算单位、方向和币种，前端据此加载候选账户并逐组选择；创建事务内重新校验账户归属与状态。
- 草稿账单可变更为同一结算单位、正确用途和币种下的其他启用账户，并更新快照；账单确认后账户快照不可修改。

### R1 跨组织财务权限一致性

- 统一费用明细台账、账单、发票、资金流水、核销、提成的列表、详情和动作组织作用域。
- 财务页面采用“授权组织聚合视图”：页面只聚合当前用户对该项功能实际拥有读取权限的组织数据。角色数据范围为全部组织时展示全部组织；范围为指定组织、组织树或当前组织时，只展示相应范围。
- 不存在“财务人员天然可看全部公司”的产品规则。不得在前后端根据角色名称、用户名、部门、所属公司或是否进入财务路由直接放行。
- 每项读取和写入动作都继续由角色中对应的权限码及其数据范围控制。拥有某动作权限且该权限的数据范围覆盖目标公司时才允许执行；没有对应权限码时，即使能查看全部公司也不能执行该动作。
- 角色管理员可按实际职责分别配置账单、发票、资金、核销、对冲和提成等权限及各自数据范围；不同动作权限可以具有不同范围，任何一个权限都不能借用另一个权限的组织范围。
- 聚合列表必须展示组织名称或其他明确组织标识，避免跨组织视图中误操作。
- 所有财务列表默认提供“所属公司”列与公司筛选器；详情页、抽屉、导出和操作确认框也必须显示所属公司，不能只在列表首屏显示一次。
- 禁止前端传入任意组织 ID 扩大范围；组织集合由认证主体和权限解析结果生成。
- 创建动作必须确定唯一目标组织并验证该动作权限的数据范围。由账单、费用或其他来源资源发起时，目标组织从来源资源确定；无来源的独立创建由财务显式选择目标公司，不再强制归属当前工作区，且候选公司只能来自该动作权限的可写组织集合。
- 动态候选必须与其用途使用同一权限范围：创建资金流水时只能加载所选可写组织的往来单位；创建提成时核销、规则和人员候选必须来自同一提成管理可写组织。客户端不得上传权限码，也不得在未选公司时静默退回当前工作区候选。
- 从跨组织财务列表进入的财务详情继续按相同财务读权限授权并显示所属公司；不得要求用户额外具备订单或客商详情权限才能读取已经获准查看的财务明细。完整业务页面仍按其自身权限独立控制。
- 跨组织列表必须返回所属组织；金额汇总必须按本位币分组，禁止把不同本位币金额合并成一个数字。
- 跨组织能力不能允许一张发票、资金核销或提成计算混用多个组织的业务对象。
- 从已有账单、资金流水或核销等资源发起后续动作时，组织必须由来源资源确定，不接受前端自由指定；无来源资源的独立创建必须显式选择一个有写权限的目标公司，禁止跨公司混合业务对象。

### R2 发票业务语义收口

- 销项方向使用“确认开具”“开票日期”“作废/红冲”等语义。
- 进项方向使用“确认收票”“发票日期/收票登记”“退票或进项红冲登记”等语义；不得要求用户把进项发票理解为本公司开具。
- 后端可以继续复用 `ISSUED` 状态，但 API、审计和页面提示不得把进项动作错误描述为销项开具。
- 草稿发票可取消；已生效发票的作废与红冲必须区分，并保留号码、日期、原因、操作者和时间。
- 首版不自动判断税务申报期或电子税局状态，但危险操作文案必须说明只有在线下税务条件允许时才能作废，否则应红冲。
- 账单创建或确认阶段可以保存并展示预计开票汇率、预计开票币种和预计开票金额，供财务与结算单位核对；这些字段必须明确标注“预计”，不得作为发票已开具、已收票或本位币入账事实。
- 实际创建并生效发票时，以发票实际开票日作为默认汇率日期，通过组织汇率配置重新解析真实开票汇率；财务可以在确认前手工调整。
- 发票确认后固化实际开票汇率、汇率来源、汇率日期、关联汇率设置、本位币金额及操作者；账单上的预计开票汇率不得强制覆盖或限制发票的实际汇率。
- 发票详情需要同时展示来源账单的预计开票值与本发票的实际开票值及差异，差异仅作为可审计提示，不反向修改已经确认的账单金额。

### R3 开票粒度

- 账单与发票采用多对多分摊：一张发票可以引用多张账单的部分或全部可开金额，一张账单可以分多次进入多张发票。
- 分摊粒度固定为账单明细/费用项，不接受只有账单总金额而没有来源明细的模糊分配。
- 每条发票分摊必须保存来源账单、来源账单明细、来源费用、税率、原币金额、未税金额、税额和有效状态，形成不可变业务快照。
- 用户按具体账单明细填写本次价税合计开票金额；服务端依据该明细的税率和含税口径计算未税金额与税额，禁止前端自行计算后充当财务真相。
- 同一账单明细的全部有效发票分摊累计不得超过该明细价税合计；账单已开金额和剩余可开金额由其明细有效分摊汇总得到。
- 末次分摊该明细全部剩余金额时，服务端吸收十进制舍入尾差，保证累计未税金额、税额和价税合计分别等于来源明细快照。
- 创建发票时在事务内按稳定顺序锁定来源账单及相关有效分摊，重新计算余额；并发争抢最后可开余额时只能有一个请求成功。
- 发票草稿取消、已生效发票作废或红冲后，原分摊失效并准确恢复对应账单或明细的可开余额。
- 幂等重试必须返回原发票；相同幂等键但分摊意图不同必须返回冲突。
- 同一发票选择的分摊必须具有相同收付方向、结算单位、账单币种和本位币；禁止把不同结算主体、方向或账单币种拼入同一发票。
- 页面按账单展开可开明细，展示每条明细的费用名称、税率、总额、有效已开金额、本次开票金额和剩余可开金额；提交前展示发票未税、税额和价税合计。
- 发票分摊继承来源账单的结算单位与账户快照用于追溯；同一发票不得混入不同结算单位。同一结算单位下，不同结算账户的账单只要收付方向、账单币种、本位币和开票抬头一致，仍可合并到同一张发票，账户差异不作为税务拆票维度。

### R4 基础提成防重复计提

- 同一组织、同一人员角色、同一生效日期不得同时命中多条相互冲突的基础提成规则。
- 同一有效核销、同一员工、同一人员角色最多存在一张未取消的基础提成；不能通过选择不同规则重复计提。
- 额外奖励、补发和扣回使用现有提成调整单，不通过叠加基础规则实现。
- 提成确认前继续重算来源并校验来源指纹；来源变化时拒绝确认并要求取消后重新生成。
- `PAID` 明确定义为“财务确认线下已经实际发放”，不在本任务内接入银行或工资支付。

### R5 最小逾期应收能力

- 账单列表支持“仅看未结清”“仅看已逾期”和到期日范围筛选。
- 已确认、未全额核销且到期日在当前业务日期之前的应收账单显示“逾期 N 天”。
- 页面展示当前筛选范围内的逾期应收本位币金额；取消账单、应付账单和已结清账单不得计入。
- 首版只提醒，不因信用额度或逾期自动禁止接单、出单、开票或核销。

### R6 验收证据闭环

- 保留并复用现有一次性 PostgreSQL 验收编排，不再建设第二套验收框架。
- 补齐应付外币连续链：应付费用、账单、进项发票、付款、核销和应付汇兑损益。
- 补齐提成确认后标记已发放，并验证反核销对未发和已发提成的不同处理。
- 补齐跨组织读取、只读拒写、可写动作和无权限组织拒绝场景。
- 补齐部分核销后再次核销至结清，以及并发超额核销拒绝。
- 每个新增筛选、状态约束和错误原因都有对应领域/数据层测试；高风险链路用真实 PostgreSQL 验收。

### R7 财务汇总口径纠正

- 账单台账的有效金额默认只统计已确认账单；草稿与已取消账单不进入应收、应付和未核销经营指标。
- 发票“已开具/已收票金额”只统计仍有效的 `ISSUED` 记录；已取消和已红冲记录不计入正数有效金额。
- 资金流水金额只统计已确认且未取消记录，未核销金额以有效核销分配为准。
- 核销金额只统计有效核销；已反核销记录保留审计但不进入有效金额。
- 跨组织汇总按本位币分别返回和展示，不做未经定义的币种换算。
- 列表筛选条件与指标卡使用同一业务谓词；不得出现表格已过滤但统计仍计算全部状态的情况。

### R8 同一往来单位的双向往来

- 同一往来单位可同时存在应收费用、应付费用、应收账单和应付账单；系统不得因为其是同行或国外代理而强制只能选择一个方向。
- 应收与应付仍分别建账、分别保留原始金额、税额、币种、账户和审计轨迹。
- 财务在批量建单工作台显式选择“普通账单”或“对冲账单”；系统不得按往来单位或余额自动对冲。
- 普通账单的一次批量建账操作只能选择一个收付方向，不能混入相反方向费用，也不能由系统在同一批次中静默按收付方向拆成两批。
- 普通账单的一次批次可以包含同一方向下的多个结算单位；结算单位作为强制分组键分别生成账单，财务一次保存即可批量生成全部单位的账单，不需要按单位重复发起建账。
- 当同一结算单位同时存在应收和应付费用时，页面必须明确提示：“普通账单需将应收、应付分别建账，请先完成一个方向，再创建另一个方向。”财务需要对应收执行一次建账、对应付再执行一次建账，先后顺序由财务决定。
- 费用管理的批量选择不锁定收付方向，财务可以同时勾选应收和应付费用，以便检查双向往来或转入对冲流程。
- 当当前选择同时包含应收和应付时，“建普通账单”操作必须禁用或在触发时明确拒绝，并提示“普通账单不能同时包含应收和应付，请只保留一个方向后再建账，或改用对冲账单”；不得自动取消其中一方、静默拆成两个普通批次或替用户切换为对冲模式。
- 即使绕过前端直接调用预览或创建接口，服务端也必须拒绝普通模式下的混合方向费用；前端禁用按钮只用于提前反馈，不能成为唯一业务约束。
- 完成第一个方向的建账后，另一方向未建账费用保持原状态并可继续发起下一次普通建账；系统不得因为一次普通账单创建而自动处理或占用相反方向费用。
- 对冲账单允许财务选择同一往来单位的应收与应付费用，但底层仍分别生成应收、应付原始账单，并额外生成一张对冲结算单关联双方账单与抵销金额。
- 对冲金额为双方可对冲余额的较小值；应收大于应付时形成净应收，应付大于应收时形成净应付，相等时净额为零。
- 原始应收、应付账单继续分别承担销项/进项发票、税额和毛额审计；对冲结算单只表达双方结算抵销事实，不把净额伪装成发票金额。
- 对冲确认后，在双方原始账单上形成独立有效的对冲分摊；普通资金核销只处理抵销后的剩余余额。
- 对冲创建、确认、取消或反转必须具备幂等、版本校验、稳定加锁顺序和完整审计；反转后准确恢复双方账单未结清余额。
- 不允许跨往来单位或跨组织对冲；首版只允许最终账单币种相同的应收、应付账单互抵，不要求来源费用原币相同。
- 若不同原币费用已经在各自账单确认时按正式账单折算汇率转换并锁定为相同账单币种，可以按该账单币种对冲；对冲不得重新解释或改写来源费用和账单折算汇率。
- 最终账单币种不同的应收、应付账单不得直接对冲。首版不提供对冲汇率、跨币种抵销或对冲汇兑差额；需要对冲时应在账单确认前先形成相同账单币种，或分别通过正常收付款核销。
- 对冲金额、双方已对冲金额、剩余余额和反转恢复均以双方共同账单币种计算；对冲单只保存一个币种，不存在混合币种总额。
- 对冲模式至少各包含一笔正向应收和应付，单边费用应使用普通账单。

### R9 批量建账分组与逐单编辑

- 批量建账工作台沿用旧系统已经验证过的操作模型：选择费用后，由财务设置拆分维度，服务端实时返回确定性的拟生成账单分组，前端以层级标签逐张定位和编辑，最终一次批量保存。
- 分组键分为两类：
  - 强制边界：组织、结算单位和本位币。不同强制边界的费用永远不能进入同一账单；“结算单位”在界面上可以显示为默认勾选但不可关闭，避免给用户可以跨单位合并的错误预期。收付方向不是普通模式下的自动拆分维度，而是整次建账的准入条件；普通模式一次只能选择应收或应付，对冲模式才允许同时选择两个方向并分别形成原始账单。
  - 可选拆分维度：计价币种、税率和订单。勾选表示该字段值不同就分别生成账单；未勾选表示不因该字段不同而额外拆单，但仍必须满足账单金额与后续结算口径。
- 首次进入工作台的默认值对齐旧系统：按结算单位固定拆分、默认勾选“分币种”和“分订单”、默认不勾选“分税率”；用户每次建账均可调整可选维度，不把上一次选择静默作为全局规则。
- 选择“分币种”时，不同费用计价币种分别生成账单，账单币种等于该组费用币种；每张账单分别保存账单汇率、本位币金额和对应币种的结算账户快照。
- 不选择“分币种”时，必须先确定统一的账单币种及费用折算口径；不同币种费用不能直接相加，也不能只在界面分栏而让一张账单同时拥有多个未定义的应收付余额。
- 关闭“分币种”时，每个结算单位分支默认采用该往来单位主数据中的默认结算币种；不同结算单位独立继承、独立改选，修改一家单位不得改变其他单位的币种或金额。未配置默认结算币种时，该分支必须由财务手工选择后才能完成预览和创建。
- 自动账单折算汇率以各叶子账单的账单日期为汇率日期；账单日期未填写时，系统可以当前业务日期给出临时预览，但必须清楚标识。财务填写或修改账单日期后，重新解析对应日期汇率并重算该叶子。
- 系统按每个叶子中的“费用原币 → 账单币种”组合解析一条默认账单折算汇率；同一组合下的全部费用必须使用相同汇率，禁止逐条费用设置不同汇率制造无法解释的账单金额。
- 财务可在账单确认前覆盖系统解析出的币种组合汇率；人工覆盖必须填写调整原因，汇率来源固化为 `MANUAL`，并记录原系统建议汇率、调整后汇率、操作者和时间。切换回系统汇率时重新按当前账单日期解析。
- 人工汇率只能在当前用户具备账单写权限时修改；账单确认后，系统汇率与人工汇率均锁定，后续差异不得反写账单，应在真实发票、资金核销或专门调整流程中留痕。
- 原币与目标账单币种相同的明细折算率固定为 `1`；币种不同时，若汇率配置中不存在直接汇率且无法通过合法基准币套算，必须阻断该叶子的创建并提示“未找到 [原币] 到 [目标账单币种] 在 [账单日期] 的有效折算汇率，请先维护汇率”。禁止用 `1`、`0`、最近任意日期或其他静默回退值代替。
- 账单币种、账单日期或任何账单折算汇率输入发生变化时，必须重新计算受影响的费用折算明细，并轮转整个批次的服务端预览令牌；旧请求迟到不得覆盖新结果，旧令牌不得继续创建账单。
- 每条折算明细固化费用原币、原币金额、目标账单币种、账单币种金额、折算汇率、汇率来源、汇率日期和关联汇率设置；所有明细折算金额之和必须等于账单头金额，舍入尾差按确定性规则落在最后一条明细。
- 选择“分税率”时，不同税率分别生成账单；不选择时允许同一账单包含多个税率，但税率、含税金额、未税金额和税额仍逐明细固化，后续发票按明细分摊，不使用账单头的单一税率替代。
- 选择“分订单”时，不同订单分别生成账单；不选择时允许同一结算单位的多个订单合并，账单明细仍保留订单 ID、订单号和业务类型以供追溯。
- 预览区按照固定的层级顺序展示标签：结算单位为第一层；启用“分币种”时账单币种为下一层；启用“分税率”时税率为下一层；启用“分订单”时订单为下一层。未启用的维度不显示对应层级。
- 层级标签只是对服务端叶子分组的导航表达，真正的分组结果仍以组织、单一收付方向、结算单位、本位币和所有已启用维度组成的完整组合键为准，不能依赖前端点击路径自行拼单。
- 切换上层标签时，下层标签自动切换到该分支的有效选项，并显示该分支下最近选择或首个叶子；下方表单始终只编辑当前叶子对应的一张拟生成账单，切换标签不能丢失其他叶子已经填写的内容。
- 顶部或侧边必须持续展示叶子总数、已完成配置数和仍缺必填配置数，避免 14 家结算单位、40 笔费用等大批次下遗漏某张账单的账户、汇率或日期。
- 每个拟生成账单独立编辑账单标题、账单日期、账期/到期日、结算账户、汇率和备注；任何影响分组结果的维度变化都必须重新请求服务端预览，并使旧预览令牌和旧分组表单失效。
- 页面同时展示当前标签金额和本次选中费用的批次总计。批次总计按币种分别列示；只有币种相同的金额才能相加，禁止用一个币种标签包装多个币种的算术和。
- 保存前必须校验所有叶子分组均已完成必填配置；任何一个叶子缺失结算账户、账单币种、必要汇率或日期时，整批不得部分创建，并应直接定位到首个错误叶子。
- 保存时提交当前分组策略、全部分组配置、预览令牌和幂等键；服务端在事务内重读并锁定费用、重新计算分组和金额，任何费用状态、版本、结算单位、收付方向、币种、税率或订单事实变化均应拒绝旧预览创建。
- 保存成功后返回本批次实际生成的全部账单；批量确认仍逐账单携带 `expected_version`，不能用批次操作绕过单据状态机和并发校验。
- 费用折算到账单币种时使用的账单折算汇率、账单页面用于核对的预计开票汇率、发票生效时的实际开票汇率和资金流水确认时的结算汇率属于不同业务含义与时点，继续分别保存与审计；页面不得用一个“汇率”字段覆盖这些阶段。
- 关闭“分币种”后，将费用原币折算为统一账单币种的汇率会直接决定账单应收付金额，因此是账单事实并在确认后锁定；它不能被标记为仅供参考的预计开票汇率。预计开票汇率只用于把账单币种金额预估为未来发票金额。

## 验收条件

- [ ] AC0：一个往来单位可维护多个结算账户，同一账户可按用途供应收、应付或两者使用；账单只能选择正确用途、正确往来单位、启用且币种一致的账户，并保存不受主数据后续修改影响的账户快照。
- [ ] AC1：角色对组织 A、组织 B 具备某财务读取权限时，用户能在对应列表识别并查看两地数据；只有读取权限而没有目标动作权限时，对相关财务对象的写操作返回权限错误。
- [ ] AC2：账单、发票、资金流水、核销和提成对同一份权限范围得到一致结果，不再出现“能看账单但看不到对应发票/核销”的断链。
- [ ] AC3：销项发票呈现“确认开具”，进项发票呈现“确认收票”；相同后端状态不会造成方向相反的操作文案。
- [ ] AC4：草稿取消、已开票作废和已开票红冲分别保留完整审计信息，并正确释放账单开票占用。
- [ ] AC5：一张发票可分摊多张账单明细，一张账单及其明细可分多次开票；有效累计分摊不超过明细可开金额，并发争抢最后余额仅一个请求成功，末次分摊无舍入尾差，取消/作废/红冲后余额准确恢复。
- [ ] AC6：同一核销、员工和人员角色不能因选择不同基础规则生成多张有效提成；补发或扣回仍可通过提成调整单完成。
- [ ] AC7：提成 `DRAFT → CONFIRMED → PAID` 可完成，`PAID` 记录操作者和时间；已发提成对应的核销反转后生成可追踪的扣回调整。
- [ ] AC8：账单可筛选未结清、已逾期和到期日范围；逾期天数和逾期应收本位币汇总与真实未核销余额一致。
- [ ] AC9：应付外币链从费用到核销连续使用同一组业务对象，并断言各阶段汇率快照及应付汇兑损益方向正确。
- [ ] AC10：现有 CNY 和应收外币验收不回归；服务端检查、前端定向检查和最终风险匹配门禁通过。
- [ ] AC11：草稿、取消、红冲和反核销记录不进入对应有效财务金额；列表与指标卡在相同筛选条件下口径一致。
- [ ] AC12：跨组织列表逐行显示所属组织，不同本位币金额分别汇总，不产生“CNY 数字挂 USD 标签”等混币结果。
- [ ] AC13：同一结算单位、方向、原币、本位币和开票抬头一致时，即使来源账单选择了不同银行账户，也可以合并到同一张发票；账户差异不改变发票税务分组。
- [ ] AC14：同一同行或代理可以在不同业务中同时作为应收、应付结算单位，账户无需按角色重复维护，两种方向的账单和发票分别保留完整事实。
- [ ] AC15：财务可自主选择普通或对冲模式；对冲模式原子生成应收账单、应付账单和对冲结算单，按较小余额抵销并只保留净额待收付，发票仍按两边原始明细分别处理。
- [ ] AC16：同一批费用并发创建普通或对冲账单时只能有一个请求成功；对冲反转后双方账单余额准确恢复，既有发票和原始费用快照不被改写。
- [ ] AC17：财务在一次批量建账中可按结算单位强制分组，并自主开关分币种、分税率和分订单；默认值为分币种、分订单开启，分税率关闭。服务端预览标签数、逐组表单、批量创建结果与所选维度一致，切换标签不丢值，改变维度会使旧预览失效。
- [ ] AC18：预览同时展示当前拟生成账单金额和本批次所有费用总计；多币种总计分别列示，任何页面、接口或导出都不会直接相加不同币种金额。
- [ ] AC19：同一账单始终只有一个明确账单币种；不分币种时，各费用按确认的账单汇率折算并保留原币、原金额、折算率和账单币种金额快照，发票、资金与核销能够基于账单币种继续闭环。
- [ ] AC20：费用管理允许同时选择应收和应付；只选单一方向时可以创建普通账单，同时选中两个方向时“建普通账单”不可用并给出明确提示，服务端普通账单预览与创建接口同样拒绝混合方向。系统不会自动删选、静默拆成两个普通批次或自动切换对冲；财务只保留一个方向后分别执行两次普通建账，或主动选择对冲账单。
- [ ] AC21：同一方向的费用涉及多个结算单位时，普通建账工作台按“结算单位 → 已启用可选维度”的层级标签导航全部叶子账单；不同单位绝不合单，但财务一次保存即可原子批量生成所有叶子的账单编号，无需按单位重复操作。
- [ ] AC22：以 14 家结算单位、40 笔费用的批次为基准，页面能显示叶子总数、配置完成度、当前叶子金额和按币种分别列示的批次总计；任一叶子缺少必填配置时整批不创建，并定位到具体叶子。
- [ ] AC23：账单页面的预计开票汇率和预计开票金额有明确“预计”标识，不限制后续发票；发票默认按实际开票日解析汇率并允许财务在确认前调整，确认后固化真实汇率全套快照。账单预计值与发票实际值存在差异时可追溯，但双方互不反写。
- [ ] AC24：关闭分币种时，不同结算单位分别继承自己的默认结算币种且可独立改选；缺少默认值时必须手工选择。修改任一叶子的账单币种或账单日期只重算受影响叶子，但会轮转批次预览令牌，迟到响应和旧令牌均不能生效。
- [ ] AC25：自动折算以账单日期为汇率日期；仅账单日期未填时允许用当前业务日期临时预览。缺少直接或合法套算汇率时明确阻断，不使用 `1`、`0` 或任意日期回退；创建后的每条明细均可追溯原币金额、目标币金额和完整汇率快照，明细合计严格等于账单金额。
- [ ] AC26：同一叶子账单内相同“原币 → 账单币种”组合统一使用一条折算汇率；财务可在确认前按组合覆盖，但必须填写原因并记录系统建议值、人工值、操作者和时间，来源标记为 `MANUAL`。逐费用行设置不同汇率以及确认后直接修改均被拒绝。
- [ ] AC27：只有组织、结算单位和最终账单币种均相同且方向相反的有效账单可以对冲；来源费用原币可以不同，但已确认账单的折算事实不得被对冲改写。不同最终账单币种的对冲在前后端均被拒绝，系统不生成对冲汇率或跨币种汇兑差额。
- [ ] AC28：财务页面只聚合当前角色对该功能实际拥有读取权限的组织数据；配置全部组织、指定组织、组织树或当前组织等不同数据范围时，列表结果严格匹配。每行、详情、导出和操作确认均能识别所属组织，公司筛选有效，不同本位币分别汇总。无来源单据只能在该动作可写组织集合中显式选择一个目标组织；缺少权限码或目标组织不在数据范围时，前后端均拒绝。

## 非目标

- 会计科目、借贷分录、记账凭证、总账、会计期间和月末关账。
- 电子税局、开票平台、税务申报或发票真伪自动校验。
- 银行流水导入、自动匹配、资金账户余额、真实付款执行。
- 工资系统、提成付款批次或银行代发。
- 完整信用额度审批、超额阻单、坏账准备和逾期计息。
- 历史数据兼容、旧字段双写、旧流程 fallback 或开发数据自动修复。
- 新订单品类接入及与本任务无关的订单页面重构。

## 暂缓项

- 我方银行账户主数据与流水账户引用。
- 完整账龄区间报表、催收任务和信用风控。
- 自动判断发票是否跨期、已申报或只能红冲。
- 会计凭证和外部系统集成。
