## 需求

1. 全量列出受版本管理的文档，并盘点相关未跟踪文档；按现行说明、规范、历史计划、任务档案、框架模板、第三方许可分类。
2. 核对根目录及 server/web README、docs 开发配置说明、现行领域和开发规范中的功能状态、目录入口、依赖版本、命令、权限、工作区及数据流程。
3. 修正有源码证据的陈旧描述，统一跨文档口径，修复失效的仓库内导航；对不能从仓库证实的部署、外部服务和真实业务验收状态如实标注。
4. 早期计划、已归档任务与会话日志保留历史语义；仍可能误导现行开发的旧计划补充当前状态和权威入口。第三方许可及框架模板不做无依据改写。
5. 保存可审阅的核查清单，记录核查范围、差异、源码依据、处理和验证结果；按可验证分组提交中文 Conventional Commit。

## 验收标准

- 有覆盖所有受版本管理文档的分类清单，说明未修改类别的理由；不宣称逐条验证了未经执行的历史验收场景。
- 所有发现且有源码依据的现行文档差异均已修正；README 不再把已退役功能写成当前能力。
- 新增和修改的命令与 `package.json`、Makefile、CLI 参数一致，引用的源码路径及文档导航有效。
- 已执行文档适用的链接、命令和差异检查，并在核查记录中明确范围及未运行项；不因纯文档变更启动数据库写入或全量业务测试。
- 用户原有未提交目录完整保留，本任务改动已提交 Git。

## 范围外

- 修改业务代码、依赖、数据库、迁移、API 契约、权限或部署配置。
- 重写历史事实、补造验收结果、改动第三方许可证、自动升级 Trellis 或其框架模板。
- 保证未来代码变更后文档永久自动同步。
