# 技术设计：统一订单审核锁

## 状态与数据流

唯一运行态审核锁复用 Order 的 locked_at、locked_by、lock_generation 及 OrderLockRecord；“审核并锁定”原子生成审核依据与既有单证快照。整票 fee_review_status 不再作为并行的可写业务状态；finance_locked 不再用于编辑门禁或页面锁展示。费用内容版本、审核快照与历史事件按审计／并发用途保留，不能借这些字段恢复第二套审批。

数据流：订单页／费用管理 → Proto → service 身份及 DTO → biz 用例 → data 统一事务 → 审计与通知。service 不查 Ent，前端不自行推断权限和金额。数据库悲观锁及版本冲突检测继续使用；它们不属于用户操作的订单审核锁。

## 审核与授权

以现有 business.order.<type>.lock 权限作为统一“审核／解锁／补审”资格，依赖同品类必要的订单、费用读取权限。保留普通费用 create/update/delete 与财务建账、账单处理、票据、反核销和反对冲的独立职责。退役 system.finance.fee.review 的独立审批行为及入口，不能把旧费用审核角色自动扩权为所有品类订单审核人。

审核用例复用现有费用快照构建和单证版本能力：预览读取订单版本、费用内容版本／指纹、单证相关事实；执行在事务内复核并同时写 OrderLockRecord、审核快照、订单锁及审计。无单独“提交费用→整票待审冻结”步骤。允许具备权限的申请人自审，亏损说明沿用现有校验。

同公司另一名具备目标品类审核权限的人员可补审；实时校验用户、组织、成员及角色资格，不能只匹配原 locked_by，也不能拼接不同授权来源越权。原审核人和每次补审人保留不同记录。取消所有 AUTO_SETTLEMENT 触发路径、后台接线与展示分支。

## 普通编辑与建账

普通修改／删除资格 = 现有生命周期允许维护 + 订单未审核锁定 + 当前费用无有效账单关联 + 对应权限。新增没有源费用占用，但仍需校验订单与权限。复用 effectiveBillLinePredicate，草稿占用有效；详情、列表、批量操作和数据层写入口同源。

建账不再调用 validateApprovedOrderFees 的整票批准前置。选中费用必须为当前正式有效费用、无有效账单占用、无针对自身的待审变更；继续校验公司、方向、币种、结算单位及账户。不以同票另一笔待审申请整体阻止建账。批量建账保留现有整批事务语义。

服务端返回可执行动作及具体原因，前端统一消费。刷新覆盖订单锁、费用、申请、账单关联及财务进度；换公司不泄漏旧响应。ProTable 使用 request/actionRef，表单以 onFinish 管理提交。

## 补录／变更

统一用户入口为“费用补录／变更”，复用 OrderFeeCorrectionRequest 的 ADD／REPLACE／VOID；调减属于 REPLACE 的前后金额变化。原只支持应付新增的补录入口收敛到同一流程，避免平行实现。

申请依据改为当前 OrderLockRecord／lock_generation 与源费用版本、申请快照。执行前要求订单已人工审核锁定；REPLACE／VOID 源费用在提交和批准时都必须无有效账单占用。申请中的金额不进入正式明细、汇总或候选。

暂保留当前同票一份 PENDING 申请约束，不引入并行审批平台；申请仅阻止其源费用再次建账。同票 ADD 待审不阻止既有费用建账。解锁在存在 PENDING 时拒绝，并提示先撤回／退回；从而申请依据不会跨审核代次静默复用。

批准原子更新正式费用、申请终态、审核历史、必要提成差额及通知；以现有未建账更正的历史保留方式记录原费／替代关系，作废不再参与当前费用汇总，历史保留。任何内部历史冲回不得产生待结算账务；已建账原费的冲回建账分支退役。前端正式表只显示当前经济费用，历史在申请明细查看。

补审预览令牌复核目标费用及相关提成事实；其他费用的账单关联变化不应伪装成审批内容变化。已有待审变更对受影响提成确认／发放的防护继续保留，避免审批中途发放过时金额。

## 回退与资金、提成

复用 FinanceBill.Cancel、FinanceInvoice.Cancel/RedFlush、Verification.Reverse、FinanceNetting.Cancel/Reverse。按实际依赖清理后才能取消账单，不能手改七状态。页面显示关联单据、所需操作及权限；整单回退可能影响合并账单其他订单费用，提前展示范围，不新增单行拆账。

账务回退不要求解锁订单。回退释放占用后，未锁订单直接编辑，已锁订单仍走补审。所有资金流水、原核销、发票和已发提成保留。普通费用新增／更新／删除在移除提成财务锁后也需接入现有经济重算和差额调整，覆盖同票其他有效收款来源，不能仅处理补审路径。

复用 ProjectFinanceBillLineSettlements、ProjectCommissionEconomics 与来源反转重算口径；原员工／规则快照、已发事实、人工奖惩及系统差额分开处理。反核销释放分配，不伪造退款，重建账及重核销不得重复产生提成。

## 事务与并发

复用 biz.Transactor/WithTx；事务仓储经 Data.client(ctx) 或显式事务客户端查询。继续使用现有 version／expectedVersion、幂等键和状态检查，源费用并发变化返回 409。

审核权限父行的锁序、订单集合排序、共享 MBL／MAWB 单证锁序及提成来源关联订单闭包需要统一校对：授权父行 → 排序后的完整 Order 集合 → 业务子资源，遵守各既有子资源顺序；不能在已锁单票后临时追加反序关联订单。复用现有闭包扩展并在锁内重验集合，变化则冲突重试。

审核与普通编辑、建账与申请提交共享订单／费用保护。解锁与申请提交／批准、反核销与费用调整、提成发放与批准全部在权威锁内重验，任一失败零部分写入。响应在提交后重读。

## 契约、Schema 与迁移

修改 order_lock.proto、order_fee.proto、订单查询与费用台账相关契约：统一审核能力／状态、逐费可编辑与可建账能力、补审依据及账务阻断信息；源接口及仓库内调用方一次性同步，旧整票审核 RPC 退出写路径。

Ent 按新审核依据调整申请字段／约束、订单审核快照关联及废弃状态索引；记录型 OrderLockRecord 与申请的版本字段复用，不引入通用锁表。历史审批事件及会计历史只作为审计证据保留，不做旧状态双读双写。新写入必须使用统一人工审核依据。

正式迁移由 Ent Schema 变更驱动并随代码审阅。迁移前检查旧自动锁、独立费用批准、未结束补录／更正及其账务关系：不能从收款事实推定人工审核，也不能凭空选审核人。无法无歧义转换的记录明确阻断并列出需要处理的对象，后续具体数据处置需用户决定；不得以重置开发库代替。新环境和无歧义夹具使用完整有序迁移验收。

权限 Manifest、生成权限键、Proto／OpenAPI、前端客户端与开发种子同组更新；种子改为明确人工审核事实，不用隐藏兼容分支。

## 风险与回退

主要风险：移除整票财务锁后普通改费遗漏提成差额；申请与建账竞争；旧审核状态与新人工锁不一致；合并单据回退扩大影响；共享单证快照依赖。验证矩阵覆盖上述路径。

按契约、实现、调用方组成完整交付阶段，不单独发布只放宽前端或建账校验的提交。发布前在专用数据库演练迁移；正式数据迁移后不能仅回退二进制使用旧双锁逻辑，需配套数据恢复／前向修复方案。未授权执行生产迁移或清库。
