# 后台任务通知唤醒设计

## 架构与边界

保留 PostgreSQL 持久化任务/租约，新增一条数据库通知通道和每个服务实例一条专用
监听连接，向本实例已启用 worker 分发可合并的唤醒信号。任务仍由现有 usecase
领取和处理；通知不携带业务载荷，也不直接调用业务写操作。

- `internal/data`：pgx 专用 LISTEN 连接、重连、查询最近调度时间、通知路由适配。
  数据库访问与 PostgreSQL 类型停留在此层。
- `internal/biz`：最小调度接口，表达订阅、状态/唤醒和最近到期时间；只暴露纯 Go
  时间、消费者类别及取消语义。无需重写领域用例。
- `internal/server`：Kratos 生命周期与 worker 等待逻辑，处理收到信号、定时到期、
  停止；通过接口访问调度信息，不直连数据库、不转换业务 DTO。
- `server/migrations`：显式新增通知函数/触发器，覆盖已有直接写表路径。
  两张现有表及 Ent 字段/索引不变，不修改生成的 Ent 文件。
- `cmd/server` 与 Wire：注册监听生命周期，生成 `wire_gen.go`；不得手改生成物。

拟使用 `BackgroundTaskScheduler` 一类最小接口（实际名称实施时按已有命名核对）：
订阅消费者类别得到缓冲唤醒信号；按类别获取最近待执行时间；统一启动/停止监听。
同一实例共享底层连接；通知必须广播给全部匹配订阅者，不能用多个 worker
争抢同一个 channel 的方式分发。订阅 channel 容量 1，重复唤醒可合并。

## 通知产生：业务提交与调度变化同事务

当前多个仓储直接 `tx.BackgroundTask.Create()`；逐个添加应用层调用易遗漏，且
共享事务结束点容易被误判。采用两张持久化调度表的精确触发器，在正式迁移中安装：

1. `background_tasks` 的 INSERT 和调度字段 UPDATE。
2. `ding_talk_approval_inbox_events` 的 INSERT 和调度字段 UPDATE。

监听固定通道（如 `roncin_task_schedule_changed`）。payload 仅含 Schema 名和固定
消费者类别；Schema 用于隔离集成测试的 `search_path`，类别用于过滤唤醒。
不发送组织资料、账号、任务报文、token 或连接串。payload 必须验证并限制字段，
未知类别忽略，不从 payload 拼接 SQL。映射：

| 持久化类型 | 消费者 |
| --- | --- |
| DINGTALK_NOTIFICATION | 通知发送 |
| OBJECT_STORAGE_DELETION | 对象删除 |
| DINGTALK_APPROVAL_CREATE / 审批 inbox | 钉钉审批 |
| DINGTALK_DIRECTORY_SYNC | 通讯录同步 |

只在调度状态/时间发生有效变化时通知；RUNNING/PROCESSING 领取变更也需让其他
实例更新租约到期计时，终态变化可让其撤销已无必要的计时。对不在本期范围的
类型不唤醒业务 worker。通知在事务提交后可见，回滚自动丢弃；没有“事务内先通知
本地 Go channel”的旁路。触发器不执行业务规则、不创建任何业务任务。

触发器属于数据库运行行为，集中由正式 SQL 迁移管理；无需虚构 Ent 字段来表达。
冷启动/升级及生成后运行态验证检查函数/触发器存在，禁止依赖 Schema.Create。

## 监听生命周期

- 使用现有 pgx/v5 的专用连接，阻塞等待通知，不能从连接池借出后跨查询继续 LISTEN。
  此连接不承载业务事务，不长期占用普通查询连接。
- 先建立并提交 LISTEN，再广播初始扫描；消费者注册时若监听已就绪，同样收到
  初始信号。不依赖 Kratos 多 Server 启动顺序；订阅必须早于消费者首次扫描。
- 通知按当前连接解析出的实际 Schema 过滤；订阅者只接收该 Schema 的类别通知。
  公共通道仍可能收到其他 Schema 通知，不将其当成业务数据。
- 连接异常记录一次断线状态，有界指数退避重连（1 秒起、最大 30 秒，可取消）；
  恢复后重新 LISTEN 并唤醒所有订阅者扫描，记录恢复状态。
- 所有消费者关闭不建监听连接。最后一个订阅释放后关闭专用连接。
- Stop 取消上下文并解除全部等待，退出顺序容忍 worker 与监听者并发停止，不能
  向已关闭 channel 写入。连接串、通知载荷和每次正常唤醒都不写日志。

## 到期时间与等待循环

正常消费循环：处理可领取任务直到无任务 → 查询本消费者最近调度时间 → 等待
“匹配通知 / 最近到期计时器 / 60 秒恢复检查 / 取消”中的第一个 → 再次领取。

最近到期查询严格复用已有领取条件：

- 背景任务 PENDING/FAILED 的 `next_run_at`，RUNNING 的 `lease_expires_at`。
- 审批 inbox RECEIVED/FAILED 的 `next_run_at`，PROCESSING 的
  `processing_expires_at`。
- 钉钉审批合并派发和已启用 inbox 的最近时间；回调功能停用时不查 inbox。
- 同一查询只选启用消费者支持的类型与非终态，不依赖全量加载或跨组织漏筛。
  调度器是系统后台全局领取，继续沿用现有 ClaimAny 的范围语义。

无到期记录时等通知，60 秒定时检查用于恢复事实核验；这项检查是明确的设计行为，
连接异常持续存在时状态可见，不静默切回原有 2 秒轮询模式。
等待期间有新的更早任务/重试时间会经通知重算；进程重启也重新计算，无需持久化
Go timer。查询刚结束、进入等待前发生的通知必须由缓冲信号保留。

若查询时间已到而领取失败/数据库报错，必须有有界错误退避，不能将过期时间反复
设为 0 导致忙循环。错误重试与通知/取消可同时打断等待；不更改业务重试次数。
处理长任务期间收到信号可合并，完成后持续清队列并再次计算最近时间。

## 一致性、并发与实施限制

通知不是可靠持久化消息；启动/重连主动扫描、时间驱动和低频检查承担恢复责任。
重复/合并通知合法，不提供“每次通知恰好执行一个任务”的接口。
现有 `ForUpdate`、租约 token 和幂等键保持真相源，本任务不做 SKIP LOCKED 或
恰好一次执行改造；需用两消费者实际领取竞争证明有效租约互斥。

不新增用户配置和基础设施。一个实例最多多占一条数据库连接；跨实例均监听并
竞争现有任务，需要观察瞬时重复唤醒，但当前阶段不引入选主或复杂负载均衡。

## 迁移与运维

新增正式 SQL 迁移，不能手动在开发库创建触发器代替迁移交付。应用代码启动前先
执行迁移；迁移失败原样中止。代码与迁移一组提交。

回滚应用等待逻辑时触发器可以暂时保留，不影响旧消费者领取，但需记录残留；
若实际要求撤回数据库行为，用正式后续迁移删除精确触发器/函数，禁止直接重置库。
验证阶段只使用独立临时数据库并清理，不影响现有唯一管理员和基础数据。
