## 行为核对

- 仅通过唯一 `is_bootstrap_admin` 初始账号识别补齐目标，不接管普通同名账号，不为其他系统管理员自动加入公司。运行时仍依赖真实启用成员与有效角色，不以初始标记绕过权限。
- 首次账号、唯一系统工作台、默认 BJ/CD 公司、管理员成员及绑定在统一事务中建立；重复执行不更新密码、姓名，不要求首次密码。所有实际存在的公司纳入计划，部门和团队不重复建成员。sync:dev 的员工及经营数据仍归北京公司。
- 手工公司创建要求初始管理员已有完整有效的系统成员、管理员角色和绑定；缺项返回 `ADMIN_BOOTSTRAP_SYSTEM_REQUIRED`，先由 bootstrap 补齐。新公司及公司角色、初始管理员成员、绑定、默认配置和审计同事务。
- 初始账号停用/待分配、系统资格不可用或多系统工作台先失败；公司、角色、成员停用或角色使用失效 self 范围明确跳过，保留状态与配置，不造替代角色。可处理项只补缺失成员、绑定及 Manifest 合法权限，保留其他角色。
- 公司管理员权限由工作台允许范围过滤；bootstrap 的权限目录同步与全局管理员角色同步分离。摘要仅在提交后输出，区分新增、已满足与跳过，失败不输出成功摘要。
- 既有账号路径按 User → 组织 → 成员 → 角色加锁，各类多行按主键排序。角色采用 `FOR NO KEY UPDATE`，阻止业务角色状态/配置更新，并与目录同步关联插入的外键 `KEY SHARE` 相容；不宣称该锁串行化目录工具的所有关联写入。
- 没有 Proto 或 Ent Schema 变化，无新增迁移或生成物；根 README、server README、环境示例和既有测试调用/夹具已同步，不引入真实秘密。

## 审查发现与修复

以下问题由审查指出、实现代理完成，checker 已复查最终代码：

1. `bootstrap_administrator.go` 原先只判断 Enabled，可能接受运行时已失效的 self 数据范围。现统一视为不可用，系统整体失败、公司跳过，不自动改范围。
2. 手工建公司原先仅核对账号，可能在系统资格缺失时直接授予公司资格。现要求系统角色、成员及绑定完整有效，缺失明确提示先 bootstrap。
3. 系统工作台定位曾存在配置编码与种子唯一查询不一致。现拒绝多系统与配置编码冲突；已有身份缺失系统时不建立另一套系统资格。
4. sync:dev 原先可能重建缺失系统工作台，现要求先完成 bootstrap，并复用统一预检与补齐契约。
5. 管理员角色全独占锁与权限目录同步所需外键锁可能形成反向等待。现从首次读取采用 `FOR NO KEY UPDATE`，不先共享再升级，同时保留业务配置写互斥。
6. sync:dev 先持初始管理员锁、后写员工，可能与批量成员接口按用户主键锁定形成反向锁环。现种子入口首先按 ID 排序独占锁全部现有用户，再读取组织和补齐公司；新建用户尚不可见，不增加自动重试。
7. 数据层直接导入 `security/password` 违反分层检查。首次密码哈希改为命令层注入专用 `HashPassword` 回调，只在首次空账号分支锁内调用，缺少回调明确失败；重复补齐不调用哈希。现有初始化夹具同步输入，未添加测试。
