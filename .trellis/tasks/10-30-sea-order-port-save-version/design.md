# 资料变动提前提醒设计

## 范围与边界

原缺陷修复已通过独立 review 与首轮前端门禁。用户进一步明确：业务人员不关心内部版本；订单被别人改动后，即使一直停留页面也应提前收到刷新提醒。

仅在海运订单详情加入轻量变动检查和常驻提醒，不修改服务端接口、权限、并发保护或全局 Query 配置。不自动覆写表单，不建立消息推送基础设施。

## 数据流

- 使用现有生成客户端与 React Query 查询当前订单快照中的变动标识，检查订单及关联主单/分单/活动关联的版本或身份变化。
- 只对当前活跃路由对应的订单开启检查；浏览器隐藏时停止周期检查。15 秒检查一次，切回内部页签或浏览器页面立即检查。
- 变动检查的读取与表单初始化/编辑基线分离：探测新快照只用于判断是否发生变化，绝不推进编辑版本或覆盖输入。
- 发现变动后在订单内容顶部展示常驻提示「这个订单已经发生变动，请重新刷新。」并提供刷新入口。重复检查不得反复弹通知；检查失败不得伪装成无变化或清除已有提醒。
- 用户主动刷新前，如当前页面有未保存草稿则确认；取消保留内容，确认后复用已有完整刷新与身份/代次保护。成功重置快照后清除提醒，失败保留内容。
- 真实保存仍由服务端并发校验兜底；只有明确并发错误 reason 使用统一业务文案，其余错误保留业务原因。

## 生命周期与并发

- 查询身份包含用户工作区/组织、订单品类与订单 ID，不能串用结果。
- 非活跃内部页签和隐藏浏览器页不轮询；激活后立即重新检查。
- 页面刷新、保存成功和正式单证动作的合法基线更新应同步检查参考点，避免把本人的成功动作误报为外部变动；不得用探测结果补编辑版本。
- 订单或组织变化时清理旧提醒和在途 UI 副作用，沿用当前页面身份与令牌保护。
- 开始实现前由只读研究确认既有活跃页签信号与草稿能力，优先复用现有能力，不扩展全站模板接口。

## 兼容与交付

无数据迁移、契约生成或历史兼容。回滚仅涉及本次前端保存与提醒逻辑。新行为的回归与独立审查完成后重跑受影响验证，最终前端门禁通过后提交、合并、推送并安全删除修复分支。
