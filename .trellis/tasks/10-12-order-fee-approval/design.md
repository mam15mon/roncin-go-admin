# 订单费用审核与建账准入：技术设计

状态：用户已批准开始实施，in_progress。业务目标及验收以 prd.md 的 R1–R18、AC1–AC18 为准。

## 1. 边界与取舍

- 单一交付任务，按 implement.md 的阶段顺序提交；审核、建账、补录和提成登记共享财务一致性，阶段成果可独立验证但不单独上线。不创建通用流程引擎，不新增工资／跨月抵扣子系统。
- Proto 是接口唯一源；Service 转换与边界校验，Biz 持有纯领域状态机、decimal 计算和用例，Data 管理 Ent、事务、锁与授权事实。前端消费生成客户端和服务端能力投影。
- 新增专用整票审核事件及订单投影，复用原费用、补录申请、提成调整、通知任务及审计。禁止为每笔费用复制独立审批状态。
- 费用批准冻结不能被业务解锁、净额财务锁释放、已建账编辑配置或 bootstrap 身份绕过。

## 2. 权限和可见范围

新增唯一权限 `FinanceFeeReview = system.finance.fee.review`，名称「费用审核」，Requires 现有 `FinanceFeeRead`；审核、退回、撤销批准和补录审批共用。建账与提成实际执行继续分别用原权限，不因审核授权获得付款操作。研究文档提出同时依赖所有品类 OrderRead 的备选，本设计不采用：保留按实际职责配置对应品类列表读取能力，避免一项审核授权扩大到所有业务品类的订单详情。

提交复用对应订单品类的费用新增或编辑权限，撤回还须本人待审申请。角色配置需同时授予相应品类订单列表读取权限，才能从该订单列表进入；不要通过新增审核权限自动授予所有订单品类读权限。独立审核预览接口在该权限范围内返回必要的整票费用、提成影响，不泄露其他订单或员工全局收入。

每个批准／退回／撤销动作在事务内重读用户、有效成员、有效角色、权限及组织范围，权限和 scope 必须出自同一 grant。候选提醒复用相同资格判定，按用户去重，不把提交时候选快照当永久白名单。自审允许，未绑定钉钉不丧失资格。组织切换和停用采用现有公司工作台边界；跨组织动作定位实际订单后按该审核权限范围检查，不能仅用当前 organizationId 判定全部目标。

授权变更与决策的竞态：读取相关授权行并加共享锁；授权写路径须锁定同一 Role／Membership 父行再更新关联，不以“锁了角色行”假定独立权限关联删除已经串行。只统一参与本次决策的既有授权变更，不新建权限框架。动作当时合法批准保留，日后撤销权限不倒推修改历史批准。

## 3. 存储与状态机

### 3.1 订单当前投影

Order 新增：

| 字段 | 作用 |
| --- | --- |
| fee_review_status | UNSUBMITTED / PENDING / APPROVED / REJECTED / REVOKED |
| fee_content_version | 当前整票费用内容版本，初值 1，内容成功变更时递增 |
| fee_review_version | 审核操作并发版本，初值 1，每次审核生命周期或补录待审状态变化递增 |
| current_fee_review_event_id | 当前提交／状态事件 |
| approved_fee_review_event_id | 当前有效整票批准，撤销后清空；历史事件永不删除 |

`has_pending_fee_supplement` 从 PENDING 补录申请事实查询，不在 Order 再存一份布尔缓存。新增组织＋审核状态索引及补录每订单至多一笔 PENDING 的部分唯一索引，Ent 注解与正式 SQL 一致。

### 3.2 追加式审核事件

新增 `OrderFeeReviewEvent`：订单／组织、动作、关联提交事件、操作者与姓名、授权来源快照、意见／原因、时间、内容版本、内容指纹、整票费用及利润快照、补录申请来源（可空）、动作幂等键与请求摘要。

事件动作 SUBMIT / WITHDRAW / APPROVE / REJECT / REVOKE / SUPPLEMENT_APPROVE；提交、批准、撤销通过追加事件记录，不将历史 APPROVE 改写为另一个决定。费用快照以版本化的 JSON 结构存 decimal 字符串，费用历史引用不因费用硬删除级联丢失。事件写与订单投影同事务。

```text
未提交／已退回／已撤销批准 --提交--> 待审核
待审核 --批准--> 已批准
待审核 --退回--> 已退回
待审核 --提交人撤回--> 未提交
已批准 --无有效账单、有审核权限撤销--> 已撤销批准
已批准 --申请补录--> 已批准 + 待审补录
已批准 + 待审补录 --批准补录--> 已批准（新的完整快照）
已批准 + 待审补录 --退回／撤回补录--> 已批准（原快照）
```

待审补录存在时不允许撤销原整票批准，先结束补录申请，避免悬挂批准依据。双重冻结和专用补录撤销约束继续独立成立。撤销整票批准须整票不存在任何有效账单关联（含 DRAFT），不是只取消用户选中的一张账单。

### 3.3 内容版本与快照

完整费用集合按主键排序；快照包含方向、费用科目、结算单位、数量／单价／税率／金额、币种、费用汇率及来源／日期、本位币金额、发生时间、备注、补录来源及收入成本利润汇总。用 decimal 纯函数规范化、聚合和计算指纹。

内容变化覆盖普通新增／单改／批改／删除、专用补录生成／合法撤销、拆票转移；一个事务更改同票多行只递增一次内容版本。建账／取消账单只修改关联和 OrderFee 通用 version，不递增费用内容版本。订单非费用资料、费用标签等独立分类元数据不参与经济快照，标签维护不解除费用冻结。

审批指纹不包含订单通用 version、OrderFee 通用 version、updated_at、账单占用，避免普通建账错误使批准失效。包括原始费用集合身份与归属，不能只合计金额，也不能删一行加同金额另一行蒙混通过。

审批利润使用费用保存的组织本位币快照，所有行本位币一致且合法；纯日期／金额展示遵守现有格式化工具。利润率在收入为零时显示不可计算，不自动认定亏损／盈利。不给“录齐”添加必须两侧都有一行的猜测性约束，依靠提交人确认与人工整票审核。

账单日汇率仍按账单契约解析，不重写审核费用汇率；提成计算使用其原本的账单和历史快照口径。界面明确“费用审核利润”和“提成影响”，禁止以审核利润直接重算所有历史提成。周汇率主数据更新不使历史快照悄悄变化，手工费用汇率修改则必须先撤销批准。

## 4. 接口与幂等

复用 `server/api/order/v1/order_fee.proto` 的 OrderFeeService，新设以下 RPC 族（最终 protobuf 消息名按同名用例一致落地）：

- GetOrderFeeReview：当前审核状态、版本、能力、完整费用快照及历史；查看权限不同只返回允许的字段。
- SubmitOrderFeeReview / WithdrawOrderFeeReview：订单 ID、expectedReviewVersion、expectedContentVersion、幂等键、完整性确认／原因。
- PreviewOrderFeeReview / ApproveOrderFeeReview / RejectOrderFeeReview / RevokeOrderFeeReview：关联提交 ID、版本、服务端预览摘要、意见／原因。
- PreviewOrderFeeReviews / ApproveOrderFeeReviews：显式订单数组，每项带自己的申请／版本／预览摘要／意见／动作键；上限复用统一 200，重复 ID 拒绝，不展开全部分页。
- 原补录 Preview/Approve 同步扩展当前批准 ID、内容版本、审核版本、补录版本、影响预览 token、审批意见。

批量审核逐票事务，返回每票成功结果或稳定业务错误码／原因；请求格式整体错误在处理前返回，已处理行不因其它行失败回滚。已成功动作同幂等键同意图返回历史结果，异意图冲突；不能将幂等重放解释为给当前费用重新批准。数据库约束保证事件唯一键。财务批量建账仍按原契约整批事务，不能与批量审核混为一套事务语义。

订单 ListOrders 和费用台账契约新增 feeReviewStatus、hasPendingFeeSupplement，Count 与分页复用同一谓词。列表行仅投影授权后的摘要、状态、可审核能力、阻断原因及版本。费用建账候选包含审核状态、canBill 和稳定 blockedReasons；前端不根据利润或金额本地推算批准资格。

所有预览是只读，批准时锁内重算并比对。补录审批 token 包括整票快照、提成行、调整集合、使用的汇率与计算版本，任何影响差额变化必须要求刷新，不能静默批准审核人没看过的新金额。

错误使用统一中文业务错误，版本／状态冲突 HTTP 409；无权限按现有 403／授权不存在契约；空白亏损意见和非法数组 400。新错误原因入 proto 源并生成常量。静态批量路径必须声明在可能匹配的参数路径之前，用真实 HTTP 注册测试验证。

## 5. 统一冻结与建账准入

普通费用写入在最早 Order 锁内统一调用审核冻结判定，覆盖 Add、Update、Remove、BulkUpdate、BulkRemove、费用抽屉写入、拆票克隆／删除。PENDING、APPROVED 拒绝；REJECTED／REVOKED／UNSUBMITTED 还需满足原业务锁和财务锁。

拆票改变费用集合或归属时必须先撤回／撤销批准，结果订单初始化未提交；禁止复制原批准。纯非费用改配不随意使批准失效。专用补录撤销不可仅删除费用后留下仍可建账的旧批准：合法无已确认冲减且无相关占用时，在同一事务撤销当前整票批准、删除补录费、递增内容／审核版本，要求重新整票审核；任何已确认／已扣回冲减继续拒绝。

建账判定：APPROVED + 当前内容版本／指纹等于批准快照 + 所选费用属于该完整快照 + 无待审补录 + 无有效账单关联 + 现有组织／建账权限及账户币种等条件。首次读取、预览和写事务共用同一规则；所有入口最后必须到达该规则，不依赖前端筛选。第一次分次建账不会消耗或撤销整票批准。

取消账单按原下游限制处理，只释放关联，不自动撤销批准；撤销批准和建账争抢同一订单锁，不能互相穿透。

## 6. 受控补录与提成影响

补录只在整票已有有效批准时创建，PENDING 中费用仅为申请快照。原 BUSINESS/FINANCIAL/BOTH 锁证据模型一次性更新为批准事件／费用内容版本证据，保留原两把锁的事实供审计与普通编辑限制；不能伪造业务锁代次，不按旧 lock grant 回退资格。

补录申请、拒绝、撤回在订单锁内增审核版本，形成待处理阻断。批准先验证审核资格、申请状态、现行批准、完整快照与所有提成影响预览，再一个事务执行：

1. 创建真实正数应付，递增整票内容版本；保留原费用。
2. 根据每条原提成的历史计算版本、比例、收入分母及成本快照算本次差额。
3. 生成 CONFIRMED 系统冲减及 confirmedAt/by，复用订单行／父单两层额度校验；差额为零不建调整，未知版本／币种不一致／快照缺失明确拒绝，不能忽略。
4. 写完整新整票批准事件、当前批准指针与申请 APPROVED；入队结果／员工知情通知和审计。

所有步骤失败一并回滚，外部钉钉发送事务外执行。审批人以费用审核资格确认规则算出的经济影响，实际执行仍要求提成管理权限。

连续补录须按每条原提成快照中的 fee ID 判断哪些成本已经包含；不能把订单所有补录成本统一加到每一条原成本快照上。新增费用发生日折算与历史已建账行折算各保留实际依据，采用逐提成确定增量；详见 supplement-commission-design.md 的计算与验证要求。

待审补录门禁覆盖单笔提成确认、月度申请整批批准、提成发放、相关调整执行及预览。原月度申请如果含受影响订单，现有整单批准行为应整体拒绝并列出原因；不改为部分批准。单笔父提成横跨多订单时无法拆付，整笔登记被阻断并说明关联订单，其他独立提成单不受影响。

## 7. 发放登记防重复扣减

当前 paid_at/by 不足以表达本次实际执行。最薄扩展在原提成模型增加不可变发放快照（本位币／实际金额、原金额、动作键／摘要、时间／操作人），并在调整记录保存执行方式和关联的父提成发放身份；优先复用父单 ID 作为一次发放身份，不建设多次分期支付引擎。

增加 PreviewCommissionPayment，用已锁父单、调整集合、待审补录状态生成预览 token；MarkCommissionPaid 携带 token、expectedVersion、确认的实际金额和幂等键。实际金额必须等于服务端锁内重算结果，不允许手填任意金额悄悄留下差额。

- 父单 CONFIRMED 尚未发：名义提成 + 尚未执行的已确认增提 − 尚未执行的已确认冲减，作为本次金额。新契约下，父单尚未发放时调整只能随父单一并净额登记，不能先独立增付／扣回。所含调整同步标记执行且挂发放身份，父单记录净额并 PAID；净额 0 显示“抵扣结清”，不声称产生转账。算出负金额拒绝，不用 max(0) 隐藏差额。
- 父单 PAID：后续冲减只保留独立执行登记，不能改原发放快照。已经用于父单少发的调整，不能再次通过“标记已扣回”执行。
- effectiveCommissionAmount 是累计权益净额，不能当成本次实际现金金额；本次实付必须来自支付预览。新执行记录精确标明“发放抵扣”或“单独执行”。
- 确认/发放/调整执行都与补录竞争同一订单及父提成锁；版本和预览指纹变化 409，不能自动缩小金额或重试新数字。

实际付款仍在线下，本系统登记事实，不调用银行或工资扣款。不允许从员工别的订单自动扣，不创建跨月余额。该最小事实记录是本次“同步确认冲减后财务执行”的必要闭环。

反核销／反对冲相邻防护：父单未发且无独立执行事实时，沿用取消未支付权益；父单已发时，追回必须对应实际已付敞口。若存在尚未执行的已确认增提，首期明确阻断反转并提示财务先处理该增提（真实执行或按原规则取消），避免将尚未支付的增提也列为现金追回。有待执行冲减时复用原有冲减与新增差额合计，不重复追偿；金额超过可证明的净已付敞口或缺历史证据时明确失败。此处不扩展自动逆向支付引擎。

## 8. 事务与锁序

研究已发现既有 Order→Bill 和 Bill→Order 的反向持锁，新增门禁不能在已锁 Fee 后再补锁 Order。仅调整本任务涉及及直接相邻路径，统一相对顺序：

`全部目标 Order（主键排序） → 财务来源 → Bill → BillLine → OrderFee → SupplementRequest → Commission → Adjustment`。

只读预定位用于收集完整集合，不用于最终授权。先锁完整订单集合再进入下游，锁内重读关联，集合变化报冲突，不在持下游锁后追加新的订单。每类多行查询显式 ORDER BY 主键再 ForUpdate，不能仅排序 IN 参数。既有单证 Order→MBL 顺序保留于费用锁前。

必须联动首个持锁入口：LoadBillableFeesScoped、建账／取消／改草稿、费用批量、拆票、补录、GetGenerationContext、calculateCommission、月度申请审批、提成／调整状态迁移，以及会调用这些函数的反核销／反对冲路径。明细见 backend-approval-design.md 的证据矩阵；实现验收需实库并发证明，不能仅在注释写统一锁序。

用例 WithinTransaction，仓储经 Data.client(txCtx)，局部 WithTx 自动合并。不要在共享回调内调用 withSQLTx；只用普通 ctx 的辅助函数不得意外脱离事务。完整响应提交后重读，网络通知只入队不在事务内发送。

## 9. 前端和通知

用户已确认费用交互统一围绕审核状态与允许动作组织。费用页、列表费用抽屉、费用台账集中展示服务端能力及阻断原因，不并列堆放三套锁控操作，不新增审批锁字段／开关或财务解锁动作。自动提成保护用“存在有效提成，原费用不能直接修改”等具体说明表达，关联账单／提成记录仅向具备相应读取权限者提供跳转。待审提示先撤回；已批准提供符合资格的补录／撤销操作；已有账单、业务锁或有效提成时准确列出当前限制，不承诺撤销批准后一定可改。保留业务锁本身的资料与单证保护，受控补录不要求先解业务锁或财务保护。净额归零只解除提成保护，不能清除批准状态；这属于界面与能力投影收敛，不删除底层校验。

按 research/frontend-approval-design.md 实施：订单末列审核、hover/focus 摘要、完整明细 Drawer、ModalForm 确认、逐票亏损意见、混合批次结果、筛选及页签恢复。公共 OrderListTemplate 只增加末列／动作插槽，审批实现留领域层，保留列设置与首尾冻结规则。

订单费用页及列表费用抽屉共用服务端写能力。财务费用、账单页、订单费用三个建账入口均消费候选准入，成功 actionRef.reload，详情 Query 按组织隔离并失效。加载失败或组织切换不能保留旧可审批上下文。

BackgroundTask + NotificationDelivery 复用现有机制，新增审核待办、结果、补录结果模板，事件＋接收人唯一键。通知只含必要订单号与动作，不直接推送整票成本／员工收入；跳转后实时授权。无钉钉绑定明确未投递，审批仍在 Roncin 可查。网络失败重试不重复生成审核事件。

钉钉渠道明确使用现有机器人通知能力：`server/internal/data/dingtalk.go` 的 SendText 已按收件人调用企业机器人单聊接口，复用已有候选人逐人投递方式，不因“机器人”一词另建群机器人配置。首次费用提交在成功转 PENDING 的同一事务入队，提交后才由 worker 发送；普通保存、失败提交不生成提醒。文案包含订单号、提交人、已完成录入并等待审核的说明及 Roncin 处理链接。审批操作仅通过 Roncin API 完成；不接入 OA dispatch／callback，不在消息内提供批准／退回动作，送达、已读或点击链接均不构成审批。已有结果提醒仍属机器人通知，不增加外部审批流程。

## 10. 迁移、开发数据与发布

- 先改 Ent Schema，再运行 Ent 生成、基于其差异产生正式 SQL，CHECK／索引／外键与生成元数据一致；仓库没有已确认的专用迁移生成 CLI，实施阶段使用当前 Ent 的 migration diff API 针对正式迁移构造的临时库生成并审阅，不在业务库运行 Schema.Create。
- 存量订单初始化 UNSUBMITTED，不伪造审批人和批准时间；原账单／核销／提成／费用保留，新增建账必须真实整票审核。旧账单不因迁移删除或自动取消。
- 存量 PENDING 补录、DRAFT 系统补录冲减、“父提成未发但调整已执行”等事实在只读预检中列出。没有人工确认依据时不自动升级为 CONFIRMED、不自动撤回／删除；新契约迁移在这些前态阻断并给出处理清单，按原受支持动作人工处理后重跑，不保留长期新旧双轨。研究提出上线后新审批人确认旧 DRAFT 的兼容处理窗口，本设计不采用，以迁移前一次性人工整理收敛；已有 CANCELLED 历史不复活、不重复创建冲减。
- 历史 PAID 未记录实付金额就保持缺省并展示“未记录”，不能拿当前净额回填历史实付；未来发放必须保存新快照。新付款逻辑不允许以缺证据为由猜测抵扣关系；涉及历史现金敞口且证据不足的反转明确阻断，具体人工核对列入交付清单，不默认用名义金额执行追回。
- 开发种子与夹具按新流程同步，在受控演示用例显式构造审核和发放事实；sync:dev 幂等且不得覆盖真实审批，不重置数据库。
- 先核验专用集成库完整 SQL 迁移及旧前态拒绝，再考虑应用开发迁移。生产保持严格校验，数据库操作需要现有授权范围内的明确目标，不能把任务批准当成数据库清空授权。
- 源契约、生成物、服务端和前端同一发版。出现问题停止相关写入口并修复；有新审批／付款事实后不能回滚旧二进制绕过门禁，不提供删除历史表式回滚。

## 11. 明确限制与最终审阅重点

1. 新补录一旦产生已确认冲减，即使费用尚未建账，也不能直接撤销该补录；恢复已确认提成属于后续专项，不用一般撤销批准偷渡。
2. 批量审核逐票结果、事后权限变化不追溯旧批准、每票一个待审补录、首期仅显式选中订单及付款快照记录，均随最终方案整体确认。
3. 若迁移预检发现必须人工处理的数据，只交付清单并说明原因，不自动确认旧冲减或重置开发库。
4. 当前文档阶段没有执行迁移、业务生成或运行业务测试；implement.md 定义的实际验收通过后才能报告功能完成。
