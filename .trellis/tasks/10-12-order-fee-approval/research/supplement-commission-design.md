### 2. 补录资格与锁适用性的最薄扩展

当前两把锁均不存在时，`Create` 返回 NOT_APPLICABLE（usecase:226）。仅新增费用审核冻结后，批准费用但没有业务/财务锁的订单，普通新增被禁止、补录又不适用，必须一次修正两条入口。

建议把“当前有效整票批准及费用修订号”作为新补录的直接依据，不建设三把锁的 7 种组合。新增申请固化有效批准 ID、费用修订号和费用内容指纹；业务/财务锁继续作为独立事实展示和普通修改限制。新补录要求已有有效整票批准，批准时仍匹配同一版本；锁定/解锁及提成净额释放不替代、也不自动撤销费用批准。申请期间允许退回/撤回，不允许普通费用变更。

实现选择：给既有申请的 `lock_basis` 新增 `FEE_APPROVAL` 并携带新的证据字段，其他旧值仅保留历史读取；所有新请求统一使用批准依据。一次同步 biz 校验、Ent CHECK、正式 SQL CHECK、DTO 和前端文案。若需要把 BUSINESS/FINANCIAL/BOTH 完全移除，须先有一次性迁移分类，不能把旧申请伪造为新批准依据。这里是明确迁移历史痕迹，不能添加新请求回退到旧锁资格的兼容分支。

`ListLockGrantApprovers` / `HasRealtimeLockGrant` 的调用覆盖创建、预览、批准、退回、列表能力及专用撤销，均替换为新费用审核资格解析；服务层也同步独立权限。候选资格和实际审批复用同一谓词：有效用户/成员/角色授权 + 订单组织范围。本人有权限允许本人审批，不做岗位/原锁定人例外。

建议单订单至多一条 PENDING 补录（订单锁内检查 + 部分唯一索引），批量首次审核不包含补录批准。多笔成本逐笔申请批准，减少同时待审多个费用版本的冲突。既有开发数据如存在多条 PENDING，不能为加索引删除申请；应先预检并列出，让用户逐条撤回或退回。现有 `Create` 未限制同订单多个 PENDING（request.go:20-29）。

### 3. 审核预览与批准事务

现有预览只展示利润变化（usecase:110-114），没有提成影响；现有批准接口也没有批准意见（usecase:442），批准不写 DecisionReason。必须扩展为同一个预览返回完整费用、当前/拟新增成本、利润、逐员工逐原提成的冲减及封顶原因；亏损意见必填，写入决策记录及整票审批历史。

批准请求至少携带申请 expected_version、费用修订号、审核预览指纹（涵盖费用/汇率/审批资格相关范围及提成上下文版本）和意见。事务内重算，若预览事实变化返回冲突并提示刷新，不在用户确认后静默采用新的冲减金额或汇率。现有 `ResolveFeeFactsForApproval` 与 usecase:489 会按费用发生日重新解析非手工汇率，必须纳入指纹。

共享事务顺序建议：订单 FOR UPDATE → 验证有效整票批准/申请版本及审核资格 → 锁申请 → 重解析费用 → 父单按 UUID 升序 → 调整按主键升序 → 重算并验证预览指纹 → 新费用 → 新整票批准快照/修订号 → 已确认冲减 → 申请终态 → 审计与知情通知。所有步骤失败整体回滚。批准时只能在订单锁下通过唯一的受控费用创建，不调用普通费用新增以规避冻结门禁。

现有费用、原账单、CONFIRMED/PAID 提成计算快照不改；父单调整序号递增属于既有治理字段，建议连同父单版本递增或付款预览指纹显式纳入调整集合，以避免新调整出现后旧发放确认仍有效。

### 4. 冲减算法可复用部分与必须修正的证据

- 版本路由复用 `CommissionSupplementCostSensitivity`（biz/order_fee_supplement.go:499）：当前 V3 的毛利口径敏感、收入口径不敏感；未知版本失败，不能假定都按毛利。
- 毛利历史分母、已实现收入、比例、每次 8 位舍入与利润零下限复用 `ComputeSupplementMarginalImpact`（:539）。成本敏感要求 READY 分母、同本位币（usecase:559-563）。缺历史快照不能用今日费用总数补成“当时事实”。
- 双层限额复用 `CapSupplementSuggestion`（:553），以及 `TransitionAdjustment`（data:227-295）确认时父单/订单行余额检查；新流程在同一锁内计算并直接创建 CONFIRMED，填 actual reviewer、confirmed_at，不仅改枚举。
- 现有其他 DRAFT DECREASE 预留仍要计入（mapping:209），DRAFT INCREASE 不增加可用余额。封顶产生的不足额和原因展示给审核人并记录，不跨订单或员工转扣。
- 新来源取消接口稳定拒绝 CONFIRMED / PAID；前端从“待处理冲减建议”改为“待执行冲减”，不再暴露确认/忽略。但人工调整来源和其他来源原有能力不能一并误删。

**发现一个复算基线缺口：** `LockCommissionImpactContext`（approval.go:96-110）把全订单所有现存补录成本汇总为统一 PriorSupplementBaseAmount；每条提成又用“自身 total_payable_snapshot + 此总数”。若提成是在此前补录批准之后产生，历史分母已经包含该成本，再加一次会重复计算，接近零利润时可能漏冲减。当前计提引擎 `calculation.go:480-520` 将全部费用 ID 保存为该行 `FeeSnapshot`，可以按每条提成行排除快照已包含的补录费用，只累计后续补录；不要按一个订单统一 before 基线替代逐提成证据。必须验证重复/缺失费用快照的完整性，不能解析失败就算零。历史快照分母使用账单日折算（calculation.go:382），后续增量应明确采用补录批准的本位币金额，与 UI 一致；本次不重写全部历史账单汇率。

### 5. 待审门禁完整落点

订单存在 PENDING 补录时，在订单锁内重读事实，统一拒绝该订单新增建账、受影响的提成确认及发放登记。投影/UI 只用于提示；服务端必须检查。

| 入口 | 当前保护 | 新门禁 |
| --- | --- | --- |
| 单提成确认 | 重算来源指纹 + 无未建账费用，write.go:100-138 | 所有来源订单无待审补录，费用批准有效 |
| 月申请批准 | write.go:201-245 整批确认，任一失败回滚 | 相同门禁，不因月申请绕过 |
| 单提成发放 | write.go:155-159 仅 CONFIRMED→PAID | 父单所有订单无待审补录，付款指纹/净额一致 |
| 手工调整确认 | adjustment.go:223，两级余额复核 | 对目标订单的待审补录阻断经济状态变化 |
| 调整执行登记 | adjustment.go:298-302 仅 CONFIRMED→PAID | 对目标订单检查待审补录，使用付款执行模式及证据 |
| 原提成已发放后补录冲减独立执行 | 当前只有状态时间 | 相同订单门禁，记录实际执行事实，不跨月自动抵扣 |
| 提成新建草稿/申请提交 | 可以生成 DRAFT | 建议可保留草稿及申请，但确认必须阻断，并明确显示待审原因；批准补录后旧指纹需重算/重提 |

同一父提成可能包含多个订单，父单发放是整单操作，任何一个来源订单待审就阻断该父单；员工其他不含该订单的提成单仍可发放。月申请当前整单批准无部分批准，一票待审会阻断该申请整单批准，不能声称同月申请内其他明细仍能批准。若用户要求拆分同一父单或同一申请，本期之外；审阅说明应明确现有粒度。

撤回/退回只解除 PENDING 阻断，不恢复失效批准；原批准本身有效时保持冻结。补录批准原子替换批准快照；旧审批历史保留。撤销整票批准时不允许仍有待审补录，避免申请悬空。

### 6. 本次实付与有效权益必须分别建模

现有 `EffectiveCommissionAmount` 是 B + 全部 CONFIRMED/PAID 符号化调整（mapping.go:31-43），是**当前有效权益**，随以后补录变化。`MarkCommissionPaid` 只写 paid_at/by（write.go:159），未保存实际金额；不能把动态 effectiveAmount 标成“当时发了多少”。

最薄建议：新增一条不可变的父提成付款快照（或在父单新增一次写入的付款字段 + 调整执行关联，二者选一）；不建设工资台账/跨月余额。快照至少保存 commission_id（唯一）、原提成金额、实际本币与 CNY 发放金额、原父单汇率快照、本次纳入调整 ID/方向/金额/版本、已独立执行调整的核对明细、付款预览指纹、登记人/时间。新增调整执行模式 `OFFSET_WITH_PARENT` / `SEPARATE`，随 PAID 一次记录；与父付款关联的调整不可再次独立执行。

发放确认页面必须先请求付款预览，列出本次净额和具体调整，再提交 expected_version + fingerprint / expected actual amount。在订单→父单→全部调整锁内复核，一次保存付款快照、父单 PAID、本次抵扣/增付调整 PAID 和审计。双击或两入口竞争只能成功一次。不得仅靠父 expected_version：新调整现在只改 adjustment_sequence 不改 version（approval.go:273），调整状态变化也不改父 version，预览指纹必须覆盖调整集合。

记 B 为原提成金额，s(a) 为 INCREASE 正、DECREASE 负。在父单尚未发放时：

```
有效权益 E = B + Σ s(a)，a ∈ {CONFIRMED, PAID}
本次父单实付 P = B + Σ s(a)，a 为仍未执行的 CONFIRMED 调整
已独立执行净额 S = Σ s(a)，a 为有明确 SEPARATE 证据的 PAID 调整
因此 P = E − S
```

已 PAID 的独立增付/扣回已实际执行，不能在父发放时再加/减一遍。示例（单位同父本币）：

| 原额 B | 调整 | 有效权益 E | 父单本次付款 P |
| --- | --- | --- | --- |
| 200 | CONFIRMED DECREASE 50 | 150 | 150；这条冲减同时记 OFFSET_WITH_PARENT / PAID |
| 200 | 已独立 PAID DECREASE 50 | 150 | 200；之前已收回 50，不再少发 |
| 200 | 已独立 PAID INCREASE 20，CONFIRMED DECREASE 50 | 170 | 150；之前增付 20 不再重复发 |
| 200 | CONFIRMED INCREASE 20，CONFIRMED DECREASE 50 | 170 | 170；两条均随父付款执行 |

DRAFT / CANCELLED 调整既不参与权益，也不参与付款；UI 显示未确认调整另行处理，不能偷偷确认。父付款后再批准补录产生的 CONFIRMED 冲减，不改原付款快照，只走 SEPARATE 执行。父付款前后的单独增付/扣回允许与父付款竞争，但必须同一父单锁互斥并重新验证指纹，谁先执行就以事实重算。

**负付款边界：** E≥0 不保证 P≥0（已独立增付较多时会出现 P<0）。不能用 max(P,0) 吞掉差额，也不能声称已发放。最薄做法阻断父付款，明确列出须先独立执行的冲减，由财务实际处理后再预览发放；首期不做部分执行和自动跨月抵扣。P=0 可以登记“本次零额结清”，并原子执行本次已确认调整，避免整单永远留在未发放；该行为需在最终审阅明确。

相关提成发生后续冲减，动态 E 与历史 P 均要展示；历史父付款净额不随以后成本变化重新计算。调整 PAID 文案按执行模式显示“已随提成抵扣/增付”或“已独立扣回/发放”，防止财务把抵扣当作另一次现金收回。

### 7. 与反核销/反对冲的相邻风险

`PlanCommissionReversal`（biz/types.go:228-233）将任一 PAID 调整视为有已付敞口，再按完整有效权益生成冲减（:255-277）。新增 OFFSET_WITH_PARENT 时父单 PAID 与调整 PAID 同事务，所以通常完整有效净额对应已支付净额；但现有“父单 CONFIRMED，只有一条 INCREASE 已独立 PAID”组合，可能把尚未发放的原 B 也列成待追回。

例：父单未发 100，已独立增付 10，反核销当前算法可能生成待追回 110。不能把这 110 全部说成真实已付款。设计应在相邻路径验证：区分取消未支付权益与追回实际净付款，依据明确付款快照/独立执行证据，不允许通过添加 PAID 状态把未付款金额变成已付款。如果维持现有反转计划，需要明确其是冲销经济权益且未付父单随后零额结清/剩余财务执行的过程，不能新增 UI 声称全额现金追回。该项是现有事实模型限制，应由主设计选择最薄修正；不擅自增加红冲/工资引擎。

### 8. 冻结、撤销与纠错的实际限制

`evaluateCancelCapability`（cancel.go:139-141）任何关联调整曾 confirmed_at / paid_at 或当前 CONFIRMED / PAID 均禁止删补录成本；更晚补录存在也禁止早期撤销（:105-130），已建账须先取消（:95-103）。

用户认可的方案保留该保护；因此**新补录一旦同步产生已确认冲减，即使还没建账，也不能直接撤销这笔成本**。整票“撤销批准”只能撤销审核门禁，不会清除该不可变来源限制。已取消账单仍不能绕过 confirmed adjustment 保护。无冲减的补录可沿用专用撤销条件，但删除费用必须同事务失效/更新整票批准，禁止删完还显示可建账。

错误補录在上述受限场景暂缺业务纠错闭环，应在最终审阅显著说明；本期保留限制，没有授权自动建设冲减反向调整/成本红冲。不得声称“所有费用先取消账单撤销批准即可改”。

### 9. 不重置、不伪造人工批准的数据策略

本研究未读取本地实际业务数据，以下是正式迁移/一次性整理策略，实施时需只读预检数量与异常清单，不打印敏感载荷。

1. 订单新审核状态默认未提交，批准外键为空；既有业务锁、有效账单、提成确认不等价于整票人工批准。现有账单/核销/付款事实保留，后续新增建账和提成确认/发放要求人工完成新整票审核。
2. 开发库 Schema 走新正式迁移，不 reset、不改旧记录的审批人/时间为当前人；旧补录 APPROVED 只表示旧补录申请获批，不能迁移成新整票 APPROVED。
3. 旧 PENDING 补录保留为待审未决，并持续阻断该订单新建账/发放。新整票首次审核可将当前费用及该待审申请一起呈现，但不能默默批准新成本。推荐由本人撤回/审核人退回旧申请，完成人工整票审核后重新申请，旧记录留痕；若新索引发现多个 PENDING，先人工整理，再应用索引。
4. 旧 LOCKED_FEE_SUPPLEMENT 的 DRAFT 调整不能迁移批量 CONFIRMED，不能继续暴露财务“忽略”绕开本次规则，也不能直接删除。建议一次性人工处理窗口：新费用审核人在首次整票审核确认界面同时查看旧建议及已生效补录成本，明确批准冲减；同事务锁定原调整并复核双层限额、状态/版本，写实际当前确认人/时间、整票批准。旧建议金额不可变且来源唯一，若与真实可确认影响不符或超额，整票批准阻断，进入明确人工数据核对；不自动缩额、不新建重复来源调整。此为当前未决事实的迁移确认，不为所有运行期新补录保留 DRAFT 双流程。
5. 旧 CANCELLED/CONFIRMED/PAID 调整及历史审批不改写。旧建议已被财务忽略的成本仍进入当前整票利润，但本次不偷偷重建当时扣减；列入预检异常及人工核对，避免新批准等价于默认认可过去忽略决定。
6. 新付款快照列/表不为历史 PAID 伪造金额、调整归因；旧 PAID 时间只能证明登记过状态，不能证明当时是原額还是净額。展示“历史金额未记录”，有 PAID 调整但无明确执行证据的未发父单，阻断新净发，财务先提供可审计的人工核对事实，再继续。零调整的未付父单可直接产生新付款快照；不会因旧父 PAID 缺快照阻止真实新增冲减单的独立执行，但必须先核对必要已付敞口，不把权益当现金。
7. `sync-dev` 以后新样本用明确开发种子来源，展示为测试审批/测试执行事实，禁止替现存人工作业订单自动填批准。现有提成种子 `devseed` 指纹且无 READY 分母（main.go:2551、2570-2594），不能靠按今日总费用填分母修复。新样本应按正式领域计算流程生成，旧样本保持并清晰列为需核对；不要强行变为 V3/NATIVE。

上述一次性人工整理需要进入实施设计/验收，不能只在发布说明写“旧数据不兼容”而在新门禁下让旧未决记录永久无入口处理。

### 10. 并发锁序注意

补录、付款、调整经济状态变更至少保持订单升序→提成父单升序→调整主键升序，锁内读取 PENDING、批准版本与付款事实，等待后重新验证。

但当前单提成确认的计算器先锁来源/账单再订单（write.go:100、calculation.go:312、354），月申请批准先锁订单/父单再重算来源（write.go:210、213、229），反核销先订单再来源（verification.go:352、357）。存在不同来源锁序的交叉风险；不能为新门禁随手再把订单锁放到单提成计算之前而不看来源查询。设计应列出所有受影响写入口统一锁层次，或明确复用现有入口后于计算所得订单锁检查门禁；并发测试至少覆盖单确认/月批准/反转与补录，不能只测新审核接口。需要强制串行的 source/bill/order 跨链路必须在父设计统一安排，研究不擅自选锁序改全部财务模块。

### 11. 针对性验收用例

| 场景 | 应验证结果/路径 |
| --- | --- |
| 仅费用审核批准，无业务/财务锁 | 普通新增拒绝，受控补录可申请；usecase:226 新依据 |
| 没有整票批准但业务/财务锁存在 | 不得仅因锁/旧角色批准而新建账；必须先人工整票审核 |
| 财务有建账权无费用审核权 | 无法批准/退回补录；候选列表与实际执行一致 |
| 同组织有权限本人申请自审 | 成功，实际审核人留痕 |
| 非盈利补录预览，意见空 | 拒绝，无费用/冲减/新审批快照写入 |
| 新增应付，毛利计提 CONFIRMED/PAID | 同事务费用、新整票批准、CONFIRMED 冲减；故障注入全回滚 |
| 按收入计提 | 无成本冲减，仍新增/冻结费用并更新审批 |
| 未知算法/缺历史分母/本位币不一致 | 明确阻断，无以零代替或新分母回填 |
| 补录 A → 新核销产生新提成 → 补录 B | A 不被重复加入已包含 A 的新提成分母 |
| 正毛利降至零/负毛利 | 原算法零下限、差额、封顶正确，亏损意见保留 |
| 其他 DRAFT 冲减预留/其他订单有余额 | 预留及双层余额正确，不跨订单冲减 |
| 两人同时审批/撤回/退回 | 只一人成功，不重复费用/调整/通知 |
| 提成确认/月申请批准/父发放/调整执行与补录提交竞争 | 订单锁线性化；提交先成功则相关动作阻断；动作先成功则补录以最新付款/确认事实计算 |
| 同员工其他订单提成 | 不含待审订单的父单继续可发放 |
| 含待审订单的多订单父单/月申请 | 整单阻断，既有原子语义明确 |
| 原 200 + 未执行减 50 | 父付款快照 150，减 50 同时 PAID/抵扣，不可再扣回 |
| 原 200 + 已独立减 50 | 父实际付款 200，不再减；历史权益仍 150 |
| 原 200 + 独立已付增 20 + 未执行减 50 | 本次付 150，现金合计净 170；不重复增付 |
| 调整在付款预览后批准/执行 | 即使父 version 未变也指纹冲突，要求重新查看金额 |
| 父已付 150 后补录冲减 20 | 旧付款仍 150，新独立待执行减 20，动态权益 130 |
| P=0 / P<0 | 零额结清清楚留痕；负额阻断且列明确待执行项，不 max 到零 |
| 反核销/反对冲 + 父未付但增付已独立执行 | 不把未支付原額宣称为已付款追回，支付事实不失真 |
| 已确认冲减补录尝试删除/撤销批准后删除 | 明确拒绝，不经普通入口洗掉来源限制 |
| 无冲减补录专用撤销 | 删除与审批失效同事务；更晚补录/有效账单限制保留 |
| 迁移前旧费用/旧批准补录/旧 DRAFT 建议 | 不自动人工批准，不删历史；有明确人工核对入口 |
| 历史 PAID 无实际金额、来源未知 | 不伪造金额、不隐式 fallback，展示未知并阻断需这些事实的新净发 |
