# 技术设计：员工月度提成申请与财务整批审批

## 1. 设计目标

在已完成的提成方案、员工分配、计提来源和工作台本人视图之上，增加一个独立的“申请批次”层：员工按自然月提交一批完整的历史合格提成，财务整批确认或驳回。申请批次不是银行付款单，也不替换现有 `FinanceCommission` 的计算与财务状态机。

核心关系：

```text
核销/对冲来源 + 订单提成归属 + 有效提成方案
                         │
                         ▼
                 FinanceCommission
                 （逐来源、逐员工、逐身份计算事实）
                         │ 申请明细引用
                         ▼
            FinanceCommissionApplication
            （员工 × 组织 × 申请月份）
                         │
                         ├─ PENDING_REVIEW：财务待审
                         ├─ REJECTED：原单可重提
                         └─ APPROVED：整批已确认
```

## 2. 状态与日期口径

### 2.1 申请状态

申请头使用独立状态，不复用提成单四态：

- `PENDING_REVIEW`：员工已经提交，等待财务整批处理；
- `REJECTED`：财务整批驳回，保留原因和明细，原申请可重新提交；
- `APPROVED`：财务整批批准，申请内每条提成明细均已通过；
- 首期不提供申请人撤回、财务部分批准、申请取消或删除。

已有提成单继续使用 `DRAFT → CONFIRMED → PAID / CANCELLED`。员工提交申请时，服务端把完整计算结果固化为可追踪的提成事实并与申请明细关联；财务批准时在同一事务内将申请内全部可确认的 `DRAFT` 提成统一转为 `CONFIRMED`。`PAID` 仍只表示既有系统中的人工发放事实，不代表银行付款。

### 2.2 自然月

- 服务端用 `FinanceBusinessDate(now)` 得到上海业务日期，不使用浏览器日期。
- `application_month` 是提交发生的自然月 `YYYY-MM`；`coverage_to` 固定为提交月份前一个自然月的最后一天。
- 新申请只能在完整月份结束后提交；例如 4 月申请覆盖最多到 3 月 31 日。
- 申请提交后才新满足条件、即使 `commission_date` 属于更早月份的提成，不回填原申请；下次申请重新计算时按未申请明细纳入。
- `commission_date` 继续使用核销日期或对冲确认日期；月份展示和截止过滤都以该字段为准。

## 3. 数据模型与历史

### 3.1 `FinanceCommissionApplication`

新增申请头表，至少包含：

- `organization_id`、`employee_id`、`application_month`、`coverage_to`；
- `status`、`version`；
- `commission_count`、本位币总金额快照及可审计的汇总字段；
- `submitted_at`、`submitted_by`、`decided_at`、`decided_by`、`decision_reason`；
- 创建/更新时间和审计关联。

数据库唯一索引：`organization_id + employee_id + application_month`。被驳回的申请仍占用该唯一键，只能原申请重新提交；批准后也不允许在同一月份新建替代申请。

### 3.2 `FinanceCommissionApplicationLine`

新增申请明细表，至少包含：

- `application_id`、`commission_id`、组织和员工；
- 提成归属日期、来源核销/对冲 ID、人员身份、方案 ID/版本/名称；
- 提成原币、本位币金额、计算口径、来源指纹和提交时的金额/方案快照；
- 创建时间及明细版本/审计字段。

申请明细引用 `FinanceCommission`，采用 `NO ACTION` 外键，禁止删除造成历史申请断链。一个提成事实只能进入一张申请；被驳回时仍保留在原申请，不回到可被其他申请抢占的公共池。申请批准后明细和快照不可修改。

### 3.3 现有提成兼容

- 不改变现有逐来源唯一键、提成方案快照、核销/对冲计算公式和调整单模型。
- 员工提交前，服务端完整解析所有符合截止日的来源；已存在本人对应来源/身份的非取消 `FinanceCommission` 可作为申请明细复用，但不得已经归属于其他有效申请。
- 尚无提成事实的合格来源由申请提交事务通过内部受控生成路径创建 `DRAFT` 提成，再关联申请明细；不向员工开放现有财务“任意选择来源/员工”的管理接口。
- 已经 `CONFIRMED`、`PAID` 或 `CANCELLED` 的提成不能进入待申请集合；已有 `DRAFT` 若已关联其他申请或来源指纹失效，提交返回明确冲突，不静默复制或改变历史金额。

## 4. 员工申请流程

### 4.1 读取

工作台新增本人月度申请摘要/明细读取：

- 按月份返回 `待申请`、`本月累计中`、`审批中`、`已批准`；
- `待申请`按 `commission_date <= coverage_to` 汇总所有未进入有效申请的合格来源；
- 当前月来源只能进入累计中，不返回可提交的申请 token；
- 申请详情包含来源订单、核销/对冲日期、人员身份、方案快照、金额和当前状态；不暴露同事记录。

首页金额和预计卡继续用于提示，不直接作为申请金额；申请页必须走完整候选查询和服务端分页明细。

### 4.2 提交/重提

服务端从当前会话取得组织和员工，不接受客户端传入的员工 ID、组织 ID、金额或任意明细 ID 作为授权依据。事务内：

1. 计算服务端财务日期、申请月份和固定 `coverage_to`；拒绝当前月提前申请。
2. 按组织、员工和申请月份锁定/创建唯一申请头；已 `PENDING_REVIEW` 或 `APPROVED` 返回稳定冲突，已 `REJECTED` 只能走原申请重提。
3. 按来源 ID 排序锁定候选来源、订单财务锁证据和已有提成父单，重新解析方案员工分配、归属身份、费用和回款条件。
4. 排除已进入其他有效申请的提成；对剩余来源完整计算并写入/复用 `DRAFT` 提成，写申请明细快照和汇总。
5. 候选为空时拒绝提交，不创建空申请；任一候选来源变更或唯一性冲突时整体回滚。
6. `REJECTED` 重提沿用原申请 ID 和申请月份，保留上一版审计；服务端重新形成本次提交版本，不能新建替代申请。员工不能直接编辑金额、方案、来源或明细，数据纠正必须先修改上游事实后再重提。

申请提交成功后，申请头与明细在同一事务提交；迟到的历史来源不会自动追加到已提交申请。

## 5. 财务整批审批

### 5.1 查询与权限

- 申请列表、详情和导出沿用目标组织的 `system.finance.commission.read`；普通员工只能读取本人申请。
- 批准、驳回沿用 `system.finance.commission.manage`；权限按当前目标组织实时解析，不因申请创建时的权限快照绕过当前授权。
- 财务列表以申请头为行，显示员工、申请月份、覆盖截止日、笔数、金额和申请状态；明细下钻才显示订单与来源。

### 5.2 批准

整批批准在一个共享事务内完成：

1. 锁申请头并校验 `expected_version` 与 `PENDING_REVIEW`；
2. 按明细提成 ID 排序锁定申请明细、来源订单和提成父单；
3. 重算每笔来源指纹，确认仍为同一员工/身份/方案快照，确认没有草稿费用或其他阻断事实；
4. 所有明细均通过后，按固定财务锁序将对应 `DRAFT` 提成统一转为 `CONFIRMED`；任一明细失败整体回滚；
5. 更新申请为 `APPROVED`、记录决策人/时间、递增版本并写审计。

不调用会自行开启独立事务的逐笔确认接口，避免整批操作出现部分提交。批准不自动变更 `PAID`，也不调用银行或工资接口。

### 5.3 驳回与重提

- 驳回只允许整单操作，必须填写原因；申请转为 `REJECTED`、递增版本并保留明细和快照。
- 员工重提只能更新原申请的当前提交版本；历史驳回记录不可覆盖。
- 驳回不会把明细静默分发到新申请，也不会让同月重新创建第二张申请。

## 6. 并发、权限与审计

- 月度唯一键、申请头 `FOR UPDATE`、`expected_version` 和明细/提成固定排序锁共同防止重复提交与并发审批。
- 员工提交与财务审批竞争时只有一个事务成功；已进入 `PENDING_REVIEW` 的申请不能被另一浏览器重复提交。
- 申请及明细跨组织查询都显式带 `organization_id`，本人接口由主体固定 `employee_id`；前端隐藏不能替代服务端授权。
- 审计记录申请创建、提交、重提、批准、驳回，包含员工、申请月份、覆盖截止日、明细 ID 集合、金额快照、版本、操作者和原因；日志不记录完整收入报表或令牌。

## 7. 迁移、回退与性能

- 以 Ent Schema 为源生成申请头/明细表和正式 SQL 迁移；不修改或删除既有提成与方案历史。
- 旧提成没有申请关系时保持现状，可在员工下一次申请中被纳入；不批量回填一张虚假的历史申请。
- 回退代码时保留新表和申请快照；已批准申请仍通过既有提成状态保留，禁止自动拆回或删除。
- 完整候选查询只处理当前员工与一个截止日期，使用来源日期、员工、组织、申请关联索引；申请页面明细分页，但提交事务必须覆盖完整集合，不能套用工作台 20 条估算上限。
- 提交/批准前记录代表性数据量的查询和事务耗时；若真实数据超标，优先按来源批量查询与索引优化，不引入银行、缓存或薪酬快照平台。
