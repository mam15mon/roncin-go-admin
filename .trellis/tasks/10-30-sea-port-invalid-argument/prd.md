# 排查修复订单无修改保存时报字段不合法

## 目标

订单刷新后不修改任何内容直接保存应正常通过；多个地点字段引用同一有效港口或机场时不能误拒绝，真实失效地点返回明确业务提示。

## 已确认场景

- 用户最终更正：没有修改港口或其他字段，直接刷新后点击保存仍失败。
- 用户提供实际更新请求，其中 `originLocationId` 与 `destinationLocationId` 相同；该地点在本地数据库存在且启用。
- `server/internal/data/order_sync.go:76` 收集四个地点引用，`order_convert.go:352` 只过滤 nil、不去重；`order_sync.go:108` 的 SQL IN 返回唯一记录数，`:112` 却与未去重的引用数量比较。用户请求的地点引用数为 2、唯一 ID 数及匹配启用港口数均为 1，会错误返回 `ORDER_INVALID_ARGUMENT`。
- `validateAirportIDs` 同文件 `:118` 存在相同计数问题；现有读路径测试允许重复地点引用，但写路径测试只覆盖单个地点，未覆盖此场景。
- 此前的主单版本漏传修复与本次失败无关；本次不改前端版本或单证保存语义。

## 需求与验收

- R1：地点有效性校验按唯一 ID 集合计数，多个字段引用同一有效地点时正常通过；不改任何业务字段的值。
- R2：同步修复同链路机场校验，仍拒绝缺失和停用引用，不放宽现有启用策略或组织/权限/版本保护。
- R3：港口/机场引用确实缺失或停用时返回明确地点提示，避免只报「订单字段不合法」；保留现有错误 reason，不扩为全站错误体系重构。
- AC1：用户实际请求的起运港/目的港重复 ID 场景在真实仓储写入验证中通过，刷新后无修改保存正常。（R1）
- AC2：地点有效性校验允许任意重复组合及四字段同 ID，字段位置与实际值原样保留；海运完整保存覆盖起运/目的相同与四同，空运完整保存保持既有起降机场必须不同的规则，仅其他地点字段重复。（R1、R2）
- AC3：重复地点中夹带缺失或停用 ID 时仍拒绝，错误指出港口/机场无效，事务不部分写入。（R2、R3）
- AC4：实现后补定向单元/正式迁移 PostgreSQL 集成回归，运行受影响 Go 测试、vet、diff 检查及风险匹配最终后端门禁。无前端改动则不重复完整前端门禁。

## 范围与状态

- 不修改业务数据、不清空或重建数据库，不为通过校验添加兼容回退。
- 不更改地点是否允许相同的业务规则，不新增同港禁止规则，不自动改港口，不变更接口或生成客户端。
- 用户原请求已提供，未保存完整业务载荷到任务文档；仅记录定位所需的字段关系与只读统计。
- 轻量后端缺陷任务；根因已通过代码与只读数据库计数核实，无待决产品问题。用户已确认方案并授权修复、review、合并主分支、安全删除分支和 push；已进入实施。
