# 技术设计：我的工作台、提成方案员工分配与订单提成摘要

## 1. 设计目标

在不改变核销/对冲计提来源、提成金额公式和现有提成/调整状态机的前提下，完成三个相互依赖的能力：

1. 将提成规则从组织级人员角色规则改为「组织 + 提成方案 + 多员工有效期分配」，使提成资格与计算方案具有唯一真相源，并降低批量维护成本。
2. 新增服务端工作台读模型，按本人事实和权限组合首页；无提成人员不接收提成金额模块。
3. 为海运出口订单列表提供批量提成摘要，并在服务端完成本人视图与组织级财务视图的隐私投影。

设计继续复用现有提成单快照、订单提成归属、权限组织范围和财务状态机，不建立工资、月结批次、跨期负余额或新的审批引擎。

## 2. 总体边界与数据流

```text
当前登录主体（用户 + 当前工作区组织 + 权限组织范围）
                  │
        ┌─────────┴─────────┐
        │                   │
提成方案与员工分配      订单协作与财务事实
        │                   │
        ├──── 计提候选解析 ──┤
        │                   │
        ├──── 工作台读模型 ──┤
        │                   │
        └──── 订单列表提成隐私投影
```

- `server/api/finance/v1/settlement.proto` 继续承载提成规则、候选、预览和生成契约。
- 新增 `server/api/workbench/v1/workbench.proto`，只承载登录员工的工作台聚合读接口；工作台动作继续跳转并调用原业务接口。
- `server/api/order/v1/order.proto` 为订单列表项增加可选提成摘要，由订单列表服务在取得已授权订单页后批量附加。
- `internal/biz` 负责资格、规则解析、可见范围和状态语义；`internal/data` 负责 Ent 查询、聚合和事务锁；`internal/service` 只转换 DTO、解析当前主体并调用用例。

## 3. 提成方案与员工有效期分配

### 3.1 Schema 变更

保留 `FinanceCommissionRule` 作为提成方案主表，新增 `FinanceCommissionRuleAssignment` 员工分配表：

- 方案主表继续保存组织、方案名称、人员身份、计提口径、比例、方案生效区间、启用状态和版本；`finance_commissions.rule_id` 继续引用方案并保留现有快照。
- 员工分配表至少保存 `organization_id`、`rule_id`、`employee_id`、必填的 `effective_from`、可空的 `effective_to`、`cancelled_at` 及创建/取消/终止操作者与时间；方案、组织和员工外键使用 `NO ACTION`，禁止删除造成历史断链。未生效分配的撤销通过 `cancelled_at` 标记，不额外引入状态枚举。
- 分配日期采用与现有财务日期一致的 `YYYY-MM-DD`，闭区间判定；实际有效区间为方案区间与员工分配区间的交集。
- 同一方案、员工和分配起始日唯一，允许员工退出后在另一不重叠区间重新加入同一方案；增加 `organization_id + employee_id + effective_to`、`rule_id + effective_to` 等候选与门禁查询索引。
- 方案返回当前/未来适用员工与历史分配摘要，但不把员工 ID 数组存入方案字段；多选只是 API 和 UI 的批量操作表现。

### 3.2 旧规则退出与迁移

正式迁移不删除规则、提成单或调整单：

1. 新增员工分配表、正式约束和查询索引，不修改或清空既有提成、调整和快照。
2. 将迁移前存在且没有任何员工分配的旧角色规则统一置为 `enabled = false`，使其不能继续生成新提成或开启工作台资格。
3. 旧规则保留为历史只读方案，继续满足 `finance_commissions.rule_id` 引用；接口以「历史规则，待复制」标识，不允许向旧规则补挂员工或重新启用。
4. 财务只能复制旧规则为具有明确起始日和真实适用员工的新方案；系统禁止按角色自动把组织内所有同岗员工加入方案。

该迁移不清空开发数据，也不对既有提成快照重算。

### 3.3 日期区间、名单变更与并发一致性

同一 `organization_id + employee_id + personnel_role` 下，所有已启用方案与未取消员工分配形成的实际闭区间不得相交；新方案与新分配的起点必填，空终点视为正无穷。迁移前起点为空的旧规则保持停用，只能复制成起点明确的新方案。

由于现有生效日期以 `YYYY-MM-DD` 字符串存储，本期不引入 PostgreSQL range 类型或依赖表达式索引。写路径采用稳定父行锁保证并发安全：

1. 进入 `Data.WithTx`，对员工 ID 排序去重；
2. 按排序后的员工顺序锁定当前组织对应 `Membership` 行 `FOR UPDATE`，并确认成员和用户有效；
3. 再锁定目标方案并校验 `expected_version`；创建新方案时先锁员工成员关系，再创建方案；所有写入口使用同一锁序；
4. 对每名员工查询同组织、同身份的其他已启用方案与分配，计算实际区间并判断重叠；
5. 无冲突才写入方案和分配变更，并将方案版本递增、写入同一审计事件。

员工名单变更规则：

- 新启用方案的 `effective_from` 必须是系统业务日期当天或未来，且至少包含一名有效员工；初始分配的起始日等于方案起始日，终止日默认跟随方案终止日。未启用草稿可以没有员工，但启用前必须补齐并重新校验。
- 方案尚未生效且分配也未生效时，可直接调整名单；移除尚未生效且未被引用的分配可以取消，但保留审计。
- 已生效方案新增或移除员工时必须提交 `change_effective_date`，只允许当前财务日期或未来日期。新增分配从该日开始；移除分配通常在该日前一日结束；若变更日不晚于分配起始日，则将该段分配标记取消并保留审计，不写入起止倒置的无效区间。
- 普通管理端禁止把变更生效日设为过去。历史错误不修改分配行解决，而是通过取消错误提成或财务调整保留审计链。
- 同一员工相关方案写入被 Membership 稳定父行串行化，因此首次分配也不存在「没有关系行可锁」的竞态。未生效方案作废、变更名单和成员停用前的分配终止仍遵循相同锁序。

方案参数变更规则：

- 未到生效日、没有提成引用且没有已生效员工分配的方案，可以修改身份、口径、比例、区间和名单，仍执行版本及区间冲突校验。
- 方案到达生效日后，身份、计提口径、比例和起始日不可原地修改，且不得用 `enabled = false` 追溯失效。调整通过【复制为新方案】完成：新方案从系统业务日期或未来日期生效，旧方案的终止日设置为新方案生效日前一日。
- 系统业务日期由服务端统一财务日期口径提供，不使用浏览器本地时区决定。缩短旧方案终止日及名单变更均不得早于系统业务日期。
- 已生效方案仍保持 `enabled = true` 并通过 `effective_to` 自然结束，使历史来源日期继续能够命中原方案；`enabled = false` 仅用于从未生效的草稿/作废方案和迁移后的无分配旧规则。

### 3.4 规则解析与计提流程

- 来源日期继续使用现有 `commissionDate`：核销日期或对冲确认日期。
- 计提候选键改为 `employee_id + personnel_role`。候选成立需要：
  1. 员工在来源涉及的订单上具有相同身份的 `OrderCommissionAttribution`；
  2. 来源日期同时命中一条已启用方案和该员工在方案中的有效分配，且该身份只有一个结果；
  3. 现有应收来源、费用状态和金额校验全部通过。
- 规则候选列表不再让财务先挑一条组织级角色规则。选择来源后，服务端直接返回「员工 + 身份 + 已解析方案 + 预计金额」候选。
- `PreviewCommissionRequest` 与 `CreateCommissionRequest` 接收来源二选一、`employee_id` 和 `personnel_role`，不再信任客户端提交 `rule_id`；后端按来源日期重新解析规则。响应仍返回实际命中的规则 ID/名称/版本用于说明和快照。
- 同一员工在同一来源中同时具备多个身份时，各身份形成独立候选；现有按「来源 + 员工 + 身份 + 非 CANCELLED」的唯一索引继续阻止重复生成。
- 成员停用路径在同一业务事务中检查其当前/未来方案分配；存在时拒绝停用并返回需先终止的方案清单，管理员先在方案管理中以离开日期结束分配后才能停用成员。员工当前已离职、Membership 已停用或登录账号已禁用时，不能新增未来分配，但财务仍可为来源日期落在其离职前有效分配期间的记录生成应得提成；历史资格由来源日期、方案区间和员工分配区间决定，不以当前账号状态抹除。
- 预览、创建、确认都重新校验来源、归属与规则指纹；规则或归属发生变化时沿用现有冲突语义拒绝确认。

### 3.5 API 与页面调整

- `CommissionRuleInput` 增加初始 `employee_ids`；`FinanceCommissionRule` 增加当前/未来适用员工数量和受控名单投影；列表增加 `employee_id` 过滤，关键字覆盖方案名、用户名、展示名和已有搜索键。名单单独增删接口携带方案 `expected_version` 与 `change_effective_date`。
- 方案管理页新增员工远程多选、适用人数和名单抽屉，组织变化时清空员工；人员选择器服务端关键字分页，最大 `pageSize = 200`。交互复用现有企业资源人员多选模式，但后端不能物理删除已生效分配。
- 创建/编辑方案保留身份、口径、比例、日期、启用状态和版本冲突处理；方案生效后核心计算字段只读并提供【复制为新方案】，名单变更显示生效日与影响提示，旧无分配规则只读展示且只能复制为新方案。
- 计提弹窗先选来源，再从服务端返回的员工身份候选中选择；候选行展示规则、身份和预计金额，不再提供可任意组合的规则与员工两个输入框。

## 4. 工作台读模型

### 4.1 契约拆分

新增 `WorkbenchService`，所有接口均为登录态接口并从会话取得当前用户和当前工作区组织，不接收可改写的员工 ID 或组织 ID：

- `GetWorkbenchOverview`：模块门禁、本人提成状态汇总、少量近期订单、可靠作业待办计数、当前用户有权查看的财务/审批摘要。
- `ListMyCommissions`：本人提成与调整明细，服务端分页并按状态/日期过滤。
- `ListMyReceivables`：与本人合法提成归属相关的已确认应收未结项及预计说明，服务端分页。
- `ListMyRecentOrders`：本人真实订单协作关系下的近期海运出口订单；首页可直接使用 Overview 内的前 5～10 条，更多记录走分页接口或现有订单页。

首页只取摘要和少量记录；完整台账、补录审批、冲减处理及发放动作继续走原接口。

### 4.2 提成模块门禁

仓储一次性判断当前组织与当前用户：

```text
has_commission_eligibility =
  存在 employee_id = caller 的当前/未来未取消员工分配
       且其提成方案 enabled = true
       且方案与分配实际区间尚未结束
  OR 存在 status ∈ {DRAFT, CONFIRMED, PAID} 的本人提成单
  OR 存在 status ∈ {DRAFT, CONFIRMED, PAID} 的本人提成调整单
```

- 未来已配置且已分配本人的方案属于明确提成员工，门禁为真，并返回最近实际生效日供页面显示。
- 已取消方案分配、提成或调整不能单独开启门禁；订单协作与提成归属也不能单独开启。
- Proto 使用 `optional bool has_commission_eligibility` 并由服务端始终赋值；前端仍按仓库规范使用 `!== true` 处理 false 可能省略的风险。
- 门禁为假时服务端不查询也不返回本人提成金额模块，前端不渲染标题、骨架、入口或零金额卡片。

### 4.3 自适应内容

- 有当前/未来有效方案分配或历史提成：显示提成卡、回款及本人订单/待办。
- 无提成资格但有订单协作：显示本人近期订单、费用草稿和本人可见的未解决异常等现有可靠事实。
- 无订单协作及业务待办：显示欢迎信息、当前组织、账号边界和已有授权快捷入口。
- 组织公告、费用补齐时限、异常责任人、待电放责任在当前模型中没有完整真相源，本期不返回伪待办。
- 财务卡片独立按具体权限与组织范围出现；个人提成门禁为假不影响持权用户查看财务摘要。

### 4.4 财务及审批摘要

- `system.finance.commission.read` 只控制授权组织内提成/冲减摘要读取；`system.finance.commission.manage` 才暴露处理入口能力。
- 补录审批摘要复用 `OrderFeeSupplementUsecase` 的实时资格判定。数据层先有界查找 `PENDING` 候选，再通过抽取出的共享资格函数过滤，禁止在工作台另写一套“财务角色即审批人”规则。
- 工作台只返回计数、少量待办和目标页面参数；通过、驳回、确认、忽略、标记已发等操作仍调用原端点并重新鉴权。

## 5. 订单列表提成摘要

- `Order` 增加可选 `commission_summary`，仅 `ListOrders` 的海运出口结果按需填充；详情接口不因该字段自动扩大财务数据。
- `OrderService.ListOrders` 在取得已授权且已分页的订单后，将该页订单 ID 一次性交给提成用例批量查询，不逐行发起 SQL 或 HTTP 请求。
- 对每一订单组织单独判定：
  - 调用者对目标组织拥有 `system.finance.commission.read`：查询该票全员状态与汇总；
  - 否则只查询 `employee_id = caller.UserID` 的提成、调整和预计机会。
- 数据层按组织与可见模式分组批量聚合。普通员工的响应不包含他人数量、姓名、状态、金额或“整票是否有提成”等旁路字段；本人无记录时只返回本人空态。
- 摘要以可并存的事实集合表达待确认、待发、已发、预计机会和待冲减，不制造整票互斥状态。金额仅返回当前可见范围，取消记录不参与有效汇总。
- 首期不提供基于他人提成事实的列表过滤或排序，避免通过结果顺序和总数推断隐私。

## 6. 查询与性能

- 工作台聚合使用有界查询与数据库聚合，Overview 最近订单和待办都有固定上限；明细统一分页且 `pageSize <= 200`。
- 订单列表提成摘要只处理当前页订单 ID；为提成单、调整单、规则和归属补充与 `organization_id / employee_id / order_id / status` 相匹配的索引。
- 不预建快照表或缓存。以代表性数据量记录 Overview 与订单列表附加查询耗时；核心查询目标 200ms，只有测量证明必要时再单独设计缓存。
- 不同组织本位币不合计；当前工作区个人提成使用该组织本币，回款保留原币。

## 7. 安全、审计与错误

- 本人接口只能从主体读取用户与组织，忽略或拒绝任何客户端人员/组织改写参数。
- 提成方案及员工分配沿用 `system.finance.commission.read/manage` 及其组织范围；方案和名单写审计增加员工 ID 集合、人员身份、方案/分配生效区间、变更生效日与版本。
- 方案或员工分配区间重叠、回溯名单变更、成员失效、版本冲突、来源日期无唯一方案、身份归属不匹配均返回明确领域错误；驱动约束错误映射为同一业务语义。
- 工作台无权模块采用“不返回模块数据”语义；直接调用写端点仍返回权限错误，不能依赖前端隐藏保证安全。
- 日志不记录完整工作台响应、员工收入明细或令牌。

## 8. 验证策略

- 方案领域测试：多选员工、员工差异方案、同员工不同身份、相邻/重叠/开放区间、今天/未来名单变更、拒绝回溯、已生效核心字段只读、复制新方案衔接、无效成员、版本冲突。
- PostgreSQL 集成测试：两个并发事务把同一员工身份加入重叠方案时仅一个成功；多员工按主键固定锁序；成员锁先于重叠查询；旧无分配规则不能直接启用。
- 计提测试：方案与员工分配唯一命中、多身份分别生成、固定薪人员无候选、名单加入/退出日期边界、离职后仍可生成来源日期落在离职前有效区间的资格、历史快照不重算、核销与对冲同构。
- 工作台权限矩阵：无方案分配无历史、有未来方案分配、有过期方案分配但有历史、仅取消记录、订单协作但固定薪、个人与财务权限并存、组织切换迟到响应。
- 订单列表权限矩阵：普通员工仅本人、财务整票、同一主体在不同组织权限不同、本人无提成但同事有提成时无泄露、多身份和多状态并存。
- 前端测试：门禁为 false/undefined 时从首次渲染起无提成 DOM；门禁为真时空态与未来生效提示；组织切换清理旧数据；生成枚举与生成客户端类型保持一致。

## 9. 风险与回退

- 最大风险是旧角色规则或无效名单被误当成个人资格。迁移与所有候选查询都必须要求来源日期命中有效员工分配，并将无分配旧规则停用。
- 最大隐私风险是订单列表先聚合全员再由前端裁剪。必须在 SQL 查询条件中先限定本人或授权组织视图，禁止把全量结果传到前端过滤。
- 最大并发风险是首次分配无目标关联行可锁，以及一次多选员工产生交叉锁。统一按员工 ID 排序锁定 Membership 稳定父行，不使用“先查冲突再插入”的无锁模板。
- 最大审计风险是编辑多选名单时物理删除关系或回溯生效日。所有已生效分配以终止日期退出，普通操作只允许今天或未来日期。
- 代码回退时新增分配表和停用旧规则可保留；重新启用无分配的组织级规则会恢复歧义，禁止作为自动回退方案。需要业务恢复时由财务把旧规则复制成起始日明确、员工分配真实的新方案。
