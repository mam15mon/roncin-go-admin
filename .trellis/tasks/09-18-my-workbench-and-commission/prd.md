# 产品需求文档：我的工作台与提成透出看板

## 1. 目标与本期边界

将静态首页 `/welcome` 改为按当前用户的业务归属和实际权限组合内容的「我的工作台」；让员工看见本人可追溯的提成、回款与近期订单，让有权限的人员及时处理财务待办，并在海运出口订单列表透出不误导人的提成摘要。本期交付的是基于现有订单、核销/对冲、提成及补录事实的查询与操作入口，不重建提成计提、工资发放或汇率规则。

- 用户价值：业务人员能区分已发、待发与尚未实现的预计金额，定位逾期客户和未结尾款；有资格的审批人与财务人员能从首页直达现有处理流程。
- 系统定位：货代业务协同与结算系统，不存储底薪、社保公积金或个税，不自动执行工资扣款或银行打款。
- 首期业务范围：当前工作区组织的海运出口订单、员工本人提成、应收及财务待办；不把不同组织的本位币金额合并为一个数字。

## 2. 已确认的现状与遵循的业务事实

1. `/` 跳转 `/welcome`，现有首页仅展示账号、组织与权限信息，具备改造空间。依据：`web/config/routes.ts:33-39,259-260`、`web/src/pages/Welcome.tsx:13-139`。
2. 当前仅海运出口订单列表接入实际路由；订单列表可按销售、操作等人员筛选，但用户自助视图的范围必须由服务端根据登录身份判定，不能信任客户端提交的人员 ID。依据：`web/config/routes.ts:118-158`、`server/internal/data/order_query.go:145-148,204-212`。
3. 基础提成按有效应收核销或已确认对冲的实际分摊计算已实现收入，可在客户分期回款时多次生成；提成单按来源、员工、人员角色去重，状态是 `DRAFT → CONFIRMED → PAID`，另有 `CANCELLED`。同一订单可关联多名员工、多张提成单和不同状态，不能被视为「一票一张、一次性落袋」。依据：`server/internal/data/finance_commission.go:557-635,674-699`、`server/internal/data/ent/schema/finance_commission.go:13-14,86-100`。
4. 锁后补录的 `LOCKED_FEE_SUPPLEMENT` 冲减建议是原 `FinanceCommissionAdjustment` 的 `DECREASE + DRAFT`，财务可确认、必填原因忽略，确认后仍需在实际少发/扣回后标记 `PAID`；系统只在原提成订单行与父单余额内封顶，不建立员工跨月负余额。依据：`.trellis/tasks/archive/2026-09/09-17-locked-order-fee-policy/prd.md:53-69,129-137`、`web/src/pages/finance/commissions/components/PendingDecreasePanel.tsx:65-67,82-210`。
5. 补录申请的读取和审批资格由申请所有权、费用读取权限及目标订单实时直接解锁资格分别决定；财务角色本身不自动获得所有申请的审批权。依据：`server/api/order/v1/order_fee.proto:75-110`。
6. 组织本币设定后不可变，前后端已执行；现行汇率契约仍支持历史周继承与预设下周，历史单据保留自身汇率快照。本任务不改变它们。依据：`server/internal/biz/admin_organization.go:84-104`、`web/src/pages/admin/components/org/OrgEditModal.tsx:96-104`、`.trellis/spec/server/backend/exchange-rate-single-rate.md:25-30,54-65`。

## 3. 本期需求

### R1. 能力组合式首页

- 保留 `/` 与 `/welcome` 的现有访问路径，以 `<PageContainer>` 展示欢迎信息及用户可访问的卡片；卡片依据现有 `/auth/me` 权限、本人业务归属和具体待办的实时资格独立出现，同一人可同时看到个人与财务模块，不按「业务员／操作员／财务／管理员」互斥分流。
- 无权访问某模块时不展示其入口或汇总；没有业务归属的用户不被强行展示为业务员，仍可访问其已获授权的模块和基础欢迎信息。前端只决定显示，服务端对每个读取和写入动作重新验证授权及组织范围。
- 切换当前工作区组织后，各卡片、金额币种和近期订单同步按新组织刷新；迟到的旧组织响应不得混入当前页面。
- 首页待办以摘要、少量记录和现有业务页面入口为主；不在首页复制完整财务台账或发明另一套审批状态机。

### R2. 员工本人提成与回款看板

- 提供仅供登录员工本人读取的工作台数据：服务端固定 `employee_id = caller.UserID`，并限定员工在当前工作区组织的有效成员关系及其合法的订单/提成归属；请求参数不能改查同事。员工不必因此取得组织级 `system.finance.commission.read`。
- 提成卡严格分桶：`DRAFT` 是「待财务确认」，`CONFIRMED` 是「已确认待发」，`PAID` 才是「已发放」；`CANCELLED` 不计入有效金额。已发累计支持本年、本月查看与对应提成单下钻；冲减建议 `DRAFT` 标示「待处理、尚未扣回」，`CONFIRMED` 标示「已确认、尚未实际扣回」，`PAID` 才标示「已扣回」。本人可查看其锁后补录来源的最小详情及审批来源，不得读取他人的提成或无关财务明细。
- 「预计可计提」只表示员工已有可计算的有效应收核销/对冲来源、但尚无对应有效基础提成单的机会，沿用现有计提引擎的来源、规则、人员归属和费用草稿校验；不附加「整票应收必须 100% 收齐」的新计提门槛。「预计」金额不得并入已确认待发或已发金额；规则或数据不具备可靠估算条件时显示「暂无法估算」及原因，不把未知值记作零。
- 「在途回款」逐票展示已确认应收的未结余额、到期日与逾期状态；能按当前费用、提成规则和人员归属估算的潜在提成须显著标记为「预计，非应发承诺」，并说明尚未回款/核销、费用或规则变化都会影响结果。不同原币的欠款分别标明币种；本位币提成汇总仅在当前工作区组织内计算。未形成已确认应收的收入不假装为客户已欠尾款。
- 「我名下的近期订单」仅展示本人作为销售或操作等真实协作人员归属的最近 5～10 票海运出口订单，按现有订单读取权限与组织范围控制；可跳转订单详情、费用和已有单证/里程碑页面。无订单时提供明确空态。
- 首期风险提醒复用能由现有事实准确判定的逾期应收与费用草稿；「订单创建超过设定时限但尚未录齐费用」及「放单后信用期超限」须先有可验证的时限与完成事实，本期不根据零费用或主观漏录推断责任。

### R3. 财务与审批待办

- 为当前用户聚合其**实时有权审批**的 `PENDING` 锁后费用补录申请，展示订单、费用、币种、金额、原因、发起人与申请时间；支持打开申请详情后沿用现有通过/驳回动作和版本冲突提示。不能按「全公司待审批」扩大申请可见范围，也不因为拥有财务角色就自动允许审批。
- 对具备相应组织范围的 `system.finance.commission.read` 用户，展示现有 `LOCKED_FEE_SUPPLEMENT + DECREASE + DRAFT` 冲减建议摘要并链接现有待处理冲减视图；只有具备 `system.finance.commission.manage` 的用户才可确认、忽略或标记已扣回。忽略必须填写原因，确认不等于已实际扣回。
- 展示当前有权读取的已确认待发提成摘要及跳转现有提成台账、现有导出/逐单「标记已发放」动作；按原提成单状态展示，不伪造月度「应发结算单」或声称已经线下打款。不同本位币分别展示，导出沿用原权限。
- 本期不提供批量审批、批量冲减、批量发放，也不自动扣减下月提成；既有冲减建议仍受原提成订单行与父单的双层余额约束。

### R4. 海运出口订单列表提成摘要

- 仅在现有 `/orders/sea-export` 列表增加【提成】摘要及下钻；服务端按当前订单列表的组织/业务类型授权范围与提成读取资格计算，不由页面逐行请求提成详情。普通员工即使能查看订单，也只能看到本人在该票订单上的提成状态；本人没有可显示的提成或预计机会时显示「我暂无提成」等仅针对本人的空态，不暗示整票或其他员工是否有提成。普通员工不能从列表、统计、筛选、排序或下钻获知其他员工有无提成及其金额。
- 持有目标组织 `system.finance.commission.read` 权限的财务/管理人员可查看整票全员的提成状态与汇总，并下钻到授权范围内的员工及来源；是否为管理员或财务角色本身不代替这项权限。同一用户兼具普通员工归属与上述组织级权限时按组织级权限展示全员汇总，切换组织后重新判定。
- 摘要在**当前用户可见的提成范围内**保留「尚无有效提成／有预计可计提来源／有待确认草稿／有已确认待发／有已发提成／有待处理冲减」这些**可并存的事实**，允许同票多员工、多来源、分期回款及不同状态同时存在。`PAID` 仅表示对应提成单已发，不宣称整票所有员工和所有回款均已结清；`DRAFT` 冲减不能显示成「已扣回」。取消的提成不当作有效已发。
- 可使用灰、蓝、青、绿、橙等现有 Tag 视觉语义，但「待冲减」作为独立风险标识与基础状态并列，不用一个互斥五态枚举掩盖混合状态；详情下钻仅能识别当前用户有权查看的员工、来源单与状态，金额及汇总服从相同的本人或组织级权限。

## 4. 非功能要求

- 沿用全站 Fluid 满宽布局、`#f5f7fa` 背景、公共 `@/components/ui` 页面组件和纯白高密度卡片；不引入页面私有 `maxWidth: 1440` 或居中外壳。
- 数据隔离同时覆盖个人卡片、下钻、统计、导出及订单列表摘要（包括筛选和排序）；订单可读不等于全员提成可读，服务端先确定本人或授权组织的可见范围，再形成状态与汇总。对越权人员 ID、越权组织和不可见提成返回一致的拒绝或无数据语义，不泄露他人记录存在性。财务卡片的读取与动作分别按对应权限及目标组织校验；补录审批遵循目标订单实时资格。
- 使用数据库侧聚合或有界分页，避免首页 N+1 与全量拉取后在浏览器汇总；以设计阶段明确的测试数据量验证首页核心查询 200ms 目标。先测量，再决定是否需要增量快照，快照不是本期预设方案。
- 关键金额采用既有十进制与币种口径；区分订单欠款原币、提成组织本位币、`PAID` 发放事实与尚未实现的估算值。页面和接口不能将多币种裸数相加。

## 5. 验收标准

- [ ] AC1：访问 `/` 或 `/welcome` 时，仅展示当前用户有资格查看的模块；业务与财务权限兼有者可同时看到两类模块，单一角色或无业务归属用户均有正确空态；切换组织不残留上个组织的数据。
- [ ] AC2：员工本人在当前组织能看到 `DRAFT`、`CONFIRMED`、`PAID` 及补录冲减 `DRAFT/CONFIRMED/PAID` 的不同含义、本年/本月已发累计与对应详情；改造请求中的 employee_id 或 organization_id 不能读取其他员工或越权组织。
- [ ] AC3：有效部分核销/对冲可以形成「预计可计提」机会而不要求整票全额结清；无可靠规则、人员归属或计算数据时不显示假精确金额；估算与已确认、已发金额分别展示。
- [ ] AC4：在途应收逐票展示正确的未结原币余额、到期及逾期状态；未形成已确认应收、已结清和已撤销来源不会误算为未回款；本人近期海运出口订单只包含可见的真实协作归属。
- [ ] AC5：审批人只看见其对目标订单实时有权处理的 `PENDING` 申请；失去资格时工作台入口和审批接口均不再允许处理。财务只在授权组织范围看见冲减建议，读权限不能执行确认/忽略/发放操作。
- [ ] AC6：冲减从待处理到已确认、实际已扣回三阶段的文案和金额与现有状态机一致；忽略必须填写原因，确认时订单行及父单余额不足稳定拒绝；财务待发摘要、导出与原台账不矛盾。
- [ ] AC7：海运出口订单列表中，只有订单读取权限的普通员工仅能看到本人在该票订单上的状态；无本人提成时不暴露同事有无提成，且不能从列表、筛选、排序、统计或下钻推断同事的提成及金额。持有目标组织 `system.finance.commission.read` 的财务/管理人员能看到整票全员的状态与汇总；同一用户兼具本人归属和该权限时展示授权组织全员视图，移除权限或切换到未授权组织后立即回到本人视图。可见范围内的摘要能同时反映多员工、多笔分期提成及待冲减，不把部分 `PAID` 宣称为整票全部已发，也不把冲减草稿算作实际扣回。
- [ ] AC8：本期不改变组织本币不可变规则、现行汇率继承/预设策略、费用方向更新契约、提成计提来源和线下支付语义；不同币种不能合并为一个金额，个人查询及首页聚合具备风险匹配的服务端与前端验证。

## 6. 非目标与后续专题

- **月度提成结算与跨期余额**：原设想的「当期应发 = max(0, 当期新单提成 − 已确认冲减)」、未扣完金额挂账并抵扣下期、员工负余额台账、月度结算单/批次、批量发放及自动支付，单独定义财务期间、余额归属、抵扣顺序和审计后再立项。本期仅展示现有提成单与独立调整单事实，不改变锁后补录的双层封顶和不跨单顺延规则；更不接触底薪。
- **汇率与费用事实不可变治理**：原提议的当周无汇率强阻断、废除 `INHERITED_LAST_WEEK`/四级容灾、空白历史周补录、禁止预设未来周、被费用/账单/发票引用即永久只读、零引用才能停用重建、错误汇率的红字冲销，以及费用 Direction 创建后永久不可变，均属于需要与现行契约和纠错链路共同评审的独立专题，不作为本期验收条件。本期沿用已存在的组织本币不可变规则。
- **新工作流**：业务员「申请计提」、新的争议审批实体、完成费用录入的显式签认、按时间阈值催补费用、按放单事实的信用期风险判定、首页批量审批/发放；未有可验证的事实和审批规则前不在本期假实现。
- 其他订单品类、跨组织合币总额、面向员工的银行/工资发放、实时缓存快照平台，均不在首期范围。
