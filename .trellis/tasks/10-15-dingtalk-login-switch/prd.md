# 登录方式切换保留有效钉钉二维码

## 目标与背景
用户观察到从管理员账号登录返回扫码时重复出现占位和二维码加载，要求开始修复并明确同意创建 Trellis 任务。既有首次 HTML 提前加载已完成；本期修复切换造成的重复销毁/配置请求，不承诺降低钉钉自身网络耗时。

## 已确认问题
`web/src/pages/user/login/index.tsx:182` 条件渲染卸载扫码组件；`:334` 切换先销毁预载节点，返回又强制刷新配置。扫码组件真实卸载会销毁 iframe，因此缓存配置本身不能保留已加载二维码。

## 需求与验收
- R1：在同一登录页从扫码切到密码再返回，保留未过期、未用于认证的同一 iframe 和浏览上下文，不改 src/父节点；不新增配置请求或授权导航，不重现初始占位。覆盖 HTML 提前实例和 SPA/刷新后动态实例。
- R2：密码模式隐藏整个扫码区及外部 iframe，停止接受扫码认证消息，不能遮挡密码字段或留可聚焦 iframe；切回有效实例后恢复认证。
- R3：密码模式下过期立即退役旧实例，但不发后台配置请求；返回时按需刷新一次。明确失败或配置错误可在返回时重新获取。已用于认证的实例不能恢复。
- R4：主动刷新、到期（扫码模式）、换码回调、退出登录页沿用现有严格 origin/source/state/回调/去重与清理；密码提交成功或进入工作台选择不得接受隐藏扫码消息。
- R5：保留首次 HTML 提前加载及首屏零配置 GET；StrictMode 和快速切换不多建实例，不残留监听/计时器。

## 验证标准
- 真实 Chromium 连续切换至少 3 次，始终同节点/contentWindow，配置和授权请求数不增加，切回不出现加载占位；分别验证 HTML 首屏和手动刷新后实例。
- 测试密码模式的成功/失败消息被忽略；过期隐藏时无 GET、返回恰好一次 GET；真实卸载和旧消息无效。
- 定向测试、改动文件 Biome、tsc、架构检查与风险匹配前端门禁通过；独立审查通过。

## 范围外与限制
不更换 SDK/钉钉端点、不改 API/数据库/服务端；不增加全局保活平台、不通过隐藏错误伪装速度。真实企业扫码需企业账号验证，协议模拟不替代该项。
