# 钉钉扫码优先与组织成员管理简化

## 目标与授权

让员工打开登录页即可扫码，管理员能完成新公司的初始配置，并以明确的组织成员关系维护人员与角色。

用户于 2026-10-13 明确要求“开始写 trellis 任务”，随后补充创建公司自动加入管理员、bootstrap:admin 为现有组织补齐管理员授权。本轮授权为任务规划，全部任务保持 planning，尚未批准实施。

## 已确认产品方向

- D1：默认进入组织不应是管理员可配置项，取消“主要组织”配置概念。
- D2：“加入其他组织”支持多选，角色选填不能成为组织只能单选的理由。
- D3：除管理员外员工都用钉钉扫码，登录页优先展示扫码。用户在“直接展示二维码，管理员另行切换密码登录”的建议后授权创建任务。
- D4：每家公司应具备管理员角色，创建公司自动加入管理员；bootstrap:admin 可给已有组织补齐管理员授权。
- D5（2026-10-13 已确认）：自动加入各公司的对象仅限 bootstrap:admin 创建的初始管理员账号；用户对此明确回复“对的”。后来手工授予系统管理员角色的账号不自动加入各公司，仍需明确授权。

## 已核实背景

详细证据见 research/current-state.md。

1. 密码登录和钉钉扫码回调都已在多工作台时展示选择页，主要组织不会跳过选择。
2. primary 还影响用户摘要与角色编辑目标，不能只删除界面开关。
3. 后端允许空角色加入组织，现有接口一次接收一个 organization_id。
4. 新建公司已经创建公司管理员角色，但不自动授予任何账号；角色存在与管理员已加入公司是两回事。
5. bootstrap 当前仅允许账号表为空，只将初始管理员加入系统管理。本次要求会改变该约定。
6. 系统管理和公司独立维护角色库，部门/小组复用所属工作台角色。

## 验收标准

- [ ] AC1（R1）：打开登录页即出现可扫码的二维码，无须先点击按钮跳转才出现二维码；管理员能切换密码并返回扫码。
- [ ] AC2（R1、R7）：二维码加载/失效/失败可明确处理和重试；密码入口仍可达；未同步、待分配、停用账号结果正确。
- [ ] AC3（R2、R3）：密码和扫码均单工作台直进、多工作台选择；用户管理没有主要组织配置和标签。
- [ ] AC4（R3）：编辑某条成员关系只改该组织角色；仅保存用户基础资料不修改隐式选中的组织角色。
- [ ] AC5（R4）：一次选择两个组织，不选角色也可加入，之后可分别维护角色。
- [ ] AC6（R4、R7）：跨公司角色、越权、无效组织、重复/并发加入有明确结果，失败行为按确认后的原子性规则验收。
- [ ] AC7（R5、D5）：新公司创建后初始管理员能进入并维护人员/角色，公司管理员不获得系统专属权限；后来手工授予系统管理员角色的账号不会自动获得新公司成员资格。
- [ ] AC8（R6）：空库初始化、保留公司后首次创建管理员、已有初始管理员补齐授权均通过针对性验证；重复执行不改密码或普通员工授权。
- [ ] AC9（R7）：停用公司/账号/成员/角色按明确规则处理，不静默恢复，不以管理员标记跳过准入。
- [ ] AC10：契约、生成物、正式迁移、开发数据及规范一致，不清库、不覆盖并行任务。

## 范围外

不改通讯录同步、员工开通及业务审批；不因员工通常扫码就顺便禁用普通账号密码接口；不增加登录偏好记忆、默认组织配置或通用身份平台；本轮不运行 bootstrap、迁移或任何账号授权操作。

## 相关约定的替代关系

- 原 10-09-dingtalk-directory-provisioning 的 D2/R3/R5/R7 仍写默认工作台由管理员维护，实施时同步标注被替代要求。
- 原任务 D3 是多人批量开通逐人原子、允许部分成功；本任务是单人多组织加入，不能机械复制其失败语义。
- auth-session-org-switch.md 当前要求 bootstrap 不自动授公司资格；D4 是用户明确提出的新行为，要同步规范与测试。
- 后台任务通知优化正在同一工作区实施，本轮只新增本任务规划文件。

## 待收敛决策（按优先级）

1. 多选角色交互：选填已确认；建议选中后按组织逐项选填，另一方案是先批量加入、再逐条分配，待确认。
2. 补齐与停用边界：建议只补缺失项，已停用账号/公司/角色/成员关系明确报告、不静默恢复；用户尚未明确恢复规则。组织范围建议为系统管理和全部启用公司，部门/组复用公司范围、不逐节点重复加成员。
3. 单人多组织失败语义：建议全成全败，避免只加入部分组织；尚待用户确认。
