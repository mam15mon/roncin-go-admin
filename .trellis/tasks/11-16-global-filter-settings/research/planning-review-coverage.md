# 规划审阅：全站筛选覆盖与业务输入保护

- 研究问题：父任务与两个筛选子任务的规划是否覆盖用户要求及 F01–F33 清单，是否存在会让隐藏条件继续生效、候选选择丢失或表单误提交的缺口？
- 范围：只读审阅父 prd.md／design.md／implement.md、两个筛选子任务三份规划及已有筛选研究；必要时回查触发风险的现行源码。未修改产品、任务状态或其他规划。
- 日期：2026-11-16（Asia/Shanghai）

## 结论

全站覆盖、五项筛选定制、账号跨浏览器保存和特殊业务路径已进入规划，没有发现遗漏整个 F 分组的范围缺口。审阅发现 **2 项需在最终方案前明确的行为缺口**：提成申请／待执行冲减请求阶段补默认状态，以及提成方案现有计提口径搜索没有后端能力。

本结论是规划审阅，不是实现验收。两项在规划中明确处理方式并纳入定向验证后，可以继续最终方案审阅；均不要求新增业务接口。主会话已在本轮明确采纳 C1 的“可见字段显式初始化”方案，需由主会话同步正式规划；本研究不改其他文件。

## 阻塞项 C1：两个面板请求阶段补默认状态会让隐藏条件继续生效

### 触发与证据

- `web/src/pages/finance/commissions/components/CommissionApplicationsPanel.tsx:352` 起的 request 使用 `filters.status ?? FINANCE_COMMISSION_APPLICATION_STATUS_PENDING_REVIEW`。即使隐藏状态并把 committedFiltersRef.status 清为 undefined，后续请求依然只查询待审批。
- `web/src/pages/finance/commissions/components/PendingDecreasePanel.tsx:319` 起的 request 使用 `filters.status ?? FINANCE_COMMISSION_STATUS_CONFIRMED`，同样会把被移除的状态补回来。
- 当前父 PRD R6 与父 design.md 第三节要求“移除筛选项清除条件并刷新”，但两个子任务没有明确如何处理以上默认注入；照原请求路径接公共隐藏适配会违反该验收。
- 现有 Proto `server/api/finance/v1/settlement.proto:1175` 的申请 status、`:1155` 的调整 status 都是 optional；服务端 `server/internal/service/settlement_commission_application.go:34` 和 `settlement_commission.go:719` 直接转换该 optional 状态，不要求调用方传默认队列值。因此解决不需要新增业务参数或后端筛选功能。

### 建议收敛方式

优先把“默认聚焦待审批／已确认”从 request 的无条件补值移到可见状态字段的显式初始已提交条件：首次进入该状态字段可见时，表单、chips 和实际请求一致展示默认状态；字段已隐藏或被用户移除后不再补默认状态，请求不传 status。重新添加不恢复被清除的业务值；恢复布局默认不能暗中复活旧状态值。清空状态的现有交互应与移除状态保持同一无条件语义。

另一个可选做法是把状态认定必显队列条件，但这会缩减用户可隐藏字段的范围，需要在最终方案明示，不应由实施者临时决定。

### 必须补入的验证

1. 默认字段可见：首次进入真实显示默认状态且请求同值。
2. 选择非默认状态并提交，再从设置移除状态：请求不再携带默认或旧 status，其他已提交条件保留，第1页展示。
3. 收起／展开：仍保留状态条件；重新添加：不恢复移除前状态。
4. 隐藏后刷新／换浏览器：账号偏好先就绪，默认初始化不能再次注入 status。
5. 其它未提交员工、月份或关键字草稿不因移除状态而提前提交。

## 一致性项 C2：提成方案计提口径不是有效后端筛选

- 当前 `CommissionRulesDrawer.tsx:294` 的 calculationBasis 列未设置 search:false，因此官方 ProTable 会呈现筛选控件，但 `:465` 的请求只传 name→keyword、personnelRole、enabled、organizationId 和 employeeFilter。
- 简核现有契约：`server/api/finance/v1/settlement.proto:1115` 的 ListCommissionRulesRequest 只有 page/page_size/keyword/personnel_role/enabled/organization_id/employee_id，**没有 calculation_basis**。`server/internal/service/settlement_commission.go:161` 也没有对应领域过滤。
- 本期不新增业务筛选能力，建议把 calculationBasis 表格列明确 search:false，保留展示和编辑；筛选设置仅声明真实可用的名称、适用角色、状态和员工。不能在当前页本地筛选替代服务端完整过滤，也不能只是把无效控件默认隐藏但仍允许用户加回。
- 此项属于盘点时发现的现存无效 UI，处理方式需在最终方案明确。定向验证确认有效字段正常请求、计提口径不再显示无效搜索项，表格列与表单计提口径仍可正常展示／编辑。

## 已明确且实施时不可退化的约束

- **隐藏值复活**：父方案已写偏好就绪后初始化 queryState/form，且隐藏同步 store、committed、chip 和 sanitize。实施中还须测 `resetFields` 原始 initialValues 复活隐藏值、重新添加字段恢复初始值、远端读取迟到三条路径。布局子任务“字段重新显示不复活业务值”可作为直接判定依据。
- **查询与选择分离**：台账筛选变化清当前批量选择；核销／建账／发票／增费候选搜索保留已选业务实体。不能在公共组件内全局清 selectedRowKeys。
- **纯展示变化**：拖拽、宽度、收起数量不改业务查询、不触发 reload、不清输入。隐藏只有被移除项已生效时才需查询刷新，不能借设置变化提交其他草稿。
- **必要视图项**：F12／F22 仍需可达设置入口、允许的宽度与默认恢复；必显表示不能隐藏，不表示整个区域从覆盖矩阵删除。具体币种、成员关系选中视图值不进入展示配置。
- **原生搜索与表头分离**：布局子任务 design.md:11 已明确表格列显隐不连带控制搜索字段；ProTable 适配必须读取完整搜索声明，不能直接使用被 useColumnSettings 剔除后的列作为搜索真相。
- **全隐藏状态**：所有可选项都隐藏时，查询、重置和设置入口仍须可达；单字段区特别容易因为外层条件渲染连齿轮一起消失。父计划已有可达性验收，建议组件定向验证增加该状态。

## 主会话收敛结果

C1 已在父 PRD／design 和全站接入设计明确采用可见字段显式初始／重置查询值；恢复默认布局不恢复业务条件。C2 已明确移除无效计提口径搜索，保留列展示与表单编辑。全部可选项隐藏后的入口可达性也补入公共布局设计。两项规划缺口已收敛，后续仍需实施与定向验证，不能把本记录当产品修复已经完成。
