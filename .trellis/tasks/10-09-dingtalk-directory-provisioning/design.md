# 钉钉人员同步与待分配管理：技术设计

状态：2026-10-09 用户已明确批准最新整体方案，进入实施。产品依据为 PRD，D1/D2/D3 已逐项确认；本文把其余实现选择限定在当前需求和既有行为内。

## 1. 边界与复用

- 钉钉通讯录维护人员基础资料；本系统维护账号开通、组织成员关系、角色和默认工作台。
- 继续使用 User → Membership → RoleAssignment，不建设独立员工主档或通用身份源平台。
- 继续使用现有钉钉应用 token、身份校验、角色工作台解析、提权校验、事务封装和后台任务调度。
- 新同步、全局待分配和开通仅在系统管理工作台提供；公司管理员沿用原有组织范围。系统工作台权限不因此获得公司业务读取能力。
- 本地账号和企业微信现有入口不扩大改造；新增手工账号绑定/跨身份合并无本期现实用例，明确不纳入。已有钉钉身份按唯一标识复用用户 ID，不按姓名或手机号合并。

## 2. 人员模型与状态

在 User 增加布尔 `pending_assignment`，默认 false；它只表示等待首次分配或迁移后的待开通，不替代现有 enabled，也不引入完整人事状态机。

| 状态依据 | 含义与行为 |
| --- | --- |
| pending_assignment=true、enabled=false | 待分配；没有启用成员关系/角色，不可建立业务会话 |
| pending_assignment=false、enabled=true | 已开通；实际登录仍须有有效组织成员关系，不能因 enabled 绕过工作台校验 |
| pending_assignment=false、enabled=false | 按现有停用/离职和其他身份待授权规则展示；不会被同步改回待分配或启用 |

Schema 声明 `pending_assignment` 为 true 时 enabled 必须为 false 的同源 CHECK；无启用成员关系的跨表不变量由所有成员写入口共同保证。系统停止自动把无组织人员推断成离职，先判断待分配，再沿用已有用户状态投影。企业微信待授权仍按其现有流程识别。

来源资料继续使用现有 display_name、email、avatar_url、dingtalk_unionid、dingtalk_userid；新增钉钉工号、手机号、来源部门快照和最后成功同步时间。来源部门快照是有类型的部门 ID/名称列表，不生成本系统 Organization。现有 dingtalk_name 展示字段由同一个同步写入口与 display_name 保持同源，不做双源回退。

用户 ID 保持稳定，订单责任人、费用、提成、审计引用不重建。手机号仅为可选资料，DTO 展示脱敏，不作为开通或身份匹配条件。无授权的可选资料不阻塞身份/姓名/部门的核心同步，但必须在结果中明示可用字段；未授权字段不展示未经本次授权确认的旧敏感值。已授权字段的空值与接口不完整响应分开处理，接口异常不能冒充清空资料。

## 3. 手动同步

### 调用与执行

业务入口为“开始同步、查询同步状态/结果”。采用专用后台任务种类 `DINGTALK_DIRECTORY_SYNC`，沿用现有任务表的入队、领取、租约、完成与失败。现有 INTEGRATION 类型被限制在经营公司工作台，不借用该类型绕过权限。

新增一张与 BackgroundTask 一对一的 DingTalkDirectorySync 业务明细表，保存企业标识、操作者、范围检查摘要、去重人数、新增/更新/未变化/失败数量、完成时间和脱敏失败明细。调度表不存业务 JSON。失败明细仅含定位所需的用户/部门标识和稳定原因码，不保存完整接口响应或 token；API 按公共分页上限输出明细。

同一企业只允许一项未结束的同步。创建与完成均通过统一事务更新任务和业务记录，业务记录维护活动标记并通过数据库唯一约束防止并发创建；不得仅靠前端按钮或进程内锁防重。业务记录与调度状态的原子一致性需覆盖崩溃/租约过期测试，包括 Claim 超过重试次数转 DEAD_LETTER 时清理活动标记、明确人工重试时重新竞争唯一活动资格，避免任务已经终止却永久阻塞下一次同步。

首期执行期限严格短于租约，不实现新的通用续租平台；逾期明确失败。每次手动同步采用有界执行，人员逐个写入且不持有跨外部请求的长事务。再次执行重新遍历，基于身份幂等更新；统计属于当前执行，不将前一次的累计计数重复加到结果中。应用重启后由现有租约机制接管，旧 lease 不能继续提交人员数据或完成结果。部分失败明确显示，不伪装为全员成功。

### 获取与匹配

1. 使用当前企业应用凭据核验通讯录范围；页面标明范围不足，不能将部分授权说成全员。
2. 服务端遍历部门及部门人员分页，按本企业 userId 去重，合并其来源部门。
3. 核验企业 userId 与 unionId。二者命中不同本地用户或与已绑定身份冲突时，本条失败并报告，不自动改绑。
4. 已绑定身份命中时保留原用户 ID，只更新 D2 允许的资料；新身份创建禁用、待分配、无成员关系的用户。
5. 原账号停用/离职、角色和默认组织不会被同步修改。某人本次未返回不引发删除、离职或清空身份。

现有企业 token 缓存可复用，新的部门/人员网关接口由 biz 声明，HTTP/JSON 留在 data。正式实施先核对钉钉当前接口文档及实际权限；公开文档只能证明能力存在，不能证明本企业已开全员范围。此项属于实施前环境核验，未获得权限时准确报告外部阻塞，不更改上述产品行为。

## 4. 查询、授权与批量结果

扩展现有 ListUsers 的状态筛选，支持待分配、已开通、离职/停用；兼顾已有组织移除视角。系统工作台的待分配查询直接从 User 起查，不要求 Membership；公司工作台保持组织范围谓词，不能读取全局待分配池。无组织用户 DTO 的组织锚点为空，不伪造 system 组织 ID。

复用 `system.user.authorize_dingtalk` 表达钉钉人员开通，新增独立通讯录同步权限，登记到 Manifest 并投影为系统管理专属。同步结果读取同样检查权限。旧 invitation.manage 删除；角色权限迁移与权限目录同步一起验证。

提供单人与批量“分配并开通”契约，载荷只接收用户 ID、目标组织与角色 ID，不再接收 displayName/email。目标可为有效公司或其部门/团队，角色必须来自对应公司工作台，至少一个角色；不允许将普通员工通过该入口开通为 system 管理员。首次成员关系作为 primary，默认工作台映射到所属公司。

批量上限复用项目公共最大批次/分页常量 200。入参用户 ID 去重，响应逐人包含 userId、success、稳定原因码和中文信息。整体请求格式/操作者权限不合法时整体拒绝；合法批次中单人的状态或目标授权冲突按 D3 返回条目失败。每个成功条目提交后才能报告成功，断网时通过重新查询状态确认，不能因缺少响应就覆盖已经提交的授权。

### 事务与并发

开通属于一次性状态流转，使用 `ForUpdate + 状态复核`，不为此把整个用户域扩展为 version 编辑体系。多人编辑既有成员资料的行为不扩大重构。

每人的事务通过 WithTx 或共享 Transactor 建立：锁定用户 → 复核仍待分配 → 在事务内确认目标组织、所属工作台、角色和操作者授权 → 创建成员关系、角色、primary → 清除 pending_assignment 并启用 → 写审计。必要关联读取使用共享锁；多行同类锁按主键排序。两个管理员同时开通时先提交者成功，后者得到 409，不能清空或替换成功者的成员关系。

批量外层不包一个共享事务，每人独立事务；失败后保留已成功人员。组织/角色停用与提权校验不能只在锁外预检，必须在写入事务内复核。仓储辅助方法通过 tx 客户端或 txCtx 参与事务，禁止闭包里拿普通 ctx 落到连接池。

普通 CreateUserMembership、UpdateUser、密码设置等入口复核待分配约束，不能通过其他入口提前建立成员关系或放开登录。已有钉钉 USER_AUTHORIZED 通知可继续在成功事务内入队；通知派发失败不回滚已完成的开通，按已有通知机制报告。

## 5. 登录与资料写入

- 保留现有钉钉 OAuth/state/企业身份校验；先解析用户身份及开通状态，再解析业务工作台凭证。
- 未同步：返回明确的“请联系管理员同步开通”；待分配：返回“尚未分配组织”。二者不创建用户、注册申请或业务会话。
- 已开通：复用有效成员关系、默认工作台和现有会话生成；组织停用仍拒绝，不能自动回到 system。
- 离职/停用：继续禁止登录。人工重新开通复用同一用户 ID，经明确操作重新分配有效组织/角色并审计，不由同步或扫码自动复职；沿用现有返聘需求而移除自助申请前置。
- OAuth 的昵称/头像不再更新通讯录基础资料；后台接口对钉钉资料修改显式拒绝，前端只读。业务角色编辑通过成员关系维护，不把基础资料只读误扩展成所有管理动作不可用。
- 本地管理员和企业微信资料维护走现有权限；共享代码需避免因钉钉分支收敛而退化。

## 6. 旧流程与迁移

撤除邀请创建/查询/撤销、公开邀请信息、注册确认、待审批列表、批准/驳回/转派的业务接口、前端入口、专属 token 配置与通知生产路径。Auth 返回结构、错误目录、权限键及 OpenAPI 客户端一次性生成更新。钉钉订单解锁审批、消息机器人和普通开通通知保留。

新增正式 SQL 迁移：增加新字段/同步明细表及约束；按现有待审批谓词识别候选，并进一步排除 bootstrap、已启用账号、有实际角色或存在其他有效业务归属的用户。仅可确认属于旧注册占位的成员关系允许移除，人员身份、历史业务和审计保留。迁移前后核对数量及 ID。分类不唯一时报告冲突并停止相应迁移，不将所有 system 成员批量转走。

原本已开通或离职的钉钉账号保持状态，pending_assignment=false；本地/企业微信账号不因迁移进入待分配。旧待审批人员转入 pending_assignment=true，待下一次成功同步补全来源资料后再分配。来源身份不完整时明确失败，不伪造标识。

旧邀请记录和已发送通知可作为静态历史保留，停止所有业务写入和开通消费；这不构成旧接口兼容。未发送的旧注册/邀请专属通知通过迁移标记为不可重试的历史任务，原因写“入职流程已替换”，避免上线后继续推送失效入口；不动其他通知/审批任务。为保留历史而存在的 Schema 枚举与约束应明确说明，只用于既有记录读取。旧邀请数据物理清理不纳入本期，避免把功能撤除扩大为数据清空。

## 7. 前端实现

- 继续使用现有 PageContainer/用户管理容器，消除邀请/注册审批子页签，以待分配、已开通、离职/停用为主。
- ProTable request 管理列表与筛选，actionRef.reload 刷新；同步任务状态由 React Query 查询，只在任务运行时轮询，结束停止。
- 同步/分配权限复用生成权限键与 access，不复制规则。手机号脱敏、时间用 formatDate；技术 ID 放详情，不挤占主表格。
- ModalForm.onFinish 返回 Promise；部分失败时展示逐人结果并仅保留失败选择，不把整个批次提示为失败或全部成功。分页/筛选切换时不带入不可见的旧选择。
- 移除旧回调页面的确认注册、自选组织、邀请 token 消费；展示未同步/待分配状态及返回登录操作。

## 8. 发布与验证

先在隔离 PostgreSQL 上执行正式迁移链，覆盖旧待审批、真实管理员、已开通、离职、企业微信五类夹具；不依赖 Schema.Create。验证未修改用户 ID、业务外键、实际授权与业务审批。

最终运行定向测试、真实 PostgreSQL 事务/并发/迁移测试、权限生成一致性和 `pnpm run check:fast`；回调路由在开发代理及生产同域各验收一次，相关构建变更再运行构建。检查记录区分 PASS、SKIP 和本企业接口未实测。

发布前备份并审阅迁移。代码与新契约同批发布，不用旧接口回退维持双轨；失败时先停止同步/开通入口，按已审阅的迁移影响选择修复发布，数据库回退须依备份与明确操作授权，不自动重置环境。
