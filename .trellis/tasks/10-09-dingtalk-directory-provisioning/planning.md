# 钉钉人员同步与待分配管理：方案建议

本文是产品与实施方向草案。用户已确认统一钉钉员工开通入口（见 PRD 的 D1）；其余未标明确认的建议仍待收敛，尚未批准最终方案或实施。

## 1. 推荐的业务流程

```text
钉钉企业通讯录
    ↓ 系统管理员点击“同步人员”
待分配人员（身份已确认，无组织、无角色）
    ↓ 选择公司/部门 + 角色，点击“分配并开通”
已开通人员
    ↓ 钉钉扫码
进入默认公司工作台，按角色使用业务
```

钉钉提供人员身份和来源资料，本系统管理员决定业务组织与角色。钉钉部门作为分配参考展示，例如“钉钉部门：华东销售部”，系统归属单独显示“上海公司 / 海运销售组”。钉钉调岗不自动修改本系统业务授权。

### 人员状态与动作

| 状态/情形 | 用户管理展示 | 扫码结果 | 管理员动作 |
| --- | --- | --- | --- |
| 首次同步且未开通 | 待分配，所属组织为空 | 尚未分配组织，请联系管理员 | 单人或批量分配并开通 |
| 已分配有效组织、角色且启用 | 已开通，显示组织与角色 | 进入默认工作台 | 调整组织、兼职和角色 |
| 已办理离职/停用 | 单独列表，并保留真实状态标签 | 明确不可登录 | 查看历史；复职需明确人工操作 |
| 从某一组织移除，但仍在其他组织 | 在对应组织视角标记已移除 | 只能进入剩余有效工作台 | 按现有组织范围维护 |
| 钉钉成员尚未同步 | 不自动授予组织或角色 | 推荐提示联系管理员同步开通 | 管理员同步后分配 |

“待分配”是本系统开通状态，不等同于钉钉在职状态；不得用一次通讯录查询是否返回此人来决定离职。已开通人员因组织被停用而失去可用工作台时，也不能重新解释成从未开通的人员。

## 2. 管理页面

继续使用现有用户管理入口与公共页面骨架，将“注册审批 / 邀请”旧入口撤除（D1），建议以人员状态作为新的主要工作区。

```text
用户管理                           [同步钉钉人员]
最近同步：本地时间   新增 n 人 / 更新 n 人 / 失败 n 人

[待分配 n] [已开通] [离职/停用]
姓名/工号搜索      钉钉来源部门筛选      系统组织筛选

□ 姓名  钉钉来源部门  工号  系统组织  角色  状态  操作
□ 张三  海运事业部    001   未分配    —     待分配  [分配并开通]

选中 n 人                                  [批量分配并开通]
```

- “待分配”默认展示当前需要管理员处理的人员；“已开通”用于日常账号维护。组织管理员不显示全员待分配入口。
- 搜索和筛选走服务端分页，复用公共上限 200。姓名检索覆盖中文全拼与首字母；组织/角色选择器服务端过滤，不循环拼接全量分页。
- 列表主信息以姓名、来源部门、系统归属和角色为主，钉钉技术 ID 放到详情中；手机号仅在确需展示且有权限时脱敏。
- 来源部门允许一人多个；多部门不产生多条人员记录。
- 分配表单先选目标公司及可选部门，再加载该公司角色库，展示最终公司、组织与角色确认信息。部门/团队沿用所属公司角色，不创建独立角色库。
- 首期批量只对多个人设置相同目标组织和角色；复杂兼职通过已有单人组织成员维护完成。
- 建议批量逐人返回结果，已成功人员从待分配列表移出，失败人员保留并说明原因。该业务口径确认后才确定接口与事务划分。
- 同步时显示进行中状态并防止重复发起；结果区提供错误摘要，避免管理员只看到“完成”却不知道漏了人员。

## 3. 最小实现方向

### 复用现有模型

优先复用 User、Membership、RoleAssignment，不额外建设另一套独立员工主档。待分配用户不建 Membership；业务开通后建立现有组织/角色关系。必须给待分配与离职提供可可靠区分的状态依据，不能继续单凭 enabled=false 和缺少有效成员关系推断离职。

最终状态字段、来源资料存储、正式迁移方式，以及共享事务/锁/版本范围，在需求确认后写入 design.md 审阅。本轮不确定字段名或直接生成 Schema。

### 同步流程

1. 核验当前钉钉企业、应用通讯录读取权限与范围，只记录范围摘要，不记录凭据或原始通讯录响应。
2. 由服务端遍历授权部门、分页读取部门人员，对多部门人员按企业内身份去重。
3. 将企业 UserID 与登录使用的 UnionID 对齐；已有身份命中时复用用户 ID，来源资料按确定的字段所有权更新。
4. 新人员创建为待分配；重复任务或重试不得重复建人、重复建成员关系或改变授权。
5. 显示新增、更新、未变化、失败数量；部分失败与全部成功明确区分。缺少字段按必需/可选契约处理，不凭空补值。

优先复用现有后台任务执行与结果查询能力承载批量同步，核验任务租约、重试和管理范围后决定最薄扩展。同步任务可归系统管理上下文，但不因此把同步出来的人员加入系统管理组织。任务执行外部 API 调用时不持有长数据库事务。

### 分配与登录

- 在真正写入前校验操作者管理范围、目标组织可用性、角色所属公司与提权限制。
- 一个人的状态更新、成员关系、默认组织、角色分配及审计作为同一业务原子操作；遇到并发开通需明确冲突，不能覆盖对方配置。
- 待分配身份应在解析业务工作台凭证之前识别并返回明确状态，否则现有逻辑会先报“无权访问组织”。不为提示页面签发业务会话。
- 已开通人员继续通过现有有效成员关系解析默认工作台，角色与组织权限继续由当前授权体系计算。
- 保留本地管理员登录能力。现有未绑定钉钉的普通账号是否需要管理员人工绑定，须按实际人员使用情况决定；不按姓名或手机号偷偷合并账号。
- 离职、角色调整和成员移除继续覆盖原有会话撤销及工作台权限重算要求。

## 4. 现有邀请与注册审批：已确认统一替换

用户已明确同意钉钉员工只保留一条开通链路：同步 → 管理员分配。撤除定向手机号邀请、通用邀请二维码、自助选择组织、注册审批与转派这些入职入口，扫码页面用于登录及展示开通状态。

新员工必须先由管理员同步和分配；未同步人员扫码时提示联系管理员同步开通，不自动建立注册申请，也不保留扫码登记的额外开通分支。

实施时需要一次性检查删除或修改的范围：前端页签与回调页面、Auth/Admin Proto、服务与用例、邀请 token/通知逻辑、相关权限、开发数据和旧规范。已发布的旧邀请链接不再开通用户或提交申请，员工通过统一登录入口获得明确的当前状态；不为旧接口保留自动回退。订单解锁等业务审批继续独立运行。

现有待审批人员的迁移和旧邀请数据的存储清理分别审阅：前者建议转入待分配并保留身份，后者须在技术设计中列明迁移对象，不因撤除功能而擅自清空用户或业务数据。

已有已开通人员保持用户 ID 与历史业务引用。可明确识别的待审批账号建议通过正式迁移改为待分配，移除仅为旧注册收口建立的成员关系；不能按“在系统管理组织里”粗暴批量移除，真实管理员及其他身份流程必须排除。身份异常、来源不明的数据先报告，不重置数据库，不静默修复。

## 5. 建议实施阶段

| 阶段 | 交付内容 | 通过条件 |
| --- | --- | --- |
| A：需求与接口核验 | 确认开通入口、管理责任、字段与批量口径；核验钉钉全员权限和必要字段 | 产品待定项收敛，已知当前应用是否具备目标范围权限 |
| B：基础契约与状态 | 明确状态、无组织人员可见性、来源资料、迁移与 API；生成服务端/前端契约 | 待分配与离职可区分，组织范围与身份唯一性不被绕过 |
| C：同步与开通后端 | 部门/人员同步、身份匹配、任务结果、单人/批量开通、登录提示 | 重复同步、失败重试、并发开通、越权和登录核心场景通过 |
| D：管理界面与旧流程收敛 | 人员状态列表、同步摘要、分配表单、批量结果；按决定移除旧入口 | 管理员可完成完整开通操作，员工扫码可进入正确工作台 |
| E：全链路验收 | 正式迁移回归、权限、角色、离职/会话、生产同域登录回调、规范更新 | 受影响定向测试、真实 PostgreSQL 集成与全栈门禁通过 |

建议先作为一个完整业务任务管理，按以上阶段提交可验证变更。单独上线“只同步但无法分配”的半成品没有业务价值；确需多会话拆分时再建有明确依赖的子任务。

## 6. 验证重点

- 钉钉接口：多级部门、跨部门重复人员、游标分页、授权不全、超时、部分失败、错误不泄露 token。
- 身份：同步前已有账号、同步后首次扫码、同名不同人、UserID/UnionID 冲突、离职账号再次同步。
- 权限：系统管理员、公司管理员、普通用户分别访问同步/待分配/开通接口；跨公司目标和越权角色拒绝。
- 原子性：单人开通任一步失败不留部分授权；两名管理员同时开通不会覆盖；批量结果与数据库一致。
- 登录：未同步、待分配、已开通、离职、组织停用、默认组织和多组织切换。
- 迁移：真实待审批人员与真实系统管理员区分；既有业务外键、成员历史及审计不丢失。
- 前端：ProTable request/actionRef、ModalForm Promise 提交、失败结果和重试、按钮权限、来源/系统组织区分。
- 开发过程先运行定向 Go/Vitest 和修改文件检查；最终由于涉及身份、权限、契约与迁移，运行 `pnpm run check:fast`，并用正式 SQL 迁移进行真实 PostgreSQL 集成验证、确认没有静默 SKIP。涉及生产入口或回调构建配置时再增加构建验收。

## 7. 后续能力

定时同步、入离职事件回调、明确离职事件后的自动停用、按钉钉部门推荐组织，均在手动同步开通流程稳定并有真实需求后独立规划。首期同步缺失仅是同步结果，不能演变成自动删除或停用。
