# 费用审批异常闭环审查与修复

## 目标与授权

用户要求核对五条业务审查意见，确认有问题后创建 Trellis 修复任务。本轮完成代码核查与任务登记；未授权跳过规划评审直接实施。维持「业务录费 → 有权限的人批准 → 财务建账」主流程，补齐金额判断、状态准入和纠错出口。单人持有审核权限不是本任务缺陷。

## 审查依据与结论

基线为本地 main `39235097da72e177caac692d16b51480403d25d6`。远程 SSH 22 端口连接失败，未确认远端最新版本；本轮为静态审查，未做数据库复现。逐项证据及限定见 [审查记录](research/review.md)，不得将算例或代码推导写成实测结果。

| 编号 | 性质及优先级 | 结论 | 归属 |
| --- | --- | --- | --- |
| R1 | 正确性缺陷，P1 | 订单行金额减整账单结清金额，可在部分收款恰好等于单票金额时误锁；跨币种汇总也不成立 | 自动锁单子任务 |
| R2 | 更正流程缺口，P1 | 正数应付补录无法覆盖应收追加、调减及结算对象错录；普通修改被审批/账单保护 | 更正子任务 |
| R3 | 更正流程缺口，P1 | 补录产生系统冲减后不能撤销；已有手工提成增减，但不能同步纠正费用及来源关系 | 更正子任务，与 R2 合并 |
| R4 | 状态准入缺口，P1 | 结案未检查待审补录；补录入口也没有 CLOSED 校验，单补结案检查不足以完整限定后续利润变化 | 结案子任务 |
| R5 | 已明确不实施 | 用户决定继续依靠人为判断费用完整性，保留现有确认与人工审核，不增加清单或估算流程 | 本任务范围外 |

R1 的「全额结清仍不自动锁」是现有代码及测试明确选择的保守策略，应与误锁漏洞区分。可讨论改善漏锁策略，不得悄悄改成订单级人工分摊。R2/R3 的受控限制本身合理，不能通过解除保护实现纠错。

## 子任务及顺序

1. [自动锁单结清判断](../10-13-auto-lock-settlement/prd.md)：先修最直接的财务事实误判。
2. [待审补录与结案门禁](../10-13-closure-pending-supplement/prd.md)：可独立交付，须先明确结案语义。
3. [费用与提成联动更正](../10-13-fee-commission-correction/prd.md)：R2/R3 共用一套审批、更正和审计事实，避免做成两个不一致的修补入口。

总任务负责需求映射、跨子任务一致性与最终验收，不直接作为产品实现目标。子任务可单独规划、实现、验收和提交；更正上线时必须重验自动锁单与结案条件，不得假定任务树自动表达依赖。

## 跨任务验收

- AC1：部分合并账单款项不被重复或错误归属订单；不同币种不相抵；有效核销/对冲、反转和取消口径一致。
- AC2：待审批费用变动与结案规则一致，并发不能绕过；前端展示阻断原因与后端一致。
- AC3：已批准费用更正须受控审批；原费用、账单、核销及提成历史可追溯，不以直接改写历史或普通解锁绕过。
- AC4：补录 1,000 元实际应为 100 元时，费用、利润及提成有一致且不重复执行的更正结果。
- AC5：普通审核、分次建账、共享主单整组锁定、反核销/反对冲与提成发放相邻路径保持正确。
- AC6：实现后按风险补测试；真实 PostgreSQL 用正式迁移验证，SKIP 不计通过；最终执行 `pnpm run check:fast`，涉及生成物须重新生成并同组提交。

## 不在当前确认范围

不新增第二把锁、多级审批或复杂治理平台；不自动重置数据库；不新增兼容分支；不把结案直接定义为收付全部完成；不承诺系统凭空识别遗漏费用。用户已明确第五条依靠人为判断：保留现有完整性确认和人工审批，不新增结构化清单、待回成本登记、估算成本流程或自动漏费检测，也不将其作为修复验收前提。

## 待决策

1. 最高优先：结案是否采用「业务完成但允许后续收付款；费用补录或更正必须先反结案」？推荐如此，另一选择是允许结案后受控更正但明确利润仍可变。此项决定 R4 的双向门禁及 R2/R3 准入。
2. 自动锁单是否接受逐张关联应收账单全额结清的保守判定，或确实需要合并账单未结清时认定某票先结清？推荐前者，后者需要新的金额分配业务契约。
3. 更正的首期账务范围，见更正子任务；R5 已排除，不再作为待决策项。
