# 财务全链路测试覆盖审计设计

## 审计目标

以可复核证据判断当前测试对以下链路的保证程度：

```text
汇率配置/解析
  → 订单录入与订单费用
    → 财务账单与开票
      → 收付款资金流水与核销
        → 提成预览、生成、调整与支付
```

审计对象是测试证据，不是功能清单。实现存在、页面可访问或某个包测试通过，均不能
单独证明完整业务链正确。

## 证据等级

| 等级 | 证据类型 | 可以证明 | 不能证明 |
|---|---|---|---|
| E1 | 纯函数/领域单元测试 | 单条规则、精度、状态机输入输出 | 数据库约束、事务、路由、页面 |
| E2 | 仓储 SQL/mock 测试 | 查询谓词、排序、错误映射、锁 SQL 形态 | 真实 PostgreSQL 行为和跨模块链路 |
| E3 | 真实 PostgreSQL 集成测试 | 真实约束、事务回滚、锁与并发、持久化快照 | HTTP 权限、前端、未进入夹具的上游创建流程 |
| E4 | 真实 HTTP/API 验收脚本 | 路由、鉴权、DTO、用例、仓储和数据库的组合行为 | 浏览器交互、未被脚本断言的内部不变量 |
| E5 | Playwright 浏览器验收 | 用户可见页面和真实 API 交互 | 未覆盖的业务组合、生产并发与运维风险 |

只有一条测试使用同一业务标识和真实生产入口顺序贯穿相邻阶段时，才记为跨阶段链路
证据。下游测试直接插入上游表数据时，记为该下游模块的真实数据库证据，不记为上游
到下游的端到端证据。

## 审计矩阵

### 业务阶段

1. 汇率：币对方向、本位币、业务日期、汇率类型、继承/专用配置、手工覆盖、八位精度。
2. 订单：创建、费用应收/应付、税额、币种快照、确认、幂等、版本冲突。
3. 账单/开票：费用占用、聚合、账单汇率快照、批次幂等、确认、发票状态。
4. 收付款/核销：资金汇率快照、分摊、汇兑损益、余额、冲销、方向隔离、并发。
5. 提成：来源订单/费用/核销、归属、利润、规则、CNY 快照、调整、确认/支付、审计。

### 横向风险

- 金额、税额、币种和汇率方向/日期；
- 数据库事务、回滚、幂等、锁顺序和并发；
- 组织数据隔离、权限和审计；
- API 契约与错误传播；
- 前端输入、显示、筛选、导出和浏览器交互；
- 测试运行环境、夹具隔离、清理及是否进入日常/CI 质量门。

## 证据来源

- `server/**/*_test.go`：领域、仓储、真实 PostgreSQL 和服务层测试。
- `web/**/*.test.*`、`web/tests/e2e/**`：组件、页面和浏览器测试。
- `scripts/acceptance-*.mjs`、根 `package.json`：真实 API 验收路径及组合命令。
- `.trellis/tasks/archive/**`、Git 历史和开发日志：测试最后执行记录与历史独立检查。
- 质量门命令定义：确认哪些测试默认运行、哪些需要专用环境而默认跳过。

## 输出结构

任务报告 `research/audit-report.md` 必须包含：

1. 一句话上线判断和置信边界；
2. 业务阶段 × 证据等级矩阵；
3. 已存在的跨阶段链路及其真实起止点；
4. 当前能证明的事项；
5. 当前不能证明的事项；
6. P0/P1/P2 风险或测试缺口，严格区分缺陷与缺证；
7. 上线前最低补测路线图和每项完成定义；
8. 文件、测试名、命令或提交记录锚点。

## 复核原则

- 独立检查者必须逐项挑战 E4/E5 和“完整链路”结论。
- 任一“完整覆盖”主张必须能说明：起点如何创建、阶段间如何传递同一业务 ID、最终
  如何验证提成结果，以及是否使用真实 PostgreSQL、HTTP 和浏览器。
- 测试默认因缺少环境变量而跳过时，必须记录为“测试存在但默认质量门未执行”；只有
  有真实运行记录时才可记为最近已通过。
- 不因为全量 `go test ./...` 通过就把需专用环境的 PostgreSQL 测试视为已执行。

## 兼容与回滚

本任务只新增审计文档，不修改产品。若审计发现生产缺陷，只记录证据、影响和建议，
不在本任务中修复。报告不改变运行时行为，因此不需要数据迁移或产品回滚。
