# 审计订单到提成财务全链路测试覆盖

## Goal

审计多币种汇率、订单录入、财务账单、收付款核销与提成链路的现有测试证据、覆盖边界
和上线风险。

本任务不以“所有测试通过”代替风险判断，而是回答现有自动化测试能够证明什么、不能
证明什么，以及距离可声明核心财务链路具备上线信心还缺哪些验证。

## Confirmed Scope

- 多币种汇率配置、解析、日期口径和本位币/CNY 折算。
- 订单录入、订单费用、订单状态及提成归属等财务来源数据。
- 应收/应付账单的创建、明细、状态流转与订单费用关联。
- 收付款资金流水、核销单、核销分摊及其对账单和订单数据的影响。
- 提成预览、生成、CNY 快照、调整、确认/支付、导出和审计。
- 跨模块完整链路，而不只统计各包单元测试数量。

## Requirements

1. 建立“业务阶段 × 测试层级 × 风险维度”的证据矩阵，区分纯函数/单元测试、仓储
   SQL 测试、真实 PostgreSQL 集成测试、HTTP/权限测试、前端组件测试和浏览器 E2E。
2. 每项“已覆盖”结论必须能追溯到测试文件、测试名称或历史质量门，不得依据实现
   文件存在、测试数量或口头完成报告推断。
3. 检查数据是否真正跨越汇率、订单费用、账单、资金流水/核销和提成，而不是多个
   相互独立的模块测试被误称为端到端测试。
4. 重点审计金额精度、币种方向、汇率日期、状态机、事务回滚、锁顺序、组织隔离、
   权限、审计、重复请求/幂等、并发和失败恢复。
5. 对缺口按风险分级，明确区分“已发现生产缺陷”“缺少测试证据”和“自动化测试
   本身无法证明的生产风险”，禁止把缺少证据直接描述为已有缺陷。
6. 给出是否具备上线信心的分层结论，并提供最小补测清单、建议顺序和每项完成定义。
7. 本任务只读审计代码、测试、配置、历史任务和提交证据；未经新的实施批准，不修改
   业务代码或新增测试。

## Acceptance Criteria

- [ ] 形成覆盖汇率、订单、账单、资金流水/核销和提成五个阶段的证据矩阵，每条结论
      都有可核查的文件或测试锚点。
- [ ] 明确回答是否存在一条覆盖完整业务链的自动化端到端测试，以及它运行在 mock、
      SQLite、真实 PostgreSQL 还是浏览器环境。
- [ ] 明确列出金额/币种/日期、事务、并发、权限/组织隔离、审计和用户界面的已覆盖项
      与缺口。
- [ ] 对所有高风险结论进行第二轮独立复核，消除把单层测试误报为全链路保证的情况。
- [ ] 输出“当前能证明”“当前不能证明”“上线前最低补测”三部分结论，并对上线信心
      给出有条件或不建议的明确判断。
- [ ] 审计报告不使用“完全没有问题”“100% 正确”等自动化测试无法支持的绝对表述。

## Out of Scope

- 本轮不修改生产业务逻辑、数据库结构、接口、前端页面或部署配置。
- 本轮不新增、改写或执行破坏性生产数据测试。
- 本轮不把性能压测、安全渗透、灾备恢复和生产监控审计伪装为功能测试覆盖；若缺失，
  只作为上线风险单列。
- 补测和缺陷修复需要用户在审计结论后另行批准。

## Deliverable

- 一份任务内审计报告，包含证据矩阵、风险分级、全链路断点和最小补测路线图。
- 面向用户的简明结论，能直接回答“当前测试是否足以证明财务全链路完全没问题”。
