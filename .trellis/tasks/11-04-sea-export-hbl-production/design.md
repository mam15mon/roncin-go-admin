# 海运出口 HBL 单证制作设计

## 1. 目标与交付边界

以一条闭环交付：订单入口 → 读取真实 HBL → 制作并保存同一 HBL → 选择草稿/正本/电放/副本 → PDF 预览、打印、下载。

前后端及 PDF 模板相互依赖，不拆成可单独验收的父子任务；实施分契约、页面、输出、验收四个阶段。用户已在最终摘要后批准实现，并要求 review 完成后合并回主分支。

## 2. 业务决策

- 制作编辑保存回原 HBL；收发通知人、货描、唛头、件重尺、条款继续使用 `SeaBillContent`，不另存打印稿。
- 四种输出由操作人员选择，均不要求利润审核锁单；打印本身不修改审核状态、HBL 状态或放单方式。
- 锁单限制资料修改，不限制读取和输出已保存内容；制作页不提供绕过审核锁的写入口。
- 模板只适用于自有签发。首期固定模板为附件中的北京公司版本；开发库只读盘点确认当前公司代码为 `BJ`（融迅北京）与 `CD`（融迅成都）。北京模板只绑定真实北京签发主体，不将成都或客户/代理主体冠以北京抬头。
- 样例 PDF 中的客户、货物、日期、联系人和 ICN 不是默认业务数据。公司抬头/Logo 与模板固定条款来自用户提供的参考；电话、邮箱、签发地日、装船日等由本票维护，不预填样例值。

## 3. 页面与入口

- 新增 `/orders/sea-export/:id/hbl`，使用现有 `canReadSEOrders` 路由权限，组织切换落点回 `/orders/sea-export`。
- 详情页提供「HBL 制作」动作，海运列表「海运单证」直接进入该制作页。直单、无有效 HBL、非适用签发主体显示明确原因和返回订单资料入口，不新建虚假 HBL、不切换模式。
- 原「导出单证 (POD)」更名为「放货凭证 (POD)」，继续使用原登记面板与权限。
- 页面用 `PageContainer`、`PageHeaderShell`、`SectionCard`、`StickyFooterBar`。全宽 12px 内容边距；分节为收发通知人、运输印字、货物与箱号、签发与补充信息。
- HBL 号码和签发主体为身份信息，只读显示；改号、改主体和模式切换留在原有单证入口。制作页可编辑正文与印字资料。
- 输出版本使用四项选择器，默认草稿；只控制本次 PDF 标识，不写入 `releaseType` 或 `billForm`。
- 「预览」打开大抽屉，展示实际 PDF；预览中提供下载和浏览器 PDF 打印入口。编辑有未保存内容时明确提示，并由保存动作将编辑写回同一 HBL 后刷新输出基线，不将未保存内容混作已保存版本。

## 4. 数据与契约

### 4.1 现有正文

复用 `SeaBillContent` 的 16 个现有字段。既有 HBL 正文优先，不用订单统计或 MBL 内容自动覆盖；首次制作展示订单来源的可带入信息，重新带入需显式操作并保护手工输入。

### 4.2 HBL 专属印字资料

新增 `SeaHouseBillPrintDetails`，挂在 `SeaHouseBill`、`SeaHouseBillInput` 和 `SeaDocumentVersion` 上，追加新的 Protobuf 字段号。它只补齐正文之外的打印资料，不复制收发通知人/货描等已存在字段。

| 字段组 | 字段 | 来源与语义 |
| --- | --- | --- |
| 页眉与参考 | `header_contact_text`、`booking_no_text`、`export_references_text`、`footer_reference_text` | 联系方式和参考号人工维护；订舱号初次取订单，不拿 MBL 号代替 |
| 前程与指示 | `pre_carriage_text`、`place_of_receipt_text`、`domestic_routing_text`、`point_of_origin_text`、`onward_routing_text` | 按本票填写，可空 |
| 海运印字 | `vessel_voyage_text`、`port_of_loading_text`、`port_of_discharge_text`、`place_of_delivery_text` | 初次取已保存订单/航程名称；可调整英文印字，不反写共享航程 |
| 箱货补充 | `containers_text` | 从本票实际箱及共享箱的本票分配显式带入，人工可调整印字；箱计划不是实际箱 |
| 签发 | `original_count`、`shipped_on_board_date`、`issue_place_text`、`issue_date`、`delivery_contact_text` | 份数可空，非负整数；日期为无时区的 `YYYY-MM-DD`，装船日与签发日独立，均不从 ETD/当天推导 |

运输条款、运费条款、国外代理和特别条款仍使用正文现有字段。全部补充字段可空，不为普通订单保存新增必填项，也不因缺少可选印字字段拒绝某种输出。

后端校验固定字段形状、长度、合法日期和份数边界；短印字最多 500 字符，说明/联系人最多 3000 字符，箱号明细最多 12000 字符，份数范围 0～99。字段限制在 biz 定义并由前端复用对应契约，不接受任意动态键或 HTML。

### 4.3 持久化

- 在 `SeaHouseBill` 和 `SeaHouseBillVersion` 的 Ent Schema 增加可空 `print_details` JSONB，历史版本字段为 Immutable；不新建单证实体或独立打印草稿表。
- JSONB 使用 data 层的固定 PO 结构；biz 为独立纯 Go 结构，service 与 proto 逐字段转换。复用主数据固定 JSONB PO 的已有范式，不把 proto 或 Ent 类型带入 biz。
- 修改 Ent Schema 后生成绑定代码及正式 SQL 迁移，审阅迁移仅增加目标字段，不重置数据库、不开运行期建表、不改写已有历史数据。
- 空 `print_details` 表示尚未维护打印补充资料，不是旧版兼容分支；初次制作从当前已保存订单提供带入值，用户保存后作为本票印字保留，后续不随共享航程静默刷新。
- 已锁定且尚无补充印字的 HBL，也能使用现有已保存 HBL/订单资料形成只读输出，未填写的印字留空；不能因为首次预览初始化了表单就强迫解锁或先保存。用户实际修改后才进入未保存编辑状态。

### 4.4 同一 HBL 的所有路径

普通 `UpdateSeaHouseBill`、整单保存、创建、改单、作废、模式切换快照、拆票/改配涉及的 HBL 转换，以及前端 `sea-document-form.ts` 的表单基线/比较/载荷需同步传递新字段。

- 完整 HBL 载荷包含当前 `printDetails`；修改其他正文或只保存订单时不得清空已保存印字。
- 新字段纳入 HBL 内容哈希、改单逐字段差异、请求指纹、不可变版本写入和版本 DTO。历史只读取版本 JSON，不回读当前印字。
- 打印补充资料本身不改变批次唯一性、共享 MBL 和运输执行；拆票新票不能把原票已人工签发的日期和号码当成新票事实，沿用原票/新票明确语义，只保留适用正文。
- DTO 增加只读 `print_template`，由后端按 HBL 的真实签发主体计算，首期为 `RONCIN_BEIJING` 或空。固定模板绑定现有不可变公司代码 `BJ` 及 `SELF_ORGANIZATION`，不硬编码数据库 UUID、不做名称模糊匹配、不建立多品牌配置平台。

## 5. 请求、保存与并发

- 查询使用 React Query + 生成客户端，复用订单详情、海运单证聚合、实际箱相关读接口；实际箱带入仅在具备对应读取权限时请求，失败明确提示，不能伪造空结果或换用箱计划。
- 保存复用 `SeaDocumentService.UpdateSeaHouseBill`，携带打开/上次保存时的 HBL 版本与 Link 版本，遵循既有 `Order → MBL → Active Link → HBL` 锁序及 `WithTx`。不新设事务、版本字段或旁路保存接口。
- 事务内复验组织、归属、活动关系、锁状态与版本，原有错误原样外传；提交后普通上下文重读。成功响应经 `isWriteResponse` 验证后推进编辑基线，并失效订单/单证查询缓存。
- 同一公司下有读权限可预览/输出，编辑还需现有订单 update 权限、当前所属公司工作台及服务端允许动作；不新增打印权限清单。
- 复用现有变动检测：前台每 15 秒及切回立即检查 Order/Link/HBL 标识，后台暂停。检测到变化持续提示并保留编辑；刷新覆盖输入先确认，不能把检测到的新版本当成提交基线。
- 预览生成前刷新轻量单证基线校验，发现 HBL/Link 已变更则提示同步；PDF 生成不触发业务写入。锁定后也能输出现有数据，不引入审核门槛。
- 用户/组织/订单/HBL 切换时重新挂载，清理旧 PDF Blob 和迟到请求；失败保留输入并提供明确重试，不静默覆盖。

## 6. PDF 与打印

### 6.1 选型

使用按需加载的 `@react-pdf/renderer` 4.x，锁定经工程验证的版本；PDF 文档组件与 Ant Design 表单分离。浏览器生成 PDF，不增加服务器 Chromium、PDF 转换服务、OSS 自动归档或后台任务。

官方文档支持原生分页、固定页眉/页脚和 Web Blob 生命周期；技术验证及字体来源见 [PDF 选型研究](./research/pdf-output.md)。不选 `pdf-lib` 作为主渲染器：本轮 CJK 字体子集探针出现实际缺字，而 react-pdf 静态字体探针正常。

### 6.2 字体与品牌资产

- 同域提供静态简体中文 TTF（Noto Sans SC 常规字重），禁止运行时从外部 CDN 拉字体。字体源文件、静态化过程、校验和及 OFL 许可证随资产记录。
- 对字体不支持的特殊字符明确提示所在字段，不能用空白字形悄悄输出；输入仍保留，用户可自行调整。
- 品牌英文标题可用 PDF 标准字体，正文使用嵌入字体，确保中文和英文均可选取、打印；不将文字整页截图。
- 复用 `web/public/images/logo-mark.png`，不将含客户信息的样例 PDF 当底图，不重新生成近似 Logo。
- 公司抬头和底部固定条款属于本期模板；联系信息、业务参考和签发内容属于本票数据。底部涉及正本份数的文字须与本票填写值一致，不能固定 THREE。

### 6.3 版式与长内容

- A4 竖版，通常资料保持单页，参照样例表格分区；抬头、收发通知人、运输、箱货和签发区保持可辨。
- 文本按 PDF 引擎自动换行，保留人工换行。长货描、箱号或地址允许内容续页；续页带 HBL 号、版本标识及页码，打印/下载包含全部页。
- 不对大段正文设置不可分页的 `wrap={false}`；仅短表头/短签发块可保持整体，避免超高块被压缩或吞字。表格边框和续页标题须实际渲染验证。
- 四种输出标识为 `DRAFT`、`ORIGINAL`、`SURRENDERED / TELEX RELEASE`、`NON-NEGOTIABLE COPY`；标识不能遮盖业务文字。只做文件表现，不声称办理了电放或签章。
- 未填内容保留空格；重量/尺码遵循数量精度，金额遵循全站金额口径。日期按纯日期格式显示；下载名包含真实 HBL 号、版本和本地可读时间，不暴露原始 ISO 字符串。

### 6.4 一份 PDF，三个入口

使用 `usePDF` 管理生成实例。按已保存数据和输出版本创建不可变渲染输入，版本改变时显式更新；生成中/失败时不误用上一版本的文件。

预览 iframe、下载链接和打开打印查看器消费同一个 Blob URL。打印使用浏览器原生 PDF 查看器/打印工具栏；验证 Chrome/Edge 的整页及续页输出，禁止把网页表单本身打印成提单。切换、关闭和卸载释放 Blob URL，重新预览基于明确的当前基线生成。

## 7. 影响范围

后端：`api/order/v1/sea_document.proto`、`internal/biz/sea_document*.go`、`internal/service/sea_document*.go`、data 中 HBL 创建/更新/转换/哈希/版本路径、两份 HBL Ent Schema、正式迁移及生成物。

前端：海运路由、订单入口/页头菜单、`sea-document-form.ts`、HBL 正文表单与历史展示、新增同模块制作页/组件/Hook/PDF 文档、字体与授权文件、`web/package.json` 及 `pnpm-lock.yaml`。

不提取全站 PDF 平台，不改空运，不重写原有锁单/改单，不将前端业务内容传给第三方服务。

## 8. 验证与发布

- 实现后补定向测试，遵守禁止 TDD；验证 HBL 保存往返、普通保存不丢印字、冲突零写入、锁定可读不可写、快照不会随当前内容变化。
- 前端验证四种输出、无 HBL/外部主体/不匹配公司、错误重试、工作区切换、15 秒检查及输入保护。
- 使用中文、英文、长地址、长货描、多个箱号及四种版本实际渲染 PDF，检查文本完整性、页码、边框和打印；不能仅断言 PDF 文件存在。
- 依赖及静态资源进入生产路径，执行 `pnpm run build`；跨层契约及迁移执行 `pnpm run check:fast`，正式迁移在专用 PostgreSQL Schema 验证，不清空开发数据。
- 发布按正常生成/迁移/构建流程。本次为可空字段增量迁移；出现故障先停止入口并修复，不自动降级旧模板、不回写历史、不删除新数据。

## 9. 延后项与已知限制

- 成都及第三方签发模板、背面条款第二版模板、电子签名、自动盖章、PDF 自动归档与历史导出文件台账延后。
- 首次预览要加载 PDF 模块及约 10.6 MB 的完整静态字体；浏览器缓存复用，PDF 仅嵌入所用字形。生成规模和最终生产包体积在实现验收时量测。
- 当前输出是已保存内容的一次文件结果，不把「导出过 PDF」视为新的签发/放货事实；不新增原本不存在的审核或放单流程。
