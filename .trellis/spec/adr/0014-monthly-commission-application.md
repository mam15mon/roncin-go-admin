# ADR 0014: 月度提成申请——自然月汇总、整单审批、显式重提

- 状态：已采纳
- 日期：2026-09-19（实体、契约与工作台同日上线；审批口径在任务规划中先行明确）
- 主题：业务设计（财务域）

## 背景

提成按核销/对冲来源逐条计提（`FinanceCommission`），量大且随时间持续
产生。若员工逐条勾选申请、财务逐条审批，双方操作量都不可行；若允许
部分批准，会产生「半申请」的中间状态，账务口径难以解释。此外计提存在
迟到来源（核销晚于申请发生），需要明确归期。

## 决策

- **自然月汇总门禁**：员工按完整自然月一次性申请该月全部未申请的合格
  提成（`FinanceCommissionApplication` / `...Line` 明细快照）；月度唯一，
  不做跨月拼凑申请。
- **整单审批**：财务对申请整单批准或整单驳回，不做部分批准；批准即整批
  确认，驳回不改变提成本身状态。
- **显式重提**：驳回后由员工对原单显式发起重提（Resubmit），不自动复活、
  不允许静默改判。
- **迟到顺延**：申请提交后才满足计提条件的提成顺延到下一次申请，不回填
  已提交的本申请（见
  [../../../server/internal/data/ent/schema/finance_commission_application.go](../../../server/internal/data/ent/schema/finance_commission_application.go)
  注释与集成测试）。
- **完整候选与有界估算分离**：月度申请解析全量未申请来源（无分页上限的
  完整候选语义，是 ADR 0006 的记录在案例外）；工作台展示是有界估算——
  两条路径不得混用（见
  [../domain/architecture-map.md](../domain/architecture-map.md) 要点 5）。

## 理由

- 汇总 + 整单把「员工申请」压缩成每月一次操作，把「财务审批」压缩成
  每人每月一个决定；中间状态最少，对账口径最简单。
- 部分批准需要拆分明细的生效子集，状态机与快照复杂度陡增，收益只是
  极少数争议行——按快速交付阶段约束（[../../../AGENTS.md](../../../AGENTS.md)）
  不建此复杂度。
- 明细快照使申请在批准后不随提成后续变化漂移，审计口径固定。

## 后果

- 员工侧流程为：自然月结束 → 查看完整候选 → 提交 → （若驳回）显式重提。
- 提成冲减建议（费用补录场景）计入候选解析，申请前需员工自行确认。
- 业务定位见 [../domain/glossary.md](../domain/glossary.md)「月度提成申请」，
  实现位于
  [../../../server/internal/biz/finance_commission_application.go](../../../server/internal/biz/finance_commission_application.go)。
