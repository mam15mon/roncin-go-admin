# ADR 0006: 列表分页统一 200 上限与主数据全量/分页二分

- 状态：已采纳
- 日期：2026-08-27 统一上限；全量/分页二分策略 2026-08～09 逐步固化
- 主题：接口与主数据

## 背景

统一前各列表接口的 `pageSize` 上限各自为政（100、500 混杂），前端曾因传
超出上限的页大小触发「管理参数不合法」报错（2026-08-22 `881c8328`）。
另一面，下拉框与选择器类页面为了拿候选项要么一次性加载全量、要么前端
循环翻页拼接——大数据集（全球港口、机场数万行）全量加载放大传输、序列化
与前端内存成本，循环翻页则放大请求数。

## 决策

- 所有常规列表接口 `pageSize` 最大值统一为 **200**，默认值按接口交互需要
  设置；公共常量与校验函数复用
  [../../../server/internal/biz/pagination.go](../../../server/internal/biz/pagination.go)
  的 `MaxListPageSize` / `ListPagination`，禁止在领域层或传输层另写
  `100`、`500` 等不一致上限；新增列表接口必须验证 `page >= 1` 且
  `1 <= pageSize <= 200` 并补边界测试。
- 主数据维护页按数据量二分：
  - 小数据集（约 5000 行以内，如货币、中国行政区划）：后端提供无
    `page/pageSize` 的全量接口（范本 `ListCurrencies`，
    [../../../server/api/masterdata/v1/masterdata.proto](../../../server/api/masterdata/v1/masterdata.proto)），
    前端 `MasterDataTemplate` 客户端模式本地完成搜索、筛选、翻页与统计，
    交互零服务器请求。
  - 大数据集（全球港口、全球机场等）：一律服务端分页 + 服务端 `keyword`
    过滤（范本 `web/src/pages/master-data/components/` 的 AirportsPanel /
    PortsPanel 模式）。
- 禁止前端为绕过 200 条上限循环翻页拼接全量；数据量跨过阈值时调整接口
  契约，不在调用方堆补丁。

## 理由

- 以「服务器总资源（交互成本）最小化」为优化目标，而非单次请求成本：
  小数据集一次全量 + 前端分页的总开销远低于每次筛选一请求。
- 上限统一后，前端组件可以放心假设契约，无需按接口猜测最大值。

## 后果

- 契约评审时 `pageSize` 超过 200 的接口视为违规。
- 主数据新页面先判断数据量级再选模式；选择器类查询必须支持服务端
  `keyword` 过滤（检索键要求见 ADR 0007）。
- 例外有明确记录：月度提成申请的候选解析是「完整候选」语义，服务端解析
  全量未申请来源、不受分页上限约束，与工作台的有界估算分成两条路径
  （见 [../domain/architecture-map.md](../domain/architecture-map.md)）。
