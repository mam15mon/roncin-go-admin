# ADR 0009: 服务端状态归 React Query，不镜像进全局 store

- 状态：已采纳
- 日期：2026-08-20（随工程骨架引入），规范随 Trellis 沉淀固化
- 主题：前端

## 背景

管理后台的绝大多数前端状态其实是「服务端数据的缓存」：列表、详情、
字典、权限。常见反模式是把接口响应写进全局可变 store 再派生 UI——缓存
失效、刷新时机、多页面共享同一份数据的一致性都要手工管理，最终必然出现
「A 页面改了，B 页面还显示旧值」。

## 决策

- 接口数据优先由 React Query 等服务端状态工具管理；缓存键按业务领域
  命名，列表查询携带与后端一致的筛选参数。
- 不把接口响应镜像进全局 store 再派生，直接消费服务端状态层。
- 表单、弹窗开合等 UI 状态留在组件内；跨页面共享的 UI 偏好才考虑全局。
- 所有后端请求经过统一请求配置或 OpenAPI 生成客户端，页面禁止自行拼接
  后端主机地址（与 ADR 0001 契约单向流配套）。
- 长流程例外按专项契约管理：跨页签表单草稿以「用户 ID + 组织 ID + 页签
  key + pathname」命名空间持久化在 sessionStorage，由 `OrderFormTemplate`
  独占生命周期（详见
  [../web/frontend/state-management.md](../web/frontend/state-management.md)）。

## 理由

- 缓存失效是计算机难题，React Query 的查询键 + 失效协议已解决 95% 场景；
  自建全局镜像等于重写一个更差的缓存层。
- 缓存键携带筛选参数使「同列表不同筛选」天然隔离，避免筛选串页。

## 后果

- 新增页面数据获取先找/建 Query Hook（约定见
  [../web/frontend/hook-guidelines.md](../web/frontend/hook-guidelines.md)），
  不往全局 store 加接口数据。
- 复用页面的业务数据隔离有额外纪律：请求必须同时校验「请求所属业务 ID」
  与请求序号，迟到响应不得覆盖当前页面（TagsView 页面复用场景，见
  component-guidelines「复用页面的业务数据隔离」）。
- 与 ADR 0012 同域部署配合后，请求层无需区分环境主机。
