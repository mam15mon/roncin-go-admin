# ADR 0005: 并发防护双层模式——ForUpdate 悲观锁 + version 乐观锁

- 状态：已采纳
- 日期：2026-08-26 引入 expectedVersion，2026-08-30 成文规范，2026-09 补锁序
- 主题：事务与并发

## 背景

订单、账单、提成等多人类协作编辑的实体，并发写冲突有三类：(a) 两人同时
编辑同一草稿，后写覆盖先写；(b) 状态流转与号码分配等原子操作存在
检查-后-写入竞态；(c) 多行写路径并发交错可能死锁。单一手段无法同时覆盖：
纯乐观锁挡不住状态机竞态，纯悲观锁又要求用户每次提交都做好「拿不到锁」
的心理准备。

## 决策

写路径范本是
[../../../server/internal/data/order_write_draft.go](../../../server/internal/data/order_write_draft.go)
的 `UpdateDraft`，四步固定顺序：

1. 事务内 `ForUpdate()` 锁定目标行（悲观锁）；
2. 比对 `existing.Version != expectedVersion`，不匹配返回 `errors.Conflict`
   业务错误（HTTP 409，中文提示「已被更新，请刷新后重试」）；
3. 通过状态机检查后才允许变更；
4. 更新时 `SetVersion(existing.Version + 1)`。

按实体分层取舍防护强度：

| 场景 | 防护 |
|------|------|
| 多人协作编辑（订单、账单、结算、提成申请等） | `version` 字段 + `expectedVersion` + `ForUpdate` |
| 状态流转、号码分配等原子操作 | `ForUpdate` + 状态检查 |
| 低频单人维护的主数据 | 可不加版本检测 |

配套纪律：

- 多行加锁先按主键排序再 `ForUpdate()`，固定加锁顺序防死锁
  （2026-09-16 `9bb43a38` 补齐）。
- 同一事务内后续要 `FOR UPDATE` 的行，首次读取禁止先 `FOR SHARE` 再升级
  （两个并发事务可同持共享锁互等升级形成死锁），从入口即 `ForUpdate`。
- 写入口对关联实体的校验读放在事务内、防护锁之后，不采用「锁外预检、
  锁内直写」；配置型读-改-写必须先锁后读权威数据（先读后锁等于没锁）。
- 唯一性由数据库唯一索引兜底，驱动错误用 `ent.IsConstraintError` 统一
  判断并映射为业务错误。

## 理由

- 悲观锁串行化临界区，乐观锁给用户确定文案；叠加后 409 语义全站一致。
- 分层取舍避免「所有表都加 version」的过度设计：低频单人主数据加版本
  检测只产生无意义的冲突报错。

## 后果

- 新增多人协作实体必须带 `version` 字段与 `expectedVersion` 校验；判定
  不清时先向用户确认，禁止默认生成。
- 锁行为无法 sqlmock 单测，依赖真实库集成测试与「加锁先于权威读取」的
  审查人工核对。
- 版本乐观锁贯穿全链：订单/账单/提成/申请全部 `expected_version` 校验，
  冲突统一 409 文案（见
  [../domain/architecture-map.md](../domain/architecture-map.md)）。
