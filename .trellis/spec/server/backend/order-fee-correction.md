# 批准后费用更正、账务清偿与提成重算

## 1. 适用范围

已批准费用追加、替换与整笔作废，以及由此触发的账单、发票、核销、对冲与提成调整。
业务结案与收付款分别处理：已存在待审批更正阻止结案，已结案可再发起受控更正，批准不反结案。
费用完整性仍由提交人与审批人判断，不增加必选费用或预计成本平台。

## 2. 接口与数据库签名

- `OrderFeeService`：Create/List/GetOrderFeeCorrectionRequest(s)、PreviewOrderFeeCorrectionApproval、Approve/Reject/WithdrawOrderFeeCorrection。
- `CreateOrderFeeCorrectionRequest`：`operation=ADD/REPLACE/VOID`，`source_fee_id`、`source_fee_expected_version`、完整正数 `target_fee`、`reason`、`idempotency_key`。
- 审批预览/批准绑定申请 `expected_version`；批准同时提交 `preview_token` 和意见。令牌绑定费用、审批、账务和提成事实。
- `order_fee_correction_requests` 保存原/新费用、申请人和决定人、版本、批准时利润与提成影响；不覆盖原申请或删除批准历史。
- `order_fees`：`economic_effect=INCREASE/DECREASE`、`source_fee_id`、`correction_request_id`、`superseded_by_request_id`、`accounting_required`。
- `finance_bills.purpose=NORMAL/CORRECTION_REVERSAL`；内部对冲 `correction_request_id`，对冲分配 `source_fee_id`。
- `finance_invoice_bills.source_fee_ids` 固化本次发票实际覆盖费用，不能以账单级占用推断被更正的某一费用仍已开票。
- 统一清偿投影：`biz.ProjectFinanceBillLineSettlements`；提成消费 `biz.ProjectCommissionEconomics`，不另查整账核销总额推断订单收入。

## 3. 核心契约

### 费用与审批

替换保留原费用并标记 superseded，生成原额冲回与完整替代；作废只生成冲回；追加只生成正常费。
所有存储金额为正数，经济减少由 effect 表示；冲回的资金方向与经济方向相反。
未建账原费和冲回无需财务建账，替代需要；已进入有效账单的原费保留，冲回及替代分别建账。
现行经济金额只汇总未被替代的正常费。费用历史、现行经济费用、待建账冲回三个集合不可混用。

同单补录与更正待审批互斥；待审批阻止建账及受影响提成确认/发放。原有业务锁/财务锁不需解除。
受控审批、核销和对冲写入先展开关联父提成的订单传递闭包（A/B、B/C 两父单须包含 A/B/C），按主键一次加锁后重新查询集合；集合变化返回 409 重试，不中途追加反序订单锁。
审批在一笔共享事务中更新费用、整票批准快照、提成系统调整、审计与提醒；冲突和错误零部分写入。
新增复用费用创建权限，替换/作废复用费用修改权限，批准复用整票费用审核权限；精确校验所属公司、有效成员和即时权限。
只有本人查看能力时，逐条请求/列表均限制申请人，不因为该人同票存在一条申请而暴露其他申请。

### 清偿与票据

已被更正的原费用不可重新建账；其既有草稿允许确认但不可取消以逃逸调整链。
新账按资金方向、币种、结算对象及更正用途拆分。内部对冲由服务端推导同一步骤原费/冲回/替代，客户端不能自标内部对冲。
金额上限为目标费用行剩余额，不得占用合并账单其他订单余额；未收原费先清原债，不能先消耗替代账导致残留原债无处清偿。

普通核销按事件当时合法行的剩余额比例分摊，内部对冲精确指向费用行。分摊先截断 8 位，再按余数降序和稳定 ID 分配最小单位，确保合计守恒且不超过行余额。
核销按创建时间、对冲按确认时间重放；反转按反转时间释放缓存的原行归属，不能重新分摊已发生的后续回款。
连续更正继承原经济链的真实结算覆盖；退款及对冲不得消耗不存在的覆盖，依赖尚未撤销时禁止反转上游。

已开票费用更正保留原发票，财务整张红冲后按当前有效普通行重开。原账单总额保持历史事实，候选 `invoiceable_amount/net_amount/tax_amount` 另表达可开票额。
草稿发票签发前重验费用 ID 集合、金额、税额与内容快照；更正冲回行不能作为普通开票内容。

### 提成

按 `source_fee_id` 追溯经济根，在同订单、结算对象和币种内继承实际收款；不能把旧客户或旧币种回款视为新对象付款。
内部更正对冲不新增收入；真实收入退款减少原真实来源贡献，退款撤销恢复原分配。成本冲回收款不是营业收入。
实际净回款以当前有效应收封顶，按稳定时间顺序分配来源配额；收入本位币基数与成本使用统一经济投影。
受控补录/更正使用批准时经济汇率快照，后续建账的汇率不再次改变其费用提成基础；原 V3 逐步骤 Round(8) 不变。

已确认/支付原提成快照保留原员工、岗位、比例和模式；重算理论目标后只调整系统净额。
系统来源为 `LOCKED_FEE_SUPPLEMENT/FEE_CORRECTION/ECONOMIC_REALLOCATION`；手工奖励/处罚不被普通费用重算吞掉。
未执行系统调整专用取消后净重建，已执行事实永久保留并生成相反方向差额；普通确认/取消入口不能修改系统调整。
原来源整体反转走一份统一计划：未付父单取消；已付父单保留，以实际父单及已执行调整净额确定追回，避免旧反转逻辑与经济重算双重冲减。

## 4. 校验与错误矩阵

| 情况 | 结果 |
| --- | --- |
| 申请/原费用版本或预览金额已变化 | 409，刷新预览，保留用户意见 |
| 相同幂等键用于不同订单或不同目标内容 | 冲突；不得返回另一订单申请 |
| 同版本同令牌重复批准 | 返回原结果，不再写费用/调整 |
| 无有效批准、无审核人、待审批变更已存在 | 拒绝新申请，零写入 |
| 非本人撤回、无批准权限、跨组织 | 拒绝，无财务/合并账其他订单信息泄露 |
| 更正后亏损且意见为空 | 参数错误，不能批准 |
| 原债未清时普通核销/商业对冲 | 明确要求先完成更正内部清偿 |
| 行余额/退款贡献不足或不合法历史依赖 | 拒绝，不能钳零继续提交 |
| 源费用已被更正时普通修改、删除、转移或补录撤销 | 拒绝，继续走受控更正 |

## 5. 数值场景

- 应收 1,000、成本 400、实收 500、利润提成 10%：原提成 30；优惠至应收 800，按实际 500 收款，成本分摊 250，提成 25。
- 原提成 100，补录成本 1,000 后应冲减 100，后更正成本为 100：最终目标 90。尚未执行的 -100 取消并替换 -10；已实际追回 100 则保留原记录，另生 +90 补付。
- A 1,000 与 B 200 合账收 400：A 333.33333333、B 66.66666667。A 更正为 100，只能清 A 原未收 666.66666667；B 仍待收 133.33333333，不能被 A 的对冲消费。
- 错误：合并账收款总额减某票费用，或把内部对冲当实际收款再提成。

## 6. 必需验证

实现后按风险补测试，不使用 TDD。真实 PostgreSQL 使用正式迁移隔离 schema，不能依赖 Schema.Create 或以 SKIP 作为验收。
必须覆盖追加/替换/作废、不同方向/对象/币种、部分收与全收、连续更正、人工调整并存、四种提成支付状态、合并账/票其他订单不受侵占。
权限撤回、版本/幂等、并发审批/建账/付款/来源撤销、故障回滚需验证；联动回归第一阶段自动锁单及业务结案。
前端验证实际 25 元预览、版本令牌透传、失败保留输入、批准历史、冲回标识、重开金额及补付/扣回文案。

## 7. 错误与正确实现

错误：批准后解除锁，覆盖原费用和已发提成；已付款冲减用删除处理；前端手算利润推断是否可批。
正确：原事实不可变，申请审批后原额冲回/替代；未执行调整净重建，已执行补付/追回；所有资格、金额及预览指纹由服务端提供。
