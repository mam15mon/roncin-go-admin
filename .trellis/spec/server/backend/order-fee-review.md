# 整票费用审核、冻结与建账准入

## 1. Scope / Trigger

适用于六类订单的费用提交、审核、列表摘要、费用写入、拆票转移、全部建账入口以及受控补录。修改提成执行时同时参照 `finance-commission-lock.md` 和任务付款契约。本规范随实施维护，代码与 Proto 为具体字段真相源，验收结果另见任务记录。

## 2. Signatures

- `OrderFeeService`：Get/Preview/Submit/Withdraw/Approve/Reject/RevokeOrderFeeReview；Preview/ApproveOrderFeeReviews。
- `biz.BuildFeeReviewSnapshot(fees)`：完整经济内容快照及确定性指纹；不得纳入账单关联、通用行版本、更新时间或往来单位展示名称。
- Order 投影：`fee_review_status`、`fee_content_version`、`fee_review_version`、当前事件与批准事件 ID；状态 UNSUBMITTED/PENDING/APPROVED/REJECTED/REVOKED。
- `OrderFeeReviewEvent`：只追加的动作、操作者、授权来源、意见、快照、内容指纹和幂等事实。
- `system.finance.fee.review`：一个独立权限，依赖费用读取；不自动赋予建账、付款或所有订单品类详情读取。

## 3. Contracts

- 审批单位是订单费用包：每个订单的全部应收、应付和利润一次审核，明细仅供核对，不建立费用行独立审批任务。批量审核选中多个订单包。
- 整票审核同时展示完整应收、应付及费用保存的本位币利润，正利润仍人工批准；负利润意见必填。允许具备真实资格的提交人自审，提交与批准分别操作。
- 有效用户、成员、角色、权限与组织范围必须来自同一合法 grant。目标组织与授权成员所属组织都必须启用；all 范围也不能绕过停用组织。事务内先按 User→Membership→Role 加共享锁，再锁 Order 并重读授权；审核与补录不能持有 Order 后才申请授权父行锁。月度提成申请按 User（NO KEY UPDATE）→Membership→Order 获取父锁，避免交叉反序；角色更新先锁 Role 父行，成员角色替换先锁 Membership 父行，不能只锁独立关联。
- 快照复核折本币金额与费用录入统一使用 `RoundBank(8)`；不能用 `Round(8)` 拒绝合法的半数舍入结果。审批意见最多 1000 个 Unicode 字符，领域、Ent 与表单使用字符计数，不使用 UTF-8 字节长度；补录批准意见与退回原因共用的 decision_reason 同步校验，旧 varchar(500) 通过正式迁移扩容。
- 提交确认录齐费用，成功后 PENDING 冻结；本人撤回或审核退回后仍须满足业务锁、提成净额保护与生命周期条件才能编辑。
- APPROVED 禁止普通新增／修改／删除／转移；新增正数应付走补录。存在有效账单时不能撤销批准；取消账单不自动撤销费用批准。
- 内容版本只随经济内容集合变化递增；建账／取消账单只改关联，不使剩余费用的批准失效。建账时服务端核验完整快照指纹、选中费用归属、有效批准、无待审补录及既有权限与账户条件。
- 批量批准显式选中最多 200 票，逐票事务，返回逐票结果；批量建账仍按既有整批事务语义。不能用跨票合计利润遮蔽单票亏损。
- 钉钉仅机器人提醒：成功提交同事务入队，后台发送；保存、失败提交不发，消息送达／已读／打开不产生审批结果。使用现有机器人逐人渠道，所有决策通过 Roncin API。
- 审核界面用精简费用表格：单票默认显示应收/应付明细和横向利润摘要；批量一个订单包一行，展开费用明细，亏损逐票意见。费用明细仅只读核对，不逐笔批准。
- 补录状态变更成功后必须同时刷新整票审核与订单详情投影，详情结案按钮使用 `feeReview.hasPendingSupplement`；预读为空不代表服务端可以跳过权威门禁。
- 审核及发放动作必须验证成功响应后才提示成功、关闭或回调；统一请求层消费错误后返回空值时保留输入与重试幂等键。补录各成功状态流转都刷新审核查询；待审期间禁止另建补录，但保留本人撤回并预填重提入口。
- 结案仅表示业务操作完成，不要求收付结清。结案动作遇到已有 PENDING 补录时拒绝；结案成功后新提交、批准、退回或撤回受控补录仍允许，不要求或自动反结案，普通费用冻结及财务保护仍保留。
- 结案与补录共用现有 Order 行锁串行化：补录先提交则结案被挡；结案先提交则后续补录允许，CLOSED + PENDING 是合法组合，禁止以生命周期静态互斥约束阻止。
- 费用 UI 围绕审核状态、允许动作、具体阻断原因组织，不新增审批锁开关或手动财务解锁。业务锁保护资料和单证，自动财务保护仍按净额生效；受控补录只批准一次，不需先解除上述保护。

## 4. Validation & Error Matrix

| 条件 | 行为 |
| --- | --- |
| 待审核／已批准普通改费用 | FEE_REVIEW_FROZEN，409 |
| 无有效批准或内容不一致建账 | FEE_REVIEW_NOT_APPROVED，409 |
| 审核或内容版本、预览事实变化 | FEE_REVIEW_CONFLICT，409，要求刷新 |
| 组织范围不符或角色无效 | FEE_REVIEW_FORBIDDEN／现有权限错误 |
| 缺少候选审核人提交 | FEE_REVIEW_NO_APPROVER，409 |
| 结案时已有待审补录 | ORDER_CLOSURE_BLOCKED，409，提示「存在待审核补录，请先处理后再结案」 |
| 已结案后提交/批准受控补录 | 按现有费用审批资格办理，保留 CLOSED，不伪造收付完成 |
| 待审补录期间建账 | FEE_REVIEW_PENDING_SUPPLEMENT，409 |
| 亏损意见空白／未确认录齐 | 参数或完整性确认错误，400 |
| 提成净额归零但仍 APPROVED | 仍不可普通编辑，不改审核状态 |

## 5. Good / Base / Bad Cases

- Good：订单结案后发现新增成本，直接受控补录并批准，继续保留已结案状态，财务随后建账及付款。
- Good：整票批准后先建 USD 账单，再建 CNY 账单，剩余费用仍可使用同一有效批准。
- Base：提交人具有有效审核权限和范围，查看整票后显式批准自己的申请。
- Bad：解锁订单自动赋予建账资格；先生成账单再补审核。
- Bad：只按 OrderFee.version 判批准有效，第一次建账递增行版本后令整票失效。
- Bad：补成本还要求再走一次财务锁审批，或财务忽略已由费用审核确认的系统冲减。

## 6. Tests Required

按任务 R1–R18／AC1–AC18 实施后验证权限与范围、盈亏与自审、状态机、不可绕过写入口、逐票批量混合结果、完整快照及分次建账、通知入队回滚、连续补录、净额发放。

结案补录回归须覆盖已有待审阻断且零写入、退回/撤回后可结案、批准后未建账阻断、结案后完整补录审批及补录先/结案先的两种并发顺序；前端验证待审提示刷新、反结案放行和服务端失败不误成功。

并发验收必须在真实 PostgreSQL、正式 SQL 迁移的隔离环境中验证提交与编辑、批准与撤回、撤销与建账、补录与发放；还须覆盖审核与月度申请的授权父行/订单锁序、1000 字中文意见、银行家舍入边界以及失败响应不误成功；必须记录实际 PASS，SKIP 不算通过。费用页、列表抽屉、台账与三个建账入口均需验证。

## 7. Wrong vs Correct

```text
错误：可建账 = 利润 > 0 或 finance_locked；费用指纹包含 has_active_bill/version。
正确：可建账 = 有效整票人工批准且经济内容匹配、无待审补录，再检查现有建账条件。

错误：收到钉钉机器人消息或者打开链接后更新 APPROVED。
正确：成功提交创建提醒任务；Roncin 审核事务验证权限、版本和快照后才写批准事件。
```
