# 角色数据访问范围退役

## 1. 适用范围

2026-10-16 起角色不再配置数据访问范围。本规范适用于角色 CRUD、登录授权收集、权限画像、防提权、经营审批候选与初始化。工作台归属不变量见 role-workspace-ownership.md；本规范取代旧版角色可选 all / organization_tree / organization / self 的要求。

## 2. 签名与结构

- `CreateRoleRequest`、`UpdateRoleRequest` 不含 `data_scope`，原字段号 3 与名称保留为 reserved。
- `AdminRole` 不含 `data_scope`，原字段号 5 与名称保留为 reserved；管理端 DataScope 枚举已退役。
- `Auth.RoleScope` 只投影角色代码和名称，不再暴露角色级范围。`PermissionCapability{key,data_scope}` 保留为服务端推导的有效能力。
- Ent `Role` 与数据库 `roles` 不再有 `data_scope` 列；删除来源见正式迁移 `20261016100000_retire_role_data_scope.sql`。

## 3. 契约与数据流

- 角色持久化只保存所属工作台、代码、名称、状态、权限关联。前端无范围控件、列、筛选或默认提交值。
- 工作台为 company 时有效范围固定 organization；system 时固定 all；未知工作台不产生有效授权。内部范围不接受调用方输入，不从任一角色值或最大范围猜测。
- 认证及权限画像复用已加载的组织树和工作台锚点推导范围，禁止逐角色查询组织造成 N+1。
- 公司经营数据继续限定当前公司；系统工作台不能因 all 办理公司经营业务。全部能力必须同时有明确权限码、启用角色、有效成员资格和工作台资格。
- 锁定、费用审核与汇率提醒候选由目标公司工作台的角色和该公司启用成员资格决定；公司下的部门/团队可参与，到其他公司节点截止，不允许系统角色或其他公司成员借宽范围进入候选。
- 正式迁移先停用旧 self 角色，再删列，保留角色、权限、成员关系及业务数据。已停用角色不被 bootstrap 或种子重新激活。旧 system 的 organization/tree 在本期退役后按系统 all 治理；功能权限集不增加，经营边界不变。

## 4. 校验与错误矩阵

| 条件 | 结果 |
| --- | --- |
| 未知或非工作台锚点创建角色 | 明确拒绝，不默认 company/all |
| 分配操作者不拥有的权限 | `ErrAdminPrivilegeEscalation` |
| 公司 A 读写公司 B 经营数据 | 拒绝 |
| 系统工作台持有公司经营权限 | 不能据此办理经营业务 |
| 旧 self 角色迁移 | enabled=false，关联保留 |
| 旧 enabled=false 角色 | 保持停用 |
| 部门成员持有同公司启用业务角色 | 可按具体权限进入候选 |
| 其他公司或系统角色 | 不进入目标公司业务候选/提醒 |

## 5. 正常、基础与错误场景

- 正常：成都公司的财务角色只勾费用审核，成员可在成都公司执行该动作；不需要选择范围。
- 基础：系统管理人员按治理权限管理组织，进入公司业务必须有对应成员资格并切换公司。
- 错误：只删表单，服务端继续接收隐藏 data_scope；或删候选范围谓词后让跨公司角色进入审批。

## 6. 必需测试

- 无 data_scope 的角色创建、编辑、权限与停用行为；前端不出现范围控件/列/筛选。
- Proto/生成物无角色范围字段，Ent/正式迁移同源；冷启动和旧结构增量升级执行成功。
- 迁移 self 停用、其他角色启停及全部关联保留；bootstrap 重跑不恢复停用角色。
- 公司隔离、系统治理、防提权、成员角色分配、部门成员候选及跨公司拒绝。
- 集成测试必须真实提供专用 PostgreSQL，日志 PASS 才是通过，不能以 SKIP 代替。

## 7. 错误与正确

```go
// 错误：仍从已退役的角色字段决定权限，或以操作者首个角色猜测目标范围。
role.DataScope
profile.RoleProfiles[0].DataScope

// 正确：从已校验的工作台类型确定有效边界，再匹配具体权限与目标组织。
// company -> organization; system -> all; unknown -> 拒绝
```
