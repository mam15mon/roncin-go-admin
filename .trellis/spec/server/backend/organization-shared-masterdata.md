# 公共主数据与公司独立配置

## 适用范围
公共字典、费用目录、业务汇率、公司经营资料及维护权限。系统不存在集团，系统管理工作台不作为公司的业务上级。

## 归属矩阵
| 类型 | 实体 | 维护与消费 |
| --- | --- | --- |
| 公共标准资料 | 国家、币种、行政区划、标准箱型、费用大类、货物分类、异常类型、计费单位、船公司、船代、航空公司、港口、机场 | 系统管理身份及对应权限维护，各公司读取同一记录 |
| 系统初始目录 | FeeSettingTemplate | 系统管理维护；新建公司同事务复制为本公司的税务项目和费用科目 |
| 公司独立配置 | FeeSetting、TaxableService、FinanceCustomSetting | 当前公司有权人员维护，不跨公司共享、不继承系统设置 |
| 公司独立配置 | ExchangeRateSetting | 公司维护和消费当周业务汇率；旧 NULL 公共行仅保留历史事实，不参与新取值 |
| 公司经营数据 | 客户、供应商、国外代理、订单及财务单据 | 公司成员资格和公司角色授权，经营读写仅当前公司 |

## 必须遵守的契约
- 公共资料写入使用 `RequireGlobalMasterDataWrite`：系统管理工作台身份和权限码缺一不可。公司administrator角色不等于系统管理角色。
- 港口机场无organization_id，不存在本地同码覆盖。按保存ID读取允许停用记录展示；新选择和写入要求启用。缺失地点继续显式报错，禁止吞错。
- 费用模板只保存税务文本默认值，不引用某公司的TaxableService ID。复制时建立本公司合法关联；已有公司配置不会随模板更新而变化。
- 公司费用科目organization_id必填；订单费用和费用补录按目标公司校验科目与税务引用，系统模板不能直接用于经营单据。
- 公司财务编辑与信用管控策略按目标公司读写和审计，使用统一事务与版本冲突检查；禁止沿组织树查找系统节点来继承经营策略。
- 新建公司无父工作台，部门/团队只归所在公司；系统管理维护身份不自动授予公司成员资格或经营权限。

## 迁移与回归
- 正式迁移保留原ID和单据快照，地点同码或税务配置冲突必须显式拒绝，不擅自合并覆盖；不得重置开发库。
- 旧集团结构转换在原子迁移内先复制有效公司策略，再拆除公司父关系。现有成员资格保留；停止bootstrap自动补公司资格及权限穿透。
- 真实PostgreSQL隔离测试覆盖冷启动、升级、冲突回滚、已有订单引用、费用普通与补录引用映射、公司策略独立。
- 权限验证覆盖系统维护公共资料、公司拒绝公共写、系统拒绝经营读写、公司ALL仍仅本公司、模板修改不影响公司副本。

## 旧管理目录转换与开发种子
旧管理节点费用经明确批准转为系统初始模板，保留原科目ID、时间和税务默认文本；不自动填充已有公司。原税务记录完整保留，但不提供系统经营CRUD，也不进入公司选择器。模板同码冲突或原系统科目仍有经营费用/补录引用时原子拒绝。
开发seed必须在统一事务内执行，测试员工与经营数据归独立公司；系统管理员不自动获得公司成员资格。验证seed需在隔离数据库真实执行并重复运行，不能以编译通过代替实际落库验证。
默认分公司种子仅包含北京（`BJ`）和成都（`CD`）；bootstrap、补建分公司与开发数据同步均不得自动补建上海（`SH`）或重庆（`CQ`）。开发数据固定归属启用的北京公司，缺失或停用时显式报错。

## 初始目录种子迁移（20260923120000）
- 系统初始目录 122 条模板由正式迁移落库（`fee_catalog_seed.sql`）；迁移同时幂等补齐基础费用类别（与 `data.CreateDefaultOrderOptions` 同值）、异常情况与计费单位（含 `quantity_must_be_integer` 标志，故该迁移必须排在 20260923115000 之后），并向每个既有公司追加模板副本：同码跳过、应税劳务按（公司,名称）复用或按模板文本创建、同名但税率/简称/商品码不一致时显式拒绝，口径与 `initializeCompanyFeeSettings` 一致。
- 全新库顺序为：迁移先行（此时无组织，公司追加空转）→ bootstrap 建 system 组织并按 kind+code 幂等补种其余 A 型主数据（国家/箱型/货物分类）→ `CreateDefaultBranchCompanies` 新建公司时同事务复制模板。bootstrap 与后台建组织不再以"存在任意主数据行"跳过默认种子。
- SQL 种子行的 `search_keywords` 必须与 `internal/platform/searchtext.Build` 的输出逐字一致：迁移是纯 SQL，无法执行 Ent 钩子，检索键须经该函数预计算后写入（费用种子由一次性生成器产出后删除）。

## 船代公共字典与订单引用

### 1. 范围与触发
海运订单的 `shipping_agent_id` 引用全局 `master_data_items.kind='shipping_agent'`。系统管理工作台统一维护，各公司共享读取；订舱代理和国外代理仍是公司经营档案。

### 2. 命令、接口与存储签名
- 先执行正式迁移，再运行 `pnpm run sync:shipping-agents`，或由 `pnpm run sync:all` 调用。命令读取 `server/seeds/shipping-agents.hgj.20261027.json`，使用环境变量 `DATABASE_SOURCE` 连接数据库。
- `GET /api/v1/master-data/items/all`：必填 `kind=MASTER_DATA_KIND_SHIPPING_AGENT`，`enabled` 可选；返回完整目录，不接收分页参数，维护读取权限为 `system.master_data.item.read`。
- `GET /api/v1/master-data/options/search`：以同一 kind 和 keyword 查询启用船代；`page >= 1` 且 `1 <= pageSize <= 200`。
- 订单 API 沿用 `shipping_agent_id` UUID 与 `shipping_agent_name` 展示字段；正式迁移为 `master_data_items_kind_check` 增加 `shipping_agent`，Ent Schema 同步声明约束。

### 3. 契约
- 同步以 `(kind, code)` 唯一键和 `HGJ-<来源整数ID>` 导入码只补缺失行；保留已有 UUID、名称、英文、排序、来源和停用状态，不自动停用字典记录。导入码仅用于来源追溯，不代表行业标准编码。快照固定 29 条，运行时不访问第三方网站。
- 新建订单、普通复制及主动更换船代必须引用存在且启用的船代；原单编辑与拆票继承可保留同一个已停用引用。清空仍为可选。订单校验在原事务内锁定目标行，按 ID 与 kind 双重核对。
- 订单列表和详情通过同一批量名称投影显示船代，包含停用记录，不回退到 Partner；选择器 keyword 覆盖导入码、中文、英文、拼音全拼与首字母。

### 4. 验证与错误矩阵
| 条件 | 结果 |
| --- | --- |
| 缺少或停用的船代用于新选择 | 订单写入拒绝，事务不提交 |
| 原订单引用同一停用船代 | 编辑其他字段及拆票继承允许，名称仍可显示 |
| Partner ID 或其他 kind 的 UUID 用作船代 | 订单写入拒绝；迁移遇旧非空非法引用整批失败 |
| 同步再次遇到相同 `(kind,code)` | 跳过该行，不覆盖管理员配置 |
| 快照无效或数据库写入失败 | 命令报错，不产生部分写入 |

### 5. 正常、基准与错误场景
正常：迁移后同步 29 条，订单按拼音检索并选择启用船代。基准：停用已引用船代后，原单仍显示名称并能编辑其他字段。错误：普通复制把停用旧 ID 当作新选择保存，或重复同步把管理员改名恢复为快照名。

### 6. 必需验证
隔离 PostgreSQL 执行正式迁移、同步命令两次并核对新增数及稳定 UUID；人工修改名称、排序和启用状态后再次同步，断言不被覆盖。验证检索键、系统维护与公司拒写、正确 kind 与相邻代理路径、新选停用拒绝、旧引用保留、旧 Partner 引用迁移原子拒绝；检查生成契约和前端客户端一致。

### 7. 错误与正确做法
错误：把 29 条同时硬编码到迁移和同步脚本，或把 `shipping_agent_id` 继续按公司 supplier 校验。正确：正式迁移只负责类型与约束；同步命令从唯一归档快照补缺，订单按公共船代字典校验和显示。

## 港口全量中文种子契约

### 1. 范围与触发
`sync-unlocode` 装配官方海港身份与仓库中文对照，升级 ZIP、修改中文名或调整同步逻辑时同时遵守本节。中文译名不是 UNECE 官方字段，不得更改五字码或合并港区来迁就中文来源。

### 2. 命令与签名
`go -C server run ./cmd/sync-unlocode [-source ZIP] [-release VERSION] [-chinese-source CSV] [-apply]`。
`data.PortSyncRecord.NameZH` 随英文名经 `IndustryReferenceSyncStore.ApplyPorts` 的统一事务写入；更新既有记录保留 ID，新增与更新都调用 Ent 的中文检索 Hook。

### 3. 输入、环境与输出
中文表默认取 ZIP 同目录的 `ports.zh-CN.csv`，UTF-8 表头严格为 `un_locode,name_en,name_zh,name_kind,source_ref`。代码集合及 `name_en` 必须与当前解析海港逐字一致；`name_kind` 只能为 `existing` 或 `translated`，来源必填。中文必须包含汉字，非空、无首尾空格、最长 200 字且不是占位值。无通用名的编制译名显式标记为 `translated`。
默认只预览；无 `DATABASE_SOURCE` 时可以完整离线验源，明确提示未检查数据库冲突；有连接时先做数据库冲突检查，`-apply` 必须提供连接。摘要打印中文覆盖、两类数量、ZIP 与中文表 SHA-256。持久化 `source_hash` 是 `SHA256("unlocode-zh-v1\n" + ZIP摘要 + "\n" + CSV摘要 + "\n")`，任一文件变化都改变指纹。

### 4. 校验与错误矩阵
缺行、多行、重复码、英文身份不符、非法类别、无效中文或来源为空均在打开数据库前失败；不得静默跳过或在线补译。其他来源占用同码时显式拒绝；写入失败整批回滚。基础英文和中文都应显式 Set，避免保留旧的非空检索键。

### 5. 正常、基线与失败场景
正常：同版 ZIP + 完整 CSV 离线预览覆盖 100%，显式 apply 补中文且二次导入不新增。
基线：只修订一个中文名，身份与记录 ID 不变，中文检索和联合指纹改变。
失败：新增或改名后的官方地点没有配套中文行，立即报错并修订 CSV，再重新预览。

### 6. 必需验证
`cmd/sync-unlocode` 测试包含真实配套文件全量覆盖、严格失败矩阵、双源指纹及无连接预览。`TestPortChineseSyncPostgres` 通过独立 PostgreSQL 与正式迁移验证首次新增、旧行补名、旧非空检索键刷新、代码/英文/中文/全拼/首字母查询、ID及订单引用稳定、幂等、来源冲突和中途失败回滚；不得把 SKIP 当作通过。

### 7. 错误与正确做法
错误：把英文复制到中文列、按旧行业码盲目套用名字，或在同步时调用翻译服务补缺行。
正确：先按同国家、同代码及地点身份核对来源，无法核实通用名时编制有意义译名并记录依据；提交静态中文表，运行时严格读取和校验，不引入翻译依赖。
