# 海运共享主单与航程继承

## 适用范围

海运出口新建订单关联已有 MBL，以及详情中的共享航程展示和统一修改。完整业务契约见 [海运主分单契约](../../server/backend/sea-export-document-contract.md)。

主单和分单是单证关系，不能将共同海运段的航程当作每票可独立改写的资料；多航程仍需明确选择，不能将本期单航程简化扩展为全程只能一艘船。

## 现有接口与边界

- `orderServiceMatchSeaMasterBillCandidate({ shippingLineId, masterNo, ...voyage })` 返回候选 MBL、实际航次、活动成员和批次分单号。
- 创建关联携带 `seaMasterBill.candidateId/expectedCandidateVersion/candidateTeId/expectedCandidateTeVersion`，服务端事务内验证身份、版本、分单模式与航程冲突。
- `seaOrderChangeServicePreviewSeaTransportExecutionUpdate` 返回精确影响集合 `memberOrderIds`；执行继续经已有更新命令，保留 reassign 权限、业务锁、版本、外部确认和幂等约束。
- 船公司是主单身份，不能经共享航程更新命令修改；该命令只处理船名、航次、起运港、卸货港、中转港、ETD、ETA。

## 表单契约

- 新建未匹配时正常填写；命中一个航程时自动选定并省去下拉，多航程必须显式选择。
- 空白共享字段带入；非空且不同的值列明当前/共享差异，点击“采用主单航程”才替换。共享字段缺失也不能让用户误以为新票输入会更新已有航程。
- 采纳后共享字段只读；客户、分单号、收发货人、件重尺、目的地、费用保持各票独立。
- 新建的船公司和主单号仍可改选，用于重新匹配；身份变化立即失效旧候选、航次、版本、批次分单号与继承来源，不删除用户手填业务资料。
- 新建页明确展示号码核对结果：MBL 按「船公司＋主单号」识别，HBL 按当前 MBL
  内的规范化分单号查重。HBL 输入旁显示待核对、核对中、可用或重复的反馈；
  通过时只显示绿色对勾，不显示「当前主单内分单号可用」等成功说明文字。
- HBL 核对复用现有主单候选查询，不额外发起第二套查询。主单身份未齐、查询未完成
  或失败时不得显示分单可用；候选未命中且查询成功时，按新主单空集合核对。
  切换船公司或主单号立即撤销旧结果，完成新核对后重验已有号码，包括新批次为空时
  清除旧重复错误；旧身份的迟到响应不得更新当前分单反馈。
- 异步查询使用 React Query，防抖参数进入 queryKey，不能用手写请求 Effect/订阅标记防竞态。表单同步 Effect 不承担请求生命周期。
- 新建文案为“已找到主单，保存后加入”，已有 N 票、本票保存后 N+1；详情显示真实 N，不重复加一。
- 详情共享区指向“更多操作 → 修改共享航程”；新建页资料缺失通过已有成员订单的新标签链接补全，不从未保存新票直接写已有航程。
- 日期展示用 `formatDate`，表单日期与保存载荷按本地日零点序列化，禁止截取 UTC 字符串冒充换算。

## 校验矩阵

| 场景 | 行为 |
| --- | --- |
| 有主单号、无船公司 | 显示待核对；船公司必填和其它独立错误一起展示 |
| 候选含 DIRECT 成员 | 阻止加入，不自动切换单证模式 |
| 单航程且无差异 | 继承并允许按原创建链提交 |
| 有非空差异或共享缺失值 | 明确展示，采用前保留输入和阻断 |
| 多航程未选择 | 不默认第一条，阻止误关联 |
| 查询等待、失败或身份变化 | 不能使用旧候选确认保存；结束后重验完整字段 rules |
| 已填 HBL、船公司或主单号未齐 | 明确显示分单待核对，不显示绿色通过 |
| 当前主单核对中或失败 | HBL 同步显示核对中或失败，保留输入，不误报可用 |
| 当前主单核对成功且无同号 HBL（含新主单） | HBL 仅显示绿色通过图标，不显示成功说明文字 |
| 同一主单内 HBL 重复（含作废） | HBL 红色提示重复；改为可用号码或切换无重复主单后清除错误 |
| 预览成员补读失败 | 保留该 ID、失败提示和准确总数，不显示成少量或零影响 |

## 正常与错误示例

正常：已有主单 M 下只有航次 V，两张 HOUSE 订单先后加入，船期取 V，各自保留目的地和货量；修改 V 的预览列出所有受影响票。

基础：新主单没有候选，首次录入自己的航程。

错误：候选有两个航次时静默用第一个；用同批订单列表代替 `memberOrderIds`；查询失败后继续保存旧候选；直接覆盖用户冲突值。

## 必需验证

真实 Form 与独立 QueryClient 覆盖：单航程继承、冲突前保留/采用后替换、独立字段不变、缺船公司、多航程、DIRECT、候选身份切换、迟到响应、等待错误重验、共享更新权限、影响订单精确范围和补读失败；HBL 反馈须覆盖等待/加载/失败、成功未命中/命中、重复及修改清错、主单身份变化撤销旧通过、空批次清除旧重复错误。测试不得额外注册生产不存在的候选字段来让监听生效。

## 错误与正确用法

```tsx
// 错误：未解决差异就把候选确认写入表单；影响范围使用同批业务关系推断。
form.setFieldValue('seaMasterBillCandidateId', response.candidate.id);
const affectedOrders = sameBatchOrders;

// 正确：候选身份、选中航程、差异采纳都确认后才形成可提交关联；
// 统一修改的影响范围严格使用服务端预览，并按 ID 补读可读订单号。
const affectedOrderIds = preview.memberOrderIds ?? [];
```

## 从已有主单连续新增分单

- 详情主单区的「从此主单新增分单」指向
  `/orders/sea-export/new?sourceOrderId=<订单ID>`。仅同组织、具有海运创建能力且
  HOUSE 主单未作废且主单/航程身份完整时显示；来源订单的审核锁不限制新建另一票。
- URL 只传来源 ID，新建页通过当前工作区 React Query 读取并验证来源为本组织
  海运 HOUSE。无权、失败、空/重复参数或缺失活动主单/航程时明确阻断，不能
  静默退化为普通建单。既有订单是上下文来源，不是整票复制对象。
- 新票只预填船公司、主单号和 HOUSE；指定来源航程须在最新候选内按 MBL/TE ID
  找到，随后使用候选当前值和版本。指定航程失效时不能因为只剩一条航程就选它。
  客户、HBL、单证正文、货物、目的地和费用保持各票独立。
- 船公司初始选项保留来源名称，远程候选为空时也不能显示内部 ID；
  ProForm 候选请求的 `params` 包含当前选项身份与名称，避免同名字段缓存串用来源标签。
- 保留现有模块页签。普通新建、来源 A、来源 B 使用不同的规范 `draftPathname`；
  已知来源地址同时作为整个创建内容组件的 React key，表单、幂等键和提交状态
  一起重建。来源加载完成前不挂可编辑表单，首次初始化之后由模板恢复草稿，
  禁止异步默认值覆盖已恢复输入。旧实例的迟到创建结果不得提示或导航新票。
- 新建与详情 HOUSE 的 `['seaHouseBill', 'houseNo']` 均仅在 MBL 旁注册一次，复用
  `HouseBillNumberField` 的必填、批次排重和晚到候选重验。HBL 页签保留签发方与
  正文。DIRECT 不挂 HBL 号码必填；详情字段遵循只读、单证加载和终态限制，
  普通编辑统一走整页保存，订单资料与修改过的 MBL/HBL 一次提交；不再提供
  「保存主单内容」「保存分单」局部入口。模式切换继续使用原正式单证入口。
- 新建与详情的号码错误均直接定位上方输入，不切 HBL 页签；签发方与正文错误
  仍按原揭示链路切换。不要用第二个号码字段加双向同步实现位置调整。

新增回归需覆盖：单票/多票入口、无权限/跨组织/DIRECT、来源锁定、指定航程
失效、唯一号码注册与排重、模式切换、错误揭示，以及普通→A→B→A 的草稿与
幂等键隔离、来源加载不覆盖草稿、旧提交不导航当前票。

## 整页保存与单证基线

- 详情须在完整单证加载后初始化表单，再恢复本地草稿；组件晚到查询不得覆盖草稿。
- 统一保存时以规范化字段与加载基线比较，仅提交改过的单证。基线的运输条款、
  付款条款、提单形式、放单方式默认值须与真实表单一致，避免挂载默认值误触发写入。HBL 携带 ID、HBL 版本
  及活动 Link 版本，MBL 正文携带 MBL 版本；不得把模式切换混入普通保存。
- 单证组包从完整 Form store 读取，不能只用 `onFinish` 返回的已注册字段；否则未展示的
  件重尺或备注会被误清空。草稿持久化必须包含与编辑内容匹配的订单/MBL/HBL/Link
  基线版本，恢复时不得用最新查询版本替换旧草稿版本后提交。
- 主单身份与航程更新同样从完整 Form store 组包：
  `seaMasterBillExpectedCandidateVersion` 是未注册的编辑基线，必须映射到
  `seaMasterBill.expectedCandidateVersion`，不能只读取 `onFinish(values)`。
  单票草稿修改起运港、卸货港、中转港或船期时，缺失该版本会被后端判为主单冲突；
  候选同步与后台刷新不得替换已恢复草稿的原版本。回归必须通过真实 Form 提交，
  验证请求版本、连续保存后的版本推进、过期版本拒绝及输入保留，禁止为测试额外注册该字段。
- 保存期间通过 `editingDisabled` 冻结编辑与重复提交，不能以业务 `readonly` 关闭
  脏页签离开保护；失败保留字段、草稿和未保存标记。成功后同步完整
  订单/单证快照，再清草稿；不能只更新版本但仍显示另一来源的旧正文。
- 已确认写入但刷新失败时明确提示已保存，并重试读取；不得再次发送相同写入。
  写结果未知时保留原提交快照和幂等键，不得将不同载荷复用同一未知结果的键。
- 回归需验证一次提交、仅改部分单证、连续保存 Link 版本推进、失败草稿、
  已保存待重读、DIRECT/终态/只读，以及组织/订单切换时迟到响应隔离。

- 单证专用动作成功后按 master/house/mode 范围刷新基线与对应字段，保留另一份
  草稿及版本；并发完成必须以最新 state 合并，不能合并闭包旧基线。异步结果除订单
  身份外还须检查发起代次，覆盖 A→B→A 的迟到结果。
  订单编辑版本只在重读结果恰为原版本加一时推进；若包含其他人的后续订单写入，
  保留旧版本让整页保存返回冲突，不能以动作成功为由采纳任意更晚的查询版本。
- 仅校验并推进 MBL 版本的 master 动作成功后，可同步主单摘要与
  `seaMasterBillExpectedCandidateVersion`；mode/house 不推进 MBL，必须保留原主单
  编辑版本，不能借动作后的最新查询版本放行旧港口草稿覆盖并发修改。
  master 动作后的重读也须确认版本只推进了本次动作的一次增量；读到更晚版本时
  保留原主单编辑版本，让后续保存返回冲突，不能用最新查询结果替换旧航程的基线。
